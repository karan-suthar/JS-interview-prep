Promise.all() fail-fast

Waits for all promises to fulfill and returns their values in order. If any promise rejects, the whole thing rejects immediately with that reason — it doesn't wait for the others.

Full implementation
function promiseAll(promises) { return new Promise((resolve, reject) => { const results = []; let completedCount = 0; // Edge case: empty array resolves immediately if (promises.length === 0) { resolve([]); return; } promises.forEach((p, index) => { // Promise.resolve() safely handles non-promise values too Promise.resolve(p) .then((value) => { results[index] = value; // preserve ORIGINAL order, not completion order completedCount++; if (completedCount === promises.length) { resolve(results); // all done — resolve with the full array } }) .catch(reject); // ANY rejection immediately rejects the outer promise }); }); } // Usage / test promiseAll([ Promise.resolve(1), new Promise(res => setTimeout(() => res(2), 100)), 3 // non-promise values are allowed too ]).then(console.log); // → [1, 2, 3] (after ~100ms) promiseAll([ Promise.resolve(1), Promise.reject("error!"), Promise.resolve(3) ]).catch(console.log); // → "error!" (immediately, doesn't wait)
Key design points: use a results[index] = value assignment (not .push()) to guarantee original ordering regardless of which promise finishes first. Track completion with a counter rather than checking array length, since sparse assignment can make .length misleading. The first rejection short-circuits everything via .catch(reject).

Promise.race() first settled wins

Settles as soon as the first promise settles — whether that's a fulfillment or a rejection. Simplest of the four to implement.

Full implementation
function promiseRace(promises) { return new Promise((resolve, reject) => { // Note: unlike Promise.all, an empty array here means the returned // promise NEVER settles — that matches the real spec behavior! promises.forEach((p) => { Promise.resolve(p) .then(resolve) // first to fulfill wins — resolve() only acts on FIRST call .catch(reject); // first to reject also wins, if it's first overall }); }); } // Usage / test promiseRace([ new Promise(res => setTimeout(() => res("slow"), 300)), new Promise(res => setTimeout(() => res("fast"), 100)) ]).then(console.log); // → "fast" (after ~100ms) // Practical use case: timeout pattern function withTimeout(promise, ms) { const timeout = new Promise((_, reject) => setTimeout(() => reject(new Error("Timed out")), ms) ); return promiseRace([promise, timeout]); // whichever finishes first wins }
Key design point: a JS Promise can only be settled once — calling resolve() or reject() multiple times is safe; only the FIRST call has any effect, all subsequent calls are silently ignored. This built-in behavior is exactly what makes Promise.race trivial to implement — you don't need to manually track "has anyone won yet."

Promise.allSettled() never rejects

Waits for every promise to settle (fulfill OR reject) and returns a status report for each — it never rejects itself, regardless of how many individual promises fail.

Visual — mix of success and failure, all captured
p1 (100ms)
fulfilled
p2 (150ms)
rejected
p3 (300ms)
fulfilled
→ allSettled resolves at 300ms with status for ALL THREE — nothing is thrown away, p2's rejection is just recorded, not propagated
Full implementation
function promiseAllSettled(promises) { return new Promise((resolve) => { // note: no "reject" param needed — never rejects! const results = []; let completedCount = 0; if (promises.length === 0) { resolve([]); return; } promises.forEach((p, index) => { Promise.resolve(p) .then((value) => { results[index] = { status: "fulfilled", value }; }) .catch((reason) => { results[index] = { status: "rejected", reason }; }) .finally(() => { // runs whether fulfilled OR rejected completedCount++; if (completedCount === promises.length) { resolve(results); // always resolve, never reject } }); }); }); } // Usage / test promiseAllSettled([ Promise.resolve(1), Promise.reject("oops"), Promise.resolve(3) ]).then(console.log); // → [ // { status: "fulfilled", value: 1 }, // { status: "rejected", reason: "oops" }, // { status: "fulfilled", value: 3 } // ]
Key design points: the outer Promise's executor doesn't even need a reject parameter since it's never used — allSettled is designed to NEVER reject. Using .finally() to increment the counter (instead of duplicating that logic in both .then() and .catch()) keeps the code DRY and guarantees the counter increments exactly once per promise, regardless of outcome.

Bonus: Promise.any() ES2021

The "opposite" of Promise.all in terms of success/failure — settles as soon as the first promise fulfills. Only rejects if every promise rejects, with a special AggregateError.

Full implementation
function promiseAny(promises) { return new Promise((resolve, reject) => { const errors = []; let rejectedCount = 0; if (promises.length === 0) { reject(new AggregateError([], "All promises were rejected")); return; } promises.forEach((p, index) => { Promise.resolve(p) .then(resolve) // FIRST success wins immediately .catch((err) => { errors[index] = err; // track errors in original order rejectedCount++; if (rejectedCount === promises.length) { // only reject once EVERY promise has failed reject(new AggregateError(errors, "All promises were rejected")); } }); }); }); } // Usage / test promiseAny([ Promise.reject("fail 1"), Promise.resolve("success!"), Promise.reject("fail 2") ]).then(console.log); // → "success!" promiseAny([ Promise.reject("fail 1"), Promise.reject("fail 2") ]).catch(err => { console.log(err.errors); // → ["fail 1", "fail 2"] });
Notice the symmetry with Promise.all: it's essentially the SAME code structure, with fulfillment/rejection roles swapped. This is a great thing to point out in an interview — it shows you understand the underlying pattern rather than memorizing 4 separate solutions.

Common Gotchas & Interview Traps

  • ⚠️Using .push() instead of results[index] = value breaks ordering — since promises can resolve in any order, pushing results as they complete does NOT preserve the original input order. Always assign directly by index.
  • ⚠️Forgetting the empty-array edge case for Promise.all/allSettled — without an explicit check, the counter-based resolve condition (completedCount === promises.length) never becomes true because it's never even triggered by the empty forEach, so the promise hangs forever.
  • ⚠️Promise.race with an empty array never settles — this actually matches the real spec behavior (not a bug to fix), but it's a common "what happens here?" interview trap.
  • ⚠️Not wrapping items with Promise.resolve() — the input array can contain plain values, not just promises. Promise.resolve(item) normalizes both cases so .then() always works, whether item is a promise or a raw value.
  • ⚠️Calling resolve/reject more than once is safe but wasteful — a native Promise only honors the FIRST settle call and ignores the rest, which is exactly what makes Promise.race so simple. But if you're implementing your OWN promise-like class instead of relying on native Promises, you'd need to guard against double-settling manually.
  • ⚠️allSettled's counter logic must NOT stop early on rejection — unlike Promise.all, you must continue processing every promise and only resolve once ALL have settled, using .finally() or incrementing in both the success and failure branches.
  • ⚠️AggregateError needs the errors array in the SAME order as the original promises for Promise.any — mirror the same index-based assignment pattern used for successful results elsewhere.
  • ⚠️Real Promise.all/race/allSettled accept any iterable, not just arrays — technically the spec supports any iterable (Sets, generator results, etc.), though a from-scratch interview implementation using .forEach() only strictly needs to support arrays unless explicitly asked to handle iterables.

Interview Q&A — click to reveal

Q1: What's the core pattern shared by all Promise combinator implementations?
+
Return a new Promise((resolve, reject) => {...}), iterate the input array with .forEach(), wrap each item with Promise.resolve() to normalize non-promise values, attach .then()/.catch() handlers, and use a closure-captured counter (plus a results array indexed by position) to determine when and how to settle the outer promise. Only the specific resolve/reject conditions differ between all, race, allSettled, and any.
Q2: Why use results[index] = value instead of results.push(value)?
+
Because promises can resolve in ANY order regardless of their position in the input array — a slower first promise might finish after a faster third promise. results.push(value) would add results in completion order, which breaks the contract that Promise.all preserves input order. Assigning directly by index (results[index] = value) guarantees the output array always matches the input array's order, regardless of which promise settles first.
Q3: Why does Promise.race work correctly without any extra "has someone already won" tracking logic?
+
Because native JS Promises can only be settled once — after the first call to resolve() or reject(), all subsequent calls are silently ignored by the Promise machinery itself. So even though every input promise's .then(resolve)/.catch(reject) is attached, only the FIRST one to actually fire has any real effect on the outer promise. This built-in "settle once" guarantee is what makes the race implementation so short.
Q4: Why doesn't allSettled's executor function need a reject parameter?
+
By design, Promise.allSettled NEVER rejects — its entire purpose is to let you know the outcome of every promise (success or failure) without short-circuiting. Since the outer promise is only ever resolved (never rejected), there's no need to accept or use the reject parameter from the executor — you can even omit it entirely: new Promise((resolve) => {...}).
Q5: What happens if you call Promise.all([]) — an empty array? Why does your implementation need to handle this explicitly?
+
The real Promise.all([]) resolves immediately with an empty array []. In a from-scratch implementation, if you rely purely on the counter check inside the .forEach() callback (completedCount === promises.length), that check is literally never reached when the array is empty — .forEach() on [] doesn't call the callback at all. Without an explicit early-return check for the empty case, your promise would hang forever instead of resolving.
Q6: How would you use Promise.race to implement a fetch timeout?
+
Race the actual request against a promise that rejects after a fixed delay:
function fetchWithTimeout(url, ms) { const timeout = new Promise((_, reject) => setTimeout(() => reject(new Error("Request timed out")), ms) ); return Promise.race([fetch(url), timeout]); }
Whichever settles first — the real fetch or the timeout's rejection — determines the outcome. This is one of the most common real-world uses of Promise.race.
Q7: What's the difference between Promise.all and Promise.allSettled in terms of error handling philosophy?
+
Promise.all follows an "all or nothing" philosophy — it's for when every operation is required to succeed; a single failure means the whole batch is considered failed, and you get just the first error.

Promise.allSettled follows a "tell me everything" philosophy — it's for when partial success is acceptable and you want a complete report of what succeeded and what failed, so you can handle each case individually (e.g. showing results for the requests that worked while logging errors for the ones that didn't).
Q8: How is Promise.any's implementation related to Promise.all's implementation?
+
They're structural mirrors of each other with fulfillment and rejection roles swapped. Promise.all resolves when all succeed and rejects fast on the first failure. Promise.any resolves fast on the first success and rejects only when all fail (bundling every error into an AggregateError). If you understand one, you can derive the other by swapping which outcome triggers early-exit vs which requires waiting for every promise to finish.
