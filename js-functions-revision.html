Function Declarations hoisted

📜 function name() {}
Named, starts with the "function" keyword, statement (not an expression)
function greet(name) { return `Hello, ${name}!`; } greet("Alice"); // → "Hello, Alice!"
💡 Fully hoisted — both the name AND the function body are hoisted to the top of their scope. This means you can call a function declaration before it appears in the code.
// Works! Function declarations are hoisted with their full body console.log(sayHi()); // → "Hi!" (no error, even though called before definition) function sayHi() { return "Hi!"; } // Has its own `this`, `arguments` object, and can be used as a constructor function Person(name) { this.name = name; } const p = new Person("Bob"); // works — regular functions can be constructors // Named — shows up properly in stack traces function calculateTotal() { throw new Error("oops"); } // Stack trace shows "calculateTotal" — easier debugging
2

Function Expressions not hoisted

📦 const fn = function() {}
Function assigned to a variable — an expression, evaluated at runtime
const greet = function(name) { return `Hello, ${name}!`; }; greet("Alice"); // → "Hello, Alice!" // Named function expression — name only visible INSIDE the function (for recursion) const factorial = function fact(n) { return n <= 1 ? 1 : n * fact(n - 1); // "fact" usable here }; factorial(5); // → 120 // fact(5); ← ReferenceError outside — "fact" is not defined in outer scope
⚠ Only the variable is hoisted, not the function. With var the variable is hoisted as undefined — calling it before assignment throws "TypeError: greet is not a function". With let/const you get a ReferenceError (Temporal Dead Zone).
// Calling before definition — FAILS (unlike function declarations) console.log(greet2("Bob")); // ✗ ReferenceError: Cannot access 'greet2' before initialization const greet2 = function(name) { return name; }; // IIFE — Immediately Invoked Function Expression (function() { console.log("Runs immediately!"); })(); // Function expressions as arguments (very common) setTimeout(function() { console.log("delayed"); }, 1000); [1,2,3].map(function(x) { return x * 2; });
3

Arrow Functions ES6 · lexical this

🏹 const fn = (params) => { }
Concise syntax, no own this/arguments, cannot be used as a constructor
// Full syntax const greet = (name) => { return `Hello, ${name}!`; }; // Implicit return — single expression, no braces, no "return" keyword const square = x => x * x; square(5); // → 25 // Multiple params need parentheses const add = (a, b) => a + b; // No params — empty parens required const sayHi = () => "Hi!"; // Returning an object literal — wrap in parens! (else {} = function body) const makeUser = (name) => ({ name, active: true }); makeUser("Alice"); // → { name: "Alice", active: true }
🔑 Lexical this — arrow functions don't have their own this. They capture this from the enclosing (surrounding) scope at the time they're defined. This is their #1 defining feature and most common interview topic.
✗ Regular function — "this" bug
const timer = { seconds: 0, start() { setInterval(function() { this.seconds++; // ✗ 'this' is }, 1000); // window/undefined } };
✓ Arrow function — inherits "this"
const timer = { seconds: 0, start() { setInterval(() => { this.seconds++; // ✓ 'this' is }, 1000); // the timer object } };
// Arrow functions have NO arguments object of their own const fn = () => { console.log(arguments); // ✗ ReferenceError, or inherits outer scope's `arguments` }; // Use rest params instead const sum = (...nums) => nums.reduce((a, b) => a + b, 0); sum(1, 2, 3); // → 6 // Arrow functions CANNOT be used as constructors const Person = (name) => { this.name = name; }; new Person("Bob"); // ✗ TypeError: Person is not a constructor // Arrow functions have no "prototype" property const fn2 = () => {}; console.log(fn2.prototype); // → undefined

The arguments object

💡 arguments is an array-like object (has indices and .length, but NOT array methods like .map) automatically available inside every regular function — it holds all arguments passed to the call, regardless of the declared parameters.
function showArgs() { console.log(arguments); // Arguments(3) [1, 2, 3] console.log(arguments.length); // → 3 console.log(arguments[0]); // → 1 (index access works) } showArgs(1, 2, 3); // arguments captures ALL passed args, even beyond named parameters function add(a, b) { console.log(arguments.length); // → 4 (not 2!) return a + b; } add(1, 2, 3, 4); // → 3 (only a=1, b=2 are used, but arguments has all 4) // Old-school variadic function (before rest params existed) function sumAll() { let total = 0; for (let i = 0; i < arguments.length; i++) { total += arguments[i]; } return total; } sumAll(1, 2, 3, 4); // → 10
// arguments is array-LIKE, not a real array — .map/.filter don't exist on it directly function broken() { return arguments.map(x => x * 2); // ✗ TypeError: arguments.map is not a function } // Fix 1 — Array.from() function double() { return Array.from(arguments).map(x => x * 2); } double(1, 2, 3); // → [2, 4, 6] // Fix 2 — spread operator function double2() { return [...arguments].map(x => x * 2); } // Fix 3 — Array.prototype.slice.call() (old-school, pre-ES6) function double3() { return Array.prototype.slice.call(arguments).map(x => x * 2); }

⚠ Arrow functions have NO arguments object of their own — referencing arguments inside an arrow function looks it up in the nearest enclosing regular function's scope (or throws ReferenceError at the top level). Use rest parameters (...args) in arrow functions instead.

Default Parameters ES6

💡 Default parameter values are used only when the argument is undefined — not when it's missing vs explicitly passed as anything else (including null, 0, or "").
✗ Before ES6
function greet(name) { name = name || "Guest"; return `Hi, ${name}`; } // Bug: greet("") → "Hi, Guest" ✗ // (empty string treated as missing)
✓ ES6 default parameters
function greet(name = "Guest") { return `Hi, ${name}`; } greet(); // → "Hi, Guest" greet(""); // → "Hi, " ✓ (correct — "" is valid)
// Defaults trigger ONLY on undefined function test(a = 10) { return a; } test(); // → 10 (missing → undefined → default used) test(undefined); // → 10 (explicit undefined → default used) test(null); // → null (null does NOT trigger default!) test(0); // → 0 (0 does NOT trigger default) test(""); // → "" (empty string does NOT trigger default) // Default can reference EARLIER parameters function createRect(width, height = width) { return width * height; } createRect(5); // → 25 (height defaults to width → square) createRect(5, 3); // → 15 // Default can be a function call — evaluated fresh on EVERY call function logEvent(msg, time = Date.now()) { console.log(msg, time); // time is different each call if omitted } // Default with destructured object params — very common pattern function createUser({ name = "Anonymous", role = "user" } = {}) { return { name, role }; } createUser(); // → { name: "Anonymous", role: "user" } createUser({ name: "Bob" }); // → { name: "Bob", role: "user" } // The trailing "= {}" is essential — lets createUser() be called with NO args at all // Skipping a default with undefined (not with a gap) function f(a = 1, b = 2, c = 3) { return [a, b, c]; } f(10, undefined, 30); // → [10, 2, 30] (undefined "skips" to default)
⚠ Parameters with defaults are excluded from arguments.length counting behavior in some ways, and default parameters disable "simple parameter list" optimizations — but more importantly: default values are evaluated left to right, at call time, not once when the function is defined.
!

Common Gotchas & Traps

  • ⚠️Function declarations inside blocks (if/for) behave inconsistently across environments in non-strict mode. In strict mode / ES6 modules, they're scoped to the block. Avoid declaring functions inside if blocks — use function expressions instead.
  • ⚠️Arrow functions as object methods lose this: const obj = { name: "A", greet: () => this.name } — this here refers to the outer scope, NOT obj. Use method shorthand (greet() {}) instead.
  • ⚠️Named function expressions can't be called by name outside themselves: const f = function inner(){}; inner(); → ReferenceError outside f's body — the name inner is only visible inside its own scope (useful for recursion).
  • ⚠️Default parameter defaults only apply for undefined, not null — a null value passed explicitly stays null, does not fall back to the default. This is the same rule as destructuring defaults.
  • ⚠️Rest params must be last, and a function can't have both arguments-mutation tricks and default/rest parameters behaving in "simple" mode — this affects strict-mode parsing subtleties but rarely matters in practice.
  • ⚠️arguments object doesn't exist in arrow functions. If you need "all args" flexibility in an arrow function, you must use rest parameters — there's no fallback.
  • ⚠️Object literal returned by an arrow function needs parens: x => { name: x } is parsed as a function BODY with a label, not an object — returns undefined. Correct: x => ({ name: x }).
  • ⚠️Function declarations are hoisted, but if reassigned with var of the same name, the assignment happens in place — e.g. var foo = 1; function foo(){} — the function hoists first, then var foo = 1 overwrites it at that line (functions hoist "higher" than var in terms of initial value).
  • ⚠️this in a regular function depends on HOW it's called, not where it's defined (dynamic binding) — obj.method() vs const m = obj.method; m() give different this. Arrow functions avoid this entirely by using lexical this.
  • ⚠️Arrow functions cannot be generators — there is no =>* syntax. Only function* declarations/expressions support the yield keyword.

Interview Q&A — click to reveal

Q1: What's the difference between a function declaration and a function expression?
+
A function declaration (function name() {}) is a statement that is fully hoisted — you can call it before it appears in the code. A function expression (const name = function() {}) assigns a function to a variable — only the variable declaration is hoisted (as undefined for var, or left in the Temporal Dead Zone for let/const), so calling it before the assignment throws an error.
Q2: Why don't arrow functions have their own "this"? What does that mean in practice?
+
Arrow functions use lexical this — they don't create their own this binding, but instead inherit it from the enclosing scope at the point where they are defined (not where they're called). This makes them ideal for callbacks inside methods (like setTimeout or array method callbacks) where you want to preserve the outer object's this, avoiding the classic var self = this or .bind(this) workarounds needed with regular functions.
Q3: Can arrow functions be used as constructors? Why or why not?
+
No — calling new ArrowFn() throws TypeError: ArrowFn is not a constructor. This is because arrow functions have no [[Construct]] internal method, no prototype property, and no own this to bind to a newly created object. Constructors require function declarations, function expressions, or classes.
Q4: What is the arguments object, and why would you use rest parameters instead?
+
arguments is an array-like object (not a real array) automatically available in regular functions, containing every argument passed to the call. It lacks array methods like .map/.filter and doesn't exist in arrow functions.

Rest parameters (...args) are the modern replacement — they produce a real array with all methods available, work in arrow functions, and can be combined with named parameters to capture only the "extra" arguments (whereas arguments always contains everything, even values already captured by named params).
Q5: When do default parameter values actually get used?
+
Only when the argument is undefined — either because it wasn't passed at all, or because undefined was explicitly passed. Passing null, 0, false, or "" does not trigger the default — those are all valid, intentional values that get used as-is.
function f(x = 5) { return x; } f(); // → 5 f(undefined); // → 5 f(null); // → null (not 5!)
Q6: What's wrong with this code? const getUser = x => { name: x }
+
The curly braces after => are interpreted as a function body block, not an object literal. Inside that block, name: x is parsed as a labeled statement (a rarely-used JS feature), and the function implicitly returns undefined.

Fix: wrap the object in parentheses so it's parsed as an expression: const getUser = x => ({ name: x }).
Q7: What is an IIFE and why is it used?
+
An Immediately Invoked Function Expression — a function that runs as soon as it's defined:
(function() { console.log("runs immediately"); })();
Historically used to create a private scope, avoiding polluting the global namespace with variables (before let/const block scoping and ES modules existed). Still occasionally used for one-off initialization logic or to create closures around async setup code.
Q8: Why can a named function expression call itself by name, but code outside it cannot?
+
When you write const factorial = function fact(n) {...}, the name fact is bound in a special scope that is only accessible from within the function's own body — it's not added to the enclosing scope. This is useful for recursion when you don't want to depend on the outer variable name (which could be reassigned), since fact will always correctly refer to this specific function regardless of what factorial gets reassigned to later.
Q9: Give an example where using an arrow function instead of a regular function would break your code.
+
Object methods that rely on this:
const counter = { count: 0, increment: () => { this.count++; } // ✗ 'this' is NOT counter }; counter.increment(); console.log(counter.count); // → 0 (didn't work as expected!)
Should be increment() { this.count++; } (method shorthand) instead. Also breaks: functions meant to be used with new as constructors, and any code relying on the arguments object.
