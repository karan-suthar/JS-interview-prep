The 6 Steps, Overview

💡 The Critical Rendering Path is the exact sequence of steps a browser takes to convert HTML, CSS, and JS into pixels on screen. Understanding EACH step precisely — not just the names — is what lets you reason about WHY a specific change is expensive or cheap.
The pipeline, step by step
StepInputOutput
1. DOMRaw HTML bytesA tree of DOM nodes representing document structure/content
2. CSSOMRaw CSS bytes (all sources: external, internal, inline)A tree of CSSOM nodes representing computed style rules
3. Render TreeDOM + CSSOMA tree of only VISIBLE nodes, each with its resolved styles attached
4. LayoutRender Tree + viewport sizeExact geometry (x, y, width, height) for every node
5. PaintRender Tree + geometryFilled-in pixels, organized into paint records/layers
6. CompositePainted layersThe final, assembled image the user actually sees

Step 1 — DOM Construction

1
Converting raw HTML bytes into a tree of objects
Bytes → Characters → Tokens → Nodes → DOM Tree
// The DOM construction sub-steps, in order: // 1. Bytes: raw data received over the network // 2. Characters: bytes converted to characters, per the document's encoding (e.g. UTF-8) // 3. Tokens: the HTML tokenizer recognizes tags, attributes, and text as distinct tokens // e.g. StartTag: "div", Attribute: "class=container", EndTag: "div" // 4. Nodes: tokens are converted into actual DOM node OBJECTS // 5. DOM: nodes are linked together into a TREE based on nesting in the markup // Example input HTML: <html> <body> <p>Hello <span>world</span></p> </body> </html>
Resulting DOM tree
⚠ DOM construction is INCREMENTAL — the browser doesn't wait for the whole HTML document to build the whole tree. It processes bytes as they stream in, and the tree grows progressively. This is precisely why a parser-blocking synchronous <script> tag has such a big effect — it PAUSES this streaming, incremental process at exactly the point it's encountered.
3

Step 2 — CSSOM Construction

2
Converting raw CSS bytes into a tree of computed style rules
Same byte→character→token→node process as DOM, but for CSS — plus cascade/specificity resolution
// Example input CSS: body { font-size: 16px; } p { color: blue; } span { font-weight: bold; } // The CSSOM is also a TREE — child rules inherit/build on parent rules, // following the CASCADE (specificity + source order + inheritance) // A "span" inside a "p" inherits p's color UNLESS it has its own explicit rule
Resulting CSSOM tree — note child rules can inherit from parent rules
🚨 CSSOM construction is render-blocking — the browser must have the COMPLETE CSSOM before proceeding to the Render Tree step. Unlike DOM construction, this can't be done incrementally in the same way, since a rule appearing LATER in a stylesheet can override one appearing earlier, so nothing can be considered "final" until the whole stylesheet is processed.
4

Step 3 — Render Tree Construction

3
Walking the DOM and attaching matching CSSOM styles to each visible node
For each DOM node: is it visible? If so, attach its computed style, and add it to the Render Tree
// For EVERY DOM node, the browser asks: // 1. Is this node visible? (display:none → EXCLUDED entirely, no render tree node at all) // 2. What are its computed styles? (look up matching CSSOM rules, resolve the cascade) // 3. Attach a Render Tree node combining: the DOM node + its resolved computed style // Note: <head>, <script>, <meta> and similar non-visual elements are also // excluded from the Render Tree — they exist in the DOM but have nothing to render
💡 The Render Tree is NOT simply "DOM plus CSSOM stacked together" — it's a NEW tree, built by walking the DOM once and, for each visible node, looking up and attaching its final resolved style from the CSSOM. Invisible nodes (display:none, <head> contents) are dropped from this new tree entirely.
5

Step 4 — Layout (Reflow)

4
Computing the EXACT box — position and size — of every Render Tree node
Starts from the ROOT (the viewport) and walks down, computing each node's geometry in turn
// Layout starts from the viewport's dimensions and works down the tree // Every node's SIZE and POSITION depends on: // - its own CSS box-model properties (width, height, padding, margin, border) // - its PARENT's available space // - its SIBLINGS (in flow layouts like block/inline/flex/grid) // - the viewport size (for percentage/vw/vh units) // This is WHY layout can CASCADE — resizing one element can ripple outward // to affect its parent, its siblings, and anything positioned relative to it
⚠ The first Layout for a page is called "Layout" — any SUBSEQUENT recalculation (triggered by a later DOM/style/size change) is often called "Reflow." Both refer to the SAME underlying computation; the distinction is purely about WHEN it happens (initial vs. later).
6

Step 5 — Paint

5
Filling in the actual visual appearance — for every node, in the correct order
Text, colors, borders, shadows, images — converted into actual "paint records" (drawing instructions)
// Paint happens in a specific, deliberate ORDER to render overlapping elements // correctly (this is a simplified version of the actual painting order rules): // 1. Background color // 2. Background image // 3. Border // 4. Children (in DOM order, respecting z-index/stacking contexts) // 5. Outline // The browser may split painting across multiple LAYERS (e.g. for elements // with certain CSS properties like "will-change", fixed position, or video), // allowing later stages to update just ONE layer without repainting everything
💡 Paint can be a SIGNIFICANT cost on complex pages — visual effects like shadows, gradients, and blurring are more expensive to paint than simple flat colors. This is why the "Paint" flame chart in DevTools' Performance panel is worth checking for pages with heavy visual styling.
7

Step 6 — Composite

6
Assembling all the separately-painted layers into the final image, on the GPU
The cheapest, final stage — some properties (transform, opacity) can update here WITHOUT re-running Layout or Paint at all
// The GPU takes each painted layer (a bitmap) and combines them, applying // any transforms/opacity/blending, into the final on-screen image // A CSS animation using ONLY transform/opacity can update purely at this // stage — the GPU just repositions/fades an ALREADY-painted layer, with no // need to recompute geometry (Layout) or redraw pixel content (Paint) element.style.transform = "translateX(200px)"; // Composite-only update

Full Worked Example — Tracing One Page Through All 6 Steps

// The example document <html> <head> <style> .card { width: 300px; background: lightgray; } .hidden { display: none; } h1 { color: navy; } </style> </head> <body> <div class="card"> <h1>Title</h1> <p class="hidden">Secret text</p> </div> </body> </html>
StepWhat happens for THIS document, specifically
1. DOMA tree: html → head/body; body → div.card → h1 + p.hidden. Every element becomes a node, including the (invisible) <head> and its <style>.
2. CSSOMRules parsed: .card (width:300px, background:lightgray), .hidden (display:none), h1 (color:navy). No inheritance conflicts here.
3. Render TreeWalks the DOM: html, body, div.card, h1 are all INCLUDED (visible, get their styles attached). <head> and its contents are excluded (non-visual). p.hidden is EXCLUDED too — display:none removes it entirely, not just visually.
4. Layoutdiv.card gets a box: width 300px (explicit), height determined by its content (h1's rendered height, since p is excluded and contributes NO space). h1 gets positioned inside, sized based on its text content and default block-level behavior.
5. Paintdiv.card's lightgray background is painted first, then h1's "Title" text is painted in navy on top of it. p.hidden paints NOTHING — it was never in the Render Tree to begin with.
6. CompositeThe single (in this simple case) painted layer is assembled and displayed — no transforms/special layers needed for this example, so composite is trivial here.
✓ Interview tip: being able to trace a SPECIFIC, concrete example like this through all 6 steps — explicitly calling out that p.hidden disappears at the Render Tree step and never reaches Layout/Paint at all — demonstrates real understanding far better than reciting the 6 stage names alone.

How JavaScript Re-enters the Pipeline After Initial Load

💡 After the initial page load, JavaScript-driven DOM/style changes cause the pipeline to run again, but usually starting from a LATER step — not always all the way back from DOM construction.
// Adding/removing a DOM node — restarts from DOM/Render Tree construction document.body.appendChild(newDiv); // → DOM updated → Render Tree updated (new node added) → Layout → Paint → Composite // Changing a style that affects geometry — restarts from Layout element.style.width = "500px"; // → Layout (recompute geometry) → Paint → Composite // Changing a purely visual style — restarts from Paint element.style.backgroundColor = "red"; // → Paint (redraw pixels) → Composite // Changing transform/opacity — restarts from Composite ONLY element.style.transform = "scale(1.1)"; // → Composite (GPU repositions/blends the existing layer)
⚠ This is precisely why transform/opacity are recommended for animations — they're the ONLY properties that can update by re-entering the pipeline at the very LAST, cheapest stage, skipping Layout and Paint entirely.

Common Gotchas & Interview Traps

  • ⚠️DOM construction is incremental/streamable; CSSOM construction effectively is NOT — this asymmetry is exactly why CSS is render-blocking while HTML parsing can proceed progressively; a later CSS rule can override an earlier one, so nothing is "final" until the whole stylesheet is processed.
  • ⚠️The Render Tree is a genuinely NEW, separate tree — not simply "the DOM with CSS attached in place." It specifically EXCLUDES non-visual nodes (display:none elements, <head> contents), which is a distinct, purpose-built structure for what actually needs to be rendered.
  • ⚠️"Layout" and "Reflow" refer to the SAME computation — Layout is the term for the FIRST time it happens; Reflow is often used for SUBSEQUENT recalculations, but they are mechanically identical.
  • ⚠️Not every DOM/style change restarts the pipeline from the very beginning — the pipeline can re-enter at Layout, Paint, or Composite ONLY, depending on what specifically changed; understanding this is the single most practically useful takeaway of the whole topic.
  • ⚠️Layout can CASCADE beyond just the changed element — resizing one box can affect its parent's size (if the parent auto-sizes to content), its siblings' positions (in normal flow), and anything explicitly positioned relative to it, making Layout potentially much more expensive than a change to just ONE element might suggest.
  • ⚠️Reading certain JS properties (offsetWidth, getBoundingClientRect, etc.) FORCES the browser to synchronously flush any pending Layout recalculation immediately — this is the root cause of "layout thrashing" when reads and writes are interleaved in a loop.
  • ⚠️Painting isn't always a single, monolithic step across the whole page — the browser can split content into separate PAINT LAYERS (for elements with certain properties like `will-change`, fixed positioning, or video), letting it repaint just ONE layer instead of the entire page when only that layer's content changes.
  • ⚠️Composite-only updates (transform/opacity) still require an INITIAL Paint to have already happened — the GPU is repositioning/blending an EXISTING painted layer, not creating pixel content from nothing; an element that has never been painted yet (e.g. still `display:none`) can't skip straight to a composite-only update.
  • ⚠️The full 6-step pipeline (all the way from DOM/CSSOM) only runs completely for the INITIAL page load — subsequent updates are almost always partial re-entries at a later stage, which is why understanding WHICH stage a given change enters at is far more practically useful than just memorizing the 6 names in order.
  • ⚠️Different browser engines (Blink/Chromium, Gecko/Firefox, WebKit/Safari) implement these concepts with some internal naming/architectural differences — the CONCEPTUAL model (DOM→CSSOM→Render Tree→Layout→Paint→Composite) is a reasonably universal way to explain rendering, but exact internal terminology can vary slightly between engines, which is fine to mention if asked about cross-browser specifics.

Interview Q&A — Why / What / When / How

🎯 This is a foundational systems question — the strongest answers trace a CONCRETE example through the pipeline (like Section 8) rather than reciting the six stage names as an abstract list.
WhatWhat are the six steps of the Critical Rendering Path, in order?
+
1. DOM — parse HTML bytes into a tree of DOM nodes representing structure/content. 2. CSSOM — parse CSS bytes (from all sources) into a tree of computed style rules. 3. Render Tree — walk the DOM, attach matching CSSOM styles to each VISIBLE node, building a new tree that excludes non-visual content. 4. Layout (Reflow) — compute the exact size and position of every Render Tree node. 5. Paint — fill in the actual pixels (colors, text, images, borders) for every node, in the correct visual order. 6. Composite — the GPU assembles all painted layers into the final image displayed on screen.
WhyWhy is the Render Tree a separate step from just combining the DOM and CSSOM directly?
+
The DOM contains EVERY element in the document, including ones that will never actually be drawn on screen — `<head>`, `<script>`, `<meta>` tags, and any element styled with `display:none`. Building a genuinely separate Render Tree that walks the DOM and explicitly EXCLUDES these non-visual nodes (while attaching resolved styles to the ones that remain) means the LATER stages (Layout, Paint) only ever have to deal with content that actually needs to be rendered — they never waste computation considering elements that contribute nothing to the visual output. This separation keeps each subsequent stage focused purely on what's actually visible.
WhenWhen does a JavaScript-driven change re-enter the pipeline at Layout, versus Paint, versus Composite only?
+
It re-enters at Layout when the change affects an element's GEOMETRY — its size or position (width, height, top, left, margin, font-size, and similar properties) — since these require recomputing where things go before anything can be redrawn. It re-enters at Paint (skipping Layout) when the change is purely VISUAL and doesn't affect geometry — background-color, color, box-shadow, visibility. It re-enters at Composite ONLY (skipping both Layout and Paint) for `transform` and `opacity` changes specifically, since the GPU can reposition or blend an already-painted layer without recomputing geometry or redrawing pixel content at all.
HowHow would you trace a specific code change — like adding a new list item to a visible <ul> via JavaScript — through the pipeline?
+
1. `document.querySelector("ul").appendChild(newLi)` modifies the DOM tree directly — a new DOM node is added as a child of the `<ul>` node.
2. The CSSOM doesn't need to be rebuilt (no CSS rules changed) — the browser reuses the EXISTING CSSOM and simply looks up which rules apply to this new `<li>` node.
3. The Render Tree is updated — a new Render Tree node is created for the new `<li>` (assuming it's visible), with its resolved styles attached.
4. Layout runs — the new `<li>`'s size/position is computed, and since it's a NEW item in a list, this likely also affects the `<ul>`'s own height (if it auto-sizes to content) and potentially pushes subsequent siblings/content below it.
5. Paint runs — the new `<li>`'s content (text, any styling) is drawn.
6. Composite runs — the updated layer(s) are assembled into the final displayed frame.
This change re-enters the pipeline starting from the RENDER TREE step (since it's a genuine DOM structure change), not from DOM/CSSOM parsing (nothing needed re-parsing) and not skipping ahead to Layout-only either (since a new element, not just a style change on an existing one, was introduced).
WhatWhat's the difference between the terms "Layout" and "Reflow"?
+
They refer to the exact SAME underlying computation — determining the size and position of every element in the Render Tree. "Layout" is typically used to refer to this computation happening for the FIRST time, during the initial page render. "Reflow" is commonly used to refer to this SAME computation happening AGAIN, LATER, triggered by a subsequent DOM or style change after the initial render. There's no mechanical difference between them — it's purely a naming convention based on WHEN in the page's lifecycle the computation occurs.
WhyWhy does the Render Tree step specifically need to happen AFTER both the DOM and CSSOM are fully built, rather than being computed incrementally alongside them?
+
Building the Render Tree requires knowing, for EVERY DOM node, its FINAL resolved style — which depends on the complete CSSOM (since CSS rules can come from multiple sources and later rules can override earlier ones via the cascade). If the Render Tree were built incrementally alongside CSSOM construction, a node's style could be determined INCORRECTLY based on an incomplete CSSOM, and would then need to be recomputed once more CSS rules arrive — potentially multiple times per node. Waiting until the CSSOM is fully resolved before building the Render Tree ensures each node's style is computed CORRECTLY exactly once, avoiding wasted, potentially-incorrect intermediate work.
WhenWhen would a seemingly small style change (like updating one element's font-size) end up being surprisingly expensive?
+
When that element is deeply nested within a LARGE subtree, or has many siblings whose layout depends on it — changing `font-size` alters the element's rendered text dimensions, which can change ITS size, which can then change its PARENT's size (if the parent auto-sizes to content), which can shift the position of SIBLING elements in normal document flow, and so on, cascading outward. In the worst case (e.g. changing a deeply-shared/foundational element like a global header's font-size), this single change can force the browser to recompute layout for a very large portion of the entire page, not just the one element that was directly modified — this cascading potential is exactly why Layout/Reflow is considered one of the more expensive stages to trigger carelessly or frequently.
HowHow would you explain, step by step, why changing an element's opacity is cheaper than changing its width, even though both are just "one CSS property change"?
+
Changing width: the browser must re-enter the pipeline at LAYOUT — recomputing this element's geometry, which may cascade to affect its parent's size and sibling positions — THEN re-enter PAINT to redraw the now-differently-sized element's pixels (and potentially other affected elements) — THEN re-enter COMPOSITE to assemble the final frame. Three sequential, potentially expensive stages.

Changing opacity: opacity doesn't affect the element's geometry at all (its size/position in the layout remain unchanged) — so LAYOUT is skipped entirely. It also doesn't require redrawing the element's actual pixel CONTENT — the shape, colors, and text are exactly the same, just displayed with different transparency — so PAINT is skipped too. The browser re-enters the pipeline directly at COMPOSITE, where the GPU simply blends the ALREADY-painted layer at the new opacity level. This is why the SAME "one property change" framing hides a fundamentally different amount of underlying work — the specific property determines how far back into the pipeline the browser needs to re-enter.
