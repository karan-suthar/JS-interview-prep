What Are Core Web Vitals?

💡 Core Web Vitals are a specific set of metrics Google defined to measure real-world USER EXPERIENCE quality — chosen because they capture three distinct, important dimensions of a page's feel: how fast it LOADS, how RESPONSIVE it is to interaction, and how VISUALLY STABLE it is. They directly factor into Google Search ranking.
Three metrics, three different user experience dimensions
⚠ INP replaced FID (First Input Delay) as the official interactivity metric in March 2024. FID only measured the delay before the FIRST interaction started processing; INP measures responsiveness across the ENTIRE page lifecycle and the full duration of processing, giving a more complete picture. If asked about FID, be ready to explain this transition.

LCP — Largest Contentful Paint

LCP
Largest Contentful Paint
The time from navigation start until the LARGEST visible content element (usually a hero image, a large block of text, or a background image) has fully rendered on screen. It's a proxy for "when does the page feel like it has actually loaded, from the user's perspective?"
Good: ≤ 2.5s
Needs Improvement: 2.5–4s
Poor: > 4s
💡 Common causes of a bad LCP: slow server response times, render-blocking CSS/JS delaying paint, the LCP element itself being a large, unoptimized image, or the LCP element being discovered LATE (e.g. loaded via JS after initial render, instead of directly in the HTML).
Fix 1
Optimize/preload the LCP image
Compress it (modern format like AVIF/WebP), size it appropriately, and explicitly preload it so the browser discovers it as early as possible.
<link rel="preload" href="hero.avif" as="image" fetchpriority="high" />
Fix 2
Improve server response time (TTFB)
Use a CDN, enable server-side caching, optimize slow database queries, or upgrade hosting — LCP can't start its clock any earlier than the server actually responds.
// e.g. add caching headers, use // edge/CDN rendering, reduce // server-side processing time
Fix 3
Eliminate render-blocking resources
Inline critical CSS, defer non-critical CSS/JS, so the browser can paint the LCP element without waiting on unrelated resources.
<style>/* critical CSS inline */</style> <script defer src="app.js"></script>

INP — Interaction to Next Paint

INP
Interaction to Next Paint
Measures the latency of EVERY user interaction (click, tap, key press) throughout the page's lifetime, from the input to when the browser can actually paint the next visual update in response — reporting a representative (typically near-worst-case) value. It's a proxy for "does this page feel responsive when I actually use it?"
Good: ≤ 200ms
Needs Improvement: 200–500ms
Poor: > 500ms
The three phases INP measures for a single interaction
💡 Common causes of bad INP: long-running JavaScript blocking the main thread (so input can't even be PROCESSED promptly), heavy/expensive event handlers doing too much synchronous work, and large DOM updates/re-renders triggered by the interaction that take a long time to paint.
Fix 1
Break up long JavaScript tasks
Split large synchronous work into smaller chunks, yielding control back to the main thread between them, so the browser can process pending input promptly.
async function processLargeList(items) { for (const item of items) { processItem(item); await new Promise(r => setTimeout(r)); } // yields between iterations }
Fix 2
Debounce/defer expensive handler work
Use React's `startTransition` (or plain debouncing) to mark expensive, non-urgent work as lower priority, keeping the interaction itself feeling instant.
startTransition(() => { setResults(expensiveFilter(data)); }); // input stays responsive
Fix 3
Move heavy computation off the main thread
Use a Web Worker for CPU-intensive work (parsing, sorting huge datasets, image processing) so it doesn't block the main thread from handling user input at all.
const worker = new Worker("heavy-task.js"); worker.postMessage(data); worker.onmessage = (e) => setResult(e.data);

CLS — Cumulative Layout Shift

CLS
Cumulative Layout Shift
A unitless score measuring how much VISIBLE content unexpectedly shifts position during the page's lifetime — calculated from how much of the viewport moved, multiplied by how FAR it moved. Unlike LCP/INP, this is a SCORE, not a time measurement.
Good: ≤ 0.1
Needs Improvement: 0.1–0.25
Poor: > 0.25
The classic CLS bug — content shifting as an ad/image loads in
💡 Common causes of bad CLS: images/videos/iframes/ads without reserved dimensions, web fonts causing a visible reflow when they swap in (FOIT/FOUT), and content dynamically injected ABOVE existing content (like a banner or cookie notice) without reserving space beforehand.
Fix 1
Always set width/height (or aspect-ratio)
Explicit dimensions let the browser reserve the correct space BEFORE the image/video/iframe loads, so nothing has to move once it arrives.
<img src="photo.jpg" width="800" height="600" alt="..." />
Fix 2
Reserve space for dynamic/injected content
For ads, banners, or embeds that load asynchronously, reserve a fixed-size container via CSS (min-height) ahead of time, rather than letting content push everything down once it loads.
.ad-slot { min-height: 250px; /* reserved */ }
Fix 3
Control web font loading behavior
Use `font-display: optional` or preload critical fonts to minimize the visible reflow when a custom font swaps in and changes text metrics/wrapping.
@font-face { font-family: "Custom"; font-display: swap; /* or optional */ }

Common Gotchas & Interview Traps

  • ⚠️FID (First Input Delay) was RETIRED as a Core Web Vital in March 2024, replaced by INP — an outdated answer citing FID as the current interactivity metric is a signal of stale knowledge; be ready to mention this transition if it comes up.
  • ⚠️CLS only counts UNEXPECTED shifts — shifts caused directly by user interaction (like clicking a button to expand an accordion) are explicitly EXCLUDED from the score, since those are expected, intentional layout changes.
  • ⚠️LCP is measured ONCE per page load — it doesn't accumulate or repeat like CLS/INP do across the page's lifetime; it's specifically about the INITIAL loading experience.
  • ⚠️The LCP "element" can change during loading as larger content appears — the browser continuously tracks the largest element seen SO FAR and reports the final one once it stabilizes (typically once user input occurs, or the page finishes loading).
  • ⚠️Lazy-loading the LCP image (a mistake covered in the images topic) directly hurts LCP — this is a concrete, cross-cutting example of how different performance topics interact; always exempt the LCP candidate from lazy loading.
  • ⚠️A single-page app's client-side route changes are NOT automatically tracked as new LCP events by default — LCP is fundamentally tied to the initial navigation; measuring "soft navigation" performance in SPAs requires additional tooling/instrumentation beyond the standard Core Web Vitals APIs.
  • ⚠️INP reports a representative interaction, not necessarily the average — it's designed to reflect something close to a high-percentile (worst-typical) interaction on the page, so a few very slow outlier interactions can meaningfully affect the score even if MOST interactions feel fine.
  • ⚠️Web Workers can't directly manipulate the DOM — offloading heavy computation to a worker (an INP fix) requires structuring the code so the worker does the CPU-heavy part and posts a message back with the result, which the main thread then uses to update the DOM.
  • ⚠️font-display:swap can itself CAUSE a layout shift (the classic "flash of unstyled text" swapping to the custom font, which may have different metrics/character widths) — it trades a blank-text flash for a metrics-shift flash; `font-display:optional` avoids the shift but may not show the custom font at all on a slow connection, a real trade-off worth mentioning.
  • ⚠️These three metrics can trade off against each other if optimized carelessly — e.g. aggressively inlining ALL CSS to help LCP could bloat the HTML document and slow down JS parsing/execution, indirectly hurting INP; a holistic view considering all three together (not optimizing one in isolation) is the correct approach.

Interview Q&A — Why / What / When / How

🎯 Core Web Vitals questions test both conceptual understanding AND practical fix knowledge — a strong answer names the metric, explains what it measures and why it matters, and can immediately suggest concrete, actionable fixes.
WhatWhat does each of LCP, INP, and CLS actually measure?
+
LCP (Largest Contentful Paint) measures LOADING speed — specifically, how long until the largest visible content element has rendered, as a proxy for "does the page feel loaded?" INP (Interaction to Next Paint) measures RESPONSIVENESS — the latency between a user's interaction and the browser's next visual update in response, sampled across every interaction on the page. CLS (Cumulative Layout Shift) measures VISUAL STABILITY — a unitless score quantifying how much visible content unexpectedly shifts position during the page's lifetime.
WhyWhy did Google replace FID with INP as the official interactivity metric?
+
FID only measured the delay before the browser could even START processing the FIRST user interaction on a page — it said nothing about how long the interaction took to actually FINISH processing, nor anything about interactions AFTER the first one. This meant a page could have a great FID score while still feeling sluggish for every subsequent click/tap, or having a slow-but-not-technically-delayed first interaction. INP addresses both gaps: it measures the FULL latency (input delay + processing time + presentation delay) of interactions across the ENTIRE page lifetime, giving a much more complete and representative picture of how responsive a page actually feels to use, not just how it behaves on the very first click.
WhenWhen would a layout shift NOT count toward a page's CLS score?
+
When the shift happens within 500ms of a genuine USER INTERACTION (a click, tap, or key press) — these are considered "expected" shifts, since the user directly caused them (e.g. clicking a button that expands an accordion, or a "load more" button that adds content below). CLS is specifically designed to penalize UNEXPECTED, jarring shifts the user didn't cause or anticipate — like an ad loading in and pushing content down while the user is reading, or about to click something else entirely.
HowHow would you diagnose which specific element is causing a poor LCP score on a real page?
+
1. Open Chrome DevTools' Performance panel (or Lighthouse) and record a page load — the LCP marker is shown directly on the timeline, along with which specific DOM element was identified as the largest contentful element.
2. Check the BREAKDOWN of what's delaying that element — DevTools/Lighthouse typically report sub-phases: time to first byte (TTFB), resource load delay, resource load time, and element render delay — pinpointing whether the bottleneck is server response time, a slow-loading resource (like an unoptimized image), or render-blocking CSS/JS holding up the paint.
3. Cross-reference with FIELD data (via PageSpeed Insights, using real CrUX data) to confirm the lab-identified issue matches what real users are actually experiencing, since lab and field results can sometimes differ.
4. Apply the fix matching the identified bottleneck — preloading/optimizing the image, improving server response time, or removing render-blocking resources — and re-measure to confirm improvement.
WhatWhat are the three phases that make up an INP measurement for a single interaction?
+
1. Input delay — the time between the user's physical action (click/tap/keypress) and the browser actually being able to start processing it, often delayed if the main thread is busy with other work. 2. Processing time — how long the actual event handler(s) triggered by the interaction take to run. 3. Presentation delay — the time from when processing finishes until the browser can actually paint the resulting visual update to the screen. INP sums all three phases; a slow INP score can stem from a bottleneck in ANY of them, which is why diagnosing INP requires identifying WHICH phase is actually the problem, not just that "the interaction feels slow."
WhyWhy can't lab tools like Lighthouse give a fully reliable INP score, unlike LCP or CLS?
+
INP is fundamentally about measuring the latency of REAL user interactions — clicks, taps, key presses — happening at unpredictable moments throughout a real user's session. A lab test is an AUTOMATED, scripted page load with no actual human interacting with the page in a realistic way, so there's no natural interaction data to measure INP from in the same way LCP (a loading metric, measurable from an automated page load alone) or CLS (measurable by observing layout changes during an automated load) can be. Lab tools can simulate SOME interactions to approximate INP-like behavior, but the authoritative, meaningful INP score genuinely requires real user interaction data collected from the field (via Real User Monitoring or the CrUX report).
WhenWhen would offloading work to a Web Worker be the right INP fix, versus simply breaking a task into smaller chunks on the main thread?
+
Use a Web Worker when the work is GENUINELY CPU-intensive and doesn't need frequent, tight back-and-forth with the DOM — e.g. parsing a large dataset, complex calculations, image/data processing — since moving it entirely off the main thread means it NEVER competes with input handling at all, regardless of how long it takes. Simply breaking a task into smaller chunks (yielding between them) is more appropriate when the work DOES need to interact with the DOM frequently (which Workers can't do directly), or when the total work is more moderate and the goal is just to interleave it with input handling rather than eliminate main-thread involvement entirely. Web Workers offer a stronger guarantee (zero main-thread contention) but add complexity (message-passing, no direct DOM access); chunking is simpler but still consumes main-thread time, just in smaller, less blocking increments.
HowHow would you fix a page where a cookie-consent banner injected at the top of the page (after initial load) is causing a poor CLS score?
+
// ✗ Before — banner inserted with no reserved space, pushes ALL content down // when it appears (often after an async check for consent status) // ✓ After — reserve the space UPFRONT with CSS, even before the banner's // final content/visibility is determined .cookie-banner-container { min-height: 80px; /* matches the banner's expected height */ }
Reserving the space with a fixed-height (or min-height) CONTAINER in the initial HTML/CSS — present in the layout from the very first render, regardless of whether the banner's content has loaded/decided to show yet — means there's no empty-to-filled transition that pushes other content around. An alternative approach is positioning the banner as a fixed/sticky overlay (e.g. `position: fixed` at the bottom of the viewport) that doesn't participate in the normal document flow at all, so it can never push other content around no matter when it appears.
