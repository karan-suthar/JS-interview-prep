Hydration & Hydration Mismatches

What Hydration Actually Is

💡 Hydration is the process of the browser taking ALREADY-RENDERED, server-generated HTML (from SSR/SSG/ISR) and "attaching" React's event handlers, state, and interactivity to that existing markup — WITHOUT re-creating the DOM from scratch. React walks the existing HTML and the component tree TOGETHER, expecting them to match.
Hydration vs a full client-side render — different starting points, same end result
⚠ A "hydration mismatch" happens when the HTML the SERVER sent doesn't match what React would produce if it rendered the SAME component tree on the CLIENT. React expects these to be IDENTICAL — any divergence is a mismatch, which React must then reconcile (often by discarding and re-rendering, at a real performance and correctness cost).
2

The Hydration Process, Step by Step

Step 1Server renders HTML
The server runs the React component tree, produces complete HTML, and sends it to the browser — the user sees content immediately, before any JS has run.
Step 2Browser displays the static HTML
The page is VISIBLE, but not yet interactive — clicking a button does nothing yet, since no JavaScript event handlers are attached.
Step 3JS bundle downloads and runs
React's client-side code loads and begins the hydration process, starting from the root of the app.
Step 4React walks the tree, comparing
For each component, React compares what the EXISTING DOM node looks like against what it would have rendered itself — if they match, React REUSES the existing DOM node and attaches event listeners/state to it.
Step 5App becomes interactive
Once hydration completes, event handlers are live, state is initialized, and the app behaves like a normal client-side React app from this point forward.
🚨 If, at Step 4, React finds a MISMATCH between the existing HTML and what it would have rendered, it logs a hydration warning/error and typically falls back to discarding the mismatched DOM and re-rendering that portion client-side — losing some of hydration's performance benefit for the affected subtree, and potentially causing a visible flash/flicker as content changes.
3

What Causes Hydration Mismatches

Cause 1
Using browser-only APIs during render
`window`, `document`, `localStorage`, or `navigator` don't exist on the server — using them directly during rendering (not inside `useEffect`) produces different output server vs client.
// ✗ Mismatch — window doesn't // exist server-side <div>{window.innerWidth}</div>
Cause 2
Date/time or random values rendered directly
`Date.now()`, `Math.random()`, or `new Date().toLocaleString()` produce a DIFFERENT value on the server (at build/request time) than on the client (a moment later).
// ✗ Mismatch — timestamps differ <span>{Date.now()}</span>
Cause 3
Invalid HTML nesting
The browser SILENTLY auto-corrects invalid HTML nesting (e.g. a `<div>` inside a `<p>`) while parsing — resulting in a DOM tree structure React didn't expect, since React's virtual representation still thinks it's what was written.
// ✗ Browser silently restructures this <p><div>Invalid nesting</div></p>
Cause 4
Conditionally rendering based on typeof window
A common but flawed "fix" attempt — checking `typeof window !== "undefined"` during RENDER still produces different output server vs client, since the condition itself evaluates differently in each environment.
// ✗ Still mismatches — condition itself // differs between server and client {typeof window !== "undefined" ? <ClientWidget /> : null}
Cause 5
Browser extensions modifying the DOM
Some browser extensions (password managers, ad blockers, translation tools) inject attributes or elements into the page BEFORE React hydrates — React sees DOM content it never rendered itself.
// Not your app's code at all — an // extension injected e.g. a // data-* attribute or wrapper div
Cause 6
Locale/timezone-dependent formatting
Server and client can have DIFFERENT locale/timezone settings — `toLocaleDateString()` or similar formatting functions can produce different STRING output for the exact same underlying date value.
// ✗ Server (UTC) vs client's local // timezone can format differently {date.toLocaleDateString()}

How to Debug a Hydration Mismatch

Step 1Read the actual error message carefully
React's hydration error messages (especially in React 18+/Next.js) often show a DIFF between server and client HTML directly in the console — this is the single most useful starting clue, often pointing almost exactly at the offending element.
Step 2Disable browser extensions / test in Incognito
Rule out Cause 5 (extension DOM injection) first, since it's easy to mistake for an application bug — test in a clean Incognito window with extensions disabled.
Step 3Search the component for browser-only APIs, Date/random, or locale formatting
Grep the suspect component (and its children) for `window`, `document`, `Date.now()`, `Math.random()`, `toLocaleString`, or similar — these are the most common root causes by far.
Step 4Check for invalid HTML nesting
Validate the rendered markup for structurally invalid nesting (block elements inside `<p>`, `<div>` inside `<table>` without proper wrapper elements, `<a>` inside `<a>`) — the browser's silent auto-correction of these is a very common, easy-to-miss cause.
Step 5View source vs. inspect element to compare
"View Page Source" shows the ORIGINAL server-rendered HTML; "Inspect Element" shows the CURRENT (possibly already-corrected-by-browser, or already-hydrated) DOM — comparing these two directly can reveal exactly where they diverge.
✓ The fastest debugging shortcut: React 18's hydration error messages in development mode typically print BOTH the server-rendered HTML and what the client attempted to render, with the differing part highlighted — read this diff FIRST before doing any manual investigation.
5

Fix Patterns for Each Cause

✗ Browser API used during render
function WidthDisplay() { return <div>{window.innerWidth}</div>; }
✓ Move to useEffect, default for SSR
function WidthDisplay() { const [width, setWidth] = useState(null); useEffect(() => { setWidth(window.innerWidth); // client-only }, []); return <div>{width ?? "—"}</div>; }
✗ typeof window check during render
{typeof window !== "undefined" ? <ClientWidget /> : null}
✓ Use a "mounted" state flag instead
const [mounted, setMounted] = useState(false); useEffect(() => setMounted(true), []); if (!mounted) return null; // same on BOTH return <ClientWidget />;
✗ A timestamp that legitimately differs
<span>{new Date().toLocaleTimeString()}</span>
✓ Explicitly suppress for KNOWN, expected diffs
<span suppressHydrationWarning> {new Date().toLocaleTimeString()} </span> // Use SPARINGLY — only when the mismatch // is genuinely expected/harmless (like a clock)

Invalid HTML nestingFix the actual markup structure to be valid HTML — this isn't just a hydration issue, it's simply incorrect HTML

Common Gotchas & Interview Traps

  • ⚠️`suppressHydrationWarning` only suppresses the WARNING for that specific element's direct text content — it does NOT fix an underlying structural problem, and doesn't apply recursively to children. It should be reserved for genuinely EXPECTED, harmless mismatches (like a live clock), never used as a blanket fix for an actual bug.
  • ⚠️A "typeof window !== 'undefined'" check during RENDER is a classic anti-pattern that ironically CAUSES the exact mismatch it's often (incorrectly) used to try to prevent — the check itself evaluates differently server vs client, guaranteeing a mismatch rather than avoiding one.
  • ⚠️Invalid HTML nesting mismatches can be subtle and easy to miss — e.g. placing a `<div>` inside a `<p>`, or nesting interactive elements like `<button>` inside `<a>`, gets SILENTLY restructured by the browser's HTML parser, with no obvious visual symptom until React's hydration check catches the resulting structural mismatch.
  • ⚠️Browser extension-caused mismatches are a genuine, common false positive that can waste significant debugging time if not recognized quickly — always rule this out early by testing in Incognito/a clean profile before assuming it's an application bug.
  • ⚠️A hydration mismatch doesn't necessarily CRASH the app — React often recovers by discarding the mismatched subtree and re-rendering it client-side, meaning the app may still "work" while silently paying a performance cost and potentially showing a brief visual flicker; this makes mismatches easy to overlook if you're not watching the console.
  • ⚠️React 18 changed how hydration errors are reported, generally with more helpful diffs than older React versions — if referencing specific error message formats/behavior, be aware this has evolved across React versions, and it's fine to describe the GENERAL debugging approach rather than memorizing an exact message format.
  • ⚠️Rendering a value that depends on `Math.random()` or a UUID generated fresh on each render is a very common REAL bug (not just a theoretical example) — e.g. generating a "key" or an id value inline during render, rather than once and passed down, is a frequent source of this exact issue in real codebases.
  • ⚠️Passing a Date object as a prop from server to client doesn't guarantee consistent FORMATTING — the underlying timestamp might be identical, but if formatting (like `toLocaleDateString()`) happens SEPARATELY on each side, differing locale/timezone environment settings can still produce different final strings.
  • ⚠️Third-party scripts/libraries that manipulate the DOM directly (bypassing React) before hydration completes are another real, if less common, mismatch source — similar in nature to the browser extension issue, but caused by your OWN dependencies rather than something outside your control.
  • ⚠️Hydration mismatches are NOT unique to Next.js — this is a general React SSR concept that applies to any framework/setup doing server rendering with React (Remix, Gatsby with SSR features, custom SSR setups); Next.js is simply the most common context this comes up in interviews because of its popularity.

Interview Q&A — Why / What / When / How

🎯 Hydration mismatches are a very common REAL bug in production Next.js apps — interviewers value candidates who can both explain the underlying mechanism AND walk through a practical debugging process, not just recite the definition.
WhatWhat exactly is a hydration mismatch?
+
A hydration mismatch occurs when the HTML the SERVER generated and sent to the browser doesn't match what React would produce if it rendered the SAME component tree on the CLIENT, during the hydration process. React expects these two renders to be IDENTICAL, since hydration's whole point is to REUSE the existing server-rendered DOM rather than recreate it — when React detects a difference while walking the tree during hydration, it logs a warning/error and typically discards the mismatched portion, re-rendering it client-side instead, which costs some performance and can cause a visible flicker.
WhyWhy does using window.innerWidth directly during a component's render cause a hydration mismatch?
+
The `window` object doesn't exist in the SERVER'S execution environment at all (there's no browser window on the server) — so `window.innerWidth` during a SERVER render would throw an error, or if somehow guarded, would need to resolve to SOME different value entirely (since there's no real viewport on the server). When the SAME component then renders on the CLIENT, `window.innerWidth` resolves to the actual browser's real viewport width — a value the server had no way of knowing or matching in advance. This guarantees the server-rendered HTML and the client's expected render diverge specifically because of the ENVIRONMENT difference (no window server-side vs. a real window client-side), which is exactly the category of issue hydration mismatch detection is designed to catch.
WhenWhen is it actually appropriate to use suppressHydrationWarning, rather than treating a mismatch as a bug to fix?
+
When the mismatch is GENUINELY expected and harmless, and there's no way to make server and client output truly identical — the classic legitimate example is displaying a live, current timestamp (like "Last updated 3 seconds ago" or a running clock), where the server's render time and the client's render time WILL always differ by at least a few milliseconds/seconds, and this difference is not a bug but an inherent, acceptable property of showing "the current time." In this narrow case, `suppressHydrationWarning` tells React "I know this specific element's content will differ, and that's fine" rather than papering over an actual, fixable application bug. It should never be reached for as a first response to an unexplained mismatch — only after confirming the mismatch is truly expected and unavoidable.
HowHow would you debug a hydration mismatch error you've never seen before in a Next.js app?
+
1. Read the console error message CAREFULLY first — React (especially 18+) often prints a direct diff between the server-rendered and client-rendered HTML, which frequently points almost exactly at the problematic element or attribute.
2. Rule out browser extensions by reproducing in an Incognito window with extensions disabled — this is a common false positive that's easy to mistake for an app bug.
3. Search the implicated component (from the error's stack trace/diff) for browser-only APIs (`window`, `document`, `localStorage`), non-deterministic values (`Date.now()`, `Math.random()`), or locale-dependent formatting — these cover the vast majority of real-world causes.
4. Check the component's markup for structurally invalid HTML nesting that the browser might be silently correcting.
5. Once the specific cause is identified, apply the matching fix pattern — moving browser-API usage into `useEffect` with a safe default for the initial render, passing a server-computed value as a prop instead of recomputing differently on each side, or fixing genuinely invalid markup.
WhatWhat's wrong with using a "typeof window !== 'undefined'" check directly inside a component's render logic to avoid a hydration mismatch?
+
This pattern is often reached for AS a fix, but it's actually a common cause of the very problem it's trying to solve. The check `typeof window !== "undefined"` itself evaluates to `false` on the SERVER (no window object exists) and `true` on the CLIENT (window exists) — meaning the CONDITION branches differently between the two environments, which means the component renders DIFFERENT output (e.g. `null` vs. an actual widget) on each side. This is EXACTLY a hydration mismatch by definition — server and client produced different HTML for the same component. The correct fix uses a "mounted" state flag set via `useEffect` (which only runs client-side, AFTER the initial hydration-matching render), ensuring BOTH the server render and the client's FIRST render agree (both show the "not yet mounted" state), with the different content only appearing on a SUBSEQUENT client-only re-render, after hydration has already successfully completed.
WhyWhy can invalid HTML nesting cause a hydration mismatch, even if the developer never intentionally wrote different content for server vs client?
+
The HTML specification defines certain nesting rules that browsers enforce automatically during PARSING — for example, block-level elements like `<div>` are not valid children of `<p>` elements. When the browser parses server-sent HTML containing this kind of invalid nesting, it SILENTLY auto-corrects the structure to make it valid (e.g. by closing the `<p>` tag early), producing an ACTUAL DOM tree that differs from what the raw HTML text literally specified. React, meanwhile, has its own internal representation based on what it INTENDED to render (the invalid nesting, as written in the component code) — when hydration compares React's expectation against the browser's ALREADY-CORRECTED actual DOM structure, they don't match, even though the developer never wrote intentionally different server/client logic. The root cause here is fundamentally an HTML VALIDITY bug, which then surfaces specifically as a hydration mismatch.
WhenWhen would a hydration mismatch silently degrade performance without necessarily breaking functionality?
+
When React detects the mismatch, discards the affected subtree, and successfully re-renders it entirely client-side — the app may end up displaying CORRECTLY (from the user's perspective, especially if the difference is subtle), but this recovery path is strictly more expensive than a normal, successful hydration would have been: instead of REUSING existing DOM nodes (hydration's core performance benefit), React has to throw them away and create brand new ones, essentially paying the cost of both the wasted server-rendering work AND a full client-side re-render for that portion of the page. This can happen repeatedly, on every page load, without ever crashing or visibly malfunctioning — making it the kind of issue that's easy to miss unless you're actively watching the browser console for hydration warnings during development and testing.
HowHow would you fix a component that needs to display a value from localStorage (e.g. a saved user preference) without causing a hydration mismatch?
+
function ThemeDisplay() { const [theme, setTheme] = useState("light"); // SAME default, both sides useEffect(() => { // localStorage only accessed client-side, AFTER initial hydration-matching render const saved = localStorage.getItem("theme"); if (saved) setTheme(saved); }, []); return <div>Current theme: {theme}</div>; }
The component initializes state with a FIXED default value (e.g. `"light"`) that's IDENTICAL on both server and client's first render — `localStorage` (a browser-only API) is only ever accessed inside `useEffect`, which runs strictly AFTER the initial render has already successfully hydrated and matched. Once `useEffect` runs client-side and reads the actual saved preference, updating state triggers a NORMAL client-side re-render (not a hydration comparison) — meaning the user briefly sees the DEFAULT value, then it updates to their actual saved preference a moment later, which is an acceptable, common trade-off for avoiding a hydration mismatch on genuinely client-only data.
