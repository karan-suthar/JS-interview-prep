Lossy vs Lossless Compression

💡 Lossless compression shrinks a file WITHOUT discarding any information — decompressing it recovers the EXACT original pixels. Lossy compression discards some information permanently (based on what the human eye is less likely to notice) to achieve much smaller file sizes, at the cost of some quality/accuracy.
TypeFile sizeQualityBest for
LosslessLargerPerfect, pixel-exactScreenshots, logos, diagrams, images needing sharp edges/text
LossyMuch smaller (often 5-10x)Slightly degraded (often imperceptible at reasonable quality settings)Photographs, complex real-world images with lots of color/detail

The Four Formats

JPEG (.jpg)
The old reliable — universally supported, lossy only
Lossy-only compression, no transparency (alpha channel) support, no animation. Extremely widely supported (every browser, every device, decades old). Still a very reasonable default for PHOTOGRAPHS where modern format support can't be guaranteed.
PNG (.png)
Lossless with transparency — the go-to for graphics, not photos
Lossless-only compression, FULL alpha transparency support, great for images with sharp edges, text, or flat colors (logos, icons, screenshots, diagrams). Poor fit for photographs — produces much larger files than JPEG for the same photographic content, with no quality benefit for typical use.
WebP
Google's modern all-rounder — both lossy AND lossless, plus animation
Supports BOTH lossy and lossless compression in one format, alpha transparency, and animation (as a GIF replacement). Typically 25-35% smaller than equivalent-quality JPEG/PNG. Excellent, now near-universal browser support.
AVIF
The newest, most efficient format — even smaller than WebP
Based on the AV1 video codec's intra-frame compression. Typically 20-50% smaller than WebP at equivalent visual quality, supports transparency, animation, and wider color gamuts (HDR). Browser support is strong in modern browsers but slightly less universal than WebP, and encoding is computationally slower.
Roughly equivalent visual quality — relative file size comparison
⚠ These percentages are ILLUSTRATIVE, not precise — actual savings vary significantly based on the specific image content, encoder settings, and quality target. The RELATIVE ordering (AVIF < WebP < JPEG for typical photos, with PNG being disproportionately large for photographic content) is the consistent, defensible pattern to cite.

Lazy Loading Images

💡 Lazy loading defers downloading an image until it's about to actually enter the viewport (or nearly so), instead of downloading every image on the page immediately — saving bandwidth and speeding up initial load, especially for long pages with many images.
// The native, declarative way — a single HTML attribute, no JS required <img src="photo.jpg" loading="lazy" alt="A description" /> // "loading" attribute values: // lazy → defer loading until near the viewport // eager → load immediately (the default browser behavior) // auto → let the browser decide (also effectively the default)
Eager (default) vs lazy loading — what downloads on initial page load
🚨 Never lazy-load the hero/above-the-fold image (especially the Largest Contentful Paint candidate)! Lazy loading an image the user sees IMMEDIATELY delays it unnecessarily and can actively HURT your LCP (Largest Contentful Paint) performance metric — only apply loading="lazy" to images that are genuinely off-screen on initial load.

Responsive Images — srcset and sizes

💡 srcset gives the browser MULTIPLE versions of an image at different resolutions, letting it pick the most appropriate one based on the user's actual screen size and pixel density — instead of forcing everyone to download one huge image sized for the largest possible display.
<img src="photo-800w.jpg" srcset="photo-400w.jpg 400w, photo-800w.jpg 800w, photo-1200w.jpg 1200w, photo-1600w.jpg 1600w" sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 800px" alt="A description of the image" />
AttributeWhat it tells the browser
srcsetA LIST of available image files, each labeled with its actual pixel WIDTH (using the "w" descriptor) — e.g. "photo-800w.jpg 800w" means this file is 800 pixels wide
sizesA set of CSS-like media conditions describing how WIDE the image will actually be DISPLAYED at different viewport widths — this is what lets the browser calculate which srcset candidate is the best fit
srcA fallback for browsers that don't support srcset/sizes at all (very old browsers) — always still required
How the browser picks a srcset candidate
⚠ This is the classic source of confusion: sizes describes DISPLAY width (how big it appears in the layout), while srcset's "w" values describe the FILE's actual pixel width. The browser combines these with the device's pixel density to compute how many actual device pixels are needed, then picks the smallest srcset candidate that satisfies that requirement.
7

<picture> — Format Fallback & Art Direction

💡 While srcset lets the browser choose between different SIZES of the SAME image, <picture> lets you offer entirely DIFFERENT formats (AVIF → WebP → JPEG fallback) or even different CROPS for different screen sizes ("art direction") — the browser picks the first <source> it supports/matches.
// Modern format fallback — browser picks the FIRST format it supports <picture> <source srcset="photo.avif" type="image/avif" /> <source srcset="photo.webp" type="image/webp" /> <img src="photo.jpg" alt="A description" /> {/* universal fallback */} </picture> // A browser supporting AVIF uses the first source. A browser supporting WebP but // not AVIF skips to the second. Anything else falls back to the plain <img> JPEG. // "Art direction" — showing a DIFFERENT crop/composition on small screens, // not just a resized version of the same image <picture> <source media="(max-width: 600px)" srcset="photo-tight-crop.jpg" /> <img src="photo-wide-crop.jpg" alt="A description" /> </picture> // On mobile, shows a TIGHTER crop (e.g. zoomed in on a subject's face) instead of // just shrinking the same wide landscape photo, which might lose the subject entirely
MechanismSolves
srcset + sizes (on <img>)Same image, different RESOLUTIONS — browser picks based on display size/density
<picture> + typeDifferent FORMATS — browser picks the first format it actually supports
<picture> + mediaDifferent CROPS/compositions — "art direction" for different screen sizes

Common Gotchas & Interview Traps

  • ⚠️Lazy-loading the LCP (Largest Contentful Paint) image actively hurts performance — a common, easy-to-make mistake is applying `loading="lazy"` blanket-wide to every image on a page, including the critical above-the-fold hero image, which delays exactly the resource that matters most for perceived load speed.
  • ⚠️PNG is NOT a good default for photographs — a surprisingly common mistake (often from screenshot tools defaulting to PNG) that results in dramatically larger files than a properly-compressed JPEG/WebP/AVIF for the same photographic content, with no visible quality benefit.
  • ⚠️srcset's "w" descriptor is NOT the same as the "x" (pixel density) descriptor — `srcset="photo@2x.jpg 2x"` is a simpler, DIFFERENT syntax meaning "use this for 2x pixel density displays," typically used WITHOUT `sizes`; mixing up "w" and "x" descriptors in the same srcset list is invalid.
  • ⚠️Without explicit width/height attributes (or aspect-ratio CSS), images cause Cumulative Layout Shift (CLS) — the browser doesn't know how much space to reserve before the image loads, causing surrounding content to visibly jump once it arrives; always specify dimensions (even when using responsive images).
  • ⚠️<picture>'s <source> elements are evaluated TOP TO BOTTOM, and order matters — put the most preferred format FIRST (AVIF, then WebP, then the universal fallback `<img>` last), since the browser uses the first matching/supported source it finds.
  • ⚠️The `<img>` tag inside `<picture>` is REQUIRED, not optional — it serves as both the fallback for browsers that don't support any of the listed formats AND the element that actually receives `alt` text, sizing behavior, and CSS styling; `<picture>` itself is just a wrapper with no visual rendering of its own.
  • ⚠️Native lazy loading (`loading="lazy"`) has less precise control than JavaScript-based intersection-observer solutions — the exact "how far before entering the viewport" threshold is browser-determined and not currently configurable via the HTML attribute alone, unlike custom JS implementations which can fine-tune this.
  • ⚠️AVIF encoding is significantly slower than JPEG/WebP — this affects BUILD/processing time (generating the images), not runtime/decoding performance for the end user, but is worth mentioning if asked about AVIF's trade-offs beyond just file size and browser support.
  • ⚠️Responsive images (srcset) address BANDWIDTH efficiency, not necessarily FORMAT efficiency — these are complementary, separate optimizations; a truly optimized image pipeline typically combines BOTH multiple resolutions (srcset) AND multiple formats (picture/type), not just one or the other.
  • ⚠️SVG is often the better choice over PNG/WebP/AVIF for genuinely vector content (logos, icons, simple illustrations) — it's resolution-independent (scales perfectly to any size/density with no quality loss) and often produces a smaller file than a rasterized equivalent for simple graphics, a detail easy to overlook when the conversation is framed purely around JPEG/PNG/WebP/AVIF.

Interview Q&A — Why / What / When / How

🎯 Image optimization is one of the highest-leverage, most concrete performance topics — images are frequently the LARGEST portion of a typical page's total weight, so interviewers value precise, actionable answers here.
WhatWhat's the key trade-off between JPEG, PNG, WebP, and AVIF?
+
JPEG is lossy-only, universally supported, no transparency — a safe, small default for photos. PNG is lossless-only with full transparency support — ideal for graphics/logos/screenshots, but a poor fit for photographs (much larger files with no benefit). WebP supports both lossy AND lossless plus animation, typically 25-35% smaller than equivalent JPEG/PNG, with near-universal modern browser support. AVIF is the newest and most efficient (typically 40-50% smaller than JPEG), supports transparency/animation/HDR, but has slightly less universal support and slower encoding time. The general trade-off curve is: newer format = smaller files, but marginally less guaranteed support and slower to produce.
WhyWhy is PNG a poor choice for photographs, even though it's a perfectly good format in general?
+
PNG's lossless compression algorithm works well for images with LARGE areas of flat, repeated, or simply-patterned color (like logos, icons, or screenshots with sharp edges and text) — but photographs have continuous, complex gradients of color and fine detail throughout, which don't compress efficiently under a lossless algorithm designed around detecting repetition. Because PNG offers NO lossy option to discard visually-imperceptible detail (unlike JPEG/WebP/AVIF), it ends up preserving far more raw information than a human eye would ever notice missing, resulting in a dramatically larger file for the SAME apparent visual quality as a well-compressed lossy format.
WhenWhen should you avoid using loading="lazy" on an image?
+
Avoid it for any image visible in the INITIAL viewport on page load — especially the image likely to be the page's Largest Contentful Paint (LCP) candidate, such as a hero banner or a prominent above-the-fold photo. Lazy loading defers the image's download until it's about to enter the viewport; applying it to something ALREADY in the viewport at load time means the browser deliberately delays fetching it, which can noticeably worsen perceived load speed and directly hurt the LCP performance metric, which specifically measures how quickly the largest visible content element renders.
HowHow would you set up an image to serve AVIF to supporting browsers, WebP as a fallback, and JPEG as the universal fallback, while also being responsive to screen size?
+
Combine `<picture>` (for format fallback) with `srcset`/`sizes` on each `<source>` AND the final `<img>` (for resolution responsiveness):
<picture> <source type="image/avif" srcset="photo-400.avif 400w, photo-800.avif 800w, photo-1200.avif 1200w" sizes="(max-width: 600px) 100vw, 800px" /> <source type="image/webp" srcset="photo-400.webp 400w, photo-800.webp 800w, photo-1200.webp 1200w" sizes="(max-width: 600px) 100vw, 800px" /> <img src="photo-800.jpg" srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w" sizes="(max-width: 600px) 100vw, 800px" alt="A description" /> </picture>
The browser first picks a FORMAT it supports (checking `<source>` elements top to bottom), then WITHIN that chosen format's srcset, picks the best-fitting RESOLUTION based on `sizes` and the device's actual display characteristics — achieving both format and resolution optimization together.
WhatWhat's the difference between the "w" descriptor and the "x" descriptor in srcset?
+
The "w" descriptor (e.g. `photo-800.jpg 800w`) describes the image file's actual intrinsic pixel WIDTH — used together with the `sizes` attribute, which tells the browser how wide the image will be DISPLAYED at various viewport widths, letting it calculate the best-fitting candidate. The "x" descriptor (e.g. `photo@2x.jpg 2x`) instead directly describes pixel DENSITY — "use this file for 2x-density displays" — a simpler syntax typically used WITHOUT `sizes`, appropriate when the image is always displayed at a FIXED size regardless of viewport (unlike "w", which is meant for images that resize fluidly with the layout). The two descriptor types cannot be mixed within the same `srcset` list.
WhyWhy does the browser need BOTH srcset and sizes to make a good decision — wouldn't srcset alone be enough?
+
`srcset` alone only tells the browser what FILES are available and their raw pixel widths — it has NO information about how large the image will actually be rendered on the page, which depends entirely on the page's CSS layout (the image might be full-width on mobile, but only occupy a third of the width in a desktop grid layout, for instance). Without `sizes`, the browser would have to GUESS or default to assuming full-viewport-width, often resulting in downloading a LARGER image than actually needed for images that are deliberately laid out smaller than the viewport. `sizes` explicitly tells the browser "at this viewport width, this image will be displayed at THIS width," letting it accurately match against the available `srcset` candidates and choose the smallest one that still looks sharp at the actual DISPLAYED size.
WhenWhen would you use "art direction" (different image crops per screen size) instead of just responsively resizing the same image?
+
When simply shrinking a wide/landscape image down for a narrow mobile viewport would make the important subject too small to see clearly, or would awkwardly crop out key content due to the aspect ratio mismatch — for example, a wide group photo that reads fine at desktop width but becomes tiny and hard to make out at mobile width, versus a purposefully tighter, re-composed crop focusing on the key subject for mobile. Plain `srcset`/`sizes` only changes RESOLUTION (same image, different pixel dimensions) — it can't change the actual COMPOSITION/crop. `<picture>` with `media` conditions on its `<source>` elements is specifically designed for this "art direction" need, serving genuinely different image files (different crops, not just different sizes) at different breakpoints.
HowHow would you prevent layout shift (CLS) caused by images loading asynchronously, especially with responsive srcset images of varying sizes?
+
Always specify `width` and `height` attributes on the `<img>` tag (using the image's INTRINSIC aspect ratio, even though the actual rendered size may be controlled by CSS/srcset) — modern browsers use these attributes to calculate and reserve the correct ASPECT RATIO for the space before the image finishes loading, preventing surrounding content from jumping once it arrives, regardless of which specific srcset candidate ultimately gets chosen.
<img src="photo-800.jpg" srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1200.jpg 1200w" sizes="(max-width: 600px) 100vw, 800px" width="1200" height="800" {/* intrinsic aspect ratio — browser reserves 3:2 space regardless of final rendered size */} alt="A description" />
The browser uses `width`/`height` purely to compute the ASPECT RATIO to reserve, not necessarily the exact final rendered pixel size (which CSS and `sizes` can still override) — this decouples "prevent layout shift" from "control exact display size," letting both work together correctly.
