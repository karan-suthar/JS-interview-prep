The Big Picture — End to End

💡 Getting pixels on screen from a typed URL involves roughly SIX major stages: Network (fetch the HTML) → Parsing (build the DOM and CSSOM) → Render Tree (combine them) → Layout (compute geometry) → Paint (fill in pixels) → Composite (assemble layers on the GPU).

2

Network Phase — Getting the HTML

N
From typed URL to the first bytes of HTML arriving
DNS lookup → TCP handshake → TLS negotiation (HTTPS) → HTTP request/response
StepWhat happens
1. DNS lookupTranslates the human-readable domain (example.com) into an IP address — checked against browser cache, OS cache, router, then ISP/recursive DNS servers if not already known
2. TCP handshakeA 3-way handshake (SYN, SYN-ACK, ACK) establishes a reliable connection between the browser and the server at that IP
3. TLS negotiation (HTTPS)An additional handshake to establish an encrypted channel — exchanging certificates, agreeing on encryption parameters, before any actual data is sent
4. HTTP request sentThe browser sends a GET request for the page, including headers (cookies, cache validators, accepted content types)
5. Server respondsThe server sends back an HTTP response — a status code, response headers, and the HTML document body, often streamed in chunks rather than all at once
⚠ HTML parsing can start BEFORE the full response finishes downloading — the browser streams and incrementally parses HTML as bytes arrive, rather than waiting for the entire document. This is part of why a fast Time To First Byte (TTFB) matters so much for perceived load speed.

Parsing — Building the DOM and CSSOM

P
Turning raw HTML/CSS text into structured, in-memory tree objects
HTML → DOM tree (structure/content). CSS → CSSOM tree (styling rules)
Two SEPARATE trees, built in parallel from two different sources
🚨 The classic parser-blocking script rule: a plain <script> tag (no async/defer) PAUSES HTML parsing entirely while it downloads and executes — because the script might use document.write() or otherwise need to modify the DOM the parser hasn't finished building yet. This is why scripts are traditionally placed at the end of <body>, or given async/defer attributes.
Script loadingBlocks HTML parsing?Execution timing
<script src="..."></script> (default)✗ Yes, blocksImmediately, as soon as downloaded — parsing pauses to wait

Render Tree — Combining DOM + CSSOM

R
The browser merges DOM structure with CSSOM styles into ONE tree of visually renderable nodes
Only VISIBLE nodes are included — elements with display:none are excluded entirely
// This element exists in the DOM... <div style="display: none">Hidden content</div> // ...but is EXCLUDED entirely from the Render Tree — it takes up no space, // gets no layout box, and is never painted at all // Contrast with visibility: hidden — this DOES get a render tree node // and STILL occupies its layout space, it's just not painted/visible <div style="visibility: hidden">Invisible but still takes up space</div>
💡 This is the classic interview distinction between display: none and visibility: hidden — the FIRST is excluded from the render tree entirely (no space reserved); the SECOND still gets a layout box and reserves space, just isn't painted.
5

Layout (a.k.a. Reflow)

L
Computing the EXACT size and position of every render tree node
Given the viewport size, box model rules, and each element's styles — where exactly does everything go?
⚠ Layout is expensive because it can CASCADE — changing one element's size/position can ripple outward, requiring the browser to recompute the geometry of sibling, parent, and even distant elements affected by the change (e.g. content reflowing around a resized image).
// Properties that trigger LAYOUT when changed — expensive element.style.width = "500px"; element.style.height = "300px"; element.style.top = "20px"; element.style.fontSize = "18px"; // changes text metrics, cascades to layout // Reading certain properties FORCES a synchronous layout recalculation too — // a classic performance footgun called "layout thrashing" const width = element.offsetWidth; // forces layout to be computed RIGHT NOW to answer this
6

Paint

P
Filling in actual PIXELS — colors, text, borders, shadows, images
Once geometry (Layout) is known, the browser draws the visual appearance of each element onto one or more "layers"
// Properties that trigger PAINT (but NOT layout) when changed — moderately expensive element.style.backgroundColor = "red"; element.style.color = "blue"; element.style.boxShadow = "0 0 10px black"; // These don't change any element's SIZE or POSITION, so layout is skipped — // but the browser still needs to re-draw the affected pixels
7

Composite

C
Assembling separately-painted layers together, on the GPU, into the final image
The cheapest, fastest stage — some CSS properties can update WITHOUT touching Layout or Paint at all
// Properties that ONLY trigger Composite — the cheapest, GPU-accelerated path element.style.transform = "translateX(100px)"; element.style.opacity = "0.5"; // Neither changes layout geometry NOR requires re-painting pixel content — // the GPU just repositions/blends an already-painted layer // This is WHY "transform" and "opacity" are the go-to properties for // smooth, performant CSS animations
Changing this property...LayoutPaintComposite
width, height, top, left, font-size✓ Triggered✓ Triggered✓ Triggered
background-color, color, box-shadow✗ Skipped✓ Triggered✓ Triggered
transform, opacity✗ Skipped✗ Skipped✓ Triggered ONLY
✓ This table is one of the single most useful things to memorize for a performance interview — "prefer transform/opacity for animations, since they skip Layout AND Paint entirely" is a concrete, well-known optimization technique directly explained by understanding this pipeline.

Common Gotchas & Interview Traps

  • ⚠️CSS is render-blocking by default — the browser deliberately withholds painting ANYTHING until it has the complete CSSOM, specifically to avoid a "flash of unstyled content" (FOUC) it would otherwise need to immediately repaint over.
  • ⚠️JavaScript can be render-AND-parser-blocking — a plain synchronous `<script>` tag halts HTML parsing until it downloads and fully executes, since the script could use `document.write()` or otherwise need to modify the still-incomplete DOM.
  • ⚠️"Reflow" and "Layout" are the same concept, just different names — used somewhat interchangeably in different contexts/browsers' documentation; don't be thrown if an interviewer uses one term or the other.
  • ⚠️Reading certain DOM properties FORCES a synchronous layout recalculation ("layout thrashing") — properties like `offsetWidth`, `offsetHeight`, `getBoundingClientRect()`, and `scrollTop` force the browser to flush any pending layout changes immediately to give an accurate answer, which can be a serious performance problem if done repeatedly in a loop, interleaved with writes.
  • ⚠️display:none removes an element from the render tree ENTIRELY (no layout box, zero space reserved) — this is different from `visibility:hidden`, which still occupies its layout space but isn't painted, and different again from `opacity:0`, which is fully painted (and still interactive/clickable!) but simply invisible.
  • ⚠️Not every CSS/JS change triggers ALL three of Layout, Paint, and Composite — knowing which properties trigger which subset (the table in Section 7) is one of the most concrete, practically useful pieces of knowledge from this whole topic for real performance work.
  • ⚠️The DOM and CSSOM are built independently and in parallel from two different sources (HTML and CSS respectively) — they are NOT the same tree, and are only combined together into the Render Tree afterward.
  • ⚠️Preloading, prefetching, and preconnecting are three DIFFERENT optimization hints, not interchangeable — `preload` fetches a resource needed for THIS page soon; `prefetch` speculatively fetches something likely needed for a FUTURE navigation; `preconnect` just establishes the DNS/TCP/TLS connection early, without fetching any specific resource yet.
  • ⚠️Modern browsers use a "speculative"/"preload" scanner that scans ahead in the raw HTML response (even while the main parser might be blocked by a synchronous script) to discover and start downloading other resources (images, stylesheets, other scripts) early — a real optimization that somewhat softens the "parser-blocking script" problem, though it doesn't eliminate it.
  • ⚠️This pipeline runs again, PARTIALLY, for updates after the initial load — not every DOM/CSS change requires redoing the ENTIRE pipeline from Network/Parsing; JS-driven UI updates typically only re-trigger Layout/Paint/Composite (or some subset), which is exactly why understanding which specific stages a given change touches matters for performance.

Interview Q&A — Why / What / When / How

🎯 This is a foundational systems question interviewers use to check whether you understand the browser as a real, physical process — not just how to write code that runs inside it. Concrete, stage-by-stage reasoning beats a vague "the browser renders the page" answer.
WhatWhat are the major stages between entering a URL and seeing pixels on screen?
+
At a high level: (1) Network — DNS lookup, TCP/TLS handshake, HTTP request/response to fetch the HTML. (2) Parsing — the browser builds a DOM tree from the HTML and a CSSOM tree from the CSS, in parallel. (3) Render Tree construction — combining the DOM and CSSOM into one tree of visually renderable nodes (excluding anything with `display:none`). (4) Layout (a.k.a. Reflow) — computing the exact size and position of every node. (5) Paint — filling in actual pixel colors/text/images for each node. (6) Composite — the GPU assembles separately-painted layers into the final image shown on screen.
WhyWhy does CSS block rendering, while some JavaScript can also block HTML parsing — and why are these separate concerns?
+
CSS blocks RENDERING (specifically, painting) because the browser needs the COMPLETE CSSOM before it can accurately determine each element's final visual styling — painting with incomplete styles would mean immediately having to repaint once the rest of the CSS arrives, causing a visible "flash of unstyled content." JavaScript can additionally block HTML PARSING itself (a stricter, earlier-stage block) because a `<script>` tag might call `document.write()` or otherwise manipulate the DOM the parser is still in the middle of constructing — the browser can't safely continue parsing past a script tag until it knows whether that script is going to modify the document. These are separate concerns because CSS never modifies the DOM's structure, while JS potentially can, which is why JS carries the STRICTER default blocking behavior.
WhenWhen would you specifically choose to animate using transform/opacity instead of properties like width/top/left?
+
Whenever building an animation where SMOOTHNESS (consistently hitting 60fps) matters — which is nearly always for animations users will actually perceive, like transitions, hover effects, or moving elements. `transform` and `opacity` changes skip BOTH the Layout and Paint stages entirely, going straight to Composite, which runs on the GPU and is dramatically cheaper than triggering a full Layout recalculation (which can cascade to affect other elements) followed by a Paint pass. Animating `width`, `top`, `left`, or similar geometry-affecting properties forces the browser through the full, expensive Layout → Paint → Composite pipeline on every single animation frame, which is far more likely to drop frames and appear janky, especially on less powerful devices.
HowHow would you diagnose and fix "layout thrashing" caused by interleaved DOM reads and writes in a loop?
+
Diagnose: use the browser's Performance tab in DevTools to record the interaction — repeated, small "Layout" (purple) blocks tightly interleaved with script execution in the timeline is the classic signature of layout thrashing.

Fix — batch all reads together, then all writes together:
// ✗ Before — interleaved reads/writes force a layout recalculation EVERY iteration boxes.forEach((box) => { const height = box.offsetHeight; // READ — forces layout to flush box.style.height = height * 2 + "px"; // WRITE — invalidates layout again }); // each iteration: read forces a flush of the PREVIOUS write — N layouts for N boxes! // ✓ After — all reads first, then all writes, in two separate passes const heights = boxes.map((box) => box.offsetHeight); // ALL reads — one layout flush total boxes.forEach((box, i) => { box.style.height = heights[i] * 2 + "px"; // ALL writes — batched, applied together });
Separating reads and writes into two distinct passes means the browser only needs to compute layout ONCE (to answer all the reads) instead of once per iteration, dramatically reducing the number of forced synchronous layout recalculations.
WhatWhat's the difference between display:none, visibility:hidden, and opacity:0?
+
`display:none` removes the element from the Render Tree ENTIRELY — it gets no layout box, occupies zero space, and is never painted; sibling elements behave as if it doesn't exist at all. `visibility:hidden` still gets a layout box and reserves its normal space in the page's layout, but is not painted/visible, and does not receive mouse/click interactions. `opacity:0` is fully laid out AND fully painted (just rendered fully transparent) — meaning it still occupies space AND remains interactive/clickable, which is a common source of confusing bugs (an "invisible" element still intercepting clicks).
WhyWhy is it generally recommended to place render-blocking script tags at the end of the body, or use async/defer?
+
A plain `<script>` tag in the `<head>` (or anywhere before the content it depends on) blocks HTML PARSING while it downloads and executes — meaning nothing after it in the document can be parsed, built into the DOM, or displayed until that script finishes. Placing scripts at the END of `<body>` means the browser has already parsed and can display the actual page CONTENT before it even reaches the blocking script, improving perceived load speed. The `defer` attribute achieves a similar (often better) effect while keeping the script in `<head>` — it downloads in parallel with parsing WITHOUT blocking it, then executes only after parsing completes, in document order. `async` also downloads in parallel, but executes as soon as it's ready, potentially interrupting parsing at an unpredictable point — appropriate for independent scripts (like analytics) that don't depend on or need to run in a specific order relative to the page's own content.
WhenWhen does a browser need to redo the ENTIRE rendering pipeline versus just a subset of it, after the initial page load?
+
The Network and full Parsing stages (fetching and parsing the ENTIRE HTML document from scratch) only happen once, for the initial navigation (or a full page reload/different-page navigation) — they are NOT re-run for every subsequent DOM/CSS change made by JavaScript. Instead, a JS-driven UI update triggers only the LATER stages needed for what actually changed: if an element's geometry-affecting property changed, Layout runs (followed by Paint and Composite); if only a visual property like color changed, Layout is skipped and just Paint + Composite run; if only `transform`/`opacity` changed, ONLY Composite runs. Understanding exactly which subset of stages a given change triggers is the core practical knowledge this topic provides for real-world performance optimization.
HowHow would you explain, step by step, what happens differently when you change an element's background-color vs. its width via JavaScript?
+
Changing background-color: the browser detects this only affects a PAINT-level visual property, not geometry — it skips Layout entirely, re-paints just the affected element's pixels with the new color, and then runs Composite to assemble the updated layer(s) into the final displayed frame.

Changing width: the browser must first run LAYOUT — recomputing this element's size, and potentially the position/size of sibling and parent elements affected by the change (since a resized element can push neighboring content around) — before it can even know what to Paint. Only after Layout completes does it Paint the now-correctly-sized element (and anything else affected), then Composite the result. This is strictly MORE expensive than the background-color case, since it involves an additional, potentially cascading computation step before painting can even begin.
