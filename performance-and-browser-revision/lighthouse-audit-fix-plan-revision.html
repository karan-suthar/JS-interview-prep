What Lighthouse Actually Audits

💡 Lighthouse is an automated auditing tool (built into Chrome DevTools, also available via CLI/CI) that loads a page in a controlled environment and scores it across FIVE categories, each producing a 0-100 score plus a list of specific, actionable findings.
Performance
Load speed, responsiveness, Core Web Vitals proxies
Accessibility
Screen readers, contrast, semantic HTML, ARIA usage
Best Practices
Security, modern API usage, console errors, image aspect ratios
SEO
Crawlability, meta tags, mobile-friendliness
PWA
(Legacy/optional) Installability, offline support
⚠ Lighthouse's Performance score is a LAB measurement — a simulated run under controlled (often throttled) conditions — NOT the same as real-world field data from actual users. It's excellent for catching regressions and diagnosing specific issues, but shouldn't be treated as a guarantee of real-world Core Web Vitals scores.
2

How to Run a Lighthouse Audit

Method 1Chrome DevTools (quickest, most common)
Open DevTools (F12) → "Lighthouse" tab → select categories and device type (Mobile/Desktop) → click "Analyze page load." Best for a quick, one-off check during development.
Method 2PageSpeed Insights (pagespeed.web.dev)
A hosted version of Lighthouse that ALSO shows real field data (CrUX) alongside the lab results — the best option when you want both lab AND field data for a publicly accessible URL, without any local setup.
Method 3Lighthouse CLI / CI integration
# Install and run from the command line npm install -g lighthouse lighthouse https://example.com --view # Useful for CI pipelines — fail a build if scores drop below a threshold lighthouse https://example.com --output=json --output-path=./report.json
Best for AUTOMATED, repeatable checks — running as part of a CI/CD pipeline to catch performance regressions before they reach production.

Reading the Report — What Each Section Means

Report sectionWhat it tells you
Category scores (0-100)A weighted composite score — NOT a simple average; some metrics (like LCP-related ones) are weighted more heavily than others
Metrics (top of Performance)The raw numbers: LCP, TBT (Total Blocking Time — a lab proxy for INP), CLS, Speed Index, FCP
"Opportunities"Specific suggestions estimated to IMPROVE load performance, each with an estimated time savings
"Diagnostics"Additional findings that don't have a precise time-savings estimate, but still indicate real issues
Passed auditsChecks the page already satisfies — useful to confirm nothing regressed, not just what's broken
✓ Always start diagnosis from the "Opportunities" section — it's specifically curated and sorted by ESTIMATED IMPACT, giving you a natural, defensible starting point for prioritization rather than guessing which of dozens of findings matters most.

Writing a Structured Fix Plan

💡 A good fix plan doesn't just list findings — it PRIORITIZES them using a clear framework, so a team knows what to tackle FIRST. The most common, defensible framework is Impact vs Effort: high-impact/low-effort fixes go first, low-impact/high-effort fixes go last (or get cut).
The Impact vs Effort prioritization matrix
Fix plan sectionWhat to include
SummaryCurrent scores, 1-2 sentence overall diagnosis of the biggest problem areas
Prioritized findingsEach issue, its ROOT CAUSE (not just symptom), estimated impact, and estimated effort
Recommended fix per issueA SPECIFIC, actionable change — not vague advice like "optimize images"
Priority tier (P0/P1/P2)Explicit tiering so stakeholders can see what's urgent vs nice-to-have
Success criteriaHow you'll verify the fix worked (e.g. "LCP drops below 2.5s in a re-run")

Common Gotchas & Interview Traps

  • ⚠️Lighthouse scores can vary meaningfully between runs, even on the same machine/page — network conditions, CPU throttling variance, and background processes all introduce noise; running MULTIPLE audits and looking at the median/consistent findings is more reliable than trusting a single run.
  • ⚠️Mobile and Desktop audits can produce very different scores for the SAME page — mobile audits apply CPU/network throttling to simulate a mid-tier mobile device, which often reveals performance problems invisible on a fast desktop connection; always check BOTH, since mobile is frequently the more revealing (and more representative) test.
  • ⚠️A high Lighthouse score doesn't guarantee good real-world Core Web Vitals — lab conditions are controlled and don't reflect the full diversity of real user devices/networks; always cross-check with field data (CrUX/PageSpeed Insights) when available, especially for a site with real traffic.
  • ⚠️Browser extensions can significantly skew local DevTools Lighthouse results — ad blockers, password managers, and other extensions injecting scripts into the page can add noise or artificially inflate/deflate scores; running in Incognito mode (with extensions disabled) gives a cleaner result.
  • ⚠️A "fix plan" that just lists findings without prioritization is a weak deliverable — a senior-level answer explicitly reasons about IMPACT and EFFORT for each item, not just transcribes what Lighthouse reported.
  • ⚠️The root cause is often NOT what the finding's title suggests at first glance — "Reduce unused JavaScript" might point to a THIRD-PARTY script, not your own application code; always dig into WHICH specific resource is responsible before proposing a fix.
  • ⚠️Some findings have trade-offs that Lighthouse doesn't account for — e.g. Lighthouse might flag a large third-party analytics script as "unused JS," but removing/deferring it could conflict with a genuine business requirement to track events as early as possible; a good fix plan acknowledges such trade-offs rather than blindly following every suggestion.
  • ⚠️Authenticated/logged-in pages require special handling to audit — a plain Lighthouse run can't access pages behind a login wall by default; this requires either testing a public equivalent page, using Lighthouse's authenticated-audit configuration options, or manually navigating to the authenticated state before triggering the audit via DevTools.
  • ⚠️Not every audit finding is worth fixing — some flagged issues may have a genuinely low real-world impact for the specific site's actual traffic/users; a thoughtful fix plan explicitly calls out and justifies DEPRIORITIZED items, not just the ones being acted on.
  • ⚠️Re-running the audit AFTER applying fixes is a required step, not optional — an interview answer that stops at "here's my fix plan" without mentioning verification/re-measurement is incomplete; always close the loop by confirming the fix actually achieved its intended effect.

Interview Q&A — Why / What / When / How

🎯 This is a hands-on, practical exercise question — interviewers are evaluating your PROCESS (how you investigate, prioritize, and communicate) as much as your knowledge of any single Lighthouse finding.
WhatWhat's the difference between Lighthouse's "Opportunities" and "Diagnostics" sections?
+
"Opportunities" are specific suggestions where Lighthouse can calculate an ESTIMATED time savings if you implement the fix (e.g. "Properly size images — potential savings of 2.1s") — these come with a concrete, quantified impact estimate. "Diagnostics" are additional findings and best-practice checks that indicate a real issue but WITHOUT a precise time-savings calculation (e.g. "Avoid an excessive DOM size," or "Minimize main-thread work") — still valuable signals, just less directly quantifiable in terms of exact performance impact.
WhyWhy should you run a Lighthouse audit in Incognito mode with extensions disabled, rather than your regular browser profile?
+
Browser extensions (ad blockers, password managers, various dev tools, VPN extensions) often inject their own scripts or modify network requests on every page you visit — this extra activity gets swept into the SAME performance measurement Lighthouse is taking, contaminating the results with noise that has nothing to do with the actual page being tested. Running in Incognito mode (where extensions are disabled by default, unless explicitly allowed) gives a cleaner, more representative measurement of the page's OWN performance characteristics, isolated from your personal browser configuration.
WhenWhen would you prioritize fixing an Accessibility finding over a Performance finding with a larger numeric score gap?
+
When the accessibility issue represents a genuine BARRIER preventing some users from using the site AT ALL — e.g. a missing form label making a checkout flow impossible to complete via screen reader, or insufficient color contrast making critical text illegible for users with low vision — versus a performance issue that "merely" makes the experience somewhat slower for everyone. Complete inability to use a feature is generally a more severe user-impact problem than a few extra seconds of load time, even if the numeric Lighthouse score gap suggests otherwise; score magnitude alone shouldn't be the only factor in prioritization — actual USER IMPACT and legal/compliance considerations (accessibility often has real legal requirements) matter too.
HowHow would you structure your investigation process when handed a Lighthouse report with a dozen findings and limited time?
+
1. Start with the category SCORES to get the big picture — which category is worst, and by how much?
2. Within the worst-scoring category, sort "Opportunities" by their ESTIMATED SAVINGS — this gives an objective, built-in starting point for what matters most.
3. For the top 2-3 opportunities, dig into the ROOT CAUSE — click through to see which SPECIFIC resource/element is responsible, rather than assuming from the finding's generic title.
4. Cross-reference against EFFORT — a fix requiring a one-line CSS change should generally be tackled before a fix requiring a multi-week infrastructure migration, even if the migration has a larger theoretical ceiling.
5. Write up the prioritized list (Impact vs Effort framework) as a fix plan, explicitly noting which lower-priority findings are being consciously DEFERRED and why, so nothing looks like an oversight.
WhatWhat should a well-structured fix plan actually contain, beyond just a list of Lighthouse's raw findings?
+
A strong fix plan includes: a brief SUMMARY of overall scores and the biggest problem areas; each issue's ROOT CAUSE (not just the symptom Lighthouse reported); a SPECIFIC, actionable recommended fix (not vague advice); an explicit PRIORITY tier (e.g. P0/P1/P2) reflecting impact-vs-effort reasoning; and SUCCESS CRITERIA for each fix — a concrete way to verify afterward that the change actually achieved its intended effect (like "LCP drops below 2.5s on re-audit"). Simply pasting Lighthouse's own finding titles into a list, without this additional structure and reasoning, doesn't demonstrate the prioritization and communication skills the exercise is actually testing for.
WhyWhy might you choose to explicitly deprioritize or reject a Lighthouse suggestion, even though it's technically a valid finding?
+
Lighthouse doesn't have context about BUSINESS requirements, real user behavior, or trade-offs specific to your situation — it flags issues purely based on generic best-practice heuristics. A finding might be technically valid but have low real-world impact for your ACTUAL traffic (e.g. an opportunity that only matters for users on very old devices, if your analytics show virtually none exist), or fixing it might conflict with a genuine business need (e.g. deferring an analytics script that stakeholders specifically need to fire as early as possible for accurate tracking). A thoughtful engineer weighs Lighthouse's generic suggestions against this real-world context, rather than treating every single finding as an unconditional mandate to fix.
WhenWhen would you use Lighthouse CI instead of manually running audits during development?
+
Once a team wants ONGOING protection against performance REGRESSIONS, rather than periodic manual spot-checks — integrating Lighthouse into a CI/CD pipeline means every pull request or deployment automatically gets audited, and the build can be configured to FAIL if scores drop below a defined threshold. This catches regressions immediately, at the point they're introduced (when it's cheapest and easiest to fix), rather than discovering degraded performance weeks later during an occasional manual audit, by which point the responsible change may be much harder to identify among many subsequent commits.
HowHow would you verify that a fix you implemented based on a Lighthouse finding actually worked, beyond just re-running the audit once?
+
1. Re-run the Lighthouse audit MULTIPLE times (not just once) after deploying the fix, since individual runs have natural variance — look for a CONSISTENT improvement across runs, not a single lucky result.
2. Check that the SPECIFIC finding that motivated the fix has actually resolved or improved as expected (e.g. the "Properly size images" opportunity should show near-zero estimated savings now, not just a vaguely higher overall score).
3. If the site has real traffic, monitor FIELD data (via PageSpeed Insights/CrUX, or your own Real User Monitoring) over the following days/weeks to confirm the improvement holds up under actual, diverse real-world conditions, not just the controlled lab environment.
4. Watch for any REGRESSIONS in other metrics the fix might have inadvertently caused (e.g. optimizing images aggressively for size might occasionally introduce visible quality degradation, or deferring a script might introduce a new interaction bug) — a fix that "improves" one number while quietly breaking something else isn't actually a net win.
