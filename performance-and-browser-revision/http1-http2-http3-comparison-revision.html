HTTP/1.1

HTTP/1.1
Standardized 1997 — still widely used, especially as a fallback
Text-based protocol. On a SINGLE TCP connection, only ONE request can be outstanding at a time — the browser must wait for a response before sending the next request on that same connection (unless using the rarely-adopted, problematic "pipelining" feature).
HTTP/1.1's head-of-line blocking — one connection, one request at a time
⚠ This is HEAD-OF-LINE (HOL) BLOCKING at the APPLICATION level — a slow/blocking request at the "head of the line" prevents everything behind it on the SAME connection from proceeding, even if those later requests are for small, fast resources that could otherwise complete quickly.
WorkaroundWhat it doesDownside
Multiple parallel TCP connections (6-8 per origin, browser-limited)Lets several requests proceed truly in parallelEach connection has its OWN TCP handshake/slow-start overhead; still limited, doesn't scale to many resources
Domain sharding (splitting assets across subdomains)Gets around the PER-ORIGIN connection limitMore DNS lookups/connections; largely an anti-pattern with HTTP/2+
File concatenation/bundling (combining many files into one)Reduces the NUMBER of requests neededA single large bundle can't be cached/updated incrementally; one changed line invalidates the whole bundle

HTTP/2

HTTP/2
Standardized 2015 — based on Google's earlier SPDY protocol
Binary protocol (not text) that introduces MULTIPLEXING — multiple requests and responses can be in flight SIMULTANEOUSLY over a SINGLE TCP connection, interleaved as small "frames," removing the need for multiple parallel connections.
HTTP/2 multiplexing — many streams, one connection
HTTP/2 featureWhat it solves
MultiplexingSolves HTTP/1.1's APPLICATION-level head-of-line blocking — many requests proceed concurrently on one connection
Binary framingMore efficient to parse than text; less error-prone, supports multiplexing's interleaving cleanly
Header compression (HPACK)Reduces the overhead of repetitive HTTP headers (cookies, user-agent, etc.) sent on every request
Server Push (largely deprecated/removed in practice)Originally let servers proactively send resources before the client asked; poor real-world adoption due to complexity/caching issues
Stream prioritizationLets the client hint which resources matter more, so the server can allocate bandwidth accordingly

HTTP/2's Remaining Problem — TCP-Level HOL Blocking

🚨 HTTP/2 solved head-of-line blocking at the APPLICATION layer, but a NEW, deeper problem remains at the TRANSPORT layer. TCP guarantees IN-ORDER byte delivery for the ENTIRE connection — if even ONE packet is lost, TCP must wait for it to be retransmitted before delivering ANY subsequent bytes to the application, EVEN THOUGH those later bytes might belong to a completely different, otherwise-ready HTTP/2 stream.
One lost packet blocks ALL streams, even unrelated ones — because TCP doesn't know about "streams"
💡 This is precisely the problem that motivated HTTP/3 — the head-of-line blocking issue HTTP/2 solved at the application layer simply MOVED DOWN a layer, to the transport protocol itself. Fixing it required a fundamentally different TRANSPORT protocol, not just another change to HTTP.
4

HTTP/3 & QUIC

HTTP/3
Standardized 2022 — runs on QUIC instead of TCP
HTTP/3 replaces TCP entirely with QUIC (Quick UDP Internet Connections) — a NEW transport protocol built on top of UDP, specifically designed so that packet loss on ONE stream doesn't block OTHER streams, solving the transport-level HOL blocking problem TCP couldn't fix.
QUIC featureWhat it does
Built on UDP, not TCPUDP has no built-in ordering/reliability guarantees — QUIC implements its OWN reliability layer, but crucially does so PER-STREAM instead of for the whole connection
Independent stream loss recoveryA lost packet only blocks the ONE stream it belongs to — other streams' data can be delivered to the application immediately, even while one stream awaits retransmission
Built-in TLS 1.3 encryptionEncryption isn't a separate layer bolted on top (like TCP+TLS) — it's integrated into QUIC itself, reducing handshake round-trips
Faster connection establishmentCombines the transport AND encryption handshake into fewer round-trips than the traditional TCP handshake + separate TLS handshake
Connection migrationA QUIC connection is identified by a Connection ID, not an IP/port tuple — letting a connection SURVIVE a network change (e.g. switching from WiFi to cellular) without a full reconnect
QUIC's independent streams — packet loss stays contained

Common Gotchas & Interview Traps

  • ⚠️"HTTP/2 eliminates head-of-line blocking" is an OVERSIMPLIFICATION and a common interview trap — HTTP/2 eliminates APPLICATION-level HOL blocking, but TRANSPORT-level (TCP) HOL blocking remains; precisely naming which LAYER you're referring to is what separates a strong answer from a vague one here.
  • ⚠️QUIC runs over UDP, but this does NOT mean it's unreliable like raw UDP — QUIC implements its OWN robust reliability and ordering guarantees on top of UDP; it just does so PER-STREAM rather than for the whole connection, which is the entire point.
  • ⚠️HTTP/2's Server Push feature is largely deprecated/removed in practice (Chrome removed support in 2022) — it's worth mentioning it EXISTED as an HTTP/2 feature if asked, but noting its poor real-world adoption/removal shows current, accurate knowledge.
  • ⚠️The classic "6-8 parallel connections per origin" browser behavior is an HTTP/1.1-era optimization that becomes COUNTERPRODUCTIVE with HTTP/2+ — HTTP/2's multiplexing means a SINGLE connection is now preferred; techniques like domain sharding (deliberately splitting assets across subdomains to get around the per-origin connection limit) are now considered anti-patterns.
  • ⚠️QUIC's per-stream reliability doesn't mean packet loss has ZERO cost — the AFFECTED stream still needs to wait for retransmission (just like before); the improvement is specifically that OTHER, unrelated streams are no longer collaterally blocked by that one stream's loss.
  • ⚠️HTTP/3 requires UDP to not be blocked by a network's firewall/router to work at all — some restrictive corporate/public networks block or heavily throttle UDP traffic, which is why HTTP/3 deployments typically fall back gracefully to HTTP/2 (over TCP) when UDP/QUIC isn't available or working.
  • ⚠️"QUIC" and "HTTP/3" are related but distinct terms — QUIC is the underlying TRANSPORT protocol; HTTP/3 is the specific APPLICATION-layer protocol that runs ON TOP of QUIC (similar to how HTTP/1.1 and HTTP/2 both historically ran on top of TCP). QUIC itself is somewhat general-purpose and isn't exclusively for HTTP.
  • ⚠️File concatenation/bundling as an HTTP/1.1-era optimization is now more nuanced with HTTP/2+ — since individual small requests are cheap to multiplex, some teams shift toward SMALLER, more granular files/chunks (better caching — one change doesn't invalidate everything) rather than one giant bundle, though this remains debated and workload-dependent.
  • ⚠️HTTP/2's binary framing doesn't change the actual HTTP semantics (methods, status codes, headers) — it's a change to the underlying WIRE FORMAT and connection behavior, not to the conceptual HTTP request/response model developers write code against.
  • ⚠️Implementing QUIC largely in USER SPACE (rather than the OS kernel, where TCP typically lives) was a deliberate design choice that allows faster protocol iteration/updates without needing OS-level kernel changes — a detail worth mentioning if asked about WHY QUIC chose UDP as its foundation rather than proposing changes to TCP itself.

Interview Q&A — Why / What / When / How

🎯 This is a networking fundamentals question that rewards PRECISION — distinguishing application-level from transport-level head-of-line blocking is exactly the kind of detail that separates surface-level familiarity from real understanding.
WhatWhat is head-of-line blocking, and how does it differ between HTTP/1.1, HTTP/2, and HTTP/3?
+
Head-of-line blocking is when one slow or stalled unit of work prevents OTHER, independent work behind it from proceeding, even though that other work could otherwise complete fine on its own. In HTTP/1.1, this happens at the APPLICATION level — a connection can only have one request in flight at a time, so a slow request blocks every later request queued on that SAME connection. HTTP/2 solves this application-level blocking via multiplexing (interleaved streams on one connection), but a NEW, deeper form remains at the TRANSPORT level — TCP's strict in-order byte delivery means one lost packet blocks ALL streams' data from being delivered, even unrelated ones, until that packet is retransmitted. HTTP/3 solves THIS transport-level blocking by replacing TCP with QUIC, which performs loss recovery independently PER STREAM, so one stream's packet loss no longer blocks other streams.
WhyWhy couldn't the transport-level head-of-line blocking problem be fixed by just improving TCP itself, instead of creating an entirely new protocol (QUIC)?
+
TCP's in-order, whole-connection byte-stream delivery guarantee is a FUNDAMENTAL, deeply baked-in part of its design — it has no native concept of independent "streams" within a single connection at all; from TCP's perspective, there's just ONE ordered sequence of bytes. Retrofitting genuine per-stream independence into TCP itself would require fundamentally changing this core guarantee, and TCP is implemented largely in OPERATING SYSTEM KERNELS across the entire internet — changes to it require slow, widespread OS-level updates and deployment across an enormous, decentralized ecosystem, making meaningful protocol evolution extremely slow in practice. Building QUIC as a NEW protocol on top of UDP (a much "thinner," more flexible transport with fewer built-in assumptions) — largely implemented in USER SPACE rather than the kernel — let its designers add genuine per-stream independence from scratch, AND iterate/deploy updates far more quickly than waiting on kernel-level TCP changes across the whole internet.
WhenWhen might an application still see a real-world benefit from HTTP/3 even if it already fully adopted HTTP/2?
+
Specifically in conditions involving PACKET LOSS or UNSTABLE network connections — mobile networks, high-latency connections, or networks with periodic congestion are exactly where TCP's transport-level head-of-line blocking (which HTTP/2 alone can't fix) causes real, noticeable delays, since ANY lost packet stalls the ENTIRE connection's data delivery regardless of which stream it belonged to. On a fast, stable, low-loss connection (e.g. a wired office network), the practical difference between HTTP/2 and HTTP/3 may be much less noticeable, since packet loss is rare to begin with. HTTP/3 also specifically helps users who switch networks mid-session (e.g. walking out of WiFi range onto cellular data) thanks to QUIC's connection migration — an HTTP/2 (TCP-based) connection would simply drop and need to fully reconnect in this scenario.
HowHow would you explain, step by step, why a single lost packet under HTTP/2 (over TCP) blocks unrelated streams, while the same packet loss under HTTP/3 (over QUIC) does not?
+
Under HTTP/2 (TCP): HTTP/2's multiplexed streams are all interleaved as frames within ONE underlying TCP byte stream. TCP guarantees delivering these bytes to the APPLICATION LAYER strictly IN ORDER — so if a packet containing bytes from position 1,000-1,500 is lost, TCP will NOT deliver anything AFTER byte 1,500 to the application, even if those later bytes (say, positions 2,000+) belong to a completely different HTTP/2 stream that has nothing to do with the lost data — TCP itself has no awareness of "streams," it just sees one linear sequence that must arrive in order.

Under HTTP/3 (QUIC): QUIC implements its reliability/ordering guarantees SEPARATELY, per individual stream, rather than for the connection as a whole. If a packet carrying Stream A's data is lost, QUIC only withholds delivery of Stream A's SUBSEQUENT data (waiting for retransmission) — but Stream B's packets, which arrived successfully and independently, are delivered to the application IMMEDIATELY, with zero need to wait on Stream A's unrelated retransmission. This is possible specifically because QUIC was designed FROM THE START with native awareness of multiple independent streams, unlike TCP, which predates the very concept of HTTP multiplexing by decades.
WhatWhat's the relationship between QUIC and HTTP/3 — are they the same thing?
+
No — they're related but distinct. QUIC is the TRANSPORT-layer protocol (built on top of UDP), providing connection establishment, encryption, reliability, and independent multi-stream support. HTTP/3 is the APPLICATION-layer protocol that runs ON TOP of QUIC, defining how HTTP requests/responses/headers are actually mapped onto QUIC's streams — conceptually analogous to how HTTP/1.1 and HTTP/2 both ran on top of TCP as their transport layer. QUIC itself is somewhat general-purpose infrastructure — while HTTP/3 is its most prominent use case, QUIC isn't exclusively an HTTP mechanism, in principle other application protocols could also be built on top of it.
WhyWhy do domain sharding and aggressive file concatenation (classic HTTP/1.1 optimizations) become less useful, or even counterproductive, once HTTP/2 is adopted?
+
Domain sharding existed specifically to work around HTTP/1.1's PER-ORIGIN connection limit (browsers cap parallel connections per domain, typically around 6) by artificially splitting assets across multiple subdomains, tricking the browser into opening MORE parallel connections than it otherwise would for a single origin. With HTTP/2's multiplexing, a SINGLE connection can already handle many concurrent requests efficiently — sharding now just adds UNNECESSARY extra DNS lookups and connection setup overhead for connections that no longer provide a meaningful parallelism benefit, making it a net negative. Similarly, aggressive file concatenation (bundling many small files into one large file) existed partly to reduce the NUMBER of costly HTTP/1.1 requests — but HTTP/2 makes individual requests cheap enough that this trade-off shifts: a single giant bundle means ANY small change invalidates the ENTIRE cached bundle, whereas smaller, more granular files under HTTP/2 can be cached and invalidated independently, often leading to BETTER overall caching behavior despite the higher request count.
WhenWhen would HTTP/3 actually fail to provide its benefits, or fail to work at all, despite being supported by both client and server?
+
When the NETWORK PATH between client and server blocks or heavily restricts UDP traffic — some corporate firewalls, public WiFi networks, or restrictive ISPs block or throttle UDP (sometimes because it's less commonly used for typical traffic and treated with more suspicion than TCP historically has been), which prevents QUIC (built on UDP) from establishing a connection at all. In this case, browsers are designed to gracefully FALL BACK to HTTP/2 (over TCP) automatically, so the site still works, just without HTTP/3's transport-level benefits for that particular network path. This is a genuinely real-world deployment consideration, not just a theoretical edge case — it's part of why HTTP/3 adoption, while strong and growing, isn't treated as a guaranteed universal replacement the way earlier HTTP version upgrades sometimes were.
HowHow would you determine, for a real website, whether upgrading from HTTP/2 to HTTP/3 would meaningfully improve its performance?
+
1. Profile the site's REAL USER traffic conditions — check analytics/RUM data for what fraction of users are on mobile/high-latency/lossy networks, since HTTP/3's transport-level HOL blocking fix specifically helps most under these conditions, less so on stable, low-loss connections.
2. Check whether the site's users frequently switch networks mid-session (e.g. a lot of mobile usage moving between WiFi and cellular) — HTTP/3's connection migration specifically benefits this pattern.
3. Use a tool like WebPageTest (which can simulate various network conditions including packet loss) to A/B compare load performance with HTTP/2 vs HTTP/3 under REALISTIC, imperfect network conditions — not just on a fast, stable connection where the difference may be minimal.
4. Verify the site's CDN/hosting provider actually supports HTTP/3 with QUIC properly configured, and confirm via browser DevTools' Network tab (which shows the protocol used per request) that HTTP/3 is genuinely being negotiated for real traffic, not silently falling back to HTTP/2.
5. Weigh the (typically low, since most CDNs/platforms support it out of the box) implementation/configuration effort against the expected benefit given the specific traffic profile identified in steps 1-2.
