Reflow vs Repaint — Quick Recap

💡 Reflow (Layout) recomputes the SIZE and POSITION of elements — expensive, and can CASCADE to affect other elements. Repaint (Paint) redraws pixel content WITHOUT recomputing geometry — cheaper, since it skips layout entirely. Some changes skip BOTH, going straight to Composite (the cheapest path of all).
The cost hierarchy — reflow is always more expensive than repaint-only

Forced Synchronous Layout ("Layout Thrashing")

🚨 Normally, the browser BATCHES layout recalculations and defers them until right before the next paint, for efficiency. But certain JavaScript property READS force the browser to immediately, SYNCHRONOUSLY compute layout RIGHT NOW, flushing any pending changes early — this is called a "forced synchronous layout," and doing it repeatedly in a loop is "layout thrashing."
// Properties/methods that FORCE a synchronous layout flush when READ: element.offsetWidth / offsetHeight / offsetTop / offsetLeft element.clientWidth / clientHeight / clientTop / clientLeft element.scrollWidth / scrollHeight / scrollTop / scrollLeft element.getBoundingClientRect() getComputedStyle(element) // for certain properties window.getSelection()

How to Avoid Forced Synchronous Layout

✗ Interleaved reads/writes in a loop
boxes.forEach((box) => { const h = box.offsetHeight; // READ box.style.height = h * 2 + "px"; // WRITE }); // N forced layouts for N boxes
✓ Batch all reads, then all writes
const heights = boxes.map((b) => b.offsetHeight); boxes.forEach((box, i) => { box.style.height = heights[i] * 2 + "px"; }); // 1 forced layout total
✗ Reading layout in a scroll/resize handler
window.addEventListener("scroll", () => { const rect = el.getBoundingClientRect(); updateSomething(rect.top); // fires on EVERY scroll pixel });
✓ Wrap in requestAnimationFrame
let ticking = false; window.addEventListener("scroll", () => { if (!ticking) { requestAnimationFrame(() => { const rect = el.getBoundingClientRect(); updateSomething(rect.top); ticking = false; }); ticking = true; } });
TechniqueHow it helps
Batch reads, then batch writes ("FastDOM" pattern)Ensures the browser only needs to compute layout ONCE, to satisfy all reads together, instead of once per interleaved read
Use requestAnimationFrame for layout-reading logicAligns DOM reads with the browser's natural render cycle, avoiding redundant mid-frame layout flushes from high-frequency events (scroll, resize)
Cache read values instead of re-reading repeatedlyIf a value (like a container's width) won't change between uses, read it ONCE and reuse the cached value rather than re-querying it
Use CSS transform/opacity for animationsAvoids the reflow/repaint cost entirely for animated properties — composite-only, no synchronous layout risk
Use `will-change` sparingly for elements about to animateHints the browser to promote the element to its own compositor layer in advance, though overuse can waste memory
Debounce/throttle handlers that read layoutReduces how OFTEN layout-reading code runs at all, on high-frequency events

Common Gotchas & Interview Traps

  • ⚠️border-color is repaint-only, but border-WIDTH triggers reflow — a classic, easy-to-miss distinction; changing the border's THICKNESS changes the element's effective box size, while changing its COLOR does not.
  • ⚠️visibility:hidden is repaint-only, but display:none triggers reflow — `visibility` keeps the element's layout space reserved (so no geometry recalculation needed elsewhere), while `display:none` removes it from the render tree entirely, which DOES require the surrounding layout to be recomputed.
  • ⚠️filter isn't a clean composite-only property like transform/opacity — it's OFTEN GPU-accelerated in modern browsers, but this isn't a universal guarantee the way transform/opacity's behavior is; don't lump it in as equivalent.
  • ⚠️Reflow doesn't just cost the ONE changed element — it can cascade to parents, siblings, and children — this is why reflow-triggering property changes are considered dramatically more expensive than repaint-only ones, beyond just "one more stage in the pipeline."
  • ⚠️getComputedStyle() doesn't ALWAYS force a synchronous layout — it depends on WHICH specific property is being queried; querying a property affected by pending layout changes forces a flush, while others may not; it's safest to treat it as a potential trigger rather than assuming it's always safe or always forces a flush.
  • ⚠️The "read/write batching" pattern needs to span the WHOLE operation, not just one loop — if code elsewhere (a different function, a different event handler) also interleaves reads/writes on the same frame, the batching benefit can be undermined; this is why dedicated libraries like FastDOM exist, to centralize and coordinate this batching across an entire application.
  • ⚠️Chrome DevTools' Performance panel shows "Forced reflow" warnings directly — specifically flagging JavaScript calls that triggered a synchronous layout recalculation, making this a very practical, verifiable thing to check for and demonstrate awareness of.
  • ⚠️will-change should be removed/reset after the relevant animation completes — leaving it applied indefinitely on many elements can waste GPU memory by keeping unnecessary compositor layers alive longer than needed; it's a targeted, temporary hint, not a permanent "make this fast" switch.
  • ⚠️Not all reflow-triggering changes are equally expensive — a reflow on a deeply nested, complex subtree with many siblings/children is far more costly than a reflow on a simple, isolated element; "triggers reflow" is a binary category, but the ACTUAL cost varies enormously by context.
  • ⚠️React/Vue/other frameworks' virtual DOM diffing doesn't automatically prevent layout thrashing — if application code explicitly reads a layout property (like `ref.current.offsetHeight`) inside a render or effect that also writes styles, the SAME thrashing risk applies regardless of the framework; virtual DOM batches RE-RENDERS, not necessarily raw DOM read/write ordering at the browser level.

Interview Q&A — Why / What / When / How

🎯 This is concrete, actionable performance knowledge — interviewers value precise property-level examples over vague statements like "some things are more expensive than others."
WhatWhat determines whether a CSS property change triggers reflow versus just repaint?
+
The determining factor is whether the property can change an element's GEOMETRY — its size or position — either directly, or indirectly by affecting how much space it needs (like text metrics changing from a font-size update). If a property affects geometry, the browser must re-run LAYOUT to recompute affected elements' boxes before it can paint anything correctly — this is reflow. If a property only changes VISUAL appearance (color, shadows, background) without altering size or position at all, the browser can skip layout entirely and go straight to repainting the affected pixels — cheaper, since one whole stage of the pipeline is skipped.
WhyWhy does reading element.offsetHeight force a synchronous layout, when the browser would normally prefer to batch and defer layout calculations?
+
`offsetHeight` needs to return the element's CURRENT, ACCURATE rendered height — but if there are PENDING style changes the browser hasn't yet processed through layout (because it was deferring/batching them for efficiency, as it normally does), the browser has no way to know the correct up-to-date height WITHOUT actually running that pending layout computation right now. Returning a STALE or incorrect value would be a worse outcome than the performance cost of computing it immediately — so the browser is forced to synchronously "flush" any pending layout work at that exact moment, guaranteeing the returned value is accurate, at the cost of losing its normal batching/deferral optimization for that particular computation.
WhenWhen would animating with box-shadow or filter still be acceptable, despite not being purely composite-only like transform/opacity?
+
When the animated element and the affected screen area are SMALL, and/or the animation is brief/infrequent rather than a continuous, large-scale effect — a repaint (or filter's GPU-accelerated-but-not-guaranteed-composite behavior) on a small, isolated element is far less noticeable than the same property change applied to a large, complex, frequently-updating element. It's also acceptable on lower-stakes interactions (a subtle hover effect on a button) where occasional minor jank wouldn't meaningfully harm the user experience, versus a continuous, large-scale, performance-critical animation (like a full-page transition) where sticking strictly to transform/opacity matters much more. As with most performance guidance, the right choice depends on MEASURING actual impact for the specific case, not blanket-avoiding every non-composite-only property universally.
HowHow would you refactor a function that resizes 100 elements to match their tallest sibling, to avoid layout thrashing?
+
// ✗ Before — interleaved: reads EACH height, then writes, over and over function equalizeHeights(elements) { let maxHeight = 0; elements.forEach((el) => { maxHeight = Math.max(maxHeight, el.offsetHeight); // READ, forces flush el.style.height = "auto"; // WRITE — invalidates layout for NEXT read }); elements.forEach((el) => { el.style.height = maxHeight + "px"; }); } // ✓ After — all reads happen FIRST, in one pass, then all writes function equalizeHeights(elements) { // READ phase — one pass, ONE layout flush total for all of them const heights = elements.map((el) => el.offsetHeight); const maxHeight = Math.max(...heights); // WRITE phase — separate pass, no reads interleaved, no forced flushes elements.forEach((el) => { el.style.height = maxHeight + "px"; }); }
The key change is separating the function into two distinct PHASES — first, read every element's `offsetHeight` in one uninterrupted pass (the browser only needs to compute layout ONCE to satisfy all these reads together, since nothing was WRITTEN in between them), and only THEN write the new height to every element in a second pass. This reduces the forced synchronous layout count from potentially ONE PER ELEMENT (100 forced layouts) down to effectively one, since no write happens between any of the reads.
WhatWhat's the difference in cost between changing display:none and visibility:hidden, even though both "hide" an element?
+
`display:none` REMOVES the element from the render tree entirely — it occupies zero space, meaning surrounding elements need their layout RECOMPUTED to account for the now-missing space (a reflow, which can cascade to siblings/parents). `visibility:hidden` keeps the element's layout box FULLY INTACT and reserved — it simply isn't painted/visible — so no surrounding element's geometry is affected at all, meaning only a repaint (of that element becoming invisible) is needed, with no reflow required. For toggling visibility frequently (like a tooltip that shows/hides often), `visibility:hidden` (or `opacity`, for an even cheaper composite-only option, if reserving layout space is acceptable) is generally the more performant choice specifically because it avoids the reflow cost `display:none` incurs on every toggle.
WhyWhy is a reflow triggered by a change to a deeply nested element potentially MORE expensive than a reflow triggered by a change to a top-level, isolated element?
+
Layout computation can CASCADE outward from the changed element — if a deeply nested element's size change affects its PARENT's size (e.g. the parent auto-sizes to fit its content), that parent's size change can then affect ITS OWN parent, and so on up the tree, and can also shift the positions of SIBLING elements at each level along the way in normal document flow. An isolated, top-level element with no dependent parents/siblings relying on its size has a much more CONTAINED reflow — the recalculation doesn't need to propagate nearly as far through the tree. The WORST-case reflow scenario is a change deep in a complex, deeply-nested tree with many size-dependent ancestors and siblings, which can force the browser to recompute layout for a much LARGER portion of the page than the single element that was actually modified.
WhenWhen would using requestAnimationFrame NOT be sufficient to prevent layout thrashing on its own?
+
`requestAnimationFrame` helps by aligning WHEN your code runs with the browser's natural rendering cycle (avoiding redundant work firing many times per frame, like on every scroll pixel) — but it does NOT, by itself, guarantee your reads and writes stay properly SEPARATED/batched. If code INSIDE a single `requestAnimationFrame` callback still interleaves reads and writes (reading a layout property, then writing a style, then reading again, all within that one callback), the SAME forced-synchronous-layout thrashing can still occur within that single frame — `requestAnimationFrame` alone controls timing/frequency, not the read/write ORDERING discipline that the FastDOM-style batching pattern specifically addresses. Both techniques are complementary and often used together, not substitutes for one another.
HowHow would you use Chrome DevTools to actually verify whether a specific piece of code is causing forced synchronous layouts in a real application?
+
1. Open the Performance panel and record while triggering the interaction/code path suspected of causing the issue (e.g. scrolling, or clicking a button that runs the suspect function).
2. Look through the recorded timeline for "Layout" entries — Chrome specifically labels ones caused by a forced synchronous read with a warning icon and the text "Forced reflow" (or similar, sometimes phrased "Forced synchronous layout"), often directly linking to the exact line of JavaScript responsible.
3. Check HOW MANY times this occurs during the recording — a single forced layout is often negligible, but seeing it fire dozens or hundreds of times (e.g. once per item in a loop) confirms genuine layout thrashing, not just an isolated, harmless instance.
4. Click through to the flagged call stack to identify the EXACT property read (`offsetHeight`, `getBoundingClientRect()`, etc.) and the surrounding code, then apply the read/write batching refactor shown in Section 5.
5. Re-record after the fix and confirm the forced-reflow warnings are gone (or significantly reduced), and that the total time spent in "Layout" for that interaction has measurably decreased.
