The Four Strategies — Core Question

💡 Every rendering strategy answers the SAME two questions differently: WHERE does HTML get generated (browser vs server vs build pipeline), and WHEN does it get generated (on every request, once at build time, or periodically). All four trade-offs — freshness, speed, server load, and infrastructure complexity — flow directly from these two answers.
Where and when each strategy generates HTML
2

CSR — Client-Side Rendering

CSR
Client-Side Rendering
The server sends a nearly-empty HTML shell plus a JavaScript bundle. The BROWSER downloads, parses, and executes that JS, which then fetches data and renders the actual content — entirely client-side, after the fact. Classic single-page-app (SPA) architecture.
// What the server actually sends for a CSR app <html> <body> <div id="root"></div> {/* EMPTY — nothing to see yet */} <script src="bundle.js"></script> {/* this does ALL the work */} </body> </html> // A user (or a search engine crawler without JS execution) sees NOTHING // meaningful until bundle.js downloads, parses, executes, and fetches data
AspectAssessment
Initial load speed✗ Slowest — blank page until JS downloads/executes/fetches
SEO✗ Weak by default (improving, but crawlers may not execute JS reliably)
Server load✓ Lowest — server just serves static files, no per-request rendering work
Interactivity after load✓ Excellent — full client-side app, no further server round-trips for navigation
Best forApps behind a login where SEO doesn't matter (dashboards, internal tools, admin panels)
3

SSR — Server-Side Rendering

SSR
Server-Side Rendering
For EVERY incoming request, the server runs the app's rendering logic FRESH, fetches whatever data is needed, and sends back complete, ready-to-display HTML. The browser then "hydrates" this HTML to make it interactive.
// Simplified SSR flow (e.g. Next.js App Router, a Server Component) async function ProductPage({ params }) { const product = await db.products.findById(params.id); // fresh, on EVERY request return <div>{product.name} — ${product.price}</div>; } // If the price changes in the database, the VERY NEXT request sees the new price — // no rebuild, no redeploy, no caching delay
AspectAssessment
Freshness✓ Always up to date — regenerated on every single request
SEO✓ Excellent — crawlers receive complete, ready-made HTML
Server load✗ Highest — every request re-runs full rendering logic and data fetching
Time to First ByteModerate — depends on how fast the server-side data fetch/render actually is
Best forPersonalized, frequently-changing, or per-user content needing SEO — e-commerce product pages, news, social feeds
4

SSG — Static Site Generation

SSG
Static Site Generation
EVERY page's HTML is generated ONCE, at BUILD TIME — before any user ever requests it. The resulting static HTML files are then served directly (often from a CDN), identically, to every visitor.
// Simplified SSG flow (e.g. Next.js generateStaticParams, or Astro/Gatsby/Hugo) export async function generateStaticParams() { const posts = await cms.getAllPosts(); return posts.map((post) => ({ slug: post.slug })); // pre-builds EVERY blog post page } async function BlogPost({ params }) { const post = await cms.getPost(params.slug); // runs ONCE, at BUILD time only return <article>{post.title}</article>; } // If the CMS content changes, this page STAYS THE SAME until the NEXT build/deploy
AspectAssessment
Speed / TTFB✓ Fastest possible — pre-built static files, often served straight from a CDN
SEO✓ Excellent — complete HTML, no server compute needed per request
Server load✓ Minimal — essentially just serving static files
Freshness✗ Stale until the NEXT build/deploy — a real limitation for frequently-changing content
Best forContent that's the same for everyone and changes infrequently — marketing pages, documentation, blogs
5

ISR — Incremental Static Regeneration

ISR
Incremental Static Regeneration
A hybrid: pages are generated statically (like SSG), but the server can REGENERATE individual pages in the background, either after a set time interval or on-demand — WITHOUT requiring a full site rebuild/redeploy.
The "stale-while-revalidate" flow ISR uses
// Simplified ISR flow (e.g. Next.js revalidate option) async function ProductPage({ params }) { const product = await fetch(`/api/products/${params.id}`, { next: { revalidate: 60 } // regenerate this page at MOST once every 60 seconds }); return <div>{product.name} — ${product.price}</div>; } // Fast like SSG (serves cached HTML instantly), but self-updates periodically // like SSR, WITHOUT needing a full site rebuild for every content change
AspectAssessment
Speed / TTFB✓ Fast — serves cached static HTML, just like SSG
FreshnessEventually consistent — updates periodically or on-demand, without a full rebuild
Server load✓ Low — regeneration only happens occasionally, not per-request
ComplexityHigher — requires a framework/infra that supports this hybrid model well
Best forContent that's mostly static but updates periodically at scale — e-commerce catalogs, news archives with thousands of pages

Scenario Walkthrough — Picking for a Real App

The Scenario
You're building a mid-sized e-commerce site: (1) a marketing homepage and "About" page, (2) thousands of product pages where price/stock can change several times a day, (3) a personalized "My Account" dashboard behind login, and (4) a search results page with live filtering.
✓ Different strategies for different parts of the SAME app
Marketing homepage / About page → SSG. This content is identical for every visitor and changes rarely (maybe with a deploy) — maximum speed and minimum server cost, with zero freshness concerns.

Product pages → ISR. Thousands of pages rule out plain SSR (unnecessary server cost re-rendering the SAME product for every single visitor) and rule out plain SSG (a full rebuild every time ANY price changes, across possibly thousands of pages, would be painfully slow and disruptive). ISR gives fast, cached responses that self-update periodically (e.g. revalidate every 60 seconds) or on-demand when a price actually changes, without needing a full site rebuild.

My Account dashboard → CSR. This is behind a login (SEO is irrelevant here), highly personalized and interactive, and doesn't need to be indexed by search engines at all — the classic profile for CSR, avoiding unnecessary server rendering cost for content only the logged-in user will ever see.

Search results with live filtering → CSR (or SSR for the FIRST load, then CSR for subsequent filtering). The initial search page benefits from SSR/SSG for SEO (so search engines can index popular search terms), but once the user starts interactively filtering results, those subsequent updates happen CLIENT-SIDE for instant responsiveness, without a full page reload/server round-trip per filter change.
🎯 The key insight this scenario demonstrates: real applications RARELY use just ONE rendering strategy for the entire app — modern frameworks (Next.js, Nuxt, SvelteKit) explicitly support mixing strategies PER ROUTE/PAGE, and a strong answer recognizes that the "right" choice is a PER-PAGE decision, not a single global architectural commitment.
!

Common Gotchas & Interview Traps

  • ⚠️"SEO requires SSR" is an oversimplification — SSG and ISR are EQUALLY good (often better) for SEO, since they also deliver complete, ready-made HTML; SSR isn't uniquely required for SEO, just one of several ways to avoid CSR's SEO weaknesses.
  • ⚠️Modern search engine crawlers CAN execute JavaScript to some degree — Google's crawler, for instance, does render JS-heavy pages, somewhat softening CSR's historical SEO disadvantage; however, this rendering is not guaranteed to be as fast/thorough/reliable as receiving pre-rendered HTML directly, so CSR remains the WEAKEST default option for SEO-sensitive content, not a hopeless one.
  • ⚠️Choosing a rendering strategy is a PER-ROUTE decision in modern frameworks, not a single app-wide choice — presenting these four options as mutually exclusive, app-wide architectural commitments is a common but overly rigid framing.
  • ⚠️SSG's biggest practical limitation is BUILD TIME at scale — a site with tens of thousands of pages can face genuinely long build times if every single page must be regenerated on every deploy, which is precisely the problem ISR was invented to solve.
  • ⚠️ISR's "staleness window" is a real, sometimes overlooked trade-off — between the moment underlying data changes and the next regeneration, SOME users will see outdated content; this needs to be an ACCEPTABLE trade-off for the specific content (fine for a blog's view count, potentially not fine for real-time stock availability without on-demand revalidation).
  • ⚠️SSR doesn't automatically mean "fast" — if the server-side data fetching/rendering logic itself is slow (a slow database query, an unoptimized render), SSR's Time To First Byte can be WORSE than a well-optimized SSG/ISR page, despite SSR sounding like the more "dynamic, modern" choice.
  • ⚠️Hydration (the process of making server-rendered HTML interactive on the client) applies to BOTH SSR and SSG/ISR — it's not an SSR-exclusive concept; any strategy that sends pre-rendered HTML needs a hydration step before client-side interactivity (event handlers, state) becomes active.
  • ⚠️CSR isn't "obsolete" or universally worse — for genuinely interactive, behind-login applications where SEO is irrelevant, CSR remains a perfectly reasonable, often SIMPLER choice; the narrative that "SSR/SSG is always better" ignores CSR's real, legitimate use cases.
  • ⚠️On-demand ISR revalidation (triggering a specific page's regeneration immediately, e.g. via a webhook when content is updated in a CMS) is different from TIME-based revalidation — conflating these two ISR modes is a common imprecision; time-based accepts periodic staleness, on-demand allows near-immediate freshness for specific, known content changes.
  • ⚠️Not every framework supports all four strategies equally well — the specific tooling/framework choice (Next.js, Nuxt, SvelteKit, Astro, Remix, plain React+Vite) significantly affects which strategies are easy vs. difficult to implement; a real-world answer should acknowledge that framework capabilities are part of the practical decision, not purely abstract trade-offs.

Interview Q&A — Why / What / When / How

🎯 This is a classic architecture/system-design-style question — the strongest answers reason from CONCRETE content characteristics (freshness needs, personalization, scale, SEO importance) to a strategy, rather than reciting definitions.
WhatWhat is the fundamental difference between these four rendering strategies?
+
They differ in WHERE and WHEN HTML is generated. CSR generates HTML in the BROWSER, after JavaScript downloads and runs. SSR generates HTML on the SERVER, freshly, for EVERY single request. SSG generates HTML ONCE, at BUILD TIME, before any request ever arrives, and serves the same static files to everyone. ISR is a hybrid: HTML is generated at build time like SSG, but the server can REGENERATE individual pages later — periodically or on-demand — without needing a full site rebuild.
WhyWhy might a page with excellent SSR performance still be a worse choice than SSG for certain content?
+
SSR re-runs the FULL rendering and data-fetching logic on the server for EVERY single request, even when the underlying content hasn't changed at all between requests — this is genuinely wasted server compute and cost for content that's IDENTICAL across visitors and rarely changes (like a marketing page or documentation). SSG does this expensive work exactly ONCE, at build time, and then serves the identical, pre-computed result to every subsequent visitor essentially for free (often straight from a CDN) — for content matching this profile, SSG achieves the SAME (or better) end-user speed with dramatically lower ongoing server cost, making SSR's per-request re-computation an unnecessary expense rather than a meaningful benefit.
WhenWhen would ISR specifically be a better choice than plain SSG, even for content that's mostly static?
+
When the site has a LARGE number of pages (making a full rebuild for every content change slow/impractical) AND that content changes periodically, even if infrequently — e.g. thousands of e-commerce product pages where prices update daily, or a large content archive where individual articles occasionally get edited. Plain SSG would require rebuilding the ENTIRE site (or at least regenerating every affected page) on every single content change, which becomes increasingly slow and disruptive as the page count grows. ISR solves this by allowing INDIVIDUAL pages to regenerate independently, in the background, without touching the rest of the site — giving you SSG's speed and low server cost with a practical path to keeping large amounts of content reasonably fresh.
HowHow would you decide which rendering strategy to use for a NEW page/route you're adding to an existing app?
+
1. Does this page need to be indexed by search engines? If NOT (e.g. behind a login), CSR becomes a strong, simple option.
2. If SEO matters, is the content the SAME for every visitor, or personalized per-user? Personalized/per-user content generally needs SSR (or CSR with SSR for a shell).
3. If the content is the SAME for everyone, how OFTEN does it change? Rarely (deploy-time-only changes) → SSG. Periodically, but not on every single request → ISR. Needs to be correct on literally every request (e.g. real-time stock levels critical to display accurately) → SSR.
4. Consider SCALE — if choosing SSG/ISR, how many pages of this type exist, and does that make a full-rebuild-per-change approach (plain SSG) impractical, pushing toward ISR instead?
This is a decision made PER ROUTE, informed by that specific route's actual freshness, personalization, and SEO requirements — not a single global choice for the whole application.
WhatWhat does "hydration" mean, and which of these strategies require it?
+
Hydration is the process of the browser taking SERVER-GENERATED (or pre-built) static HTML that's already visible on screen, and "attaching" the client-side JavaScript framework's event handlers, state, and interactivity to that existing markup — rather than re-rendering everything from scratch. SSR, SSG, and ISR all require hydration, since all three send pre-rendered HTML to the browser that then needs to become interactive. CSR does NOT need hydration in the same sense, since it never received pre-rendered HTML in the first place — it builds the entire DOM from scratch, client-side, from an empty starting shell.
WhyWhy is "CSR is bad for SEO" not an absolute, unconditional rule anymore?
+
Modern search engine crawlers, notably Google's, DO execute JavaScript to some extent as part of their indexing process, rendering the page somewhat similarly to a real browser before extracting its content — this is a meaningful improvement over the historical assumption that crawlers only ever see raw, unexecuted HTML. However, this JS-rendering step in the crawling process can be slower, more resource-intensive, and less immediately reliable than a crawler simply reading pre-rendered HTML directly (as SSR/SSG/ISR provide) — and not all crawlers (including some non-Google search engines, or social media link-preview bots) execute JS as thoroughly. So CSR's SEO situation has genuinely improved, but pre-rendered strategies remain the SAFER, more reliably indexable default for SEO-critical content.
WhenWhen would you choose SSR over ISR for content that changes frequently, rather than just using a very short ISR revalidation window?
+
When the content needs to be CORRECT on literally every single request, with zero tolerance for even brief staleness — e.g. displaying a live, exact stock count during a high-demand flash sale, or a real-time auction price, where showing even slightly outdated data could cause a genuinely bad outcome (overselling limited stock, a user bidding based on stale price info). ISR's revalidation window, no matter how short, always has SOME period where a stale cached version could be served to a user before the background regeneration completes — for content where this window's risk is unacceptable, SSR's guarantee of fresh data on EVERY request (at the cost of higher server load) is the more appropriate, safer choice.
HowHow would you explain, using the e-commerce scenario from this guide, why using ONLY SSR for the entire site would be a mistake?
+
Using SSR for EVERYTHING means the marketing homepage — content that's IDENTICAL for every single visitor and barely ever changes — would be fully re-rendered on the server for every single request, burning server compute and adding latency for zero actual benefit, since the exact same HTML could instead be pre-built once (SSG) and served instantly from a CDN. Similarly, the logged-in "My Account" dashboard doesn't need SEO at all (it's behind a login, invisible to search engines regardless), so paying the server-rendering cost for it is unnecessary when CSR would serve the exact same user experience more cheaply. Using SSR universally treats every page as if it has the SAME freshness/personalization/SEO requirements, when in reality different pages within the SAME app have meaningfully different needs — which is exactly why mixing strategies per route, rather than picking one strategy globally, is the practically correct approach for a real, multi-page application.
