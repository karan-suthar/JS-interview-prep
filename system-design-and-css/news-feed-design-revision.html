The Full Requirements

💡 A news feed is one of the richest frontend system-design questions precisely because its FOUR pillars pull in different directions: infinite scroll needs careful DATA FETCHING; optimistic likes need careful STATE/ROLLBACK handling; real-time updates need to MERGE cleanly with a paginated list; and offline support needs a coherent strategy for ALL of the above when there's no network at all.
📜
Infinite Scroll
Load more posts as the user nears the bottom, without jank or duplicate fetches
❤️
Optimistic Likes
Instant visual feedback on like/unlike, with correct rollback on failure
🔌
Real-Time Updates
New posts/likes from OTHER users arrive live via WebSocket, merged cleanly
📴
Offline Support
The feed remains usable (read-only, and ideally queued actions) with no connection

Infinite Scroll

// IntersectionObserver watching a "sentinel" element at the bottom of the list const sentinelRef = useRef(null); useEffect(() => { const observer = new IntersectionObserver( ([entry]) => { if (entry.isIntersecting && !isLoading && hasMore) { loadNextPage(); } }, { rootMargin: "400px" } // start loading BEFORE the sentinel is actually visible ); if (sentinelRef.current) observer.observe(sentinelRef.current); return () => observer.disconnect(); }, [isLoading, hasMore]); // Cursor-based pagination request — NOT page numbers GET /api/feed?cursor=eyJpZCI6ICI0NTYifQ&limit=20
Design decisionReasoning
IntersectionObserver over scroll event listenersFar more performant — doesn't fire on every scroll pixel, and doesn't require manual scroll-position math or throttling
rootMargin to trigger loading EARLYStarts fetching the next page BEFORE the user actually reaches the bottom, so new content is ready by the time they scroll there — avoiding a visible loading pause
Cursor-based pagination (not page numbers)A feed's underlying data changes CONSTANTLY (new posts arrive) — page NUMBERS shift under you as new items are added; a cursor (pointing to a specific item) remains stable regardless of what's added ABOVE it
isLoading / hasMore guardsPrevents duplicate fetches if the sentinel triggers multiple times, and stops fetching once the feed is exhausted
Virtualization (from the earlier windowing topic)For a VERY long, continuously-growing feed, combining infinite scroll with list virtualization prevents unbounded DOM growth as more and more pages load
🚨 Page-number-based pagination breaks on a live feed — if new posts are added to the TOP of the feed between page loads, "page 2" now refers to DIFFERENT items than it did a moment ago, causing skipped or duplicated posts. Cursor-based pagination (pointing to "everything after post X") is immune to this since it's anchored to a specific item, not a shifting numeric offset.

Optimistic Likes

The optimistic update flow — success vs. failure/rollback
async function toggleLike(postId, currentlyLiked) { // 1. Snapshot the PREVIOUS state, in case we need to roll back const previousState = getPost(postId); // 2. Apply the optimistic update IMMEDIATELY, synchronously updatePost(postId, { liked: !currentlyLiked, likeCount: previousState.likeCount + (currentlyLiked ? -1 : 1), }); // 3. Fire the actual request in the background try { await api.toggleLike(postId, !currentlyLiked); // success — the optimistic state WAS correct, nothing more to do } catch (err) { // 4. FAILURE — roll back to the exact previous snapshot updatePost(postId, previousState); showErrorToast("Couldn't like this post — try again"); } }
⚠ Rapid double-clicking (like → unlike → like, quickly) needs careful handling — a naive implementation can send OUT-OF-ORDER requests to the server, or roll back an update that's since been superseded by a newer click. Debouncing rapid toggles, or tracking a per-post "latest intended state" and only syncing that final state, are common mitigations.

Real-Time Updates via WebSocket

const ws = new WebSocket("wss://api.example.com/feed-updates"); ws.onmessage = (event) => { const update = JSON.parse(event.data); switch (update.type) { case "NEW_POST": // Don't just inject it at the top — see the "New posts" banner pattern below queuePendingPost(update.post); break; case "LIKE_UPDATE": // Merge into EXISTING post data — but respect any local optimistic state in flight mergeLikeCount(update.postId, update.likeCount); break; } }; // Reconnection with exponential backoff — WebSockets DO drop unexpectedly let reconnectDelay = 1000; ws.onclose = () => { setTimeout(() => { reconnectDelay = Math.min(reconnectDelay * 2, 30000); // cap the backoff connectWebSocket(); }, reconnectDelay); };
💡 Don't auto-inject new live posts directly at the top of a feed the user is actively scrolling through — it's disorienting and can cause an unwanted layout shift right under their cursor/reading position. The standard pattern is a "New posts available ↑" BANNER, letting the user choose WHEN to actually pull in the new content.
Design decisionReasoning
"New posts" banner instead of auto-injectingPreserves the user's current scroll position and reading context — respects their control over the experience
Reconnection with exponential backoffWebSocket connections drop for many reasons (network blips, server restarts); backoff avoids hammering the server with reconnect attempts while still recovering automatically
Merging live updates without clobbering local optimistic stateIf a LIKE_UPDATE arrives for a post the user JUST optimistically liked locally, naively overwriting with the server's count could cause a visible flicker/inconsistency — needs careful reconciliation logic
Fallback to polling if WebSocket is unavailableSome networks/proxies block WebSocket connections entirely — a graceful degradation path (periodic polling) keeps the feature at least partially functional

Offline Support

// 1. Cache already-loaded feed data locally (IndexedDB, via a library or raw API) async function cacheFeedPage(posts) { const db = await openFeedDB(); await db.put("posts", posts); } // 2. When offline, serve from the local cache instead of failing outright async function loadFeed() { if (!navigator.onLine) { return await getCachedPosts(); } return await fetch("/api/feed").then((r) => r.json()); } // 3. Queue actions (like, comment) performed WHILE offline, sync when back online async function toggleLike(postId, liked) { applyOptimisticUpdate(postId, liked); // UI updates regardless of connectivity if (!navigator.onLine) { await queueOfflineAction({ type: "LIKE", postId, liked }); return; // will sync automatically once connectivity returns } await api.toggleLike(postId, liked); } window.addEventListener("online", syncQueuedActions); // flush the queue on reconnect
LayerPurpose
Service Worker + Cache APICaches STATIC assets (JS/CSS/images) so the app shell loads even with no connection
IndexedDBPersists actual FEED DATA (posts, already-fetched pages) for offline viewing — localStorage is too small/synchronous for this volume of data
navigator.onLine + online/offline eventsLets the app detect connectivity changes and react (switch data sources, trigger sync)
An offline action QUEUEStores user actions (likes, comments) performed while offline, replaying them once connectivity returns — usually also persisted to IndexedDB so it survives a page reload while still offline
Background Sync API (where supported)Lets queued actions sync even if the user has closed the tab, once connectivity returns — a more robust alternative to only syncing on the 'online' event while the tab is open
⚠ Realistically, "offline support" for a news feed usually means READ access to already-seen content, plus queued WRITE actions — it's rarely expected to support loading genuinely NEW content while offline (since that data doesn't exist locally yet); setting this scope explicitly is an important part of a strong answer.

How It All Fits Together

The full architecture — data sources feeding into ONE unified feed state
✓ The core architectural insight: REST (paginated history), WebSocket (live updates), and IndexedDB (offline cache) are three DIFFERENT data sources feeding into ONE unified client-side feed state — the rendering layer should be completely decoupled from WHICH source a given post/update came from, simplifying the UI logic considerably.

Common Gotchas & Interview Traps

  • ⚠️Page-number pagination silently breaks on a live-updating feed — new posts shifting everything down causes duplicate or skipped items on subsequent page loads; cursor-based pagination is the correct default for ANY feed that can change while being paginated.
  • ⚠️Auto-injecting new WebSocket posts directly into the visible feed disrupts the user's scroll position and reading flow — the "new posts available" banner pattern exists specifically to avoid this common, jarring UX mistake.
  • ⚠️An optimistic like update can be silently OVERWRITTEN by an incoming WebSocket like-count update if reconciliation isn't handled carefully — e.g. the user optimistically likes a post, then a WebSocket message with the (not-yet-updated) OLD server count arrives and incorrectly reverts the visible count; some form of "trust local optimistic state until the corresponding request resolves" logic is needed.
  • ⚠️Rapid, repeated like/unlike toggling can create out-of-order network requests if not handled — the LAST request to actually complete might not reflect the user's FINAL intended state; tracking only the latest intended state (and potentially cancelling/ignoring superseded in-flight requests) avoids this.
  • ⚠️WebSocket connections WILL drop unexpectedly in real-world usage (network changes, server restarts, mobile devices switching networks) — an implementation with NO reconnection logic at all will silently stop receiving live updates with no visible indication to the user that anything is wrong.
  • ⚠️"Offline support" is often vaguely scoped in interview answers — being explicit about WHAT specifically works offline (viewing already-cached posts, queuing new actions) versus what CAN'T (loading genuinely new content that was never fetched) demonstrates more precise, realistic system thinking.
  • ⚠️Combining infinite scroll with a long-running WebSocket connection without virtualization can cause serious memory growth over a long session — a feed that's been scrolled through for an hour, receiving continuous live updates, needs SOME mechanism (virtualization, or periodically trimming very old off-screen items from memory) to avoid unbounded growth.
  • ⚠️Queued offline actions need conflict resolution logic for when they finally sync — e.g. what happens if a post the user liked WHILE offline was deleted by its author before the queued like request finally syncs? A robust design considers and handles these edge cases explicitly, even if the actual behavior is just "fail gracefully and inform the user."
  • ⚠️Not all networks/environments support WebSockets reliably — some corporate proxies or restrictive environments block them; a resilient design mentions a FALLBACK mechanism (like polling) rather than assuming WebSocket connectivity is always guaranteed to succeed.
  • ⚠️Persisting the offline action queue only in memory (not IndexedDB/localStorage) means queued actions are LOST if the user closes the tab or the browser crashes while still offline — genuinely resilient offline support requires the queue itself to survive a page reload, not just survive momentarily within the current session.

Interview Q&A — Why / What / When / How

🎯 A news feed question is a genuine SYSTEM DESIGN exercise for the frontend — the strongest answers explicitly name the trade-offs at each layer, and describe how the pieces INTEGRATE, rather than treating each requirement in complete isolation.
WhatWhat's the difference between page-number-based and cursor-based pagination, and why does it matter for a news feed specifically?
+
Page-number pagination (`?page=2`) assumes the underlying dataset is STABLE between requests — "page 2" means "items 21-40," a meaning that depends entirely on nothing having changed in items 1-20 since the last request. Cursor-based pagination (`?cursor=abc123`) instead means "everything after THIS SPECIFIC item," anchoring the pagination to a concrete, stable reference point rather than a shifting numeric position. For a news feed specifically, NEW posts are constantly being added at the top — if you're on "page 2" using page-number pagination and 5 new posts get added above everything, your NEXT "page 3" request now returns items that OVERLAP with what page 2 already showed (or skips items entirely, depending on the exact shift), causing visible duplicates or gaps. Cursor-based pagination is immune to this, since it doesn't care how many new items were added ABOVE the cursor — it just returns everything after that specific anchor point, correctly, regardless of what's happened above it.
WhyWhy shouldn't new posts arriving via WebSocket be automatically inserted at the top of the feed the instant they arrive?
+
If the user is actively scrolled DOWN, reading posts further into the feed, and new content silently gets inserted ABOVE the currently-visible viewport, this shifts the POSITION of everything the user is currently looking at — potentially causing a jarring, disorienting jump, or worse, causing the user to accidentally interact with a DIFFERENT post than the one they intended, right as the layout shifts beneath their cursor. This is fundamentally the same category of problem as unwanted Cumulative Layout Shift, just caused by a real-time data update instead of a slow-loading image. The "new posts available" banner pattern defers this disruptive insertion until the USER explicitly chooses to see the new content (typically by clicking the banner or scrolling back to the top themselves), keeping the user in full control of when their current reading context gets disrupted.
WhenWhen would you choose to roll back an optimistic like update, versus silently retrying the failed request instead?
+
Roll back immediately (and inform the user) for errors that are UNLIKELY to succeed on a simple retry — e.g. a 403/401 (the user's session expired or they lack permission), or a 404 (the post was deleted) — these represent a genuine, persistent failure state where showing the optimistic "liked" state any longer would be actively misleading. Consider a silent, brief RETRY (perhaps once or twice, with a short delay) before rolling back for errors that are plausibly TRANSIENT — a timeout, a 500/503 server error, or a brief network blip — since these often succeed on a quick retry without needing to bother the user with an error state OR revert their visible action, if the underlying issue was genuinely temporary. The right choice depends on whether the specific failure reason suggests the action is fundamentally impossible right now, or just momentarily unlucky.
HowHow would you prevent an incoming WebSocket like-count update from incorrectly overwriting a user's own just-made optimistic like update?
+
// Track which posts have a PENDING optimistic action in flight const pendingLikeActions = new Set(); // postIds with an in-flight like/unlike request function handleWebSocketLikeUpdate(postId, serverLikeCount) { if (pendingLikeActions.has(postId)) { return; // IGNORE this update — trust the local optimistic state until OUR request resolves } updatePost(postId, { likeCount: serverLikeCount }); // safe to apply — no local action in flight } async function toggleLike(postId, liked) { pendingLikeActions.add(postId); applyOptimisticUpdate(postId, liked); try { await api.toggleLike(postId, liked); } catch { rollback(postId); } finally { pendingLikeActions.delete(postId); // NOW safe to accept WebSocket updates for this post again } }
The key idea is tracking, per post, whether there's currently a LOCAL, in-flight optimistic action the user just initiated — while that's true, incoming WebSocket updates for that SAME post are deliberately IGNORED, trusting the local optimistic state as more current/authoritative until the user's own request has actually resolved (success or failure). Once the local request settles (the `finally` block), the post is removed from the pending set, and subsequent WebSocket updates are trusted normally again — this prevents the specific race where a slightly-stale server broadcast arrives in the brief window between the user's click and their own request's response, which would otherwise incorrectly stomp on their just-made change.
WhatWhat should "offline support" concretely mean for a news feed — what should and shouldn't work with no connection?
+
A realistic, well-scoped offline experience for a news feed typically means: the user can still VIEW any posts that were already loaded/cached during a previous online session (served from IndexedDB); actions like LIKING a post are accepted and reflected optimistically in the UI immediately, then QUEUED locally and automatically synced once connectivity returns; and the app clearly COMMUNICATES its offline state (a banner or indicator) so the user understands why new content isn't appearing. What realistically should NOT be expected to work offline: loading genuinely NEW posts that were never fetched before going offline (that data simply doesn't exist locally, and there's no way to conjure it without a network request) — being explicit about this boundary, rather than vaguely implying "the whole feed works offline," reflects a more accurate and defensible scope for the feature.
WhyWhy is exponential backoff important for WebSocket reconnection, rather than just retrying immediately every time the connection drops?
+
If a WebSocket connection drops because the SERVER is having trouble (overloaded, restarting, or experiencing an outage), every connected client immediately retrying at full speed creates a "thundering herd" problem — potentially thousands of clients all hammering the server with reconnection attempts SIMULTANEOUSLY, right when it's least able to handle the load, which can actually make server recovery slower or prevent it from recovering at all. Exponential backoff spaces out retry attempts progressively (1s, 2s, 4s, 8s...up to some capped maximum), meaning the RECONNECTION LOAD on a recovering server ramps up gradually rather than hitting it all at once — while still ensuring the client eventually reconnects successfully once the server is healthy again, without requiring a page refresh or manual user intervention.
WhenWhen combining infinite scroll with a live feed, when would you need to consider trimming old items from memory, rather than letting the list grow forever?
+
This becomes a real concern for a genuinely LONG-RUNNING session — a user who keeps a feed tab open for hours, continuously scrolling and receiving live updates, can accumulate an unbounded amount of post data in memory over time, even with DOM-level virtualization limiting the actual rendered nodes (virtualization only limits DOM node count, not necessarily the underlying JS data array holding ALL loaded posts' data). For a typical, moderate session (a user scrolling through a few hundred posts over some minutes), this usually isn't a practical problem worth extra engineering complexity. For an application explicitly designed for very long-lived sessions (like a dashboard meant to stay open all day), it becomes worth implementing some form of data trimming — e.g. keeping only the most recent N posts' full data in memory, and re-fetching older ones on-demand if the user scrolls back up to them — trading a small amount of potential re-fetch latency for bounded, predictable memory usage over arbitrarily long sessions.
HowHow would you design the queued offline actions system to handle a conflict — like a queued "like" action for a post that gets deleted before the queue syncs?
+
1. When the app comes back ONLINE, process the queued actions IN ORDER, sending each to the server as normal API requests.
2. For the specific "like a since-deleted post" scenario, the server will naturally respond with an error (likely a 404, since the post no longer exists) — the client should catch this specific error case explicitly.
3. On this kind of "the target no longer exists" error, the correct handling is typically to SILENTLY DISCARD that specific queued action (there's nothing meaningful left to retry or roll back to — the post is simply gone) rather than treating it as a fatal error that blocks the rest of the queue from syncing.
4. Continue processing the REMAINING queued actions normally — one failed/discarded action shouldn't block or corrupt the sync of other, unrelated queued actions.
5. Optionally, surface a SUBTLE, non-blocking notification to the user (e.g. "Some of your offline actions couldn't be completed") rather than either silently failing with no indication at all, or interrupting them with an intrusive error for something that's ultimately a minor, unavoidable edge case.
