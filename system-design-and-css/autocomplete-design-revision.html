Debouncing User Input

💡 Without debouncing, EVERY keystroke fires an API request — typing "keyboard" (8 characters) fires 8 requests, most of which become instantly irrelevant as the user keeps typing. Debouncing waits for a short PAUSE in typing before actually firing the request.
Without vs with debouncing, typing "cat"
function debounce(fn, delay) { let timeoutId; return function (...args) { clearTimeout(timeoutId); // cancel any PENDING call — resets the wait timeoutId = setTimeout(() => fn.apply(this, args), delay); }; } const debouncedSearch = debounce(fetchSuggestions, 300); inputEl.addEventListener("input", (e) => debouncedSearch(e.target.value));

Caching Results

💡 Users frequently RE-TYPE or BACKSPACE through queries they've already searched (typing "java" then backspacing to "jav" then retyping "java"). An in-memory cache, keyed by the exact query string, avoids re-fetching identical requests instantly.
const cache = new Map(); // query string → results array async function fetchSuggestions(query) { if (cache.has(query)) { return cache.get(query); // instant — no network request at all } const results = await fetch(`/api/search?q=${encodeURIComponent(query)}`) .then((r) => r.json()); cache.set(query, results); return results; }
Cache design decisionConsideration
Cache keyUsually the exact, normalized query string (consider lowercasing/trimming for better hit rates)
Cache evictionAn unbounded Map can grow indefinitely for a long session — consider an LRU cache with a max size for production use
StalenessCached results can become outdated if the underlying data changes — consider a TTL (time-to-live) for cache entries in a real system
Cache scopeIn-memory (lost on page refresh) is usually sufficient — persisting to localStorage is rarely necessary and adds complexity for this specific pattern

Race Conditions — Out-of-Order Responses

🚨 Even WITH debouncing, network requests can complete OUT OF ORDER — a request for "ca" might, due to network variability, resolve AFTER a later request for "cat" — showing STALE, incorrect results if not handled, even though the requests were fired in the correct order.
The race condition — request 1 resolves AFTER request 2
// Fix 1: track a request ID/token, ignore stale responses let latestRequestId = 0; async function fetchSuggestions(query) { const requestId = ++latestRequestId; // this request's unique "ticket number" const results = await fetch(`/api/search?q=${query}`).then((r) => r.json()); if (requestId !== latestRequestId) return; // a NEWER request has since been fired — discard this stale one renderResults(results); } // Fix 2 (preferred where available): AbortController — actually CANCELS the stale request let controller; async function fetchSuggestions(query) { controller?.abort(); // cancel any IN-FLIGHT previous request controller = new AbortController(); const results = await fetch(`/api/search?q=${query}`, { signal: controller.signal }) .then((r) => r.json()); renderResults(results); }
ApproachTrade-off
Request ID / token trackingSimple, works everywhere — but the stale request still completes and wastes bandwidth, just gets IGNORED on arrival
AbortControllerGenuinely CANCELS the in-flight request, saving bandwidth/server load too — the more complete, modern solution

Keyboard Navigation

↓ Move highlight to next suggestion
↑ Move highlight to previous suggestion
Enter Select the currently highlighted suggestion
Escape Close the suggestion list
Home / End Jump to first/last suggestion
Tab Close the list, move focus normally onward
inputEl.addEventListener("keydown", (e) => { switch (e.key) { case "ArrowDown": e.preventDefault(); // stop the cursor from moving in the input itself setHighlightedIndex((i) => Math.min(i + 1, results.length - 1)); break; case "ArrowUp": e.preventDefault(); setHighlightedIndex((i) => Math.max(i - 1, 0)); break; case "Enter": if (highlightedIndex >= 0) { e.preventDefault(); selectResult(results[highlightedIndex]); } break; case "Escape": closeSuggestions(); break; } });
⚠ Focus stays on the TEXT INPUT the entire time — keyboard navigation moves a visual/logical "highlighted" state among the suggestions, but DOM focus never actually leaves the input. This is intentional and is precisely why aria-activedescendant (Section 6) is needed to communicate the highlighted item to screen readers.

Accessibility — The Combobox Pattern

<label id="search-label" htmlFor="search-input">Search</label> <input id="search-input" role="combobox" aria-expanded={isOpen} aria-controls="suggestions-list" aria-activedescendant={highlightedId || undefined} aria-autocomplete="list" /> <ul id="suggestions-list" role="listbox"> {results.map((r, i) => ( <li key={r.id} id={`option-${r.id}`} role="option" aria-selected={i === highlightedIndex} > {r.label} </li> ))} </ul> <div aria-live="polite" className="sr-only"> {results.length} suggestions available </div>
AttributePurpose
role="combobox" (on the input)Identifies the input as a combobox widget — a text input paired with a suggestion list
aria-expandedTells assistive tech whether the suggestion list is currently open
aria-controlsLinks the input to the ID of the suggestions list it controls
aria-activedescendantSince DOM focus NEVER leaves the input (Section 5), this attribute tells assistive tech WHICH option is currently "virtually" highlighted
role="listbox" / role="option"Identifies the suggestions container and each individual suggestion appropriately
aria-live="polite" regionAnnounces the RESULT COUNT as it changes — critical, since a screen reader user typing wouldn't otherwise know results appeared/changed at all
💡 This combobox pattern directly reuses the aria-activedescendant technique and aria-live announcement pattern from broader ARIA fundamentals — an autocomplete is essentially a concrete, real-world APPLICATION of those general accessibility concepts.

API Contract Design

// Request GET /api/search?q=cat&limit=10 // Response { "query": "cat", "results": [ { "id": "123", "label": "Catalog", "highlightRanges": [[0,3]] }, { "id": "456", "label": "Category", "highlightRanges": [[0,3]] } ], "hasMore": false }
Design decisionConsideration
limit parameterCaps the number of results — an autocomplete typically only needs 5-10 suggestions, not a full paginated result set
Echoing "query" back in the responseLets the client verify the response actually matches its current input, an extra safety check alongside request-ID tracking
highlightRangesLets the server indicate WHICH part of each label matched the query, so the client can bold/highlight the matching substring without re-implementing fuzzy matching logic client-side
Debounce/rate-limiting server-side tooClient-side debouncing helps, but a robust API should also rate-limit per-client server-side, since clients can't be fully trusted to behave well
Response time SLAAutocomplete APIs typically need to respond very fast (well under 100-200ms) to feel responsive — this often means a specialized search index (like Elasticsearch) rather than a generic database query

Putting It All Together

function useAutocomplete() { const [query, setQuery] = useState(""); const [results, setResults] = useState([]); const [highlightedIndex, setHighlightedIndex] = useState(-1); const cache = useRef(new Map()); const controllerRef = useRef(null); const debouncedFetch = useMemo( () => debounce(async (q) => { if (cache.current.has(q)) { setResults(cache.current.get(q)); // cache hit — instant, no network return; } controllerRef.current?.abort(); // cancel any in-flight PREVIOUS request controllerRef.current = new AbortController(); try { const data = await fetch(`/api/search?q=${q}`, { signal: controllerRef.current.signal }) .then((r) => r.json()); cache.current.set(q, data.results); setResults(data.results); setHighlightedIndex(-1); // reset highlight for the NEW result set } catch (err) { if (err.name !== "AbortError") console.error(err); } }, 300), [] ); const onInputChange = (value) => { setQuery(value); if (value.trim() === "") { setResults([]); return; } debouncedFetch(value); }; return { query, results, highlightedIndex, onInputChange, setHighlightedIndex }; }
✓ Notice how the pieces compose: debouncing reduces HOW OFTEN a request fires; caching skips the network entirely for repeated queries; AbortController protects against race conditions for the requests that DO go out. Each addresses a DIFFERENT concern, and a robust implementation needs all three working together, not just one.

Common Gotchas & Interview Traps

  • ⚠️Debouncing alone does NOT solve race conditions — a common mistake is assuming debouncing is sufficient; even a single, debounced, "final" request can still be affected by ordinary network latency variance if the user types again before that request resolves.
  • ⚠️Forgetting to reset highlightedIndex when new results arrive — if the user had item #3 highlighted and a NEW, shorter result set arrives, index #3 might not exist anymore, or might now point to a completely different, unrelated item.
  • ⚠️DOM focus should stay on the input during keyboard navigation, NOT move to each list item — moving actual focus to list items breaks the typical expected interaction model and typically requires MORE, not less, accessibility work to get right; the aria-activedescendant pattern exists specifically to avoid needing to move real focus.
  • ⚠️An empty query string should typically clear results immediately, WITHOUT even attempting a debounced fetch — a common oversight is fetching an empty query and displaying "no results," when the correct behavior is usually just showing nothing/a default state instantly.
  • ⚠️The cache can grow unbounded over a long session if no eviction strategy exists — for a genuinely production system, this matters; for an interview/demo-scale answer, mentioning the AWARENESS of this limitation (even if not fully implementing LRU eviction live) demonstrates more senior-level thinking.
  • ⚠️Clicking a suggestion with the MOUSE needs separate handling from keyboard selection — using `onMouseDown` (which fires BEFORE the input's blur event) rather than `onClick` (which can fire AFTER blur has already closed/hidden the suggestions) is a common, subtle bug avoidance technique for click-to-select.
  • ⚠️Closing the suggestion list on blur needs care to not break mouse-click selection — naively closing the list immediately `onBlur` can prevent a mouse click on a suggestion from ever registering, since the blur fires first and hides the very element the user was trying to click.
  • ⚠️Forgetting server-side rate limiting, relying ONLY on client-side debouncing — client-side debouncing is a UX/performance optimization, not a security or abuse-prevention mechanism; a malicious or buggy client could bypass it entirely, so genuine rate-limiting belongs on the server too.
  • ⚠️Announcing EVERY single result count change via aria-live="assertive" is disruptive — "polite" is almost always the right choice for this kind of frequent, non-urgent update, consistent with the general aria-live guidance from the broader accessibility topic.
  • ⚠️Not handling the loading state can leave the UI feeling unresponsive between the debounce delay and the actual response — a brief loading indicator (careful not to cause layout shift) improves perceived responsiveness during the network round-trip, especially on slower connections.

Interview Q&A — Why / What / When / How

🎯 Autocomplete is a classic "frontend system design" question specifically BECAUSE it forces you to juggle multiple concerns simultaneously — strong answers explicitly name and address EACH concern rather than jumping straight to code.
WhatWhat's the difference between debouncing and throttling, and which is more appropriate for an autocomplete input?
+
Debouncing waits for a PAUSE in activity before acting — it keeps RESETTING a timer on every new event, only firing once events stop for the specified delay. Throttling instead guarantees a function runs at most once per fixed time INTERVAL, regardless of how many events occur, firing periodically DURING continuous activity rather than only after it stops. For an autocomplete, debouncing is the better fit — you specifically want to wait until the user PAUSES typing (indicating they've likely finished a meaningful chunk of their query) before firing a request, rather than firing periodically WHILE they're still actively typing, which would still generate wasted requests for partial, soon-to-be-superseded queries.
WhyWhy can a race condition still occur even with debouncing already in place?
+
Debouncing controls WHEN a request gets FIRED — reducing the frequency of outgoing requests — but it has no control whatsoever over network conditions AFTER a request has been sent, like variable latency, server processing time, or routing differences between requests. If the user types "ca", pauses briefly (triggering a debounced request), then quickly types more to reach "cat" (triggering a second debounced request), BOTH requests are legitimately, correctly fired — but nothing guarantees they'll RESOLVE in the same order they were SENT. A slower network path for the "ca" request could cause it to resolve after the "cat" request, meaning the correct, more specific "cat" results get overwritten moments later by the stale "ca" results — debouncing reduces how often this scenario can occur, but doesn't structurally prevent it once two or more requests ARE in flight simultaneously.
WhenWhen would you choose the request-ID tracking approach over AbortController for handling race conditions?
+
When the underlying request mechanism doesn't support cancellation at all — for example, some older browser APIs, certain third-party SDK wrappers around network requests, or non-fetch-based mechanisms (like some WebSocket-based request/response patterns) may not expose an `AbortController`-compatible cancellation mechanism. Request-ID tracking works as a purely CLIENT-SIDE bookkeeping technique regardless of whether the underlying request can actually be cancelled — it simply ignores/discards a response once it arrives if a newer request has since superseded it, without needing any cooperation from the request mechanism itself. `AbortController` is preferable whenever available since it saves real bandwidth/server load by genuinely cancelling the stale request rather than letting it complete uselessly — but request-ID tracking remains a useful, universally-applicable fallback.
HowHow would you make an autocomplete's suggestion list accessible to a screen reader user, given that keyboard focus never leaves the text input?
+
1. Mark the input with `role="combobox"`, and set `aria-expanded` to reflect whether the suggestion list is currently visible.
2. Link the input to the suggestions list via `aria-controls`, pointing to the list's ID.
3. As the user navigates suggestions with arrow keys (without DOM focus ever moving), update `aria-activedescendant` on the INPUT to the ID of the currently highlighted `<li role="option">` element — this is the specific mechanism that lets a screen reader announce "which option is currently highlighted" despite focus staying on the input the whole time.
4. Mark the suggestions container with `role="listbox"` and each suggestion with `role="option"`, using `aria-selected` to reflect the current highlight.
5. Include a separate `aria-live="polite"` region announcing the result COUNT as it changes (e.g. "5 suggestions available"), since a screen reader user typing wouldn't otherwise be notified that new results appeared at all — this doesn't rely on focus or activedescendant, it's a proactive announcement of a state change.
WhatWhat should a well-designed autocomplete API contract include, beyond just a list of matching strings?
+
Beyond the basic list of results, a well-designed contract typically includes: a `limit` request parameter, capping the response to a small, UI-appropriate number of suggestions (autocomplete rarely needs more than 5-10); the ORIGINAL query ECHOED BACK in the response, letting the client double-check the response still matches its current input state as an extra safety net alongside request-ID/abort-based race protection; structured result OBJECTS (with a stable `id`, not just a display string) so the client can reliably track/select specific items even if display labels are ambiguous or repeat; and often HIGHLIGHT RANGE information indicating which substring of each result matched the query, so the client can visually bold the matching portion without needing to re-implement its own (potentially inconsistent) fuzzy-matching logic.
WhyWhy is client-side debouncing insufficient as the ONLY protection against API abuse, and what else is needed?
+
Client-side debouncing is JavaScript code running entirely within the USER'S browser — a malicious actor (or simply a different, non-debounced client, like a script calling the API directly rather than through your UI) can trivially bypass it entirely, since there's nothing on the SERVER enforcing this behavior; it's purely a client-side UX/performance optimization, not a security boundary. A robust API needs genuine SERVER-SIDE rate limiting (e.g. capping requests per API key/IP/user to some reasonable threshold per time window), independent of whatever the "well-behaved" client happens to do — this protects the backend from abuse, accidental request storms (like a buggy client with a broken debounce implementation), or deliberate attacks, none of which client-side debouncing has any power to prevent.
WhenWhen would in-memory caching alone be insufficient, requiring a more sophisticated caching strategy?
+
For a SHORT-lived, single-page-session autocomplete (like a typical search box), a simple in-memory `Map` cache is usually entirely sufficient — the cache naturally clears on page refresh, which is fine since suggestion data is rarely expected to persist across sessions anyway. It becomes insufficient specifically when: the underlying DATA changes frequently enough that stale cached results become a genuine correctness problem (requiring a TTL/expiration strategy, not just an unbounded cache); the user's session is VERY long and generates enough unique queries that an unbounded cache could meaningfully impact memory usage (requiring LRU eviction with a max size); or the SAME suggestions need to be shared/reused ACROSS different components or page loads (which might justify a more persistent cache, like sessionStorage, though this is a less common requirement for typical autocomplete use cases).
HowHow would you handle a mouse click on a suggestion without it being accidentally cancelled by the input's blur event closing the list first?
+
// ✗ Problem: onClick fires AFTER blur — but blur already closed/hid the list <li onClick={() => selectResult(item)}>{item.label}</li> <input onBlur={closeSuggestions} /> // Clicking the li: mousedown → input BLURS (closeSuggestions runs, li disappears) // → click event never has anything left to fire on, or fires on now-hidden content // ✓ Fix: use onMouseDown, which fires BEFORE the blur event, and preventDefault <li onMouseDown={(e) => { e.preventDefault(); // prevents the input from blurring AT ALL for this interaction selectResult(item); }} > {item.label} </li>
The core fix is using `onMouseDown` (which fires BEFORE the browser processes the resulting blur) instead of `onClick` (which fires after mouseup, by which point blur has already happened and possibly closed the list). Calling `e.preventDefault()` inside the mousedown handler additionally prevents the input from losing focus at all for this specific interaction, avoiding the blur-triggered close entirely and letting the selection logic run cleanly against still-visible, still-mounted suggestion elements.
