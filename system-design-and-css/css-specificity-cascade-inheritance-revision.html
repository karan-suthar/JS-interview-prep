The Three Pillars — How the Browser Decides

💡 When MULTIPLE CSS rules could apply to the SAME element and property, the browser resolves the conflict using, in order: 1. Origin & Importance (where the rule came from, and whether it's `!important`), 2. Specificity (how precisely the selector targets the element), 3. Source Order (which rule appears LAST in the stylesheet). Inheritance is a SEPARATE mechanism — it only applies when NO rule directly targets an element for a given property at all.
PillarAnswers the question...
Cascade"When multiple rules conflict, which one WINS?"
Specificity"How do I MEASURE how strongly a given selector targets an element?"
Inheritance"If NOTHING explicitly styles this element for a property, where does its value come from?"

Specificity Calculation — The Point System

💡 Specificity is calculated as a THREE-PART value (often written as three numbers, like a version number) — it's NOT a single number you can add up naively; a selector with more IDs always beats one with more classes, no matter how many classes.
Selector typeColumnExamples
ID selectorsColumn A (highest)#header, #nav-menu
Class, attribute, pseudo-class selectorsColumn B (middle).btn, [type="text"], :hover, :nth-child()
Element and pseudo-element selectorsColumn C (lowest)div, p, ::before, ::after
Universal selector, combinators0 (no contribution)*, >, +, ~, (space)
Worked specificity calculations
🚨 The most common specificity mistake: treating it as ONE combined number instead of three SEPARATE, hierarchically-compared columns. A selector with 50 classes still LOSES to a selector with just 1 ID — you compare Column A first, and only move to Column B if Column A is TIED.

Cascade Order — Beyond Just Specificity

⚠ Specificity is only ONE ingredient in the cascade — ORIGIN (where a rule comes from) and IMPORTANCE (`!important`) are checked BEFORE specificity even comes into play, and can override a "more specific" selector entirely.
1
Highest priority: User-agent !important (extremely rare, browser default styles marked important)
2
User !important (a user's own custom stylesheet, marked important — rare, accessibility-related)
3
Author !important (YOUR site's CSS, marked !important — the practically relevant "important" tier for most developers)
4
Author normal (your site's regular CSS — specificity and source order decide ties WITHIN this tier)
5
User normal (a user's own custom stylesheet, without !important)
6
Lowest priority: User-agent normal (the browser's own default stylesheet — e.g. default button styling)
💡 Within the SAME origin/importance tier, the order is: Specificity first, then Source Order (the LAST rule wins, if specificity is tied) as the final tiebreaker.
/* Source order tiebreaker example — EQUAL specificity (0,1,0) for both */ .btn { color: blue; } .btn { color: red; } /* This WINS — same specificity, but declared LAST */ /* Result: the button is RED */

Inheritance

💡 Inheritance only kicks in when NO rule directly sets a property for an element — in that case, certain properties automatically take their PARENT's computed value. Not all properties inherit by default; this is deliberately chosen per-property based on what usually makes sense.
CategoryExamplesWhy
Inherit by DEFAULTcolor, font-family, font-size, line-height, visibility, text-align, cursorTypography/text-related properties usually SHOULD flow down — you don't want to re-declare font-family on every single nested element
Do NOT inherit by defaultmargin, padding, border, width, height, background, display, positionBox-model/layout properties are usually specific to EACH element's own box — a child inheriting its parent's exact margin would rarely make sense
/* Explicit inheritance-control keywords */ .child { color: inherit; /* force this property to take the PARENT's value, even if it wouldn't normally inherit */ border: initial; /* reset to the property's default initial value, ignoring inheritance/cascade */ all: unset; /* reset EVERY property — to inherited value if it naturally inherits, else initial */ color: revert; /* reset to what it would be WITHOUT any author styles — falls back to user-agent default */ }
KeywordBehavior
inheritExplicitly take the parent element's COMPUTED value for this property
initialReset to the property's CSS-specification default value (ignores inheritance and the cascade entirely)
unsetActs like `inherit` if the property naturally inherits, or like `initial` if it doesn't — a convenient "do the sensible default" reset
revertRolls back to the value the property WOULD have had with NO author styles applied at all (i.e., the user-agent/browser default)

Debugging a Specificity Conflict, Fast

StepWhat to do
1. Inspect the elementOpen DevTools, select the element — the Styles panel shows EVERY matching rule, with overridden (crossed-out) declarations clearly visible
2. Find what's actually winningThe Styles panel lists rules in PRIORITY order (winning rule at top) — no manual calculation needed, DevTools has already resolved it for you
3. Check for !important firstAn `!important` declaration is visually flagged — if present, it explains the override regardless of specificity
4. Compare specificity of the competing rulesIf no !important is involved, compare the (A,B,C) specificity of the rules manually, or hover over a selector in some browsers' DevTools to see its calculated specificity directly
5. Check source order as a last resortIf specificity is EXACTLY tied, the rule appearing LATER in the cascade (later stylesheet, or later in the same file) wins
💡 The fastest real-world debugging approach is almost always just: open DevTools, inspect the element, and read the Styles panel — it already shows you which rule won and visually crosses out the ones that lost, doing the specificity math for you. Manual calculation matters most for EXPLAINING why, in an interview or code review, not for day-to-day debugging.

Worked Examples — Full Conflict Resolution

/* Example 1: specificity alone decides */ .card p { color: black; } /* (0, 1, 1) */ #sidebar p { color: blue; } /* (1, 0, 1) — WINS, has an ID */ /* Result: blue — regardless of which rule appears FIRST or LAST in the file */ /* Example 2: !important overrides HIGHER specificity */ #sidebar p { color: blue; } /* (1, 0, 1) */ .card p { color: red !important; } /* (0, 1, 1), but !important WINS regardless */ /* Result: red — !important is checked BEFORE specificity comparison */ /* Example 3: tied specificity, source order decides */ .title { font-weight: normal; } /* (0, 1, 0) */ .title { font-weight: bold; } /* (0, 1, 0) — tied, but declared LAST → WINS */ /* Result: bold */ /* Example 4: inline style beats ANY selector-based rule (except !important) */ <div style="color: green;" class="card">...</div> #super #specific #selector .card { color: purple; } /* (3, 1, 0) — still LOSES */ /* Result: green — inline styles have a specificity ABOVE any selector-based rule */

Common Gotchas & Interview Traps

  • ⚠️Specificity is a THREE-COLUMN comparison, never a single summed number — this is by far the most common misconception; 100 classes never outrank a single ID, because Column A is compared FIRST and completely independently of Column B.
  • ⚠️Inline styles (the HTML `style="..."` attribute) have a specificity HIGHER than any selector-based CSS rule — effectively "above" even an ID selector, though it's sometimes modeled as its own separate tier rather than literally part of the (A,B,C) system; only `!important` can override an inline style.
  • ⚠️The universal selector (*) and combinators (>, +, ~, space) contribute ZERO to specificity — a highly complex-looking selector chain using only combinators and the universal selector can have surprisingly LOW specificity if it contains no actual ID/class/element parts.
  • ⚠️!important should generally be treated as a LAST resort, not a standard tool — overusing it creates a codebase where NORMAL specificity rules stop being predictable, forcing future developers to reach for `!important` themselves just to override an existing `!important`, spiraling into a maintenance problem.
  • ⚠️CSS Custom Properties (variables, --my-var) DO inherit, by default, regardless of what property they're eventually used in — this is a distinct, separate inheritance behavior from the "does this specific CSS property inherit" table in Section 4.
  • ⚠️`unset` behaves DIFFERENTLY depending on whether the specific property naturally inherits or not — it's not a single fixed behavior; it dynamically resolves to `inherit` OR `initial` based on that property's own default inheritance behavior, which can surprise people expecting one consistent effect.
  • ⚠️CSS Layers (@layer) add an ADDITIONAL tier to the cascade, checked BEFORE specificity, similar in spirit to origin — a newer feature explicitly designed to give developers more CONTROL over cascade order without needing to fight with specificity or `!important`; worth mentioning as current, modern knowledge if relevant.
  • ⚠️Pseudo-CLASSES (:hover, :nth-child) count toward specificity (Column B) — but pseudo-ELEMENTS (::before, ::after) count in Column C, same as a plain element selector — a subtle but real distinction (note the single vs double colon syntax difference too).
  • ⚠️The `:where()` pseudo-class ALWAYS has ZERO specificity, regardless of what's inside it — while `:is()` and `:not()` take on the specificity of their MOST specific argument; `:where()` is specifically useful for writing reset/base styles that are trivially easy to override later without any specificity fights.
  • ⚠️Source order as a tiebreaker depends on the FINAL, computed order of ALL stylesheets/rules the browser sees — including the order `<link>`/`<style>` tags appear in the HTML, and (for CSS-in-JS or bundled styles) the order the build tool ultimately outputs them in, which can sometimes surprise developers who assumed source-file order alone determines it.

Interview Q&A — Why / What / When / How

🎯 Specificity debugging is a skill interviewers often test with a live, on-the-spot code snippet — being able to WALK THROUGH the resolution algorithm methodically (rather than guessing) is what demonstrates real fluency here.
WhatWhat is CSS specificity, and how is it calculated?
+
Specificity is a way of measuring how PRECISELY a CSS selector targets an element, used to decide which of several conflicting rules should apply. It's calculated as a THREE-PART value: Column A counts ID selectors, Column B counts class/attribute/pseudo-class selectors, and Column C counts element/pseudo-element selectors. These columns are compared HIERARCHICALLY, like a version number — Column A is compared first, and only if it's tied do you move to comparing Column B, and so on. This means a selector with even ONE ID always beats a selector with any number of classes, since Column A takes absolute priority over Column B.
WhyWhy does !important get checked BEFORE specificity in the cascade, rather than specificity simply being the final word?
+
`!important` exists specifically as an EMERGENCY OVERRIDE mechanism — a way for a developer to say "this declaration must win, REGARDLESS of how specific the competing selector is." If specificity were checked FIRST and always had the final say, there would be no way to override a highly-specific but WRONG or outdated rule without literally rewriting an equally-or-more-specific selector to match it — which can be impractical, especially when the conflicting rule comes from third-party CSS you can't directly edit (a library, a CMS-generated stylesheet). By checking importance BEFORE specificity, `!important` provides an escape hatch that works regardless of the competing rule's specificity — though this power is exactly why it should be used sparingly, since overusing it undermines the predictability of the specificity system for everyone working in the codebase.
WhenWhen would source order end up being the deciding factor in a real-world specificity conflict?
+
Whenever TWO (or more) competing rules have EXACTLY the same specificity value (identical A, B, and C counts) AND belong to the same origin/importance tier — in this case, specificity alone can't break the tie, so the cascade falls back to whichever rule was declared LATER, either later in the same stylesheet, or in a stylesheet/style block that's loaded/rendered AFTER the other. A common real-world example is two `.button` class selectors with the same specificity — one from a base/reset stylesheet and one from a component-specific stylesheet — where simply controlling the ORDER these stylesheets are linked/imported in determines which one wins, entirely independent of specificity.
HowHow would you determine which of these two rules wins: "#nav .menu-item.active" versus ".navigation #menu .item"?
+
Step 1 — count each selector's parts: `#nav .menu-item.active` has 1 ID (#nav), 2 classes (.menu-item, .active), 0 elements → specificity (1, 2, 0). `.navigation #menu .item` has 1 ID (#menu), 2 classes (.navigation, .item), 0 elements → specificity (1, 2, 0).
Step 2 — compare column by column: Column A: both have 1 ID — TIED. Column B: both have 2 classes — TIED. Column C: both have 0 elements — TIED.
Step 3 — since specificity is EXACTLY tied (and assuming neither uses `!important` and both are the same origin), the decision falls to SOURCE ORDER — whichever rule is declared LATER in the cascade wins, regardless of which selector "looks" more complex or specific-sounding at a glance. This example specifically demonstrates why counting the actual A/B/C values matters more than a selector's apparent visual complexity or length.
WhatWhat's the difference between the inherit, initial, unset, and revert CSS keywords?
+
`inherit` forces a property to explicitly take its PARENT element's computed value, even for properties that don't naturally inherit by default. `initial` resets a property to its CSS-specification-defined default/initial value, ignoring both inheritance and any cascaded rules entirely. `unset` is a convenient "smart reset" — it behaves like `inherit` if the property is one that naturally inherits by default, or like `initial` if it's a property that doesn't naturally inherit — letting you reset without needing to remember which category the specific property falls into. `revert` rolls the property back to whatever value it WOULD have had with NO author-level CSS applied at all — typically falling back to the browser's own user-agent default stylesheet value, which is different from `initial`'s CSS-specification default (these can sometimes differ, e.g. for `display` on different elements).
WhyWhy do typography-related properties (color, font-family) inherit by default, while box-model properties (margin, padding, width) do not?
+
This was a deliberate design choice in the CSS specification based on what's PRACTICALLY useful in the vast majority of real-world cases. Typography properties like `color` and `font-family` are usually meant to apply CONSISTENTLY across a whole section of content — you typically want all the text inside an article to share the same font and color unless specifically overridden, so having these flow down automatically from a parent (like `body`) saves having to redeclare them on every single nested element. Box-model properties like `margin`, `padding`, and `width`, on the other hand, describe an element's OWN individual spacing/sizing needs relative to ITS specific content and layout context — a child element inheriting its parent's exact margin value would rarely make sense, since each element's ideal spacing is usually independent of its parent's. This split reflects a genuinely useful DEFAULT for common use cases, not an arbitrary technical limitation — and any property CAN still be forced to inherit explicitly via the `inherit` keyword when actually needed.
WhenWhen would you deliberately reach for :where() instead of a normal selector when writing reusable/base CSS?
+
When writing BASE, RESET, or LIBRARY-style CSS that's meant to be easily overridden later by whoever consumes it — `:where()` always contributes ZERO specificity, regardless of how complex the selector inside it is, meaning even a simple single-class selector written by a consuming developer will trivially override it, with no specificity fights required. This is especially valuable for CSS reset stylesheets, component library base styles, or any "sensible defaults" CSS meant to sit at the very bottom of the cascade's specificity hierarchy — contrast this with using normal selectors for the same purpose, which could accidentally end up MORE specific than intended, making it annoyingly hard for consumers to override without resorting to `!important` or artificially inflating their own selector's specificity just to win.
HowHow would you fix a CSS conflict where a component's styles are being overridden by a global stylesheet, WITHOUT resorting to !important?
+
1. Use DevTools to identify the EXACT competing rule and its specificity — confirm whether the global rule is winning due to higher specificity, or merely due to LATER source order at equal specificity.
2. If it's a SOURCE ORDER issue (tied specificity), the simplest fix is often just ensuring the component's stylesheet loads/is declared AFTER the global one — no selector changes needed at all.
3. If the global rule genuinely has HIGHER specificity, increase the component rule's specificity just enough to win — e.g. adding one extra class or a scoping wrapper class, rather than reaching for `!important` immediately.
4. Consider whether CSS Modules, scoped styles (e.g. in a component framework), or a naming convention like BEM would prevent this entire CLASS of conflict from recurring, by ensuring component styles and global styles simply don't have OVERLAPPING selectors to begin with.
5. If available, consider using `@layer` to explicitly place component styles in a cascade layer that's declared to take priority over the global styles' layer — a modern, purpose-built solution for exactly this kind of "global vs component" cascade conflict, without needing specificity tricks or `!important` at all.
