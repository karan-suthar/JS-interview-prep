Flexbox vs Grid — When to Reach for Each

💡 Flexbox is ONE-DIMENSIONAL — it lays items out along a SINGLE axis (row OR column) and excels at distributing/aligning items within that one line. Grid is TWO-DIMENSIONAL — it lays items out across ROWS and COLUMNS simultaneously, excelling at overall PAGE/component structure.
Use caseBetter fitWhy
Navbar with logo + nav links + buttonFlexboxOne row, distributing/aligning items along it
Overall page layout (header/sidebar/main/footer)GridNeeds to control both rows AND columns simultaneously
A row of buttons that should wrapFlexboxOne-dimensional flow with wrapping
A photo gallery / card gridGridGenuinely two-dimensional — rows AND columns of equal-ish items
Centering ONE item inside a containerEither works equally wellBoth have simple, one-line centering solutions

flex-wrapWhether items wrap onto multiple lines when they don't fit
gapSpacing between items — modern, cleaner alternative to margin-based spacing

/* ── Grid approach (recommended — it's a 2D structural layout) ── */ .layout { display: grid; grid-template-columns: 240px 1fr; /* sidebar: fixed 240px, main: fills the rest */ min-height: 100vh; gap: 16px; } /* ── Flexbox approach (also valid — a simpler, single-row case) ── */ .layout { display: flex; min-height: 100vh; gap: 16px; } .sidebar { flex: 0 0 240px; } /* don't grow, don't shrink, fixed 240px basis */ .main { flex: 1; } /* grow to fill all remaining space */
✓ Both approaches work for this simple case — Grid is generally preferred for whole-page structural layouts like this, since it's explicitly designed for exactly this "define the overall skeleton" use case, and scales more cleanly if you later add a header/footer row too.

/* The auto-fit + minmax() pattern — responsive WITHOUT a single media query */ .card-grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(220px, 1fr)); gap: 20px; } // How to read this: "fit as many columns as possible, each AT LEAST 220px wide, // and let them GROW to fill any leftover space equally (1fr)"
ValueEffect
auto-fitCollapses empty tracks — if there aren't enough items to fill a row, existing cards STRETCH to fill the space
auto-fillKeeps empty tracks as empty, fixed-size gaps — existing cards stay their minmax() size instead of stretching further
minmax(220px, 1fr)Each column is AT LEAST 220px, but grows to share any extra space equally with other columns
💡 auto-fit vs auto-fill only differs visually when there are FEWER items than would fill a complete row — with many items filling multiple full rows, they behave identically; the difference only shows up in that specific "not quite enough items" edge case.

Build 3 — Centered Modal

Live demo
Centered modal content
/* ── Flexbox approach — the classic, most common one-liner ── */ .modal-overlay { position: fixed; inset: 0; /* shorthand for top/right/bottom/left: 0 */ background: rgba(0,0,0,0.5); display: flex; align-items: center; /* vertical centering */ justify-content: center; /* horizontal centering */ } /* ── Grid approach — equally valid, arguably even more concise ── */ .modal-overlay { position: fixed; inset: 0; background: rgba(0,0,0,0.5); display: grid; place-items: center; /* shorthand for BOTH align-items AND justify-items: center */ }
ApproachNotes
Flexbox: align-items + justify-content: centerThe traditional, most widely-recognized centering pattern — works great for a SINGLE centered child
Grid: place-items: centerA newer, more concise one-line shorthand achieving the identical result — increasingly the preferred modern approach for simple centering
Position + transform (older technique)`position:absolute; top:50%; left:50%; transform:translate(-50%,-50%);` — works but is more verbose and was the standard BEFORE flexbox/grid had wide support
⚠ Don't forget the modal needs its OWN internal layout too — once centered, its internal content (header, body, footer buttons) often benefits from its own nested flex/grid layout, e.g. `display: flex; flex-direction: column;` for a header/body/footer stack inside the modal box itself.

Common Gotchas & Interview Traps

  • ⚠️flex: 1 is a SHORTHAND for three properties (flex-grow: 1, flex-shrink: 1, flex-basis: 0%) — not just "grow to fill space"; understanding that `flex-basis: 0` means it IGNORES the item's natural content size as a starting point is important for predicting actual behavior with mixed-size items.
  • ⚠️justify-content and align-items SWAP meaning when flex-direction changes from row to column — `justify-content` always refers to the MAIN axis (horizontal for row, VERTICAL for column), a common source of confusion when refactoring a layout's direction.
  • ⚠️Grid's implicit rows (rows the grid creates automatically for content beyond your explicit grid-template-rows) default to `auto` sizing — unless you explicitly set `grid-auto-rows`, which can catch people off guard when adding more items than originally planned for.
  • ⚠️gap works in BOTH flexbox and grid (not just grid, despite grid getting more attention for it) — a relatively recent but now well-supported addition to flexbox specifically, eliminating the need for margin-based spacing hacks in flex layouts too.
  • ⚠️auto-fit and auto-fill ONLY behave differently when there are fewer items than would fill a complete row — a common point of confusion is expecting a visible difference in every scenario, when it's specifically an edge case involving incomplete rows.
  • ⚠️Grid items overlap by DEFAULT if you explicitly place them onto the same grid-column/grid-row — Grid doesn't automatically prevent overlapping placements the way normal document flow does; this is sometimes used deliberately (for layered/overlapping designs) but can also be an easy-to-miss bug.
  • ⚠️min-width: auto is the DEFAULT for flex items, and can prevent them from shrinking as expected — a flex item with long unbreakable content (like a long word or a wide image) may refuse to shrink below its content's natural size unless `min-width: 0` (or `overflow: hidden`) is explicitly set, a classic, non-obvious flexbox gotcha.
  • ⚠️place-items is a shorthand that sets BOTH align-items and justify-items — for individual, per-item overrides you'd use `align-self`/`justify-self` instead, and there's a separate `place-content` shorthand for `align-content`/`justify-content` (content vs items distinction still applies in Grid).
  • ⚠️Nesting flexbox inside grid (or vice versa) is completely normal and often the RIGHT approach — e.g. Grid for the overall page skeleton, with Flexbox used WITHIN individual grid cells/components for their internal one-dimensional alignment needs; they're complementary tools, not mutually exclusive choices for an entire page.
  • ⚠️Older centering techniques (position:absolute + transform) still appear in legacy codebases and are worth recognizing — even though flexbox/grid centering is now strongly preferred for new code, being able to read and explain the OLDER pattern is still a reasonable thing to be asked about.

Interview Q&A — Why / What / When / How

🎯 Layout questions are often LIVE-CODING exercises — interviewers care as much about your reasoning process (why you reached for a specific property) as the final working result.
WhatWhat's the fundamental difference between Flexbox and Grid?
+
Flexbox is a ONE-DIMENSIONAL layout model — it arranges items along a SINGLE axis (either a row or a column) and is designed to distribute space and align items along THAT one line, even when items wrap onto multiple lines. Grid is a TWO-DIMENSIONAL layout model — it arranges items across ROWS and COLUMNS simultaneously, letting you define an explicit grid structure and place items precisely within it, including having items SPAN multiple rows/columns. Flexbox excels at "arrange these items in a line, distribute space between them"; Grid excels at "define an overall structural skeleton with distinct rows and columns."
WhyWhy is Grid generally preferred over Flexbox for a page-level sidebar layout, even though Flexbox can technically achieve the same visual result?
+
A sidebar layout is CONCEPTUALLY a two-dimensional structure — even if it currently has just one row (sidebar + main content), it's the kind of layout that commonly GROWS to include a header row and/or footer row later. Grid lets you define this entire structure — including rows AND columns — in one place, using `grid-template-columns`/`grid-template-rows`, making it straightforward to add a header/footer later by just adding a row definition. Flexbox CAN replicate the single-row case (using `flex-basis` for the sidebar width and `flex:1` for the main area), but if you later need to add a header spanning both the sidebar and main content, you'd need to either nest an additional flex container or restructure the HTML — Grid handles this kind of structural evolution more naturally since it was designed for genuinely two-dimensional layout from the start.
WhenWhen would you choose auto-fill over auto-fit for a responsive card grid, or vice versa?
+
Choose auto-fit when you want existing cards to STRETCH and fill the full available width whenever there aren't enough items to complete a row — e.g. showing just 2 cards on a screen wide enough for 4, where you'd rather those 2 cards grow larger than leave visible empty space. Choose auto-fill when you want cards to maintain a CONSISTENT size regardless of how many items are present — e.g. a product grid where you specifically want every card to look uniformly sized whether there are 2 items or 20, even if that means visible empty space in an incomplete row, for a more predictable/uniform visual rhythm. The choice depends entirely on whether "stretch to fill" or "stay consistent size" is the more desirable visual behavior for that specific incomplete-row scenario.
HowHow would you build a responsive card grid that shows a MINIMUM of 3 columns on desktop but wraps down to 1 column on mobile, without using media queries?
+
.card-grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(280px, 1fr)); gap: 20px; }
Set the `minmax()` minimum value (280px in this example) to whatever the SMALLEST comfortable card width is — the grid automatically computes how many 280px+ columns can fit in the current container width, WITHOUT any explicit breakpoints. On a wide desktop screen, this naturally computes to 3+ columns (since several 280px+ columns fit); on a narrow mobile screen, it naturally computes down to just 1 column (since only one 280px-wide column fits), all through the SAME single CSS rule adapting to the container's actual available width. The "minimum of 3 columns on desktop" requirement isn't a HARD constraint enforced by this pattern (it's driven by the min-width value relative to whatever the desktop viewport happens to be), but choosing an appropriate `minmax()` minimum value achieves that practical outcome for typical desktop widths without writing separate breakpoint-based rules.
WhatWhat does flex: 1 actually mean, as a shorthand?
+
`flex: 1` is shorthand for THREE separate properties: `flex-grow: 1` (this item should grow to consume any available leftover space, sharing it proportionally with other flex-grow items), `flex-shrink: 1` (this item is allowed to shrink if there isn't enough space, again sharing the shrinkage proportionally), and `flex-basis: 0%` (the item's STARTING size before growing/shrinking is calculated is treated as zero, essentially ignoring its natural content size as a starting point and just letting flex-grow determine the final size from scratch). This specific combination is why `flex: 1` on multiple sibling items typically results in them all becoming EQUAL width, regardless of how much content each one contains — because the `flex-basis: 0` means their natural content size isn't factored into the initial space calculation at all.
WhyWhy might a flex item with a very long, unbreakable string of text refuse to shrink below its content's width, even with flex-shrink set?
+
Flex items have an implicit DEFAULT `min-width: auto` (or `min-height: auto` for column direction) — this means, by default, a flex item won't shrink SMALLER than its own intrinsic content size, REGARDLESS of what `flex-shrink` value is set. For an item containing a long, unbreakable string (like a long URL or a word with no natural break points), this "intrinsic content size" can be quite large, effectively preventing the item from shrinking as much as you might expect, even with `flex-shrink: 1` explicitly set. The fix is to explicitly override this default with `min-width: 0` (or `overflow: hidden`, which also allows shrinking below content size by clipping/scrolling overflow) on the flex item, removing the implicit content-size floor and allowing it to genuinely shrink as far as `flex-shrink` and the available space dictate.
WhenWhen would you nest Flexbox INSIDE a Grid layout (or vice versa), rather than using just one or the other for the whole component?
+
This is actually the NORMAL, expected pattern for most real-world UIs, not an edge case — use Grid for the outer, structural, genuinely two-dimensional layout (like the overall page skeleton: header/sidebar/main/footer), and use Flexbox WITHIN individual grid cells or components for their internal one-dimensional alignment needs (like a card's internal header/body/footer stack, or a row of action buttons within that card). For example: a page uses Grid to lay out a sidebar and main content area; INSIDE the main content area, a card grid might itself use Grid again (for the 2D grid of cards); and INSIDE each individual card, Flexbox handles the simple one-dimensional stacking of the card's title, description, and button row. Neither tool is meant to handle an ENTIRE complex page single-handedly — they're complementary, and mixing them at different levels of nesting is standard, well-regarded practice.
HowHow would you build a centered modal that also handles a case where the modal's content is taller than the viewport (needs to scroll)?
+
.modal-overlay { position: fixed; inset: 0; background: rgba(0,0,0,0.5); display: flex; align-items: center; justify-content: center; padding: 20px; /* prevents the modal from touching the viewport edges */ overflow-y: auto; /* KEY — lets the OVERLAY itself scroll if content is too tall */ } .modal-box { max-height: 90vh; /* cap the modal's own height */ overflow-y: auto; /* let the MODAL's own content scroll internally too */ }
The key additions beyond basic centering are: `overflow-y: auto` on the OVERLAY itself, so that if the modal is taller than the viewport, the whole overlay (and the centered modal within it) can scroll rather than the modal being cut off with no way to reach its bottom content; and `max-height` + `overflow-y: auto` on the MODAL BOX itself, so very long content scrolls WITHIN the modal's own bounds rather than making the modal grow arbitrarily tall. Together, these ensure the modal remains usable regardless of viewport size or content length, rather than the basic centering-only solution breaking down for tall content.
