The Layers of a Design System

💡 A design system is NOT just a component library. It's a stack of layers — each one depends only on the layer BELOW it, which is what lets you change one without rewriting the rest. A strong interview answer names the layers explicitly before diving into any single one.
The dependency stack — each layer only knows about the one beneath it
L1
Primitive tokens
Raw values: a color palette, spacing scale, type scale, radii. Rarely used directly by components.
L2
Semantic & component tokens
Intent-named aliases (color-action-primary) and per-component hooks (button-bg) — this is where theming happens.
L3
Primitive components
Single-purpose, accessible building blocks with a stable public API.
L4
Patterns
Opinionated compositions of primitives — higher-level, higher-churn, more product-specific.

Design Tokens — The Single Source of Truth

💡 Tokens are platform-agnostic design decisions stored as DATA (usually JSON), then COMPILED into whatever each platform needs — CSS custom properties for web, Swift/Kotlin constants for native, even Figma variables. Storing them as data, not hand-written CSS, is what makes one design change propagate everywhere.
// tokens.json — the source of truth (e.g. Style Dictionary / W3C Design Tokens format) { "color": { "purple": { "500": { "$value": "#6a4fd1" } }, // primitive "action": { "primary": { "$value": "{color.purple.500}" } // semantic → references a primitive } }, "button": { "bg": { "$value": "{color.action.primary}" } // component token → references a semantic } } // Build step compiles that SAME source into multiple outputs: // → tokens.css :root { --color-action-primary: #6a4fd1; --button-bg: var(--color-action-primary); } // → tokens.ts export const colorActionPrimary = "#6a4fd1"; // → Tokens.swift static let actionPrimary = UIColor(hex: "#6a4fd1")
TierNaming principleWho references it
PrimitiveDescribes WHAT it is (purple-500, space-4)Only the semantic tier — never components directly
SemanticDescribes its PURPOSE (action-primary, surface-raised)Components and the component-token tier
ComponentDescribes ONE component's hook (button-bg, input-border)That single component — gives consumers a narrow, safe override point
⚠ Name tokens by PURPOSE, never by appearance, at the semantic tier. A token called color-blue that later becomes green is a lie baked into your API; color-action-primary survives a rebrand untouched. This naming rule is one of the highest-leverage decisions in the whole system.

Theming Architecture

Live: one component, tokens swapped at runtime — no component code changes
/* Components consume ONLY component/semantic tokens — never raw values */ .btn { background: var(--button-bg); border-radius: var(--button-radius); padding: var(--button-padding-y) var(--button-padding-x); } /* A theme is just a re-mapping of tokens at some scope */ [data-theme="dark"] { --color-surface: var(--color-gray-900); --color-text: var(--color-gray-50); } [data-brand="acme"] { --color-action-primary: var(--color-teal-500); }
Theming axisMechanismWhy it composes
Color mode (light/dark)Re-map semantic tokens under [data-theme] or prefers-color-schemeOrthogonal to brand — independent attribute
Brand / white-labelRe-map the primitive→semantic aliases under [data-brand]Independent of mode, so 2 modes × N brands needs no N×2 stylesheets
Density (compact/comfortable)Re-map spacing tokensSame component, different rhythm
Per-component overrideOverride a single component token at a local scopeNarrow, safe escape hatch — no need for CSS specificity wars
✓ The key architectural property: themes are DATA (token mappings), not CODE (separate component variants). Adding a new brand means adding a token file — zero component changes, zero new bugs in component logic.

Component API Decisions

🚨 A component's public API is a CONTRACT you can't easily take back. Every prop you ship becomes something some consumer depends on. API design is the hardest part of a design system precisely because the cost of a wrong decision is paid across EVERY consuming team, for years.
✗ Prop explosion (config-driven)
<Card title="Hi" subtitle="..." showHeader showFooter headerIcon={<Icon />} footerAlign="right" footerButtons={[...]} /> // every new need = a new prop // API grows forever, never shrinks
✓ Composition (compound components)
<Card> <Card.Header> <Icon /> Hi </Card.Header> <Card.Body>...</Card.Body> <Card.Footer>...</Card.Footer> </Card> // new layouts need ZERO new props
API decisionRecommended approachReasoning
VariantsA small closed set via an enum-like prop (variant="primary|secondary|ghost")Constrains consumers to the design language; boolean-flag combos (primary secondary) create impossible states
PolymorphismAn as / asChild prop to render a different element (link styled as button)Avoids duplicating components for the same look on different semantic elements
State ownershipSupport BOTH controlled (value/onChange) and uncontrolled (defaultValue)Simple cases stay simple; complex cases can take full control
Styling escape hatchForward className and style, plus ref forwardingConsumers WILL need one-off adjustments; refuse them and they fork or wrap you
Rest propsSpread remaining props onto the root elementLets consumers add data-*, aria-*, event handlers without you anticipating each one
AccessibilityBuild it IN by default; make the accessible path the easy pathIf a11y is opt-in, most consumers won't opt in
Behavior vs. stylingOptionally split into headless (behavior + a11y) and styled layersLets teams with different visual languages reuse the hard part — behavior
// A well-formed primitive: forwards ref, merges className, spreads rest, closed variant set const Button = forwardRef(function Button( { variant = "primary", size = "md", as: Comp = "button", className, ...rest }, ref ) { return ( <Comp ref={ref} className={cx("btn", `btn--${variant}`, `btn--${size}`, className)} {...rest} /> ); });
⚠ Rule of thumb: it's far easier to ADD an API surface later than to REMOVE one. Start narrow, ship the smallest API that serves real use cases, and grow it only when multiple teams demonstrate the same need.

Versioning & Release Strategy

What counts as a breaking change — semver for a component library
StrategyHow it worksTrade-off
Deprecate → warn → removeMark old API deprecated in a MINOR (with a console warning + docs), remove only in the next MAJORGives consumers a migration window; costs you maintaining both paths temporarily
CodemodsShip an automated script (jscodeshift) that rewrites consumers' code for each breaking changeDramatically lowers upgrade cost, which is what lets you actually ship majors
Changesets / conventional commitsContributors declare the bump type per change; tooling computes versions and changelogsKeeps versioning honest and automated instead of a release-day argument
Monorepo with independent package versionsTokens, components, icons published as separate packagesConsumers upgrade only what they need; adds cross-package compatibility matrix to manage
Canary / pre-release channelsPublish next or canary tags for early adoptersSurfaces real-world breakage before a stable release hits everyone
🎯 The mindset shift: in a design system, the product is not the code — it's the TRUST that consumers can upgrade safely. Every versioning practice (deprecation windows, codemods, honest semver) exists to protect that trust, because once teams fear upgrades, they pin old versions forever and the system fragments.

Common Gotchas & Interview Traps

  • ⚠️Naming tokens by appearance instead of purpose (color-blue, spacing-large) bakes a lie into your API the moment the design changes — semantic names survive rebrands, visual names don't.
  • ⚠️Components that reference primitive tokens directly skip the semantic layer — which silently breaks theming, because a theme re-maps semantic tokens and the component never looked at them.
  • ⚠️Prop explosion is the default failure mode — every one-off request adds "just one more prop," and the API only ever grows. Prefer composition and a deliberately small set of variants, and say no to bespoke props that serve one team.
  • ⚠️Boolean props for variants create impossible states — <Button primary secondary danger /> is valid TypeScript and meaningless design. A single variant union makes illegal states unrepresentable.
  • ⚠️Visual changes are breaking changes even if the API is untouched — a padding tweak can break a consumer's pixel-tuned layout or snapshot tests; semver tracks API, but consumers experience rendered output and DOM structure too.
  • ⚠️Renaming a design token is a breaking change — consumers who override or reference it directly (in CSS or JS) break; treat the token names as public API, with the same deprecation process as props.
  • ⚠️Shipping a barrel file without sideEffects: false can defeat tree-shaking — consumers import one button and bundle the entire library, which is exactly how design systems earn a reputation for bloat.
  • ⚠️Runtime CSS-in-JS complicates SSR and adds per-render cost — a real consideration with streaming SSR and React Server Components; many modern systems moved to build-time CSS extraction for this reason.
  • ⚠️Making accessibility opt-in means most consumers won't — the accessible behavior (focus management, roles, keyboard handling) must be the default, with the library doing the hard parts so consumers can't easily get them wrong.
  • ⚠️Over-abstracting too early — building a flexible "universal" component from one use case produces the wrong abstraction; wait until at least 2-3 real, independent use cases show the true shared shape (the "rule of three").

Interview Q&A — Why / What / When / How

🎯 This is a senior-level frontend system design question. Interviewers listen for trade-off reasoning and for the idea that a design system is a PRODUCT with consumers, a contract, and a trust model — not merely a folder of shared components.
WhatWhat's the difference between a component library and a design system?
+
A component library is CODE — a set of reusable UI components. A design system is the broader whole: design tokens (the shared decisions), the component library implementing them, usage guidelines and documentation, accessibility standards, contribution/governance processes, and the design-tool artifacts (like Figma libraries) kept in sync with code. The library is one deliverable OF the system. This distinction matters because a library with no tokens, docs, or governance tends to drift into inconsistency — teams fork components, bypass them, or use them differently, and you get the cost of a shared library without the consistency benefit that justified building it.
WhyWhy use three token tiers (primitive, semantic, component) instead of just one flat set of variables?
+
Each tier answers a different question and gives you a different kind of flexibility. Primitives hold the raw palette/scale — they exist so you have one place that defines "what colors and sizes exist." Semantic tokens map PURPOSE onto primitives (action-primary → purple-500) — this is the layer a THEME re-maps, so dark mode or a new brand changes the mapping without touching components. Component tokens (button-bg) give each component its own narrow override point, so a consumer can tweak one component without affecting the system, and without resorting to specificity hacks. With a flat set, a rebrand means hunting down every raw value, and a one-off override has no safe place to live — you'd either mutate a shared variable (affecting everything) or hardcode a value (escaping the system). The indirection feels like overhead on day one and pays off the first time you add a second theme.
WhenWhen is it right to build your own design system versus adopting an existing one (MUI, Radix, Chakra, shadcn/ui)?
+
Adopt (or build on top of) an existing one when your visual language is conventional, your team is small, or speed to market matters — you inherit years of accessibility and edge-case work for free. Build your own when you have a distinctive brand that off-the-shelf theming can't express, MULTIPLE products that need to share a coherent identity at scale, or hard requirements existing libraries can't meet (unusual platforms, strict bundle limits, deep white-labeling). The middle path is often the best: wrap or build on a HEADLESS foundation (Radix, React Aria) for behavior and accessibility — the hardest, most error-prone part — and own only the visual layer and tokens. That way you get brand control without re-solving focus management, keyboard interaction, and ARIA semantics for every component. Building from scratch is a long-term staffing commitment, not a one-time project, and that cost is what teams most often underestimate.
HowHow would you design the API for a Button component that must also work as a link, support icons, and avoid prop explosion?
+
1. Closed variant set: a single variant union (primary | secondary | ghost | danger) and a size union — not boolean flags — so impossible combinations can't be expressed.
2. Polymorphism: an as (or asChild) prop so the same styled component can render an <a> or a router Link, keeping correct semantics: navigation is a link, an action is a button.
3. Icons via composition, not config: accept children, and provide small slot helpers or startIcon/endIcon only if usage proves it common — resist iconPosition, iconSize, iconColor props.
4. Escape hatches: forwardRef, merge className, and spread rest props so consumers can add aria-*, data-*, and handlers without you predicting each.
5. Built-in a11y: default type="button" to avoid accidental form submits, support disabled correctly (and aria-disabled for links), and make focus styles non-optional.
6. Loading state: a loading prop that disables interaction and announces state, rather than every consumer hand-rolling a spinner. The guiding principle throughout is to keep the surface area small and extend only when multiple teams show the same need.
WhyWhy can a purely visual change (like adjusting button padding) be considered a breaking change?
+
Semantic versioning formally tracks the PROGRAMMATIC API, but consumers depend on the library's rendered output too. Changing padding alters the button's dimensions, which can cause text to wrap, push a layout past a breakpoint, misalign a form that was pixel-tuned around the old size, or break visual regression snapshot tests across every consuming app at once. Similarly, changing the DOM structure (adding a wrapper element) can break consumers' CSS selectors or test queries. Because the blast radius is every consumer, a mature design system treats noticeable visual and structural changes with the same care as API changes: communicate them clearly, gate larger ones behind a MAJOR (or an opt-in flag/theme), and provide a migration note. This is why visual regression testing matters — it makes unintended visual changes visible BEFORE release rather than discovered by downstream teams.
WhatWhat's a headless component, and what trade-off does it make versus a fully styled one?
+
A headless component provides BEHAVIOR and ACCESSIBILITY — state management, keyboard interaction, focus handling, ARIA attributes — but ships NO styling (or minimal), leaving rendering and visuals to the consumer. Libraries like Radix UI and React Aria work this way. The trade-off: consumers get full visual control and can reuse the genuinely hard part (correct dialogs, comboboxes, menus) under ANY design language, but they must supply the styling themselves, so there's more setup per component and more room for visual inconsistency if governance is weak. A fully styled component is faster to adopt and visually consistent out of the box, but is harder to re-theme beyond what its token/props surface allows. Many systems layer both: a headless core for behavior, plus a styled layer on top for the organization's own look.
WhenWhen would you ship a major version, and how do you make that upgrade survivable for consumers?
+
Ship a major when you must remove or change something consumers depend on — a prop rename, a changed default, a token rename, or a structural DOM change — and the old way can't coexist. But the goal is to make majors BORING. In the preceding minor releases, introduce the replacement alongside the old API and mark the old one deprecated with a console warning and a docs note, so consumers can migrate incrementally. For the major itself, publish a clear migration guide and ideally a CODEMOD that automates the mechanical rewrites. Release a pre-release/canary channel first so early adopters surface real breakage. Batch breaking changes into infrequent, predictable majors instead of trickling them out, since every major forces N teams to schedule upgrade work. If upgrading is painful, teams pin old versions and the system fragments — so the real measure of a good release process is how cheap it makes upgrading, not how clean the codebase is.
HowHow would you support light/dark mode AND multiple brands (white-labeling) without multiplying your CSS?
+
/* Treat mode and brand as INDEPENDENT axes, each re-mapping different token tiers */ /* Brand axis: re-maps primitive → semantic aliases */ [data-brand="acme"] { --color-action-primary: var(--color-teal-500); } [data-brand="globex"] { --color-action-primary: var(--color-orange-500); } /* Mode axis: re-maps surface/text semantics */ [data-theme="light"] { --color-surface: var(--color-gray-50); --color-text: var(--color-gray-900); } [data-theme="dark"] { --color-surface: var(--color-gray-900); --color-text: var(--color-gray-50); } <html data-brand="acme" data-theme="dark"> → any combination, zero extra CSS
Because components only reference semantic/component tokens, and because each axis is controlled by an independent attribute that re-maps a DIFFERENT set of tokens, the combinations compose automatically: 2 modes × N brands requires 2 + N small token blocks, not 2N full stylesheets. Adding a new brand is a single token block with no component changes. Two details matter in practice: set the attributes on the root early (a small inline script) to avoid a flash of the wrong theme before hydration, and verify contrast for EVERY brand/mode combination — the independence that makes this cheap also means a new brand color can silently fail accessibility contrast in dark mode.
