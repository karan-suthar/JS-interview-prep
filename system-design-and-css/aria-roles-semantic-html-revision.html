The First Rule of ARIA

🚨 "The First Rule of ARIA Use" (from the official W3C spec): if a NATIVE HTML element or attribute already has the semantics/behavior you need, USE IT instead of re-purposing a generic element with ARIA. ARIA is meant to fill GAPS, not replace what HTML already does well — native elements come with built-in keyboard support, focus handling, and screen reader behavior for FREE.
NeedUse this native element FIRSTNot this
A clickable action<button><div onclick> + role="button"
A navigational link<a href><span onclick> + role="link"
A checkbox<input type="checkbox"><div role="checkbox" aria-checked>
A heading<h1>–<h6><div role="heading" aria-level>
A list<ul>/<ol> + <li><div role="list"> + <div role="listitem">

The Accessibility Tree — Where ARIA Actually Applies

DOM tree vs. Accessibility tree — a PARALLEL structure screen readers actually use
💡 This is the single most important mental model for understanding ARIA: ARIA attributes NEVER change what's visually rendered, NEVER add keyboard behavior, and NEVER change functionality — they ONLY change what gets exposed in the accessibility tree (role, name, state, properties) that assistive technology reads from. This is exactly why role="button" alone doesn't add keyboard support — that's a DOM/JS behavior concern, entirely separate from the accessibility tree ARIA controls.

role="dialog" — The Full Modal Pattern

<div role="dialog" aria-modal="true" aria-labelledby="dialog-title" aria-describedby="dialog-desc" > <h2 id="dialog-title">Delete this item?</h2> <p id="dialog-desc">This action cannot be undone.</p> <button onClick={confirm}>Delete</button> <button onClick={cancel}>Cancel</button> </div>
Attribute/behaviorPurpose
role="dialog"Announces the element as a dialog to assistive technology
aria-modal="true"Tells assistive technology that content OUTSIDE the dialog is currently inert/unreachable — reinforces the "everything else is blocked" behavior
aria-labelledbyPoints to the element that serves as the dialog's ACCESSIBLE NAME (usually its heading)
aria-describedbyPoints to additional descriptive text, announced AFTER the name, giving more context
Focus moved INTO the dialog on openJS responsibility — focus must move to the dialog (or its first focusable element) when it opens, not handled by ARIA attributes alone
Focus trapped WITHIN the dialogJS responsibility — Tab/Shift+Tab should cycle only among the dialog's own focusable elements while open
Focus RESTORED on closeJS responsibility — focus should return to whatever element opened the dialog once it closes
Escape key closes the dialogJS responsibility — a standard, expected keyboard interaction for dialogs
🚨 role="dialog" and aria-modal alone do NOTHING for focus management — this is entirely your responsibility to implement in JavaScript. This is one of the most common accessibility bugs: a visually-correct modal with the right ARIA attributes, but focus never actually moves into it, gets trapped, or returns afterward — making it effectively unusable via keyboard/screen reader despite "having the right ARIA."
✓ The native <dialog> HTML element (with its `showModal()` method) now handles much of this — focus management, Escape-to-close, and the modal/inert background behavior — natively, in modern browsers, reducing how much of this needs to be hand-rolled with a plain `<div role="dialog">`.

aria-label vs aria-labelledby vs aria-describedby

// aria-label — a direct, inline STRING used as the accessible name <button aria-label="Close dialog">✕</button> // Needed here because the visible content is just an "✕" symbol — meaningless // to a screen reader without an explicit label describing its actual purpose // aria-labelledby — POINTS TO another element's text to use as the accessible name <h2 id="section-title">Account Settings</h2> <section aria-labelledby="section-title">...</section> // Reuses EXISTING visible text as the label — avoids duplicating the same string // aria-describedby — POINTS TO additional DESCRIPTION text (announced AFTER the name) <input id="password" aria-describedby="pw-hint" /> <span id="pw-hint">Must be at least 8 characters</span> // Provides SUPPLEMENTARY info, not a replacement for the field's actual label
AttributeProvidesUse when
aria-labelThe accessible NAME, as a literal stringNo visible text exists to serve as a label (icon-only buttons)
aria-labelledbyThe accessible NAME, referencing another element's textVisible text ALREADY exists elsewhere that should serve as the label — avoids duplicating it
aria-describedbySupplementary DESCRIPTION, announced after the nameExtra context/hint text exists that shouldn't replace the primary label, just supplement it
⚠ Priority order when multiple naming sources exist: aria-labelledby > aria-label > the element's own visible text content/native label. If aria-labelledby is present, it OVERRIDES aria-label entirely, which in turn overrides visible text — a common source of confusing bugs when multiple naming mechanisms are accidentally combined.
6

aria-live — Announcing Dynamic Content Changes

💡 aria-live tells a screen reader "watch this region — when its content CHANGES, announce the new content automatically," without the user needing to navigate to it. This solves a real problem: dynamic content (a form validation error, a toast notification, a live search result count) that appears WITHOUT a page reload or focus change would otherwise go completely unnoticed by a screen reader user.
// polite — announces AFTER the screen reader finishes its current speech (most common) <div aria-live="polite"> {statusMessage} // e.g. "3 results found" </div> // assertive — interrupts IMMEDIATELY, even mid-speech (use sparingly, for urgent info) <div aria-live="assertive"> {errorMessage} // e.g. "Error: session expired" </div> // off (default) — no automatic announcement at all
ValueBehaviorUse for
politeWaits for the screen reader to finish its current announcement firstNon-urgent updates: search result counts, "saved successfully" confirmations, chat messages
assertiveInterrupts whatever is currently being announced, immediatelyUrgent, time-sensitive info: critical errors, session timeouts — used SPARINGLY since frequent interruptions are disorienting
off (default)No automatic announcementThe default for all elements unless explicitly set otherwise
🚨 The aria-live region must EXIST in the DOM BEFORE the content change happens — adding `aria-live="polite"` to a brand-new element AT THE SAME TIME as inserting its content often fails to announce anything, since the screen reader wasn't yet "watching" that region. The common fix is rendering an EMPTY live region upfront, then updating its content afterward.

Common Gotchas & Interview Traps

  • ⚠️"No ARIA is better than bad ARIA" — a widely-cited accessibility principle; INCORRECT or conflicting ARIA can make an element LESS accessible than having no ARIA at all, since it actively misleads assistive technology rather than just lacking extra information.
  • ⚠️ARIA attributes never add keyboard behavior or functionality on their own — `role="button"` alone does NOT make an element focusable or activatable via Enter/Space; that requires separately adding `tabindex` and JavaScript keydown handling, a very common incomplete-implementation bug.
  • ⚠️role="dialog" + aria-modal do nothing for actual FOCUS MANAGEMENT — moving focus in, trapping it, and restoring it on close are all JavaScript responsibilities; a shockingly common real-world bug is a "correctly" ARIA-labeled modal that's still unusable via keyboard because focus was never actually managed.
  • ⚠️aria-hidden="true" hides an element from the accessibility tree, but does NOT hide it visually or prevent it from being focused — using it on a still-visible, still-focusable element creates a confusing state where sighted keyboard users can tab to something a screen reader user is told doesn't exist; always pair it with removing focusability if the element is meant to be fully hidden.
  • ⚠️An aria-live region added to the DOM at the SAME TIME as its content often fails to announce — the region needs to already exist and be "observed" before the content change occurs; render it empty first, then update it.
  • ⚠️aria-labelledby takes priority over aria-label, which takes priority over visible text content — accidentally including more than one of these naming mechanisms can produce a confusingly different accessible name than what's visually displayed.
  • ⚠️Using assertive aria-live regions too liberally is a real anti-pattern — frequent interruptions are disorienting for screen reader users; reserve `assertive` genuinely for urgent, time-sensitive information, defaulting to `polite` for most dynamic updates.
  • ⚠️A div styled to LOOK like a heading (large, bold text) is NOT a heading to assistive technology unless it actually IS a semantic heading element or has role="heading" + aria-level — visual styling and semantic meaning are completely independent; screen reader users often navigate BY heading structure, so this gap can make a page significantly harder to navigate even though it "looks" properly structured.
  • ⚠️The native <dialog> element's showModal() method handles a lot of what used to require extensive manual ARIA + JS work — including basic focus trapping and Escape-to-close — current browser support is strong, making it worth mentioning as the modern-first option, with hand-rolled `role="dialog"` reserved for cases needing behavior the native element doesn't fully cover.
  • ⚠️Testing accessibility by SIGHT alone (does it "look" right) is insufficient — genuinely verifying ARIA/semantic correctness requires actually using a real screen reader (VoiceOver, NVDA, JAWS) or automated tools (axe DevTools, Lighthouse's accessibility audit) alongside actual keyboard-only navigation testing, not just visual inspection.

Interview Q&A — Why / What / When / How

🎯 Accessibility questions increasingly appear in frontend interviews as a core competency, not a niche specialty — precise, mechanism-level answers (not just "always use semantic HTML") demonstrate genuine understanding.
WhatWhat's the difference between using a real <button> element and a <div> with role="button"?
+
A real `<button>` gets FOUR things automatically, built into the browser: keyboard focusability (it's in the natural Tab order), activation via BOTH Enter and Space keys, correct announcement as "button" by screen readers, and native `disabled` state handling. A `<div role="button">` gets NONE of these automatically — `role="button"` alone only affects the ACCESSIBILITY TREE, telling screen readers to announce it as a button, but does nothing for keyboard focus or activation. To fully replicate a real button's behavior on a div, you'd need to manually add `tabindex="0"` (for focusability) AND a keydown handler checking for Enter/Space (for activation) — three separate pieces of manual work to match what `<button>` gives for free.
WhyWhy doesn't adding role="dialog" and aria-modal="true" to a modal automatically make it keyboard-accessible?
+
ARIA attributes ONLY affect the accessibility tree — the parallel structure screen readers and other assistive technology read from — they never change actual DOM behavior, focus management, or keyboard event handling. `role="dialog"` tells assistive technology "announce this as a dialog," and `aria-modal="true"` tells it "treat content outside this as currently inert" — but neither of these attributes actually MOVES keyboard focus into the dialog when it opens, TRAPS focus within it while it's open, or RESTORES focus to the triggering element when it closes. All of that is genuine JavaScript/DOM manipulation work that has to be implemented separately — ARIA describes what something IS and its current STATE to assistive technology, but implementing the actual interactive BEHAVIOR remains entirely the developer's responsibility.
WhenWhen would you use aria-label instead of aria-labelledby for naming an element?
+
Use `aria-label` when there's NO existing visible text on the page that could serve as the element's name — the classic example is an icon-only button (like a "✕" close button, or a magnifying-glass search icon button) where the VISUAL content gives a sighted user enough context, but provides literally no meaningful text for a screen reader to announce. In this case, `aria-label="Close dialog"` directly supplies the missing accessible name as a string. Use `aria-labelledby` instead when relevant visible text ALREADY EXISTS elsewhere on the page (like a section's heading) that should serve as the name for a DIFFERENT element (like the section container itself) — referencing that existing text avoids awkwardly duplicating the same string in two places, and keeps the two in sync if the visible heading text is ever updated.
HowHow would you implement an aria-live region for a search results count, and what mistake would you specifically avoid?
+
// ✓ The live region EXISTS from the start, initially empty or with placeholder text <div aria-live="polite" className="sr-only"> {resultCount !== null ? `${resultCount} results found` : ""} </div> // This same <div> stays MOUNTED throughout — only its TEXT CONTENT changes // as searches complete, which is what triggers the announcement
The key mistake to AVOID is creating the live-region element and populating it with content AT THE SAME TIME (e.g. conditionally rendering the whole `<div aria-live>` element only once results exist) — screen readers need the element to already be present and being "observed" in the accessibility tree BEFORE the content change happens, in order to detect and announce that change. The correct approach keeps the live region MOUNTED and present in the DOM from the start (even if empty/hidden visually via a "screen-reader-only" CSS class), and only updates its inner text content as results come in — this way the screen reader reliably detects and announces the change, since it was already watching that specific region for updates.
WhatWhat's the accessibility tree, and how does it relate to ARIA attributes?
+
The accessibility tree is a SEPARATE, parallel structure the browser builds alongside the DOM, specifically containing the information assistive technology (screen readers, voice control software, etc.) actually reads from — each node has a computed ROLE, NAME, and various STATES/PROPERTIES. Native HTML elements get sensible accessibility tree entries automatically (a `<button>` automatically gets role="button" and its text content as its name); ARIA attributes exist specifically to MODIFY or SUPPLEMENT entries in this tree when native HTML alone doesn't fully express what's needed — adding a role, overriding a name (via aria-label), or exposing additional state (like aria-expanded on a collapsible section). Critically, ARIA attributes ONLY affect this tree — they never touch the DOM's visual rendering or its actual interactive/keyboard behavior, which is why ARIA alone is never sufit to make a custom interactive widget fully accessible without accompanying JavaScript behavior.
WhyWhy is "no ARIA is better than bad ARIA" a genuinely important principle, rather than just a nice-sounding guideline?
+
Without ANY ARIA, a plain, unstyled `<div>` is simply announced as generic, unstructured content — not ideal, but at least NOT actively MISLEADING; a screen reader user correctly understands they're looking at unstructured content and can navigate accordingly. Incorrect or conflicting ARIA, however, can make assistive technology CONFIDENTLY announce something FALSE — e.g. `role="button"` on an element that isn't actually keyboard-operable tells a screen reader user "this IS a functioning button," leading them to expect button-like keyboard behavior that doesn't actually exist, creating genuine confusion and a WORSE experience than if no role had been declared at all (where the ambiguity might at least prompt more cautious exploration). Bad ARIA actively lies to assistive technology and its users about what an element actually does, which is a strictly worse outcome than simply providing no extra information.
WhenWhen is using ARIA roles genuinely necessary, rather than just a substitute for semantic HTML someone was too lazy to use?
+
ARIA roles are genuinely necessary specifically when building a CUSTOM WIDGET pattern that has NO native HTML equivalent at all — tabbed interfaces (`tablist`/`tab`/`tabpanel`), tooltips (`tooltip`), comboboxes/autocomplete widgets, and tree views are classic examples where HTML simply doesn't provide a corresponding native element, so ARIA roles are the ONLY way to expose the correct semantics to assistive technology. It's ALSO legitimately necessary for expressing DYNAMIC STATE that native HTML doesn't capture — e.g. `aria-expanded` on a collapsible section's toggle button, or `aria-selected` within a custom tab interface — since these states genuinely need to be communicated regardless of the underlying element. ARIA becomes a poor substitute specifically when it's used to RE-CREATE something HTML already provides natively (like `role="button"` on a div, instead of just using `<button>`) — the distinction is whether ARIA is filling a genuine gap in HTML's native vocabulary, or working around a native element that could have been used directly.
HowHow would you fully audit and fix a custom dropdown/select component to make it genuinely accessible?
+
1. Check whether a native `<select>` could actually satisfy the design requirements first — per the "first rule of ARIA," this eliminates almost ALL of the following manual work if it's a viable option.
2. If a genuinely custom widget is required, apply the correct ARIA pattern — typically `role="listbox"` on the options container, `role="option"` on each option, with `aria-selected` reflecting the current selection, and the trigger button using `aria-haspopup="listbox"` and `aria-expanded` reflecting open/closed state.
3. Implement full KEYBOARD support manually — Arrow keys to move between options, Enter/Space to select, Escape to close, Home/End to jump to first/last option — none of this comes for free with ARIA roles alone.
4. Manage FOCUS correctly — typically keeping focus on the trigger button while using `aria-activedescendant` to indicate the currently highlighted option (rather than moving actual DOM focus to each option), a common pattern for listbox-style widgets.
5. Test with an ACTUAL screen reader (not just visual inspection) to confirm the selected value, available options, and state changes are all announced correctly and match the sighted, mouse-driven experience.
