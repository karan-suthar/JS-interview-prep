Choosing the Tool Before You Write Code

💡 In a live layout challenge, the first 30 seconds matter most: name the layout's dimensionality out loud. If it has to line up in rows AND columns at once, reach for Grid. If it's a single line of items distributing space, reach for Flexbox. Then nest — outer structure in Grid, inner alignment in Flexbox.

Challenge 1 — The Holy Grail Layout

💡 The "holy grail": a header and footer spanning the full width, with three columns between them — fixed-width left nav, flexible center content, fixed-width right sidebar — where the footer stays at the bottom even with little content, and the center column comes FIRST in source order for accessibility/SEO. It was famously painful with floats; with Grid it's nearly declarative.

<!-- Source order: main first (best for screen readers / reading order) --> <div class="page"> <header>...</header> <main>...</main> <nav>...</nav> <aside>...</aside> <footer>...</footer> </div> /* ── The whole layout: Grid with named areas ── */ .page { display: grid; min-height: 100dvh; /* footer sticks to bottom */ grid-template-columns: 200px 1fr 200px; grid-template-rows: auto 1fr auto; /* middle row absorbs the slack */ grid-template-areas: "header header header" "nav main aside" "footer footer footer"; } header { grid-area: header; } nav { grid-area: nav; } main { grid-area: main; min-width: 0; } /* let content shrink */ aside { grid-area: aside; } footer { grid-area: footer; } /* ── Responsive: just redefine the areas, no HTML changes ── */ @media (max-width: 700px) { .page { grid-template-columns: 1fr; grid-template-rows: auto 1fr auto auto auto; grid-template-areas: "header" "main" "nav" "aside" "footer"; } }
✗ Common mistake
.page { display: grid; height: 100vh; /* no min-height, no 1fr row */ /* long content overflows; mobile URL bar breaks 100vh */ }
✓ Robust
.page { display: grid; min-height: 100dvh; grid-template-rows: auto 1fr auto; /* grows with content, footer pinned when content is short */ }
/* ── Flexbox alternative (the classic "sticky footer" version) ── */ .page { display: flex; flex-direction: column; min-height: 100dvh; } .body { display: flex; flex: 1; } /* the 3-column row grows to fill */ nav, aside { flex: 0 0 200px; } /* fixed width, no grow, no shrink */ main { flex: 1; min-width: 0; order: 0; } nav { order: -1; } /* visually first, source order unchanged */ /* Works, but needs an extra wrapper and `order` for the source-order trick. Grid areas express the same idea with less structure. */

🚨 The classic dashboard bug: a wide table or chart inside a grid/flex child blows out the layout and creates page-level horizontal scroll. The cause is the implicit min-width: auto on grid and flex items, which refuses to shrink below content width. The fix is min-width: 0 (or overflow: auto) on the item that contains the wide content — memorize this one.

Challenge 3 — Masonry (the Hard One)

🚨 Neither Grid nor Flexbox natively does masonry (Pinterest-style columns where each tile sits directly under the shortest column above it, with no row alignment). Both are fundamentally track- or line-based, so every "grid/flex-only" solution is a workaround with a trade-off. Saying this out loud — then picking an approach and naming its cost — is the winning answer.

Common Gotchas & Interview Traps

  • ⚠️Claiming Grid or Flexbox "does masonry" is the trap in this challenge. Neither does natively; every grid/flex-only version is a workaround with a stated trade-off. Say so up front.
  • ⚠️1fr is not truly "equal share" — it means minmax(auto, 1fr), so a track with wide content can't shrink below it. Use minmax(0, 1fr) when you need genuinely equal columns.
  • ⚠️The implicit min-width: auto on grid/flex items is behind most "my layout overflows" bugs; wide tables, code blocks, and long unbroken strings all trigger it.
  • ⚠️Rows in grid-template-areas must be rectangular and consistent — each string needs the same number of cells, and a named area must form a single rectangle (no L-shapes), or the entire declaration is invalid and silently ignored.
  • ⚠️Reordering with order or grid placement changes visuals but NOT tab/reading order — fine for cosmetic moves, an accessibility problem if the visual sequence stops matching the DOM sequence for keyboard and screen-reader users.
  • ⚠️grid-auto-flow: dense can reorder items visually out of source order to fill holes — convenient for masonry and galleries, but it can confuse keyboard focus order, so use it only where order isn't meaningful.
  • ⚠️Flex column-wrap masonry only wraps when the container has a constrained height — without it the column simply grows forever and nothing wraps, which looks like "flexbox is broken."
  • ⚠️Percentage heights need a definite parent height — a height: 100% child of an auto-height parent collapses, a frequent surprise when building full-height shells; prefer grid rows with 1fr over percentage chains.
  • ⚠️Use 100dvh rather than 100vh for full-height shells on mobile — 100vh ignores the collapsing browser toolbar and can cause content to sit behind it or create double scrollbars.
  • ⚠️Animating grid-template-columns works in current browsers (handy for a collapsing sidebar), but it triggers layout every frame — fine for a small shell, wasteful for large, complex content areas; consider transforming an overlay for heavier layouts.

Interview Q&A — Why / What / When / How

🎯 Layout challenges are graded on process: choosing the right tool, explaining trade-offs, handling edge cases (overflow, mobile, source order), and being honest about what CSS can't do cleanly.
WhatWhat makes the "holy grail" layout hard, and how does Grid simplify it?
+
The requirements pull against each other: full-width header and footer, three columns between them with fixed-width sides and a fluid center, a footer that stays at the bottom even with little content, and ideally the main content first in source order. With floats or tables this needed hacks like negative margins and clearfixes. Grid expresses it almost directly: grid-template-areas names the regions, grid-template-columns: 200px 1fr 200px sets fixed-fluid-fixed tracks, and grid-template-rows: auto 1fr auto with min-height: 100dvh makes the middle row absorb extra space so the footer sinks to the bottom. Source order is independent of visual placement because each element is positioned by grid-area, and responsiveness is just redefining the area template in a media query without touching the HTML.
WhyWhy does a wide table inside a grid or flex child break the layout, and how do you fix it?
+
Grid and flex items default to min-width: auto, which means "never shrink below your content's minimum size." A wide table, a long code line, or an unbroken URL has a large minimum content width, so the item refuses to shrink and pushes the track (and sometimes the whole page) wider than the viewport, creating unwanted horizontal scroll. The fix is to override that floor on the item containing the wide content: min-width: 0 lets it shrink to the track's width, and adding overflow: auto to the wrapper makes the table scroll within its own box instead of stretching the layout. For grid tracks specifically, minmax(0, 1fr) removes the same implicit minimum from the track definition. It's one of the highest-frequency real-world layout bugs.
WhenWhen would you choose Flexbox over Grid for part of a dashboard?
+
Whenever the job is one-dimensional: distributing items along a single line and aligning them on the cross axis. Examples inside a dashboard: a card header with a title on the left and actions on the right (justify-content: space-between), a toolbar of buttons that wraps, a sidebar nav list stacked vertically with a footer pinned to the bottom (margin-top: auto), or a card laid out as a column so its footer aligns across equal-height siblings. Grid is the better choice for the outer structure and for the card collection, where rows and columns both matter. In practice you nest them: Grid for the shell and the card grid, Flexbox for the alignment inside each cell. The decision criterion is whether you need to control placement on two axes at once.
HowHow would you build a masonry layout using only Grid or Flexbox, and what are the limits?
+
First I'd state that neither does masonry natively, so I'm choosing a workaround and its trade-off. Grid approach: define columns with repeat(auto-fill, minmax(220px, 1fr)), set a small grid-auto-rows (say 10px) as a row unit, enable grid-auto-flow: dense, and give each tile grid-row: span N where N approximates its height in row units. This keeps a natural left-to-right order and a responsive column count, but needs known or measured heights — from fixed aspect ratios, data, or a small JS pass computing Math.ceil((height + gap) / (rowUnit + gap)). Flex approach: flex-flow: column wrap in a container with a fixed height and tile widths set to about a third; items flow down then wrap. Simple, but it needs a hand-picked container height and the order is column-major. For true shortest-column balancing, you'd use JS to distribute items into column wrappers, or progressively enhance with native masonry behind @supports once support is verified. I'd pick the grid-span version when heights are predictable.
WhatWhat's the difference between auto-fit and auto-fill, and when does it matter for a card grid?
+
Both create as many columns as fit given the minmax() minimum. The difference appears only when there are fewer items than the available columns. auto-fill keeps the empty columns as invisible tracks, so existing cards stay at their natural size and leave blank space on the right. auto-fit collapses the empty tracks to zero, so the existing cards stretch (via the 1fr maximum) to fill the full row. With enough items to fill complete rows, they behave identically. Choose auto-fit when you want a short list to expand across the container, and auto-fill when you want consistent tile width regardless of how many items there are — e.g. a product grid that should keep a stable visual rhythm.
WhyWhy can visually reordering layout with order or grid placement be an accessibility problem?
+
Keyboard tab order and screen-reader reading order follow the DOM, not the visual arrangement. If CSS places the sidebar visually first while it comes later in the DOM (or dense backfilling shuffles tiles), sighted keyboard users see focus jump unpredictably around the screen, and screen-reader users hear content in a different order than it appears. That mismatch violates WCAG guidance on meaningful sequence and focus order. The safe pattern is to make the DOM order the logical reading order, and use CSS reordering only for cosmetic changes that don't alter meaning — for example, keeping main first in the source (a good thing for screen readers) while placing it in the center column via areas is generally fine because the sequence of content still makes sense. When order and visuals genuinely diverge in a way that matters, restructure the markup instead of papering over it with CSS.
WhenWhen would you collapse a sidebar by animating grid-template-columns, versus another technique?
+
Animating grid-template-columns from, say, 240px 1fr to 64px 1fr is elegant for an app shell: one declaration controls the whole layout, the content column reflows automatically, and modern browsers interpolate track sizes smoothly. It's a good fit when the shell is relatively lightweight and the collapse is occasional. The cost is that it triggers layout on every frame, so with a heavy content area (large tables, charts) the animation can drop frames. In that case, alternatives are to animate a transform on an overlay sidebar (composite-only, no reflow) and let the content shift instantly, or to toggle the width without animation. Also consider prefers-reduced-motion, and make sure the collapsed state keeps nav items accessible via labels or tooltips rather than icon-only ambiguity.
HowHow would you debug a layout where your grid areas aren't applying at all?
+
1. Open DevTools and enable the Grid overlay with area names — if the template is invalid, the overlay shows no areas, which immediately tells you the declaration was dropped.
2. Check grid-template-areas for ragged rows: every string must have the same number of cells, and each named area must form a single rectangle (an L-shape invalidates the whole property).
3. Verify names match exactly (case-sensitive) between the template strings and the grid-area values on the children; a typo silently creates an implicit extra track instead of erroring.
4. Confirm display: grid is on the right element — areas apply to DIRECT children only, so an extra wrapper div breaks placement.
5. Ensure grid-template-columns/rows counts agree with the template's dimensions, and check whether a later rule or a media query is overriding the template.
6. If content overflows, look for the implicit min-width: auto trap and try minmax(0, 1fr) or min-width: 0.
