Defining & Using Custom Properties

💡 A CSS custom property (informally called a "CSS variable") is defined with a name starting with TWO dashes (--my-variable), and READ using the var() function. Unlike Sass/LESS variables, these are REAL, LIVE values the browser evaluates at RUNTIME, not compile-time text substitutions.
/* Defining custom properties — typically on :root for global availability */ :root { --primary-color: #6a4fd1; --spacing-unit: 8px; --border-radius: 6px; } /* Using them with var() */ .button { background: var(--primary-color); padding: var(--spacing-unit) calc(var(--spacing-unit) * 2); border-radius: var(--border-radius); }
AspectDetail
NamingMust start with `--`; case-sensitive; can contain letters, digits, hyphens, underscores
Where definedAny selector — `:root` is common for GLOBAL tokens, but any element can define/override its own
Value typeEssentially ANY valid CSS token sequence — colors, lengths, even partial values, unlike typed variables in other languages
Accessible from JSYes — `element.style.getPropertyValue('--x')` and `element.style.setProperty('--x', value)`

Cascade & Inheritance — Custom Properties Are Different

⚠ Custom properties INHERIT BY DEFAULT — regardless of what property they're eventually USED in. This is a genuinely different rule from normal CSS properties (recall: most box-model properties like `margin`/`padding` do NOT inherit by default) — custom properties always flow down the DOM tree unless explicitly overridden by a descendant.
Inheritance flowing down, with a scoped override along the way
💡 This inheritance behavior is EXACTLY what makes custom properties so powerful for theming and scoped component overrides — a single override at any point in the tree cascades down to every descendant automatically, without needing to explicitly re-declare it at each level.
3

Overriding & Scoping

/* Global default */ :root { --button-bg: #6a4fd1; } /* Component-level SCOPED override — only affects .danger-zone and its descendants */ .danger-zone { --button-bg: #ff4444; } .button { background: var(--button-bg); } /* automatically picks up whichever scope it's in */ /* Media-query-based override — responsive design tokens */ :root { --container-padding: 16px; } @media (min-width: 768px) { :root { --container-padding: 32px; } } /* Every element using var(--container-padding) automatically adapts — no need to write separate responsive rules for EACH consuming element */
✓ This is the core theming mechanism: re-declaring the SAME custom property name at a more specific scope (a class, a media query, a data attribute selector) OVERRIDES it for that scope and everything nested within it — every consuming rule using `var()` automatically reflects the new value, with zero changes needed at the point of USE.
4

Fallback Values in var()

/* var() accepts a SECOND argument — used if the custom property is UNDEFINED */ .button { color: var(--button-text-color, white); /* falls back to white if --button-text-color isn't set */ } /* Fallbacks can even reference ANOTHER custom property */ .button { color: var(--button-text-color, var(--default-text-color, black)); } // Tries --button-text-color first, then --default-text-color, then finally "black"
⚠ The fallback only activates if the custom property is genuinely UNDEFINED (never declared anywhere in scope) — NOT if it's declared but happens to be an INVALID value for that context; an invalid value instead makes the property fall back to its normal `initial`/`inherited` value entirely (see gotchas).

The Design Tokens Pattern — Primitive vs Semantic

💡 Mature design systems typically use TWO layers of custom properties: primitive tokens (raw values — a color palette, a spacing scale) and semantic tokens (meaningful NAMES that reference a primitive token for a specific PURPOSE). This indirection is what makes large-scale theming maintainable.
/* ── Layer 1: Primitive tokens — the raw palette, rarely referenced directly ── */ :root { --color-purple-500: #6a4fd1; --color-red-500: #ff4444; --color-gray-900: #1a1a1a; --color-gray-50: #f5f5f5; } /* ── Layer 2: Semantic tokens — named by PURPOSE, referenced throughout the app ── */ :root { --color-brand: var(--color-purple-500); --color-danger: var(--color-red-500); --color-text-primary: var(--color-gray-900); --color-surface: var(--color-gray-50); } /* Components reference SEMANTIC tokens — never the raw primitives directly */ .alert-danger { background: var(--color-danger); } .button-primary { background: var(--color-brand); }
LayerPurposeExample
Primitive tokensThe raw, literal design values — a color scale, spacing scale, font sizes--color-purple-500: #6a4fd1
Semantic tokensNamed by INTENT/PURPOSE, pointing to a primitive — this is what components actually consume--color-brand: var(--color-purple-500)
✓ Why this indirection matters: if the BRAND color needs to change, you update ONE semantic token's definition (`--color-brand`) — every component using `--color-brand` updates automatically, without ever needing to know or care WHICH primitive color it currently points to. This decoupling is the entire point of a design token system.

Custom Properties vs Sass/LESS Variables

AspectCSS Custom PropertiesSass/LESS Variables
When resolvedRUNTIME — in the browser, liveCOMPILE TIME — before the browser ever sees the CSS
Can be changed via JavaScript✓ Yes — genuinely dynamic✗ No — already baked into static output CSS
Responds to media queries naturally✓ Yes — redefine the property inside the query✗ No — would require duplicating entire rule blocks
Inherits through the DOM / cascade✓ Yes✗ No — it's just textual substitution, no runtime concept of "cascade" at all

🎯 The key distinction to articulate: Sass variables are a BUILD-TIME text substitution tool — by the time the browser sees the CSS, they're already gone, replaced with literal values. CSS custom properties are REAL runtime values the browser tracks and can react to dynamically — which is exactly why only custom properties can power live theme switching, responsive tokens, and JS-driven style updates.
8

@property — Typed Custom Properties (Advanced)

/* Registering a custom property with an explicit TYPE and default */ @property --rotation-angle { syntax: '<angle>'; /* declares this MUST be an angle value */ inherits: false; initial-value: 0deg; } .spinner { transform: rotate(var(--rotation-angle)); transition: --rotation-angle 0.3s; /* SMOOTHLY animates — only possible because it's TYPED */ }
💡 Normal (untyped) custom properties are treated as plain TEXT by the browser, which means they CANNOT be smoothly ANIMATED/TRANSITIONED — the browser has no idea how to interpolate between two arbitrary token sequences. @property lets you register a custom property with an actual TYPE (angle, color, length, etc.), which enables genuine smooth animation/transition between values, plus better validation.

Common Gotchas & Interview Traps

  • ⚠️Custom properties inherit by default, unlike most regular CSS properties — this is precisely the opposite of the DEFAULT non-inheritance behavior for things like margin/padding covered in the specificity/cascade topic; a common point of confusion when the two topics are studied close together.
  • ⚠️An INVALID value for a custom property does NOT trigger the var() fallback — the fallback only applies if the property is UNDEFINED entirely; if it's defined but produces an invalid value in the context it's used (e.g. a custom property holding "not-a-color" used in a color context), the property instead becomes its "guaranteed-invalid value," typically resulting in the initial or inherited value for that property — a subtle, frequently misunderstood distinction.
  • ⚠️Untyped custom properties (the normal kind) CANNOT be smoothly animated/transitioned — the browser treats their value as opaque text, with no inherent understanding of how to interpolate between two values; `@property` with an explicit `syntax` is REQUIRED to enable smooth animation of a custom property's value.
  • ⚠️Custom properties are NOT available in media query CONDITIONS themselves (e.g. you can't write `@media (min-width: var(--breakpoint))`) — they can only be used as VALUES within declarations, not as part of the media query's own condition logic (though this is evolving with newer CSS features like container queries and environment variables in some contexts).
  • ⚠️Custom properties defined on :root are technically defined on the <html> element — `:root` is just a slightly higher-specificity way of selecting `html`; functionally near-identical for most purposes, but worth knowing precisely what it targets if asked.
  • ⚠️calc() combined with custom properties is extremely powerful but has real limits — you can't easily change UNITS mid-calculation (e.g. can't cleanly combine a unitless custom property with `px` without deliberate multiplication), and complex nested calc() expressions can occasionally hit browser parsing/performance edge cases in very deeply nested scenarios.
  • ⚠️JavaScript reading a custom property via getComputedStyle returns it as a STRING, always — including surrounding whitespace sometimes; numeric custom properties intended for calculation in JS often need explicit `.trim()` and `parseFloat()`/`parseInt()` handling, unlike a native, already-typed CSSOM property.
  • ⚠️Overriding a custom property inside a shadow DOM boundary (Web Components) doesn't automatically pierce through unless the CONSUMING styles are also inside/crossing that boundary appropriately — custom properties DO cross shadow DOM boundaries (unlike most CSS), but the exact inheritance/scoping behavior across component boundaries is a more advanced nuance worth being aware of if working with Web Components specifically.
  • ⚠️Overusing DEEPLY nested custom property indirection (a token referencing a token referencing a token, many layers deep) can make debugging "where does this value actually come from" genuinely harder — the two-layer primitive/semantic pattern (Section 6) is a deliberately CONSTRAINED, well-understood depth; going much deeper without good reason trades maintainability for cleverness.
  • ⚠️A custom property with NO fallback and NO definition anywhere in scope resolves to nothing usable — `var(--undefined-property)` with no fallback effectively makes the declaration invalid, again falling back to the property's initial/inherited value, NOT to some kind of empty string or silent no-op as might be intuitively assumed.

Interview Q&A — Why / What / When / How

🎯 Custom properties are a favorite modern CSS topic because they connect directly to real, practical design-system and theming work — strong answers demonstrate you've actually BUILT something with them, not just memorized the syntax.
WhatWhat's the fundamental difference between a CSS custom property and a Sass/LESS variable?
+
A Sass/LESS variable is resolved at COMPILE TIME — before the browser ever sees the resulting CSS, the preprocessor has already substituted every variable reference with its literal value, producing plain, static CSS with no trace of the original variable. A CSS custom property is a genuine RUNTIME value that the browser itself tracks and resolves live, in the actual rendered page — it can be read and changed via JavaScript, can respond to media queries by simply being redefined within them, and participates in the normal CSS cascade/inheritance mechanism. This runtime nature is what makes custom properties uniquely capable of things Sass variables fundamentally cannot do: live theme switching without a page reload, JS-driven dynamic styling, and per-component scoped overrides that adapt automatically based on DOM context.
WhyWhy do custom properties inherit by default, when most other CSS properties (like margin or padding) do not?
+
Custom properties were specifically designed to function as CONFIGURATION VALUES/TOKENS that flow through a component tree — the entire theming use case (Section 5) depends on being able to set a value ONCE at some ancestor level and have it automatically apply to every descendant that references it via `var()`, without needing to explicitly re-declare it at every single nested level. If custom properties did NOT inherit by default, achieving this same theming behavior would require either duplicating the property declaration at every element that needs it, or using `inherit` explicitly everywhere — defeating much of their practical usefulness. Regular CSS properties like `margin` don't inherit by default because each element's box-model spacing is usually independently meaningful to THAT element, not something that should automatically propagate from a parent — a fundamentally different use case from configuration/token values.
WhenWhen would you reach for the two-layer primitive/semantic token pattern instead of just defining colors directly wherever needed?
+
Specifically once a project grows beyond a small, single-purpose page into something with a genuine DESIGN SYSTEM used across multiple components/pages, especially if MULTIPLE THEMES (light/dark, brand variations, white-labeling) are a real requirement — the indirection pays off exactly when you need to change what a semantic concept like "danger color" or "brand color" MEANS, without hunting down and updating every individual component that happens to use that specific raw color value. For a small, one-off project with no theming needs and a handful of components, directly using primitive values might be simpler and perfectly adequate — the two-layer pattern's benefit scales with the SIZE and THEMING complexity of the project, and introducing it prematurely for a trivial project can be unnecessary overhead.
HowHow would you implement a light/dark theme toggle using CSS custom properties, without requiring a page reload or re-rendering the entire component tree?
+
/* 1. Define semantic tokens at :root for the DEFAULT (light) theme */ :root { --bg-color: #ffffff; --text-color: #1a1a1a; } /* 2. Override the SAME token names under a data attribute / class for dark mode */ [data-theme="dark"] { --bg-color: #1a1a2e; --text-color: #e8eaf0; } /* 3. EVERY component throughout the app just references the semantic tokens */ body { background: var(--bg-color); color: var(--text-color); } /* 4. JS toggling is a SINGLE, trivial operation */ document.documentElement.setAttribute('data-theme', currentTheme === 'light' ? 'dark' : 'light');
Because EVERY component throughout the app references the SAME small set of semantic token names (never hardcoded literal colors), and because custom properties naturally CASCADE/inherit down from the point of the override, changing just ONE attribute on the root `<html>` element instantly updates every themed value across the entire page simultaneously — the browser re-resolves all the `var()` references and repaints, with ZERO JavaScript needing to know about or touch individual component styles, and no component tree re-render required at all (this is pure CSS re-evaluation, not a React/framework re-render).
WhatWhat happens if you use var(--some-property) and --some-property is never defined anywhere, with no fallback provided?
+
The `var()` reference becomes what the spec calls a "guaranteed-invalid value" for that declaration — this does NOT crash anything or throw an error, but it means the specific CSS DECLARATION using that `var()` is treated as invalid and essentially ignored, causing the property to fall back to its normal `initial` value (for non-inherited properties) or its `inherited` value from the parent (for properties that naturally inherit) — NOT to some empty/blank state as might be intuitively expected. For example, `color: var(--undefined-color);` with no fallback and no definition anywhere would result in the element's `color` falling back to whatever it would normally be WITHOUT that declaration at all (typically inherited from its parent, since `color` naturally inherits).
WhyWhy can't a normal (untyped) custom property be smoothly animated with a CSS transition, and how does @property solve this?
+
A normal custom property's value is treated by the browser as an opaque sequence of TEXT TOKENS, not as a value with any specific, understood TYPE (like a number, a color, or an angle) — smoothly animating/transitioning a value requires the browser to INTERPOLATE between a start and end value (compute intermediate values along the way), which fundamentally requires understanding what TYPE of value it's dealing with (you can interpolate between two colors or two numbers, but not between two arbitrary, untyped strings of text in any meaningful way). `@property` solves this by letting you explicitly REGISTER a custom property with a specific `syntax` (like `<angle>`, `<color>`, or `<length>`), giving the browser the type information it needs to correctly interpolate between values — which is precisely what enables smooth, animatable custom properties that wouldn't otherwise be possible.
WhenWhen would you scope a custom property override to a specific component's class, rather than redefining it globally on :root?
+
When the override is meant to affect ONLY a specific component or section of the page, rather than the entire application — for example, a "danger zone" section of a settings page that needs its buttons to use a red/warning color scheme instead of the app's normal brand color, WITHOUT affecting buttons anywhere else on the page. Scoping the override to that specific component's class (e.g. `.danger-zone { --button-bg: red; }`) means the override only applies within that component's DOM subtree, thanks to custom properties' natural inheritance behavior — components OUTSIDE that scope continue using the global `:root` default undisturbed. Redefining on `:root` instead would be the WRONG choice here, since it would incorrectly affect every consumer of that token throughout the entire application, not just the intended, specific component.
HowHow would you debug a situation where a custom property isn't resolving to the value you expect, using browser DevTools?
+
1. Select the affected element in DevTools and check the Styles/Computed panel — modern browser DevTools show the RESOLVED value of custom properties directly, similar to how they show resolved values for any other property, letting you see exactly what value is actually being used.
2. Check the "Computed" tab specifically for the custom property's NAME (e.g. searching for `--button-bg`) — this reveals which rule/scope is actually WINNING for that property, following the same cascade logic as any other CSS property (specificity, source order, etc. — but remember, since it INHERITS by default, the winning declaration might be on an ANCESTOR element, not the element itself).
3. Walk UP the DOM tree in the Elements panel, checking each ancestor's styles, to find exactly where the property is being SET or OVERRIDDEN, since an unexpected value often traces back to an override on a parent/ancestor element you hadn't considered.
4. Check for typos in the property NAME itself (a very common bug — `--buton-bg` vs `--button-bg` silently fails with no error, since undefined custom properties don't throw, they just resolve to invalid/fallback as covered in the gotchas).
5. If using `calc()` or nested `var()` fallbacks, verify each piece resolves as expected by temporarily simplifying the expression to isolate which specific part is producing the unexpected value.
