What Micro-Frontends Are — and the Problem They Solve

💡 Micro-frontends apply the microservices idea to the UI: split ONE large frontend into several smaller, independently developed, tested, and DEPLOYED applications, each owned end-to-end by a team, then compose them into a single experience for the user. The point is not smaller code — it's independent delivery for many teams working on one product.
Monolith frontend vs. micro-frontends — the unit of deployment changes
GoalHow micro-frontends serve it
Independent deployabilityA team ships its slice without coordinating a release train with everyone else
Team autonomy & ownershipOne team owns a vertical slice end to end — UI, logic, and often the backend it talks to
Scaling the organizationAdding teams doesn't linearly add merge conflicts, build time, and review bottlenecks to one repo
Incremental migrationReplace a legacy app piece by piece (strangler pattern) instead of a risky big-bang rewrite

When Micro-Frontends Fit (and When They Don't)

🚨 Micro-frontends are an ORGANIZATIONAL scaling solution, not a technical one. If you don't have an organizational problem (many teams blocked on each other), you're buying real complexity for a benefit you don't need. The most common mistake is adopting them for a small team because they sound modern.
SignalFits?Why
5+ teams contributing to one frontend, stepping on each other✓ Strong fitCoordination cost is the exact pain being solved
Releases bottlenecked by a shared release train / regression suite✓ Strong fitIndependent deploys remove the bottleneck
Migrating a legacy app incrementally while shipping features✓ Strong fitStrangler pattern: route by route, old and new coexisting
Acquired companies / separately-built products to unify✓ Good fitCompose existing apps into one shell without a rewrite
One team of 3-8 engineers✗ Poor fitNo coordination problem to solve — you only pay the costs
Highly interdependent UI with constantly shared state✗ Poor fitSeams cut through tightly coupled features, making every change cross-team
Performance-critical, bundle-size-sensitive app⚠ CarefulDuplicated dependencies and extra network hops can hurt unless managed deliberately
✓ The interview-ready heuristic: "Is the bottleneck people or code?" If it's people — teams blocked on shared releases and merge coordination — micro-frontends can help. If it's code quality or tooling, a well-structured modular monolith (or a monorepo with clear boundaries) usually solves it with far less overhead.

Integration Approaches — When Do the Pieces Come Together?

💡 The central design question is WHEN the separate apps are composed: at BUILD time, at SERVER time, or at RUNTIME in the browser. This single choice drives deployment independence, performance, and complexity more than any framework decision.
Build-time integration (npm packages)composed at BUILD
Each micro-frontend is published as an npm package; the shell installs and bundles them all into one artifact. Simple, great performance (one optimized bundle, shared deps deduped) — but you've lost independent deployment: changing one slice means rebuilding and redeploying the whole shell. This is closer to a modular monolith than true micro-frontends.
Runtime integration via Module Federationcomposed at RUNTIME (JS)
The shell loads remote bundles from other deployments at runtime, sharing dependencies like React. Independent deploys with good performance and a good developer experience — the most popular modern approach. Covered in depth in Section 4.
iframescomposed at RUNTIME (isolated)
Each micro-frontend runs in its own iframe. The strongest isolation of styles, JS, and failures, with truly zero shared runtime — useful for embedding untrusted or legacy apps. Downsides: awkward responsive sizing, painful routing/deep-linking, accessibility and focus issues, duplicated loading cost, and clunky cross-frame communication (postMessage).
Web Components / custom elementscomposed at RUNTIME (standards)
Each micro-frontend exposes itself as a custom element (<checkout-widget>), giving a framework-agnostic contract the shell can drop in. Shadow DOM offers style encapsulation. Good for mixing frameworks; trade-offs include SSR difficulty, form/a11y quirks, and inconsistent framework ergonomics.
Server-side / edge compositioncomposed on the SERVER
A server or CDN edge stitches HTML fragments from each team's service (SSI, ESI, Podium, Tailor-style) before sending the page. Excellent first-paint and SEO since the page arrives assembled; the cost is infrastructure complexity and a harder story for rich client-side interactivity between fragments.

Module Federation — How It Works

💡 Module Federation (introduced in Webpack 5, now also available for Vite/Rspack via plugins) lets one build EXPOSE modules and another CONSUME them at runtime from a different URL — as if they were local imports, even though they're deployed separately. A host (shell) consumes; a remote exposes. An app can be both.
Live: a shell composing four independently-deployed slices — click to "deploy" one without touching the others

Shell is stable. Each slice is a separate deployment with its own version.
// ── REMOTE (cart-app) webpack.config.js — EXPOSES a module ── const { ModuleFederationPlugin } = require("webpack").container; new ModuleFederationPlugin({ name: "cart", filename: "remoteEntry.js", // the manifest the host fetches at runtime exposes: { "./CartWidget": "./src/CartWidget", // what other apps are allowed to import }, shared: { react: { singleton: true, requiredVersion: "^18.0.0" }, "react-dom": { singleton: true, requiredVersion: "^18.0.0" }, }, }); // ── HOST (shell) webpack.config.js — CONSUMES that remote ── new ModuleFederationPlugin({ name: "shell", remotes: { cart: "cart@https://cart.example.com/remoteEntry.js", // where to find it, at RUNTIME }, shared: { react: { singleton: true }, "react-dom": { singleton: true } }, }); // ── In the shell's code: a normal-looking dynamic import ── const CartWidget = React.lazy(() => import("cart/CartWidget")); <ErrorBoundary fallback={<CartUnavailable />}> <Suspense fallback={<Spinner />}> <CartWidget /> </Suspense> </ErrorBoundary>
ConceptMeaning
Host / RemoteThe host loads code from remotes at runtime; a remote exposes modules. One app can be a host AND a remote simultaneously
remoteEntry.jsA small manifest published by each remote describing what it exposes and what it shares — fetched fresh at runtime so a new deploy is picked up without rebuilding the host
exposesThe explicit public surface of a remote — only listed modules can be imported by others (a deliberate boundary)
sharedDependencies negotiated between host and remotes at runtime so heavy libraries (React) load ONCE instead of per-app
singleton: trueForces exactly one instance of a library across all apps — mandatory for libraries like React where two copies break hooks and context
requiredVersion / eagerDeclares acceptable version ranges; mismatches trigger warnings or a fallback to a separately-loaded copy unless forced
⚠ Always wrap remotes in an Error Boundary and Suspense. A remote is a NETWORK dependency — it can be slow, unreachable, or mid-deploy. Without a fallback, one team's outage blanks the entire page, which defeats the whole point of independent, resilient slices.

Team Topology — Slice by Business Domain, Not by Layer

Horizontal (by tech layer) vs. vertical (by business domain) team splits
Team typeRoleWhy it exists
Stream-aligned (feature) teamsOwn a vertical business slice end to end: UI, logic, and the backend it usesEliminates cross-team handoffs for typical changes — the core payoff of the architecture
Platform teamOwns the shell, build tooling, CI/CD templates, shared-dependency policy, observabilityKeeps teams' paved road smooth so autonomy doesn't become 12 snowflake setups
Design-system team (enabling)Owns tokens, primitive components, accessibility standardsVisual and UX consistency across independently shipped slices
Enabling / architecture guildSets contracts, reviews cross-cutting decisions, spreads practicesGoverns the seams without becoming a gatekeeper
🎯 Split by business domain (checkout, search, account), never by technical layer. A good seam is where changes rarely need to coordinate. If a typical feature requires edits in three different micro-frontends, your boundaries are in the wrong place — and that's a design smell, not a tooling problem.

Cross-Cutting Concerns — Where Micro-Frontends Get Hard

ConcernRecommended approachPitfall to avoid
RoutingShell owns top-level routes (/checkout/*); each slice owns its sub-routesSlices fighting over the URL or each embedding their own router for the same path
CommunicationLoose coupling: custom events, a tiny pub/sub bus, or URL/query state; props from the shell for simple casesA shared global store that quietly re-couples every slice together
Shared stateMinimize it. Share identity/session and a few well-defined contracts; keep everything else local"Shared Redux store for everything" — a distributed monolith
Styling isolationCSS Modules / scoped styles / Shadow DOM / namespaced prefixes; shared tokens for consistencyGlobal CSS leaking between slices; resets from one team breaking another
Shared UIA versioned design system consumed by all slices (ideally via Module Federation shared or tokens only)Each team re-implementing a "slightly different" button
AuthShell handles login and passes a token/context; slices don't each implement authMultiple login flows or token refreshes racing each other
PerformanceDedupe shared deps, lazy-load slices, prefetch likely next remotes, budget bundle sizes per sliceEvery slice shipping its own React; waterfall of remote loads
ObservabilityUniform error reporting/tracing tagged by slice and versionAn error in production with no idea which team's deploy caused it
🚨 The "distributed monolith" anti-pattern: if slices share a global store, must be released in lockstep, or can't function without each other's internals, you have all the operational cost of micro-frontends and NONE of the independence. The test: can one team deploy on a Tuesday afternoon without telling anyone?

The Trade-off Ledger

BenefitThe cost you pay for it
Independent deploysRuntime version-compatibility risk; need contract testing between slices and the shell
Team autonomyRisk of inconsistent UX, duplicated effort, and divergent practices without a strong platform + design system
Technology freedom (mix frameworks)Larger bundles, harder shared state, inconsistent a11y and perf — usually a bad idea beyond migrations
Smaller, faster per-team buildsMore repos/pipelines to maintain; integration issues appear later (in the composed whole)
Fault isolationNeed explicit error boundaries and fallbacks; partial-failure UX must be designed deliberately
Incremental migrationTemporary dual systems (two frameworks, two styling approaches) that must have an end date
⚠ Pragmatic default: keep ONE framework and ONE major version of its core libraries across slices, enforced via singleton sharing. "Each team can pick its own framework" sounds liberating, but in practice it multiplies bundle size and shared-state pain; reserve it for migration windows and acquisitions.

Common Gotchas & Interview Traps

  • ⚠️Adopting micro-frontends for a small team is the classic mistake — they solve an organizational coordination problem; without that problem you only inherit the integration, tooling, and performance costs.
  • ⚠️Two copies of React break hooks and context — if shared dependencies aren't declared singleton, a remote may bundle its own React, producing the cryptic "Invalid hook call" error that's the signature Module Federation bug.
  • ⚠️Module Federation sharing is negotiated at RUNTIME, so version mismatches surface in production, not at build time — you need contract tests, version policies, and a staging environment that mirrors the real composition.
  • ⚠️A remote is a network dependency — it can fail to load, be slow, or serve a half-deployed bundle. Every remote needs an Error Boundary, a Suspense fallback, and a timeout/retry story, or one team's incident becomes everyone's outage.
  • ⚠️Sharing a global store couples everything back together — you end up with a distributed monolith: independent repos but lockstep releases. Prefer events, URL state, and narrow contracts over shared mutable state.
  • ⚠️Splitting by technical layer instead of business domain creates endless cross-team handoffs — the very coordination cost you were trying to escape. Slice vertically (checkout, search, account).
  • ⚠️Global CSS leaks across slices — one team's reset or a generic .button class restyles another team's UI. Use scoping (CSS Modules, Shadow DOM, prefixes) and rely on shared design tokens for consistency instead of shared global styles.
  • ⚠️Performance regresses quietly — duplicated dependencies, serial remote-loading waterfalls, and N small bundles can make the composed app slower than the monolith it replaced; set per-slice bundle budgets and measure Core Web Vitals on the composed page, not per slice.
  • ⚠️Mixing frameworks "because we can" multiplies bundle size and makes shared state and accessibility harder; it's justified for migrations and acquisitions, rarely as a steady-state design.
  • ⚠️Micro-frontends don't remove the need for a design system — they raise it — without shared tokens and primitives, independently shipped slices drift visually and the product feels like a patchwork of different apps.

Interview Q&A — Why / What / When / How

🎯 Micro-frontends are an architecture-and-organization question. The strongest answers lead with the PROBLEM (team coordination), name the trade-offs honestly, and show willingness to say "don't do this" when the context doesn't justify it.
WhatWhat are micro-frontends, and what problem do they actually solve?
+
Micro-frontends split a large frontend into smaller applications that are developed, tested, and deployed independently by separate teams, then composed into one user experience — the frontend analogue of microservices. The problem they solve is primarily organizational scaling, not technical: when many teams contribute to one frontend, they get blocked on shared release trains, merge conflicts, long builds, and cross-team coordination. By giving each team ownership of a vertical slice with its own deployment pipeline, a team can ship on its own schedule without waiting for others. They also enable incremental migration off a legacy app. Importantly, they are NOT a way to make the code "cleaner" or the app faster — they typically add integration complexity and some performance overhead, which is the price of independence.
WhyWhy is Module Federation's shared-dependency configuration so important, and what breaks if it's wrong?
+
Without sharing, every remote bundles its own copy of heavy libraries, so the user downloads React several times and the page pays a large bundle and memory cost. Sharing lets the host and remotes negotiate at runtime to load one copy. For libraries with internal global state — React above all — it's a correctness issue, not just performance: two React instances means hooks and context from one copy don't work with components rendered by the other, producing the infamous "Invalid hook call" error. That's why such libraries are marked singleton: true. Because the negotiation happens at RUNTIME, mismatches (a remote requiring React 18 while the host provides 17) show up in production rather than failing the build — so you also need an agreed version policy, contract testing, and a staging environment that mimics the real composition. In short: misconfigured sharing yields either bloated bundles or hard-to-diagnose runtime breakage.
WhenWhen would you recommend AGAINST micro-frontends?
+
When there's no organizational coordination problem to solve — a single team or a few small teams who can coordinate in a standup. In that case micro-frontends add pipelines, versioning surfaces, runtime integration risk, and performance overhead for no payoff. I'd also advise against them when the product's UI is highly interdependent with constant shared state, since any seam would cut through tightly coupled features and every change would span multiple slices — creating a distributed monolith. And I'd be wary when the app is extremely bundle-size or latency sensitive and the team can't invest in managing shared dependencies carefully. A good alternative in many of these cases is a modular monolith or a monorepo with enforced module boundaries (lint rules, package-level ownership, CODEOWNERS), which delivers much of the code-organization benefit without runtime integration complexity. The diagnostic question I'd ask is: "Is our bottleneck people waiting on each other, or the structure of the code?"
HowHow would you decide where to draw the boundaries between micro-frontends?
+
1. Follow business domains, not technical layers. Boundaries like search, checkout, and account map to how users and the business think — a feature change usually stays within one slice. Splitting into "UI team / state team / API team" forces every feature across all teams.
2. Look at change coupling. Examine history: which files and features change together? Things that change together should live together; seams belong where changes rarely need coordination.
3. Align with team ownership (Conway's Law). Each slice should be ownable end to end by one stream-aligned team, including the backend it depends on where possible.
4. Minimize the communication surface. A good boundary can be described by a small contract — a few events, URL parameters, or props. If two slices need to share lots of state, they probably belong together.
5. Sanity-check with a "Tuesday deploy" test. Can the team deploy its slice without telling anyone? If routine changes require coordination, the boundary is wrong.
6. Start coarse. It's easier to split a slice later than to merge prematurely-split ones; begin with a few large slices and refine as real friction appears.
WhatWhat are the different ways to integrate micro-frontends, and how do you choose among them?
+
The options differ by when composition happens. Build-time (npm packages) is simplest and fastest but sacrifices independent deployment. Runtime via Module Federation keeps independent deploys with good performance by sharing dependencies — the common modern default for a single-framework React/Vue ecosystem. iframes give the strongest isolation (useful for legacy or untrusted apps) at the cost of awkward routing, sizing, accessibility, and performance. Web Components provide a framework-agnostic contract with Shadow DOM encapsulation, good when mixing frameworks. Server/edge composition assembles HTML fragments before the page ships, excellent for first paint and SEO but heavier on infrastructure. I choose by what I need most: if independent deployability plus performance matters and the stack is homogeneous, Module Federation; if SEO and first-paint dominate, server-side composition; if I must embed a legacy or third-party app, iframes; if frameworks are heterogeneous, Web Components. And if teams don't truly need independent deploys, build-time composition is the cheapest answer.
WhyWhy do shared global state stores undermine micro-frontend independence?
+
Independence depends on slices being able to change internally without anyone else noticing. A shared global store makes the store's shape a universal contract: any slice that reads or writes a key becomes coupled to every other slice that touches it, so a change to the state structure requires coordinating all of them — and since they deploy separately, mismatched versions of the store contract break in production. You end up with independent repositories but lockstep releases, which is the "distributed monolith": the operational cost of micro-frontends without the benefit. Better patterns keep state LOCAL to each slice and communicate through narrow, explicit, versioned contracts: custom events or a small pub/sub bus for notifications, URL/query parameters for shareable state, and props or context from the shell for truly global concerns like the authenticated user. The guiding rule is to share as little as possible, and to make what you do share an intentional, documented interface.
WhenWhen is it acceptable to let teams use different frameworks within micro-frontends?
+
Mainly in two situations: during a migration (the strangler pattern — React slices gradually replacing an Angular or jQuery app, with both coexisting temporarily) and after acquisitions where separately-built products must be unified quickly. Outside those, I'd discourage it as a steady-state design. Each additional framework adds its runtime to the page (larger bundles, more memory), complicates sharing state and design-system components across slices, and fragments accessibility and testing practices; hiring and cross-team mobility suffer too. Even in the justified cases, I'd treat polyglot as TEMPORARY with a defined end state and plan to converge, wrap each slice behind a framework-agnostic contract (Web Components or a mount/unmount lifecycle), and keep a single design-token source so users don't see the seams. The "technology freedom" benefit is real but frequently oversold relative to its recurring cost.
HowHow would you make a micro-frontend system resilient and observable in production?
+
Resilience:
1. Wrap every remote in an Error Boundary with a purposeful fallback (hide the widget, show a retry, or a degraded read-only version) plus Suspense for loading states, so a failing slice never blanks the page.
2. Add timeouts and limited retries on remote loading, and consider pinning the last-known-good remote version as a fallback.
3. Use versioned or immutable remote URLs with a manifest/registry, enabling controlled rollouts, canaries, and instant rollback of one slice without touching the others.
4. Run contract tests between each slice and the shell, and an integrated end-to-end suite on the composed app.

Observability:
5. Tag every error, log, and performance metric with the slice name and version, so a spike traces immediately to a specific team's deploy.
6. Measure Core Web Vitals on the COMPOSED page, with per-slice bundle budgets enforced in CI to catch silent performance regressions.
7. Provide a shared reporting and tracing library via the platform team so every slice gets this by default rather than each team reinventing it.
