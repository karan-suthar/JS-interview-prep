Iterators & Iterables — The Foundation

💡 An object is iterable if it implements Symbol.iterator — a method returning an iterator: an object with a .next() method that returns { value, done }. This protocol powers for...of, spread syntax, and destructuring. Generators are simply a much easier way to CREATE objects that follow this protocol.
// The iterator protocol, by hand — verbose and easy to get wrong function createRangeIterator(start, end) { let current = start; return { next() { if (current <= end) { return { value: current++, done: false }; } return { value: undefined, done: true }; } }; } const it = createRangeIterator(1, 3); it.next(); // → { value: 1, done: false } it.next(); // → { value: 2, done: false } it.next(); // → { value: 3, done: false } it.next(); // → { value: undefined, done: true } // Making something ITERABLE (usable with for...of) needs Symbol.iterator const range = { start: 1, end: 3, [Symbol.iterator]() { return createRangeIterator(this.start, this.end); } }; for (const n of range) console.log(n); // → 1, 2, 3 [...range]; // → [1, 2, 3] (spread also uses the iterator protocol)
⚠ Writing this by hand is verbose and error-prone — manually tracking state (current) outside the function. Generators solve exactly this problem, which is why they exist.

Generator Basics function* ES6

💡 A generator function (declared with function*) can be paused and resumed. Calling it doesn't run the body — it returns a generator object (which is both an iterator AND iterable). Each call to .next() runs the body until the next yield, then pauses.
// The SAME range example — trivially easy with a generator function* range(start, end) { for (let i = start; i <= end; i++) { yield i; // pause here, hand back "i", wait to be resumed } } const gen = range(1, 3); // nothing runs yet! returns a generator object gen.next(); // → { value: 1, done: false } (runs until first yield) gen.next(); // → { value: 2, done: false } (resumes, runs until next yield) gen.next(); // → { value: 3, done: false } gen.next(); // → { value: undefined, done: true } (loop ends, function returns) // Generators are automatically iterable — for...of just works for (const n of range(1, 3)) console.log(n); // → 1, 2, 3 [...range(1, 3)]; // → [1, 2, 3]

// A "return" inside a generator sets the FINAL value with done: true function* example() { yield 1; yield 2; return "finished!"; // this becomes the value on the FINAL next() call } const gen = example(); gen.next(); // → { value: 1, done: false } gen.next(); // → { value: 2, done: false } gen.next(); // → { value: "finished!", done: true } // ⚠️ for...of and spread IGNORE the final return value! [...example()]; // → [1, 2] ("finished!" is dropped — done:true values are excluded)
🔄 yield is a two-way street — it both sends a value OUT and can receive a value IN via the next call to .next(valueToSend).
function* conversation() { const name = yield "What's your name?"; const age = yield `Nice to meet you, ${name}! How old are you?`; return `${name} is ${age} years old.`; } const convo = conversation(); convo.next(); // → { value: "What's your name?", done: false } convo.next("Alice"); // → { value: "Nice to meet you, Alice! How old are you?", done: false } convo.next(30); // → { value: "Alice is 30 years old.", done: true } // Note: the value passed to the FIRST .next() call is always discarded // (there's no "yield" waiting to receive it yet on the first call)
function* example() { try { console.log("start"); yield 1; console.log("after first yield"); // never reached if .return() called first yield 2; } catch (err) { console.log("caught:", err.message); } finally { console.log("cleanup"); // runs on early return OR throw OR normal completion } } const gen1 = example(); gen1.next(); // logs "start" → { value: 1, done: false } gen1.return("early exit"); // forces early completion → logs "cleanup" // → { value: "early exit", done: true } const gen2 = example(); gen2.next(); // logs "start" gen2.throw(new Error("oops")); // injects an error AT the paused yield point // → logs "caught: oops", then "cleanup"

Lazy Evaluation — Why Generators Matter

✓ Lazy evaluation means values are computed ONLY when actually requested (via .next()), not all upfront. This lets you represent infinite sequences and avoid wasting memory/computation on values nobody asked for.
✗ Eager — computes everything upfront
function getFirstNSquares(n) { const result = []; for (let i = 0; ; i++) { result.push(i * i); if (result.length === n) break; } return result; // entire array built } // before returning ANYTHING getFirstNSquares(1000000); // builds a million-item array even if you only need the first 3
✓ Lazy — computes only what's consumed
function* squares() { let i = 0; while (true) { // infinite! but that's OK yield i * i; i++; } } const gen = squares(); gen.next().value; // → 0 gen.next().value; // → 1 gen.next().value; // → 4 // only 3 values ever computed, regardless of "infinite" definition
// Practical lazy pattern — take(n) helper to pull N items from an infinite generator function take(iterable, n) { const result = []; const it = iterable[Symbol.iterator](); for (let i = 0; i < n; i++) { const { value, done } = it.next(); if (done) break; result.push(value); } return result; } take(squares(), 5); // → [0, 1, 4, 9, 16] (works on an INFINITE generator safely) // Infinite Fibonacci sequence — impossible to represent as an array upfront function* fibonacci() { let [a, b] = [0, 1]; while (true) { yield a; [a, b] = [b, a + b]; } } take(fibonacci(), 8); // → [0, 1, 1, 2, 3, 5, 8, 13]
💡 Lazy pipelines: you can chain generator functions together to build lazy transformation pipelines (like a lazy version of map/filter) — each step only pulls the next value when the step after it asks, avoiding building large intermediate arrays.
// Lazy map/filter — process an infinite stream without intermediate arrays function* mapGen(iterable, fn) { for (const item of iterable) yield fn(item); } function* filterGen(iterable, predicate) { for (const item of iterable) if (predicate(item)) yield item; } // Chain lazily: "even fibonacci numbers, doubled" — computed ONE AT A TIME const pipeline = mapGen(filterGen(fibonacci(), n => n % 2 === 0), n => n * 2); take(pipeline, 4); // → [0, 4, 16, 6*8=? ...] processes only as many fib numbers as needed

yield* — Delegating to Another Generator

💡 yield* delegates iteration to another iterable (often another generator) — it yields each of ITS values one by one, as if they were written inline. Great for composing generators without manual loops.
function* inner() { yield 1; yield 2; } // Without yield* — tedious manual delegation function* outerManual() { for (const val of inner()) yield val; yield 3; } // With yield* — clean delegation function* outer() { yield* inner(); // yields 1, then 2, automatically yield 3; } [...outer()]; // → [1, 2, 3] // yield* also works on ANY iterable, not just generators function* flattenOnce() { yield* [1, 2, 3]; // arrays are iterable yield* "abc"; // strings are iterable too — yields 'a', 'b', 'c' } [...flattenOnce()]; // → [1, 2, 3, 'a', 'b', 'c'] // Practical: recursively flatten a nested tree structure, lazily function* flattenTree(node) { yield node.value; for (const child of node.children || []) { yield* flattenTree(child); // recursive delegation } }

Async Generators & for await...of ES2018

⚡ An async generator (async function*) combines generators with async/await — each yielded value can come from an awaited operation. Consume it with for await...of instead of a regular for...of.
Sync generator
function* syncGen() { yield 1; yield 2; } for (const v of syncGen()) { console.log(v); }
Async generator
async function* asyncGen() { yield await fetchOne(); yield await fetchTwo(); } for await (const v of asyncGen()) { console.log(v); }
// Practical: yielding results from a series of API calls, one at a time async function* fetchUsers(ids) { for (const id of ids) { const res = await fetch(`/users/${id}`); const user = await res.json(); yield user; // pause here until the CONSUMER asks for the next one } } async function main() { for await (const user of fetchUsers([1, 2, 3])) { console.log(user.name); // processes each user as soon as it arrives } // — doesn't wait for ALL fetches before showing the first result } // Async iterables also exist natively — e.g. reading a stream async function readStream(response) { for await (const chunk of response.body) { console.log("Received chunk:", chunk.length, "bytes"); } }

Real-World Use Case: Pagination

✓ Pagination is a textbook use case for async generators — the consumer treats a paginated API as a single, flat, lazy stream, without manually managing page numbers or "has more" flags at the call site.
Auto-paginating async generator
async function* fetchAllPages(baseUrl) { let url = baseUrl; while (url) { const res = await fetch(url); const page = await res.json(); yield* page.items; // flatten — yield each ITEM, not the whole page url = page.nextPageUrl || null; // null/undefined stops the while loop } } // Consumer code — reads like a flat list, no pagination logic visible! async function findFirstAdmin() { for await (const user of fetchAllPages("/api/users?page=1")) { if (user.role === "admin") { return user; // stops fetching further pages immediately! } } return null; } // If the admin is on page 1, pages 2+ are NEVER fetched — true laziness!
Cursor-based pagination (common with REST/GraphQL APIs)
async function* paginate(fetchPage) { let cursor = null; let hasMore = true; while (hasMore) { const { items, nextCursor, hasNextPage } = await fetchPage(cursor); yield* items; cursor = nextCursor; hasMore = hasNextPage; } } // Usage — pass in an API-specific fetch function, generator handles the loop const fetchGithubRepos = (cursor) => fetch( `/api/repos?cursor=${cursor || ""}` ).then(r => r.json()); for await (const repo of paginate(fetchGithubRepos)) { console.log(repo.name); if (enoughReposLoaded()) break; // stop early — remaining pages never fetched }
💡 Why this beats a plain array-returning approach: loading ALL pages into memory upfront wastes bandwidth/memory when the consumer might only need the first few items (e.g. "find the first match" or "show 10 items, load more on scroll"). The generator pattern fetches pages on-demand, exactly when the consumer's loop asks for more.

Common Gotchas & Traps

  • ⚠️Calling a generator function does NOT run its body — it only creates a generator object. The body starts running (up to the first yield) only on the FIRST call to .next(). This trips people up in traces/output-prediction questions.
  • ⚠️Generators are single-use / one-directional — once exhausted (done: true), calling .next() again just keeps returning { value: undefined, done: true }. You cannot "reset" a generator; you must call the generator function again to get a fresh one.
  • ⚠️for...of and spread ignore the generator's final return() value — only values from yield are collected; a trailing return "something" is silently dropped by these consumption methods (though accessible via manual .next() calls).
  • ⚠️The value passed to the first .next(value) call is discarded — there's no paused yield expression yet to receive it on the very first call; it only starts mattering from the second .next() call onward.
  • ⚠️Arrow functions cannot be generators — there is no () =>* {} syntax. Only function* declarations, expressions, and generator methods in object/class literals support yield.
  • ⚠️An infinite generator with no break/take-limit will hang your program if consumed with a plain for...of or spread — always pair infinite generators with an explicit limit (like a take(n) helper or a break condition).
  • ⚠️Async generators require for await...of, not a plain for...of — using a regular for...of on an async generator gives you Promise objects instead of resolved values, since each .next() call returns a Promise.
  • ⚠️yield inside .forEach() or other synchronous callbacks doesn't work — yield can only appear directly inside the generator function's own body, not inside a nested regular function passed as a callback. Use a plain for/for...of loop instead of .forEach() when you need to yield per iteration.
  • ⚠️Generator .throw() only works if the generator is paused at a yield — calling .throw() before the first .next(), or after the generator has already completed, throws the error at the CALL SITE instead of being catchable inside the generator's own try/catch.
  • ⚠️Breaking out of a for...of loop early triggers an implicit .return() on the generator, running any finally blocks — useful for cleanup, but can surprise you if you didn't expect the generator's cleanup code to run on an early break.

Interview Q&A — click to reveal

Q1: What is a generator function, and how is it different from a regular function?
+
A generator function (function*) can be paused and resumed, unlike a regular function that always runs to completion once called. Calling a generator function doesn't execute its body immediately — it returns a generator object that implements the iterator protocol. Each call to .next() runs the function body until the next yield statement, returns that value wrapped in { value, done }, and pauses execution there until .next() is called again.
Q2: What is lazy evaluation, and why are generators well-suited for it?
+
Lazy evaluation means computing a value only at the moment it's actually needed, rather than eagerly computing everything upfront. Generators naturally support this because each yield pauses execution — no further work happens until the consumer explicitly calls .next() again. This makes it possible to represent infinite sequences (like all Fibonacci numbers) or expensive computations, and only pay the cost for the values you actually consume, potentially saving significant memory and CPU time compared to building a full array upfront.
Q3: How would you implement an infinite sequence generator, and safely consume a limited number of values from it?
+
function* naturals() { let n = 1; while (true) yield n++; } function take(gen, n) { const out = []; for (const val of gen) { if (out.length >= n) break; // stop pulling — avoids infinite loop out.push(val); } return out; } take(naturals(), 5); // → [1, 2, 3, 4, 5]
The key is NEVER consuming an infinite generator with something that tries to exhaust it fully (like spread [...gen] or an unconditional for...of) — always pair it with an explicit stopping condition.
Q4: What's the difference between a sync generator and an async generator?
+
A sync generator (function*) yields plain values immediately and is consumed with for...of. An async generator (async function*) can await inside its body before yielding, and each .next() call returns a Promise that resolves to { value, done } — so it must be consumed with for await...of instead of a plain for...of. Async generators are ideal for streaming data that arrives asynchronously, like paginated API results or chunked network responses.
Q5: How would you use an async generator to handle API pagination cleanly?
+
Write an async generator that internally loops through pages, fetching the next page only when the previous one's items have all been yielded, and using yield* to flatten each page's items into a single stream:
async function* fetchAllPages(url) { while (url) { const page = await fetch(url).then(r => r.json()); yield* page.items; url = page.nextPageUrl; } }
The consumer then just writes for await (const item of fetchAllPages(url)) and treats the whole paginated resource as one flat, lazy stream — pagination details are completely hidden, and if the consumer breaks early (e.g. found what it needed), later pages are never even fetched.
Q6: What does yield* do, and how is it different from a regular yield?
+
A regular yield value produces exactly ONE value from the generator. yield* iterable delegates to another iterable (often another generator), yielding EACH of ITS values one at a time, as if they were written inline in the outer generator. It's commonly used to compose generators (call one generator from another) or to flatten/recursively traverse nested structures without manually looping and re-yielding each value.
Q7: Why can't you use .forEach() to yield values inside a generator?
+
yield can only be used directly inside the body of the generator function itself — it cannot cross into a nested regular function, including a callback passed to .forEach(), because that callback is its own separate (non-generator) function scope where yield is simply not valid syntax. Using a plain for or for...of loop directly inside the generator body works fine, since that stays within the generator's own function scope.
Q8: What happens when you break out of a for...of loop early while iterating a generator?
+
The engine automatically calls the generator's .return() method behind the scenes — this causes the generator to terminate as if it had hit a return statement at its current paused position, which means any finally block inside the generator DOES run (useful for cleanup like closing a file handle or database connection), but any code AFTER the currently-paused yield that isn't inside a finally block is skipped.
