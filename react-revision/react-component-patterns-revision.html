Why These Patterns Exist

💡 All three patterns solve the SAME underlying problem: sharing logic/state across components without duplicating code — they predate (and in HOCs/render props' case, are largely superseded by) custom hooks, which solve much of the same problem more simply for STATEFUL LOGIC reuse specifically.
Problem being solvedPre-hooks patternModern equivalent
Reusing stateful logic across componentsHOC or Render PropsCustom hooks (usually simpler)
Building flexible, composable UI widgets (tabs, accordions, selects)Compound ComponentsCompound Components — still the best fit, hooks don't replace this
Injecting cross-cutting concerns (auth checks, logging, theming)HOCHooks + explicit composition, or Context
⚠ Compound Components did NOT get replaced by hooks — hooks solve LOGIC reuse, while Compound Components solve a different problem: expressing a flexible PARENT-CHILD UI relationship declaratively in JSX. This is why Compound Components remain the standard choice for widget-style components even in fully hooks-based, modern codebases.

Compound Components

<Tabs><Tabs.List><Tabs.Tab /></Tabs.List><Tabs.Panel /></Tabs>
A set of components designed to be used TOGETHER, implicitly sharing state (usually via Context) so the consumer can compose and rearrange them freely, without manually wiring props between every piece.
Implicit state sharing via Context — no manual prop wiring between siblings
// Full implementation of a compound Tabs component import { createContext, useContext, useState } from "react"; const TabsContext = createContext(null); function Tabs({ children, defaultTab }) { const [activeTab, setActiveTab] = useState(defaultTab); return ( <TabsContext.Provider value={{ activeTab, setActiveTab }}> <div className="tabs">{children}</div> </TabsContext.Provider> ); } function TabList({ children }) { return <div role="tablist">{children}</div>; } function Tab({ id, children }) { const { activeTab, setActiveTab } = useContext(TabsContext); // reads shared state return ( <button className={activeTab === id ? "active" : ""} onClick={() => setActiveTab(id)} > {children} </button> ); } function TabPanel({ id, children }) { const { activeTab } = useContext(TabsContext); // same shared context return activeTab === id ? <div>{children}</div> : null; } // Attach as static properties for the ergonomic dot-notation API Tabs.List = TabList; Tabs.Tab = Tab; Tabs.Panel = TabPanel; export default Tabs; // ── Usage — the consumer freely composes/reorders pieces ── <Tabs defaultTab="profile"> <Tabs.List> <Tabs.Tab id="profile">Profile</Tabs.Tab> <Tabs.Tab id="settings">Settings</Tabs.Tab> </Tabs.List> <Tabs.Panel id="profile">Profile content</Tabs.Panel> <Tabs.Panel id="settings">Settings content</Tabs.Panel> </Tabs>
✓ Where compound components truly shine: the consumer can freely REORDER, OMIT, or wrap individual pieces (e.g. add a custom wrapper div around one specific `Tab`) without the parent needing to know or care — a single monolithic `<Tabs items={[...]} />` API would need extra render-prop-style escape hatches to offer the same flexibility.

Render Props

<DataProvider render={(data) => <Chart data={data} />} />
A component accepts a PROP whose value is a function — instead of rendering fixed JSX itself, it calls that function (passing whatever internal state/data it manages) and renders WHATEVER that function returns, giving the consumer full control over the output.
// A render-prop component that tracks mouse position function MouseTracker({ render }) { const [position, setPosition] = useState({ x: 0, y: 0 }); function handleMouseMove(e) { setPosition({ x: e.clientX, y: e.clientY }); } return ( <div onMouseMove={handleMouseMove} style={{ height: "100vh" }}> {render(position)} {/* the CONSUMER decides what to render with this data */} </div> ); } // ── Usage — different consumers render totally different UI from the same logic ── <MouseTracker render={(pos) => <p>Mouse at ({pos.x}, {pos.y})</p>} /> <MouseTracker render={(pos) => ( <Cursor style={{ left: pos.x, top: pos.y }} /> )} /> // The SAME MouseTracker logic drives two COMPLETELY different visual outputs // A common variant: using "children" itself as the function (no separate "render" prop needed) function MouseTracker({ children }) { // ...same logic... return <div onMouseMove={handleMouseMove}>{children(position)}</div>; } <MouseTracker>{(pos) => <p>{pos.x}, {pos.y}</p>}</MouseTracker>
⚠ Why this pattern has faded: the SAME "share this stateful logic across multiple UI shapes" goal is now typically solved more simply with a CUSTOM HOOK (e.g. `useMousePosition()`) — no wrapper component, no extra nesting in the JSX tree, no unusual "function as a child" syntax. Render props still appear in some older or highly generic libraries, but hooks are the more idiomatic modern default.

Higher-Order Components (HOCs)

const EnhancedComponent = withAuth(MyComponent)
A FUNCTION that takes a component as input and returns a NEW component with extra behavior/props layered on top — a way to reuse "wrapping" logic across many different components.
A HOC wraps a component, injecting extra props/behavior
// A HOC that injects authentication state as a prop function withAuth(WrappedComponent) { return function AuthenticatedComponent(props) { const user = useCurrentUser(); // some auth-checking logic if (!user) { return <LoginPrompt />; } return <WrappedComponent {...props} user={user} />; {/* injects "user" as a prop */} }; } // ── Usage ── function Dashboard({ user }) { return <h1>Welcome, {user.name}!</h1>; } const ProtectedDashboard = withAuth(Dashboard); <ProtectedDashboard /> {/* automatically gets "user" injected, or shows LoginPrompt */} // The SAME withAuth HOC can wrap MANY different components, reusing the // auth-checking logic without duplicating it in each one const ProtectedSettings = withAuth(SettingsPage); const ProtectedProfile = withAuth(ProfilePage);
🚨 HOC pain points that led to their decline: "wrapper hell" (deeply nested component trees when stacking multiple HOCs — `withAuth(withTheme(withLogging(MyComponent)))`), unclear/colliding prop names (multiple HOCs injecting differently-named or conflicting props with no visibility from the consuming component's code), and difficulty with static type inference in TypeScript for the wrapped component's final prop shape.

Decision Guide

Walk through in order
Are you sharing STATEFUL LOGIC (not UI structure) across components?
YES →
Custom Hook (default modern choice)
Are you building a widget with multiple related, flexibly-composable pieces (tabs, accordion, select, modal)?
YES →
Compound Components
Do you need a component to control EXACTLY what gets rendered from shared logic, and a hook alone won't fit the API shape?
YES →
Render Props (rare in new code — usually a hook is simpler)
Are you working in/extending an older codebase, or a library API that's already HOC-based (e.g. some routing/store connections)?
YES →
HOC (for consistency with existing patterns)
✓ For NEW code today: reach for custom hooks by default for logic reuse, and Compound Components for flexible widget composition. Render Props and HOCs are important to RECOGNIZE and understand (for reading existing code, libraries, and for interviews), but are rarely the right choice to introduce fresh in a modern codebase.
!

Common Gotchas & Interview Traps

  • ⚠️Claiming hooks "replaced" Compound Components is a common but incorrect oversimplification — hooks solve LOGIC reuse; Compound Components solve a structural/composition problem hooks don't address. They coexist and are often used TOGETHER (Compound Components internally implemented using hooks like useContext/useState).
  • ⚠️Compound Components implemented via React.cloneElement (an older technique) are fragile — they break if the consumer wraps a child in an extra `<div>` or fragment, since cloning relies on direct parent-child element structure; the CONTEXT-based approach shown above is more robust and is the modern standard.
  • ⚠️Render props can cause unnecessary re-renders if the render function is defined inline — a NEW function reference on every parent render, passed as a prop, can defeat `React.memo` on the receiving component, same as any other inline callback prop.
  • ⚠️Stacking multiple HOCs creates "wrapper hell" in React DevTools — a component wrapped in `withAuth(withTheme(withLogging(MyComponent)))` shows several nested, often unhelpfully-named wrapper layers in the component tree, making debugging harder.
  • ⚠️HOCs must correctly forward refs to be fully transparent — without explicit `React.forwardRef` support inside the HOC, a `ref` placed on the ENHANCED component won't reach the underlying wrapped component's DOM node, a frequently-missed detail in hand-rolled HOCs.
  • ⚠️HOCs should not mutate the component they receive — a correct HOC returns a brand NEW component that renders the original, rather than directly modifying the passed-in component's prototype/definition, which can cause unpredictable side effects across every usage of the original component.
  • ⚠️Naming collisions between multiple HOC-injected props are a real, hard-to-debug issue — if two different HOCs in a stack both inject a prop called `data` (for different purposes), the LAST one applied silently overwrites the other, with no compiler/runtime warning.
  • ⚠️Compound Components relying on Context still re-render ALL consumers when the context value changes — same caveat as any Context usage; splitting state into multiple smaller contexts, or using a state-management library internally, can mitigate this for performance-sensitive compound widgets with many parts.
  • ⚠️A HOC's displayName should be set explicitly for good debugging — without `EnhancedComponent.displayName = \`withAuth(${WrappedComponent.displayName || WrappedComponent.name})\`;`, React DevTools shows an unhelpful generic name for the wrapper, making the component tree harder to navigate.
  • ⚠️None of these patterns are mutually exclusive — a real component library might use Compound Components for its public widget API, WHILE internally implementing shared logic via custom hooks, and might even still expose a legacy HOC wrapper for backward compatibility with older consumer code — recognizing they can coexist shows deeper practical understanding.

Interview Q&A — Why / What / When / How

🎯 These patterns test whether you understand React's EVOLUTION and can reason about trade-offs across component design choices — not just whether you can recite a definition.
WhatWhat is a compound component, precisely?
+
A compound component is a set of related components DESIGNED to be used together as a family (like `Tabs`, `Tabs.List`, `Tabs.Tab`, `Tabs.Panel`), where the pieces implicitly SHARE state — typically via React Context provided by the top-level parent — rather than requiring the consumer to manually thread props between every sibling. This lets the consumer freely compose, reorder, or omit individual pieces in their JSX while the components automatically coordinate behind the scenes.
WhyWhy do compound components remain relevant even in a codebase that has otherwise fully moved to hooks?
+
Hooks solve the problem of reusing STATEFUL LOGIC across components — they don't address how to structure a flexible, multi-part UI WIDGET in JSX. Compound components solve a fundamentally different, structural problem: letting a consumer compose several related pieces (a tab list, individual tabs, panels) in whatever order/nesting makes sense for their specific use case, without the top-level component needing a giant, inflexible configuration-object API (like `items={[{id, label, content}, ...]}`) to achieve the same flexibility. These are complementary concerns — a compound component's INTERNAL implementation is often built using hooks (`useState`, `useContext`), while the EXTERNAL composition pattern remains a compound component regardless.
WhenWhen would you actually choose to write a render props component today, instead of a custom hook?
+
Genuinely rare in new code — but one case is when you need the SHARED LOGIC to also control something about WHERE/HOW it's mounted in the DOM tree (e.g. a component that needs to measure its own children's rendered size, requiring an actual wrapper element in the DOM, not just a hook's returned values). Another case is maintaining compatibility with, or extending, an existing library that already exposes a render-prop API. Outside of these situations, a custom hook returning the same data typically achieves the identical logic-sharing goal with less nesting and a more familiar API shape for other developers.
HowHow would you refactor a render-props MouseTracker component into a custom hook?
+
// Before — render props function MouseTracker({ render }) { const [position, setPosition] = useState({ x: 0, y: 0 }); useEffect(() => { const handleMove = (e) => setPosition({ x: e.clientX, y: e.clientY }); window.addEventListener("mousemove", handleMove); return () => window.removeEventListener("mousemove", handleMove); }, []); return render(position); } <MouseTracker render={(pos) => <p>{pos.x}, {pos.y}</p>} /> // After — custom hook, same logic, no wrapper component needed function useMousePosition() { const [position, setPosition] = useState({ x: 0, y: 0 }); useEffect(() => { const handleMove = (e) => setPosition({ x: e.clientX, y: e.clientY }); window.addEventListener("mousemove", handleMove); return () => window.removeEventListener("mousemove", handleMove); }, []); return position; } function MyComponent() { const pos = useMousePosition(); // no wrapper component, no extra JSX nesting return <p>{pos.x}, {pos.y}</p>; }
The underlying stateful logic is IDENTICAL — only the API shape for consuming it changes, from "wrap your JSX in a component and receive data via a function argument" to "call a hook directly inside your component body and use the returned value like any other variable."
WhatWhat is a Higher-Order Component, and what problem was it originally designed to solve?
+
A Higher-Order Component (HOC) is a FUNCTION that takes a component as an argument and returns a NEW component with additional behavior or injected props layered around the original — conceptually similar to a higher-order FUNCTION in general JavaScript (a function that takes/returns other functions). It was designed to solve the problem of reusing "wrapping" cross-cutting logic — like checking authentication before rendering, injecting theme values, or subscribing to an external data store — across MANY different components without duplicating that wrapping logic in each one individually.
WhyWhy has "wrapper hell" specifically been such a common complaint about the HOC pattern?
+
Because HOCs compose by NESTING — applying multiple HOCs to a single component (`withAuth(withTheme(withLogging(MyComponent)))`) results in several additional wrapper component layers stacked around the original in the actual rendered component tree. In React DevTools, this shows up as a deep chain of often generically-named wrapper components, making it hard to visually locate the ACTUAL component you're trying to inspect or debug, and making it unclear (without reading each HOC's source) exactly which wrapper is responsible for injecting which prop into the final component.
WhenWhen might you still legitimately encounter or need to write a HOC today?
+
Maintaining or extending an OLDER codebase that already uses HOCs extensively, where introducing a completely different pattern for just one new piece of functionality would create inconsistency. Using a third-party library whose public API is HOC-based (some older Redux `connect()`-style patterns, certain older routing libraries, or specific higher-order utilities from UI libraries) — in this case, you use the HOC because the library requires it, not because you're independently choosing the pattern. For entirely new, independent logic-reuse needs in a modern codebase, a custom hook is almost always the simpler, more idiomatic choice today.
HowHow would you fix a HOC that doesn't correctly forward a ref to the wrapped component?
+
Wrap the HOC's returned component definition in `React.forwardRef`, explicitly passing the received `ref` down to the wrapped component:
// ✗ Before — ref placed on the enhanced component is silently dropped function withAuth(WrappedComponent) { return function (props) { const user = useCurrentUser(); return <WrappedComponent {...props} user={user} />; }; } // ✓ After — forwardRef makes the HOC "ref-transparent" function withAuth(WrappedComponent) { return React.forwardRef(function (props, ref) { const user = useCurrentUser(); return <WrappedComponent {...props} user={user} ref={ref} />; }); }
Now a `ref` placed on the component returned by `withAuth(MyComponent)` correctly passes through to `MyComponent` itself (assuming `MyComponent` is either a DOM element or itself supports refs via its own `forwardRef`), rather than being silently discarded by the intermediate wrapper.
