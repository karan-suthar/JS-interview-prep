useState() Basics

💡 useState gives a function component a piece of state that PERSISTS across re-renders, plus a function to update it. Calling the updater schedules a re-render with the new value — it does not mutate anything in place.
function Counter() { const [count, setCount] = useState(0); // [currentValue, updaterFunction] // "0" is the INITIAL value — only used on the very first render return ( <button onClick={() => setCount(count + 1)}> Count: {count} </button> ); } // Lazy initial state — the function only runs ONCE, on mount // (useful when computing the initial value is expensive) const [data, setData] = useState(() => expensiveComputation()); // If you instead wrote useState(expensiveComputation()), it would run on EVERY render!
ConceptExplanation
What it returnsAn array: [currentValue, setterFunction] — destructured by convention
Initial valueOnly used on the FIRST render; ignored on every subsequent re-render
Calling the setterSchedules a re-render with the new value — does NOT update immediately/synchronously
Persists across renders?Yes — React keeps it tied to that specific component instance, not reset each render
Replaces or merges?REPLACES entirely (unlike class `this.setState`, which shallow-merges objects)
⚠ useState REPLACES state, it does not merge it (a common trip-up for people coming from class components' this.setState). setUser({ name: "Bob" }) completely REPLACES the previous user object — any other fields like age are LOST unless you spread them in manually: setUser(prev => ({ ...prev, name: "Bob" })).

State Updates Are Asynchronous

🚨 Calling a state setter does NOT update the variable immediately — the CURRENT render's count variable stays exactly what it was for the rest of that render's code. React schedules the update and applies it on the NEXT render.
Why logging right after setCount() shows the OLD value
function Counter() { const [count, setCount] = useState(0); const handleClick = () => { setCount(count + 1); console.log(count); // → 0 (NOT 1! "count" is still the OLD value in this closure) }; // ── Even calling setCount 3 times in a row doesn't "stack" 3 renders ── const handleTripleClick = () => { setCount(count + 1); // count is 0 → schedules "become 1" setCount(count + 1); // count is STILL 0 in this closure → schedules "become 1" AGAIN setCount(count + 1); // same thing — schedules "become 1" a third time }; // Result after handleTripleClick: count is 1, NOT 3! All three calls read // the SAME stale "count" from this render's closure. // FIX — use the FUNCTIONAL updater form to always get the LATEST value const handleTripleClickFixed = () => { setCount(prev => prev + 1); // prev is guaranteed up to date, even across queued updates setCount(prev => prev + 1); setCount(prev => prev + 1); }; // Result: count correctly becomes 3! }
✓ Rule of thumb: whenever your new state depends on the PREVIOUS state, use the functional updater form setState(prev => ...) instead of referencing the outer variable directly. It's guaranteed to receive the most up-to-date value, even when multiple updates are queued back-to-back.

Batching Behavior

💡 Batching means React groups multiple state updates that happen within the same event/tick into a SINGLE re-render, instead of re-rendering once per individual setState call. This avoids wasted, intermediate renders.
3 state updates in one click handler → still just 1 re-render
function Form() { const [count, setCount] = useState(0); const [flag, setFlag] = useState(false); const handleClick = () => { setCount(c => c + 1); setFlag(f => !f); // Even though 2 setters were called, React only re-renders ONCE // after handleClick finishes — both updates are applied TOGETHER }; console.log("rendered"); // logs ONCE per click, not twice return <button onClick={handleClick}>Click</button>; }
⚠ Before React 18, batching ONLY happened inside React-managed event handlers (onClick, onChange, etc.) — updates inside setTimeout, native DOM event listeners, or Promise callbacks were NOT batched, causing a separate re-render per setState call.
// React 17 and earlier function handleClick() { setCount(c => c + 1); setFlag(f => !f); // ✓ batched — 1 re-render (this IS inside a React event handler) } setTimeout(() => { setCount(c => c + 1); // ✗ NOT batched — causes its own re-render setFlag(f => !f); // ✗ ALSO causes a separate re-render }, 1000); // 2 re-renders total inside the setTimeout, since it's OUTSIDE React's // synthetic event system
✓ React 18's createRoot API introduced automatic batching — ALL state updates are now batched by default, regardless of where they happen (timeouts, promises, native event listeners, etc.), not just inside React's own event handlers.
// React 18+ (using createRoot) setTimeout(() => { setCount(c => c + 1); // ✓ NOW also batched! setFlag(f => !f); // ✓ same re-render as the line above }, 1000); // Only 1 re-render total — consistent batching everywhere // Escape hatch — force a synchronous, IMMEDIATE update if truly needed import { flushSync } from "react-dom"; flushSync(() => { setCount(c => c + 1); // this update is applied IMMEDIATELY, synchronously }); setFlag(f => !f); // this one is separately batched/applied afterward // Rarely needed — mainly for reading updated DOM measurements right after a state change
ContextReact 17 and earlierReact 18+
Inside onClick/onChange (React events)✓ Batched✓ Batched
Inside setTimeout/setInterval✗ NOT batched✓ Batched
Inside native addEventListener✗ NOT batched✓ Batched
Inside Promise .then()/async-await✗ NOT batched✓ Batched

useEffect() Basics

💡 useEffect lets you run side effects — code that reaches OUTSIDE the pure render process, like data fetching, subscriptions, timers, or manual DOM manipulation — AFTER React has committed changes to the screen.
useEffect(() => { // side-effect code runs AFTER the render is committed to the screen console.log("Component rendered or a dependency changed"); }, [dep1, dep2]); // dependency array — controls WHEN this effect re-runs
// No dependency array at all — runs after EVERY single render useEffect(() => { console.log("Runs after every render, no exceptions"); }); // ⚠️ rarely what you actually want — usually a mistake
// Empty array [] — runs ONCE, only after the initial mount useEffect(() => { console.log("Runs ONCE when the component first mounts"); // Classic use: initial data fetch, subscribing to an external event source }, []); // empty array = "no dependencies to watch" = never re-runs
// With dependencies — runs on mount, then again whenever any listed value changes useEffect(() => { console.log(`Fetching data for user ${userId}`); fetchUser(userId); }, [userId]); // re-runs ONLY when "userId" changes between renders // Multiple dependencies — re-runs if ANY of them change useEffect(() => { console.log("page or filter changed"); }, [page, filter]);
Dependency array formWhen the effect runs
(none at all)After EVERY render — mount and every update
[]Only ONCE, right after the initial mount
[a, b]After mount, then again whenever "a" or "b" changes value between renders

Cleanup Functions

💡 If the function passed to useEffect RETURNS another function, React treats that as a cleanup function — it runs right BEFORE the effect runs again (on dependency change) and when the component UNMOUNTS. Essential for preventing memory leaks.
Cleanup timing across the component lifecycle
// Classic cleanup — remove an event listener / clear a timer / cancel a subscription useEffect(() => { const handleResize = () => console.log(window.innerWidth); window.addEventListener("resize", handleResize); return () => { window.removeEventListener("resize", handleResize); // cleanup! }; }, []); // Without this cleanup, a NEW listener would stack up every time this effect // re-ran (if it had dependencies), and the OLD listener would leak forever // after unmount — a classic memory leak. // Timer cleanup useEffect(() => { const id = setInterval(() => console.log("tick"), 1000); return () => clearInterval(id); // stop the interval on unmount/dep-change }, []); // Preventing "setState after unmount" with AbortController useEffect(() => { const controller = new AbortController(); fetch(`/users/${userId}`, { signal: controller.signal }) .then(res => res.json()) .then(data => setUser(data)); // only runs if fetch wasn't aborted return () => controller.abort(); // cancel if userId changes or component unmounts }, [userId]);
⚠ Cleanup runs BEFORE the NEXT effect, not just on unmount — a common misconception. If the dependency array changes, React runs the cleanup from the PREVIOUS effect execution first, THEN runs the new effect. This ensures each "cycle" of setup/teardown is properly paired, preventing duplicate subscriptions.

Dependency Array — Common Traps

✗ Missing dependency — stale closure bug
function Counter() { const [count, setCount] = useState(0); useEffect(() => { const id = setInterval(() => { console.log(count); // always logs 0! }, 1000); return () => clearInterval(id); }, []); // ✗ "count" used inside but missing from deps } // The effect closure captured "count" as 0 // FOREVER, since it only ran once on mount
✓ Correct dependency, or functional update
function Counter() { const [count, setCount] = useState(0); useEffect(() => { const id = setInterval(() => { setCount(prev => prev + 1); // functional form }, 1000); // avoids needing "count" as a dep! return () => clearInterval(id); }, []); // ✓ correctly empty — no external values used }
// Object/array/function dependencies are compared by REFERENCE, not content! function Parent() { const config = { limit: 10 }; // ✗ NEW object created on EVERY render return <Child config={config} />; } function Child({ config }) { useEffect(() => { console.log("config changed"); }, [config]); // ✗ fires on EVERY Parent re-render — "config" is a NEW reference each time, } // even though { limit: 10 } "looks" identical // Fix: memoize the object/function so its REFERENCE stays stable function ParentFixed() { const config = useMemo(() => ({ limit: 10 }), []); // stable reference return <Child config={config} />; }
✓ Golden rule for dependency arrays: include every value from the component's scope that the effect actually USES (props, state, and any function/variable derived from them). React's ESLint plugin (eslint-plugin-react-hooks) can auto-detect missing dependencies — treat its warnings seriously rather than silencing them.

Common Gotchas & Interview Traps

  • ⚠️Reading state right after calling its setter shows the OLD value — the setter schedules an update for the NEXT render; the variable in the current closure never changes mid-render.
  • ⚠️Multiple setState calls referencing the outer variable "collapse" into one update — `setCount(count+1)` called 3 times in a row all read the SAME stale `count`, resulting in only +1 total, not +3. Use the functional updater form `setCount(prev => prev + 1)` to fix this.
  • ⚠️useState does NOT shallow-merge objects like class components' `this.setState` did — `setUser({ name: "Bob" })` completely replaces the previous state value, dropping any other fields unless you spread them back in manually.
  • ⚠️Forgetting the dependency array runs the effect after EVERY render — easy to do by accident, and can cause infinite loops if the effect itself triggers a state update that causes a re-render.
  • ⚠️Missing a dependency creates a "stale closure" — the effect keeps using the value from whenever it was LAST created, not the current one, since closures capture variables at creation time.
  • ⚠️Object/array/function dependencies are compared by reference, not deep equality — a new inline object/array/function literal created on every render will make the effect re-run every time, even if its contents look identical.
  • ⚠️Forgetting cleanup causes duplicate subscriptions or memory leaks — every effect that sets up a subscription, timer, or listener needs a matching cleanup function, or old ones pile up invisibly across re-renders and after unmount.
  • ⚠️"Can't perform a state update on an unmounted component" warnings happen when an async operation (fetch, timer) resolves AFTER the component has already unmounted and tries to call a state setter — fix with an AbortController or an `isMounted`/ignore flag checked before calling the setter.
  • ⚠️useEffect runs AFTER the browser paints (asynchronously, non-blocking) — if you need to measure/mutate the DOM synchronously BEFORE the user sees a flicker, use `useLayoutEffect` instead, which runs synchronously before paint.
  • ⚠️Automatic batching (React 18+) can surprise code that assumed synchronous updates outside event handlers (e.g. old timeout/promise-based code written before React 18) — if truly synchronous behavior is required, wrap the update in `flushSync` from `react-dom`.

Interview Q&A — Why / What / When / How

🎯 Practice framing your answers around WHY something behaves the way it does, WHAT the mechanism actually is, WHEN to apply a given pattern, and HOW to implement or fix it — this is how senior interviewers probe for depth.
WhatWhat does it mean that state updates are "asynchronous" in React?
+
Calling a state setter (like `setCount(5)`) doesn't immediately change the variable in the CURRENT render's scope — `count` remains whatever it was for the rest of that render's execution, since it's a `const` captured in that render's closure. Instead, React SCHEDULES a re-render; the NEW value only becomes visible once that next render function call actually runs and creates a fresh `count` binding. This is why logging state immediately after calling its setter shows the OLD value.
WhyWhy did React's team design state updates to be async instead of applying them immediately?
+
Making updates asynchronous is what enables BATCHING — grouping multiple state updates that happen close together into a single re-render pass, instead of re-rendering (and re-running potentially expensive render logic, effects, and DOM updates) once per individual `setState` call. It also gives React's scheduler the flexibility to prioritize urgent updates (like user input) over less urgent ones, and to prepare/discard in-progress renders efficiently — capabilities that would be impossible if every state change forced an immediate, synchronous re-render.
WhenWhen should you use the functional updater form (setCount(prev => prev + 1)) instead of setCount(count + 1)?
+
Whenever the NEW state value depends on the PREVIOUS state value — especially when you're calling the setter multiple times in a row within the same event handler, or from inside a closure that might be "stale" by the time it runs (like a `setInterval` or `setTimeout` callback, or an async function's continuation). The functional form always receives the most up-to-date pending state as its argument, avoiding bugs where multiple updates all read the same outdated value from the render's closure.
HowHow would you fix a click handler that calls setCount(count + 1) three times but only increments the count by 1?
+
Replace each call with the functional updater form:
// Before — only +1 total (all 3 read the same stale "count") setCount(count + 1); setCount(count + 1); setCount(count + 1); // After — correctly +3 total setCount(prev => prev + 1); setCount(prev => prev + 1); setCount(prev => prev + 1);
Each functional update is applied in sequence against the LATEST pending value, rather than all three reading the same value captured when the handler started.
WhatWhat is "batching" in the context of React state updates?
+
Batching is React's optimization of grouping multiple state updates that occur within the same synchronous block of code (like one event handler) into a SINGLE re-render, rather than re-rendering once for every individual `setState` call. If you call three different setters inside one click handler, React waits until the handler finishes, then applies all three updates together and re-renders exactly once — rather than rendering three separate times with intermediate, wasted states in between.
WhyWhy did automatic batching in React 18 matter as a change, compared to React 17?
+
Before React 18, batching only happened INSIDE React's own synthetic event handlers (onClick, onChange, etc.) — updates triggered from `setTimeout`, native `addEventListener` callbacks, or Promise `.then()` continuations were NOT batched, causing a separate, wasteful re-render for each `setState` call in those contexts. This inconsistency made performance unpredictable depending on WHERE in your code a state update originated. React 18's automatic batching makes the behavior consistent and more performant everywhere by default, reducing unnecessary re-renders across the entire app without requiring any code changes.
WhenWhen would you need to opt OUT of automatic batching using flushSync?
+
Rarely — but one legitimate case is when you need to read an updated DOM measurement (like an element's height or scroll position) IMMEDIATELY after a state change, before the browser paints, and the default batched/async update timing would be too late for your synchronous DOM-reading code. `flushSync(() => setState(...))` forces React to apply that specific update and its resulting DOM changes synchronously and immediately, before continuing — this should be reached for sparingly since it defeats the performance benefits of batching for that call.
WhatWhat is a cleanup function in useEffect, and what problem does it solve?
+
A cleanup function is whatever function you OPTIONALLY return from the callback passed to `useEffect`. React automatically calls it right before running the effect again (when a dependency changes) and one final time when the component unmounts. It solves the problem of properly "undoing" whatever the effect SET UP — like removing an event listener, clearing a timer/interval, unsubscribing from a data source, or cancelling an in-flight network request — preventing memory leaks and duplicate side effects that would otherwise accumulate silently across re-renders.
WhyWhy does React run the cleanup function BEFORE re-running the effect, rather than only on unmount?
+
If the effect sets up something tied to a specific dependency value (e.g. subscribing to updates for a specific `userId`), and that dependency changes, the OLD subscription/listener/timer from the previous value is no longer valid or wanted — it needs to be torn down before a NEW one is set up for the new value. If cleanup only ran on unmount, every dependency change would ADD another subscription/listener on top of the previous ones instead of replacing them, quickly causing duplicated side effects (e.g. multiple simultaneous data-fetching subscriptions) and memory leaks.
WhenWhen is it actually necessary to include a cleanup function, versus when can you safely omit it?
+
You NEED cleanup whenever the effect creates something that persists beyond the effect's own execution and could "leak" or duplicate if left unattended — event listeners, `setInterval`/`setTimeout` timers, WebSocket connections, external library subscriptions, or in-flight async requests that might resolve after the component no longer cares about the result. You can safely OMIT cleanup for effects that only do a one-time, self-contained action with no lingering resource — like a single synchronous DOM read, a one-off `console.log`, or firing an analytics event that doesn't need to be "undone."
HowHow would you prevent a "setState on unmounted component" warning caused by a fetch call inside useEffect?
+
Use an `AbortController` (or a simple boolean flag) that the cleanup function activates, and check it before calling the state setter:
useEffect(() => { const controller = new AbortController(); fetch(`/api/user/${userId}`, { signal: controller.signal }) .then(res => res.json()) .then(data => setUser(data)) // only reached if not aborted .catch(err => { if (err.name !== "AbortError") console.error(err); }); return () => controller.abort(); // runs on unmount or userId change }, [userId]);
When the component unmounts (or `userId` changes before the fetch completes), the cleanup function aborts the in-flight request, so its `.then()` callback that calls `setUser` never actually fires with stale/unwanted data.
WhatWhat determines when an effect re-runs, and what are the three possible forms of the dependency array?
+
The dependency array (2nd argument to `useEffect`) controls when React decides to re-run the effect, by comparing each value in the array to its value from the PREVIOUS render (using `Object.is` reference equality). Three forms: (1) no array at all — the effect re-runs after literally every render; (2) an empty array `[]` — the effect runs exactly once, right after the initial mount, and never again; (3) an array with values `[a, b]` — the effect runs after mount, then again any time `a` or `b` differs from its value in the previous render.
WhyWhy can an object or array literal in the dependency array cause an effect to run on every single render?
+
React compares dependency array entries using reference equality (roughly `Object.is`), not deep/structural equality. An object or array literal (e.g. `{ limit: 10 }` or `[1,2,3]`) written directly inside the render body creates a BRAND NEW reference on every single render, even if its actual contents are identical to the previous render's. Since the reference is different, React considers the dependency "changed" and re-runs the effect — every time, regardless of whether the logical data actually changed. Fixing this requires memoizing the object/array with `useMemo` (or moving it outside the component, or depending on its primitive fields individually instead of the whole object).
WhenWhen would you choose useLayoutEffect over useEffect?
+
When you need to read layout information from the DOM (like an element's measured size or position) and SYNCHRONOUSLY make changes BEFORE the browser paints the updated screen to the user — for example, measuring a tooltip's size to reposition it before it becomes visible, to avoid a visible flicker/jump. `useEffect` runs asynchronously AFTER paint, so any DOM mutation inside it can cause a brief visual flash of the "wrong" state first. `useLayoutEffect` runs synchronously before paint, blocking the browser from showing anything until it finishes — use it sparingly, since it can hurt performance if overused for non-visual side effects.
