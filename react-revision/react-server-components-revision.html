What Are React Server Components?

💡 Server Components (RSC) are components that render EXCLUSIVELY on the server — their code, and the libraries they depend on, NEVER get shipped to the browser as JavaScript at all. The browser only ever receives the already-rendered OUTPUT (a special serialized description of it), not the component's source code.
// app/page.js — a Server Component by DEFAULT in the Next.js App Router // No "use client" directive = this runs ONLY on the server async function BlogPage() { // Can directly access server-only resources — no API layer needed! const posts = await db.posts.findMany(); // direct database call return ( <div> <h1>Blog</h1> {posts.map((post) => ( <article key={post.id}> <h2>{post.title}</h2> <p>{post.excerpt}</p> </article ))} </div> ); } export default BlogPage; // The database client library, the query logic, and this component's own // code NEVER reach the browser — zero bytes of JS shipped for this piece
✓ The headline benefit: smaller client-side JavaScript bundles. A component that renders a large markdown parser, a heavy date library, or fetches directly from a database can do ALL of that server-side — none of that code or its dependencies ever needs to be downloaded, parsed, or executed by the user's browser.

RSC vs SSR — The Key Difference

🚨 This is the single most commonly confused distinction: SSR (Server-Side Rendering) renders NORMAL client components to HTML on the server for a fast first paint — but the SAME component code THEN ships to the browser to be hydrated and take over. RSC means the component ONLY EVER runs on the server — its code never ships at all, hydration doesn't apply to it, and it can never re-render in the browser.

✓ The clearest one-line distinction to give in an interview: SSR is about WHEN a component first renders (server, for speed/SEO) — the component still fully exists on the client afterward. RSC is about WHERE a component EVER renders (server, permanently) — it has no client-side existence at all.

The "use client" Boundary

💡 Components are Server Components BY DEFAULT. Adding the "use client" directive at the top of a file marks it (and everything it imports) as a CLIENT boundary — from that point down the tree, components behave like traditional React: they can use hooks, browser APIs, and event handlers.
// components/LikeButton.js "use client"; // marks this file — and everything it imports — as CLIENT import { useState } from "react"; function LikeButton({ initialLikes }) { const [likes, setLikes] = useState(initialLikes); // hooks ONLY work in Client Components return ( <button onClick={() => setLikes(likes + 1)}> ❤️ {likes} </button> ); } export default LikeButton;
⚠ "use client" marks a BOUNDARY, not just one file. It doesn't mean "only this component is a Client Component" — it means "from HERE DOWN, everything is part of the client bundle." Any component this file imports (even if that imported file has no directive of its own) becomes part of the client tree too.
// app/page.js — Server Component (no directive) import LikeButton from "./LikeButton"; // a Client Component async function ArticlePage({ params }) { const article = await db.articles.findById(params.id); // server-only data fetch return ( <article> <h1>{article.title}</h1> <p>{article.body}</p> <LikeButton initialLikes={article.likes} /> {/* a Client "island" inside a Server tree */} </article> ); } // Server Components CAN import and render Client Components — this is the // normal, expected direction of composition
// The REVERSE (Client importing Server) is NOT allowed directly — but you // CAN pass a Server Component as "children"/a prop into a Client Component! "use client"; function ExpandablePanel({ children }) { const [isOpen, setIsOpen] = useState(false); return ( <div> <button onClick={() => setIsOpen(!isOpen)}>Toggle</button> {isOpen && children} {/* renders whatever was passed in — could be a Server Component! */} </div> ); } // app/page.js — a Server Component async function Page() { const data = await db.getExpensiveData(); // server-only fetch, stays server-side return ( <ExpandablePanel> <ServerRenderedContent data={data} /> {/* this stays a Server Component! */} </ExpandablePanel> ); } // The Client Component never IMPORTS the Server Component — it just receives // its ALREADY-RENDERED output as "children", passed down from a parent that // CAN see both. This pattern is key to minimizing what actually becomes "client."

Data Fetching in Server Components

💡 Server Components can be async functions directly — you await data right inside the component body, with no useEffect, no loading state boilerplate, and no client-side request waterfall for that data.
✗ Traditional client-side fetching
"use client"; function Profile({ userId }) { const [user, setUser] = useState(null); const [loading, setLoading] = useState(true); useEffect(() => { fetch(`/api/users/${userId}`) .then((r) => r.json()) .then((data) => { setUser(data); setLoading(false); }); }, [userId]); if (loading) return <Spinner />; return <div>{user.name}</div>; } // Needs an API route, ships fetch logic // to the client, manual loading state
✓ Server Component data fetching
// no directive — Server Component async function Profile({ userId }) { const user = await db.users.findById(userId); // direct DB call — no API route, // no client fetch, no loading state // needed at all for THIS component return <div>{user.name}</div>; } // The component simply doesn't // render until the data is ready — // React streams the result in // (often paired with Suspense for // a fallback while it awaits)
// Pairing with Suspense for a streaming loading state import { Suspense } from "react"; async function Page() { return ( <div> <h1>Dashboard</h1> <Suspense fallback={<Spinner />}> <SlowServerComponent /> {/* streams in once its await resolves */} </Suspense> </div> ); }

The Serialization Boundary — Passing Props Across

🚨 When a Server Component passes props to a Client Component, those props MUST be serializable — they cross an actual network/process boundary in a special RSC payload format. Functions, class instances, Dates handled incorrectly, Symbols, and other non-serializable values generally CANNOT be passed as props from Server to Client.
✗ Passing a function/non-serializable prop
// Server Component async function Page() { const handleClick = () => { console.log("clicked"); // this is server-only code! }; return <ClientButton onClick={handleClick} />; // ✗ ERROR — functions can't be // serialized across the boundary }
✓ Pass plain data; define the handler in the client
// Server Component — pass plain, serializable data only async function Page() { const product = await db.products.find(1); return <ClientButton productId={product.id} />; } // Client Component — owns its own handler logic "use client"; function ClientButton({ productId }) { const handleClick = () => console.log(productId); return <button onClick={handleClick}>Buy</button>; }
Can cross Server → Client as a prop?Example
✓ Plain objects, arrays, strings, numbers, booleans{ id: 1, title: "Post", tags: ["a", "b"] }
✓ Other React elements (including Server Components as "children")<ClientWrapper><ServerChild /></ClientWrapper>

Current Limitations

No hooks in Server Components
useState, useEffect, useContext, useReducer, and any hook implying interactivity or a persistent client instance simply cannot be used — Server Components render once, on the server, and are gone.
No browser APIs
window, document, localStorage, and similar don't exist at Server Component render time — there is no browser involved in producing their output.
Framework-dependent
RSC isn't something you "turn on" in plain Create React App or a bare Vite+React setup — it requires a framework/bundler that implements the RSC protocol (currently, primarily Next.js's App Router).
Serialization boundary constraints
Props passed from Server to Client Components must be serializable — no functions, class instances, or other non-plain values, which can require restructuring code that used to pass callbacks freely.
Third-party library compatibility
Many existing libraries assume they can use hooks or browser APIs freely and aren't written with the Server/Client distinction in mind — some require wrapping in a Client Component, or don't yet officially support RSC.
Mental model / learning curve
Deciding what should be a Server vs Client Component, understanding the boundary rules, and debugging serialization errors is a genuinely new set of concepts beyond "classic" React that teams need to learn.
Tooling and ecosystem still maturing
Testing utilities, some dev-tools workflows, and broader ecosystem support for RSC-specific patterns are newer and less battle-tested than the decade-plus-mature traditional client-rendering ecosystem.
No client-side re-rendering of Server Components
A Server Component can't locally re-render in response to client interaction — updating what it shows generally requires a full server round-trip (e.g. a Server Action or navigation) to re-render and re-stream it.

Common Gotchas & Interview Traps

  • ⚠️Confusing RSC with SSR is the single most common mistake — SSR is a RENDERING STRATEGY for regular (client) components to speed up first paint; RSC is a fundamentally different CATEGORY of component that never exists on the client at all. They're complementary, not the same thing, and not mutually exclusive.
  • ⚠️"use client" does not mean the component ONLY runs on the client — a Client Component is typically still server-rendered for the initial HTML (via SSR) and THEN hydrated in the browser; "use client" means "this can ALSO run client-side," not "this ONLY runs client-side."
  • ⚠️"use client" marks a boundary that propagates to everything imported below it — accidentally importing a Client Component near the ROOT of the tree can inadvertently pull a much larger portion of the app into the client bundle than intended.
  • ⚠️You cannot import a Server Component INTO a Client Component file and render it directly — the correct pattern is to pass the already-rendered Server Component down as `children`/a prop from a common Server Component ancestor, not to import it inside client code.
  • ⚠️Passing a function as a prop from Server to Client throws a serialization error — a classic gotcha for developers used to freely passing callbacks; event handlers must be DEFINED inside the Client Component itself, not passed down from the server.
  • ⚠️Environment variables and secrets used in a Server Component are safe — but if that same value is accidentally passed as a PROP to a Client Component, it becomes part of the serialized payload sent to the browser, potentially leaking it.
  • ⚠️Server Components can't hold state across "renders" the way you might expect — since they render fresh on the server for each request/navigation, there's no persistent component instance retaining state between renders the way a mounted Client Component instance does.
  • ⚠️The RSC payload is NOT the same thing as the HTML sent for SSR — it's a distinct, React-specific serialized format describing the component tree (including "holes" for Client Components), used for the initial load AND for subsequent server-driven updates (e.g. via Server Actions or navigation).
  • ⚠️Not every component needs to fight to be a Server Component — a component that's inherently interactive (a form, a toggle, an animation) is a natural, correct fit for "use client"; RSC isn't about eliminating Client Components, it's about not defaulting everything to one when it doesn't need to be.
  • ⚠️RSC is primarily associated with (and currently mostly used through) Next.js's App Router — while the underlying React APIs are framework-agnostic in principle, production-ready RSC support outside of Next.js is still relatively limited as of now, which is worth acknowledging if asked about ecosystem maturity.

Interview Q&A — Why / What / When / How

🎯 RSC is a newer, architecture-level topic — interviewers often use it to probe whether you understand the underlying MODEL (not just the directive syntax), so practice explaining the reasoning, not just the "how to write it."
WhatWhat is a React Server Component, precisely?
+
A Server Component is a component that renders EXCLUSIVELY on the server — it has no client-side existence whatsoever. Its source code and any libraries it depends on are never included in the JavaScript bundle sent to the browser; the browser only ever receives the ALREADY-RENDERED output, serialized in a special RSC payload format, which React uses to construct the final UI (interleaved with any Client Component "holes" that do get hydrated normally).
WhyWhy were Server Components introduced when SSR already existed?
+
SSR solves "render fast for the FIRST paint," but the component's full JavaScript still has to ship to the browser afterward for hydration — meaning a component's dependencies (a heavy date-formatting library, a markdown parser, a database client) all end up in the client bundle even if the component never actually needs to re-render or respond to interaction in the browser. Server Components solve a DIFFERENT problem: reducing the amount of JavaScript shipped AT ALL for parts of the UI that are fundamentally non-interactive — letting you use server-only resources (databases, file systems, secrets) directly, and letting large dependencies stay entirely server-side, permanently, rather than just for the first render.
WhenWhen should a component be a Server Component versus a Client Component?
+
Default to a Server Component whenever the component doesn't need interactivity, state, effects, or browser-only APIs — e.g. static content, data display, layout shells, or anything that only needs to fetch and render data. Reach for a Client Component ("use client") specifically when the component needs `useState`/`useEffect`/other hooks, needs to respond to user events (onClick, onChange), needs browser-only APIs (`localStorage`, `window`), or needs to use a third-party library that itself depends on client-side behavior. The general strategy is to push Client Components as far DOWN/leaf-ward in the tree as possible — keeping the majority of the tree as lightweight, JS-free Server Components.
HowHow would you structure a page with a mix of static content and one interactive widget to minimize the client bundle?
+
Keep the outer page and most of its content as a (default) Server Component, and extract ONLY the genuinely interactive piece into its own small file marked `"use client"`, importing that small Client Component into the Server Component tree:
// app/page.js — Server Component (default, no directive) async function Page() { const data = await db.getData(); // stays fully server-side return ( <main> <StaticHeader /> {/* Server Component */} <ArticleBody data={data} /> {/* Server Component */} <LikeButton /> {/* small Client Component "island" */} </main> ); }
Only `LikeButton`'s code (and its dependencies) end up in the client JS bundle — everything else remains server-only, dramatically reducing what actually gets shipped and hydrated.
WhatWhat's the core distinction between RSC and SSR that interviewers are usually looking for?
+
SSR is about WHEN a (normal, client-capable) component first renders — on the server, for a fast initial paint — but its full code still ships to and runs in the browser afterward via hydration. RSC is about WHERE a component EVER renders — permanently on the server, with its code never shipping to the client at all, and no hydration step applying to it. SSR speeds up the first render of components that still fully exist on the client; RSC removes certain components from the client entirely.
WhyWhy can't you pass a function as a prop from a Server Component to a Client Component?
+
Data passed from a Server Component to a Client Component has to cross an actual boundary — it gets SERIALIZED into the RSC payload format that's sent over the network/process boundary to where the Client Component actually renders. Functions are not serializable in any general, safe way — you can't meaningfully represent "run this exact server-side closure" as data sent to the browser (and even if you could, invoking server-only code, potentially with access to secrets or a database connection, directly from client-triggered events would be a serious security concern). This is why event handlers must be DEFINED locally inside Client Components rather than passed down from the server — Server Actions exist as the sanctioned, secure mechanism for a client interaction to trigger server-side logic.
WhenWhen would you use the "pass a Server Component as children into a Client Component" pattern?
+
When you need a Client Component to provide interactive WRAPPING behavior (like a collapsible panel, a modal, or a tab container that needs `useState` to track open/closed or active-tab state) around content that itself doesn't need to be a Client Component — e.g. server-rendered article text or data-driven content. Rather than making the whole subtree a Client Component (which would ship unnecessary JS for the static content too), the Client Component only owns the INTERACTIVE shell, and receives the static content pre-rendered as `children`, keeping that inner content's code out of the client bundle entirely.
WhatWhat are the main current limitations of Server Components you should be aware of?
+
No hooks (useState, useEffect, etc.) or browser APIs can be used inside them, since they never run in a browser context. They're framework-dependent — you can't just enable RSC in a bare Vite/CRA setup; production support is currently centered around Next.js's App Router. Props passed to Client Components must be serializable, ruling out functions and class instances, which can require restructuring code patterns that previously passed callbacks freely. Many existing third-party libraries weren't built with the Server/Client distinction in mind and may need explicit Client Component wrapping. And the overall mental model (deciding what should be Server vs Client, understanding boundary propagation) is a genuinely new layer of complexity on top of "classic" React.
WhyWhy does "use client" propagate to everything a file imports, rather than only affecting that one component?
+
Once a component is going to run in the browser (and potentially re-render there in response to state/props changes), everything it renders as part of its OWN tree must also be capable of running in the browser — you can't have a Client Component's render output depend on a child that only knows how to run on the server, since the client has no way to re-invoke that server-only logic locally during a client-side re-render. Marking the boundary at the file level and having it propagate downward through imports is what guarantees this consistency: everything "inside" a Client Component's rendering responsibility is verifiably capable of running client-side.
WhenWhen does an app actually benefit meaningfully from adopting Server Components, versus when is it not worth the complexity?
+
RSC provides the most benefit for content-heavy applications with substantial non-interactive portions — blogs, e-commerce product pages, dashboards with mostly-static data displays, or any app where a meaningful chunk of the UI doesn't need client-side interactivity, especially if that UI relies on heavy libraries or direct backend/database access. It's less clearly worth the added architectural complexity for HIGHLY interactive apps (like a real-time collaborative editor, a complex client-heavy dashboard with constant local state updates, or a game) where the vast majority of the UI needs to be a Client Component anyway — in those cases, the JS-bundle-reduction benefit of RSC applies to a much smaller fraction of the app, while still incurring the learning curve and architectural constraints.
HowHow would you fix a "Functions cannot be passed directly to Client Components" error?
+
Identify what the function was trying to do, and choose the appropriate fix:
// Option 1: move the handler definition INTO the Client Component itself "use client"; function DeleteButton({ itemId }) { const handleDelete = () => { // logic defined HERE, client-side, using only the plain "itemId" prop }; return <button onClick={handleDelete}>Delete</button>; } // Option 2: if server-side logic genuinely needs to run on click, // use a Server Action instead of a plain passed-down function async function deleteItem(itemId) { "use server"; // marks this as a Server Action — CAN be passed to the client safely await db.items.delete(itemId); }
Either keep the handler purely client-side (using only serializable data passed down as props), or use the "use server" Server Action mechanism, which is specifically designed to let client-triggered interactions safely invoke server-side logic.
