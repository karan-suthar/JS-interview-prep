The 3 Lifecycle Phases — Overview

💡 Every component goes through three conceptual phases: Mount (created and inserted into the DOM for the first time), Update (re-rendered due to new props/state), and Unmount (removed from the DOM). Class components had dedicated named methods for each; function components use useEffect (and friends) to achieve the same timing.
The lifecycle at a glance
PhaseTriggered byHappens how many times
MountComponent first added to the treeExactly once per component instance
UpdateProps change, state changes, or parent re-rendersZero to many times
UnmountComponent removed from the tree (conditionally rendered away, parent removed, navigation, etc.)Exactly once per component instance
2

Mount Phase

M
Component created and inserted into the DOM for the first time
Class: constructor → render → componentDidMount. Function: render → useEffect(fn, [])
class UserProfile extends React.Component { constructor(props) { super(props); this.state = { user: null }; // initial state setup } componentDidMount() { // runs ONCE, right after the component is first inserted into the DOM fetchUser(this.props.userId).then(user => this.setState({ user })); // classic use: initial data fetch, subscribing to external events } render() { return <div>{this.state.user?.name}</div>; } }
function UserProfile({ userId }) { const [user, setUser] = useState(null); useEffect(() => { // empty dependency array [] → runs ONCE, right after the first render commits fetchUser(userId).then(setUser); }, []); // equivalent timing to componentDidMount return <div>{user?.name}</div>; }
⚠ Timing nuance: componentDidMount runs SYNCHRONOUSLY right after the DOM is updated, before the browser paints. useEffect with [] runs ASYNCHRONOUSLY, AFTER the browser paints. For the rare cases needing pre-paint timing (avoiding visual flicker), useLayoutEffect is the closer match to componentDidMount's exact timing.
3

Update Phase

U
Component re-renders due to new props, new state, or a parent re-rendering
Class: render → componentDidUpdate. Function: render → useEffect(fn, [deps]) whenever a listed dependency changes
class UserProfile extends React.Component { componentDidUpdate(prevProps, prevState) { // runs after EVERY update — you must manually compare to avoid infinite loops! if (prevProps.userId !== this.props.userId) { fetchUser(this.props.userId).then(user => this.setState({ user })); } } render() { return <div>{this.state.user?.name}</div>; } } // Note the MANUAL prevProps/prevState comparison — easy to forget, // and forgetting it causes an infinite fetch loop!
function UserProfile({ userId }) { const [user, setUser] = useState(null); useEffect(() => { fetchUser(userId).then(setUser); }, [userId]); // React automatically compares "userId" for you — no manual check needed! return <div>{user?.name}</div>; } // This effect ALSO runs on MOUNT (first render counts as "userId changed // from nothing to something") — one hook covers BOTH mount and update logic
✓ Key simplification hooks bring: componentDidMount and componentDidUpdate were two SEPARATE methods, often containing duplicated logic (e.g. the same fetch call in both, once unconditionally and once behind a prop-comparison check). A single useEffect with the right dependency array naturally covers BOTH the mount case and the relevant update case, since React treats the very first run as "everything changed."
4

Unmount Phase

X
Component removed from the DOM — final chance to clean up
Class: componentWillUnmount. Function: the function RETURNED from useEffect's callback
class Clock extends React.Component { componentDidMount() { this.intervalId = setInterval(() => this.forceUpdate(), 1000); } componentWillUnmount() { clearInterval(this.intervalId); // prevent memory leak — SEPARATE method, far from setup } render() { return <div>{new Date().toLocaleTimeString()}</div>; } } // The setup (componentDidMount) and teardown (componentWillUnmount) logic // live in two DIFFERENT methods, potentially far apart in the file
function Clock() { const [time, setTime] = useState(new Date()); useEffect(() => { const intervalId = setInterval(() => setTime(new Date()), 1000); return () => clearInterval(intervalId); // cleanup lives RIGHT NEXT to the setup! }, []); return <div>{time.toLocaleTimeString()}</div>; } // Setup and teardown are co-located in the SAME effect — much easier to // verify every subscription/timer/listener has a matching cleanup
⚠ Important subtlety: the cleanup function doesn't ONLY run on unmount — it also runs BEFORE the effect re-runs due to a dependency change (see the Update phase). This means a single cleanup function serves BOTH "tear down before re-running" and "tear down on final removal," which has no direct one-to-one equivalent as a separate class method — componentWillUnmount alone only covered the final removal case.

Full Class Lifecycle → Hook Mapping

Class lifecycle methodHook equivalentNotes
constructor(props)useState(initialValue)State initialization
componentDidMountuseEffect(fn, [])Runs once after first render (though timing is post-paint, not pre-paint)
componentDidUpdateuseEffect(fn, [deps])Runs when any listed dependency changes — no manual prevProps diffing needed
componentWillUnmountreturn () => {...} inside useEffectThe returned cleanup function, co-located with its setup
shouldComponentUpdateReact.memo() / useMemo() / useCallback()Different mechanism — memoization instead of a lifecycle veto
getDerivedStateFromPropsJust compute the value directly during renderNo hook needed — function components can derive values inline every render
componentDidCatch / getDerivedStateFromErrorNo hook equivalent — still requires a class (Error Boundary)One of the few remaining cases classes are still required for
this.forceUpdate()No direct equivalent (rarely needed with hooks)Hooks encourage deriving from state instead of forcing re-renders
🚨 Error boundaries are the one major exception: as of today, there is NO hook equivalent for componentDidCatch/getDerivedStateFromError — catching rendering errors in a subtree still requires a class component. Most codebases write ONE small Error Boundary class component and reuse it everywhere else via hooks/function components.

Seeing All 3 Phases in One Component

function ChatRoom({ roomId }) { useEffect(() => { console.log(`[MOUNT or UPDATE] Connecting to room: ${roomId}`); const connection = createConnection(roomId); connection.connect(); return () => { console.log(`[CLEANUP before next effect, or UNMOUNT] Disconnecting: ${roomId}`); connection.disconnect(); }; }, [roomId]); return <h1>Welcome to {roomId}!</h1>; }
ScenarioConsole output
Initial mount with roomId="general""[MOUNT or UPDATE] Connecting to room: general"
Parent changes roomId to "random""[CLEANUP...] Disconnecting: general" then "[MOUNT or UPDATE] Connecting to room: random"
Component unmounts entirely"[CLEANUP...] Disconnecting: random" (no further connect)
💡 This single, small effect demonstrates all three "phases" using ONE unified mental model: setup runs (mount, and again on every relevant update) and cleanup runs (before every re-setup, and one final time on unmount). This is a MUCH simpler mental model than tracking 3+ separate named lifecycle methods.

Common Gotchas & Interview Traps

  • ⚠️useEffect is NOT exactly "componentDidMount + componentDidUpdate + componentWillUnmount" merged — it's a genuinely different mental model (synchronize with an external system based on dependencies) that happens to cover the same use cases, not a literal 1:1 combination of the three methods.
  • ⚠️useEffect runs AFTER paint (asynchronously), while componentDidMount/componentDidUpdate run synchronously BEFORE paint — this can cause a visible flicker for effects that measure/mutate the DOM, where the class equivalent wouldn't have. Use `useLayoutEffect` for exact pre-paint timing parity.
  • ⚠️Missing a dependency in the array recreates the "componentDidUpdate forgot to check prevProps" bug in a different form — a stale closure results in the effect referencing outdated values, similar in spirit to forgetting the prevProps comparison in a class component.
  • ⚠️Multiple useEffect calls in one component are independent — each has its OWN dependency array and runs on its OWN schedule, unlike class components where ALL mount logic had to live together in the single componentDidMount method. This is often cleaner (grouping related logic together) but can surprise developers expecting one unified "on mount" block.
  • ⚠️There is no hook equivalent for getSnapshotBeforeUpdate (used rarely, e.g. for preserving scroll position before a DOM update) — this remains one of the few gaps between the class and hook lifecycle APIs, though `useLayoutEffect` can approximate some use cases.
  • ⚠️Error boundaries still require a class component — there is no `useErrorBoundary` hook as of today; `componentDidCatch`/`getDerivedStateFromError` have no functional equivalent, so most apps keep one small class-based ErrorBoundary wrapper used alongside otherwise all-functional code.
  • ⚠️StrictMode in React 18+ intentionally double-invokes effects in development (mount → cleanup → mount again) specifically to help you catch missing/incorrect cleanup logic — this can look like a bug at first, but it's a deliberate diagnostic tool, and does NOT happen in production builds.
  • ⚠️Treating useEffect purely as "the mount hook" (always using an empty array without thinking) misses its real purpose — it's meant to synchronize a component with an external system based on specific dependencies, not simply to replicate "run once" class behavior by default.
  • ⚠️shouldComponentUpdate has no direct hook equivalent — `React.memo` (for skipping a whole component's re-render when props are shallow-equal) is the closest hook-era analog, but it works at the component-wrapping level, not as an internal lifecycle method you override.
  • ⚠️Referring to "the mount phase" as happening only once is per COMPONENT INSTANCE, not per component type — if a component is unmounted and later a NEW instance of the same component type is mounted again (e.g. via conditional rendering toggling on/off), that counts as a completely fresh mount, running effects again from scratch, with entirely new state.

Interview Q&A — Why / What / When / How

🎯 These four angles cover the full depth interviewers probe for: definitions, motivations, decision points, and hands-on implementation.
WhatWhat are the three phases of a React component's lifecycle?
+
Mount — the component is created and inserted into the DOM for the first time (happens exactly once). Update — the component re-renders due to new props, new state, or a parent re-rendering (can happen zero to many times). Unmount — the component is removed from the DOM (happens exactly once, and is the final opportunity to clean up any resources the component set up).
WhyWhy did React introduce useEffect instead of just keeping the three separate class lifecycle methods for function components?
+
Class lifecycle methods often forced you to split ONE logical concern (e.g. "keep this subscription in sync with the current roomId") across TWO separate methods — the setup in `componentDidMount` and the manual re-sync logic (with prevProps diffing) in `componentDidUpdate`, plus teardown in a THIRD method, `componentWillUnmount`. This scattered related code across the file and made it easy to forget to update one of the methods when the others changed. `useEffect` unifies setup, re-sync, and cleanup for a single concern into ONE co-located block, organized around dependencies rather than named lifecycle moments — a fundamentally more cohesive mental model for "synchronizing with an external system."
WhenWhen would you still need a class component instead of hooks, in modern React?
+
The main remaining case is Error Boundaries — catching JavaScript errors thrown anywhere in a subtree during rendering requires `componentDidCatch` and/or `getDerivedStateFromError`, neither of which has a hook equivalent as of today. Most modern codebases write a single small Error Boundary class component once, and use it as a wrapper around otherwise fully hooks-based function components — you rarely need MORE than one or two class components in an entire modern app.
HowHow would you convert a class component with componentDidMount, componentDidUpdate, and componentWillUnmount into a function component?
+
Step 1: identify what the effect actually depends on (which props/state values it reads).
Step 2: move the shared "setup" logic (from componentDidMount and the relevant branch of componentDidUpdate) into a single `useEffect` callback.
Step 3: move the teardown logic from componentWillUnmount into a function RETURNED from that same `useEffect` callback.
Step 4: set the dependency array to include every value from step 1 — this makes React automatically re-run the effect (with cleanup first) whenever those values change, replacing the manual prevProps/prevState comparison that componentDidUpdate required.
// One useEffect replaces all three methods for a single concern useEffect(() => { // setup — was componentDidMount + relevant part of componentDidUpdate return () => { // cleanup — was componentWillUnmount }; }, [/* dependencies read inside */]);
WhatWhat triggers the "update" phase specifically?
+
Three things can trigger an update/re-render: (1) the component's own state changes via a state setter, (2) the component receives new props from its parent (because the parent itself re-rendered and passed different values), or (3) a parent re-renders for ANY reason (even if the props passed down are identical, by default a child re-renders too unless wrapped in `React.memo`).
WhyWhy does the cleanup function run before EVERY re-run of the effect, not just on unmount?
+
If an effect sets up something tied to a specific dependency's value (e.g. a WebSocket connection to a specific `roomId`), and that dependency changes, the OLD setup (connected to the OLD roomId) needs to be torn down before a NEW one (for the new roomId) is created — otherwise you'd end up with multiple simultaneous connections stacking up instead of one connection that correctly follows the current value. Running cleanup before every re-run — not just final unmount — is what guarantees each "cycle" of setup and teardown stays properly paired, no matter how many times the dependency changes.
WhenWhen should you use useLayoutEffect instead of useEffect to better match class lifecycle timing?
+
When you need to read layout information from the DOM (like a measured size or scroll position) and make synchronous adjustments BEFORE the browser paints the new frame — matching `componentDidMount`/`componentDidUpdate`'s actual synchronous, pre-paint timing. `useEffect` runs asynchronously AFTER paint, so any DOM-measuring/mutating logic inside it can cause a brief visible flicker of the "wrong" layout first, which `useLayoutEffect`'s pre-paint timing avoids. Use it sparingly, though — because it's synchronous and blocking, overusing it for non-visual side effects can hurt perceived performance.
WhatWhat does it mean that "mounting" happens once per component INSTANCE, not per component definition?
+
If a component is conditionally rendered — shown, then hidden, then shown again (e.g. `{isVisible && <Modal />}`) — each time it reappears after being removed, React treats it as a COMPLETELY NEW instance: a fresh mount, fresh state (any previous state is gone), and effects with `[]` run again from scratch, exactly as if it were the very first time that component type had ever been rendered anywhere. The "runs once" guarantee of a mount-only effect is scoped to that specific instance's lifetime, not to the component function/type as a whole.
WhyWhy does React's StrictMode intentionally run effects twice (mount → cleanup → mount) in development?
+
It's a deliberate diagnostic technique to help developers catch MISSING or INCORRECT cleanup logic early. If an effect sets something up (a subscription, listener, timer) but doesn't properly clean it up, running mount→cleanup→mount in development surfaces the bug immediately — e.g. you'll see duplicated console logs, doubled network requests, or leaked subscriptions that wouldn't have been obvious with only a single mount. This behavior is exclusive to development builds (specifically components wrapped in `<StrictMode>`) and does NOT happen in production, where each effect still only truly mounts once as expected.
WhenWhen would you use multiple separate useEffect calls in one component, instead of combining everything into one?
+
Whenever the component has multiple UNRELATED side effects/concerns that each depend on DIFFERENT things — for example, one effect that sets the document title based on a `title` prop, and a completely separate effect that subscribes to a WebSocket based on a `roomId` prop. Combining them into one effect would force them to share a single dependency array (even though they logically depend on different values) and would tie their cleanup/re-run timing together unnecessarily. Splitting by CONCERN, not by lifecycle phase, is the guiding principle — each effect should represent one cohesive "synchronize X with Y" relationship.
HowHow would you replicate shouldComponentUpdate's "skip this re-render" behavior in a function component?
+
Wrap the function component in `React.memo()`, which shallow-compares the new props against the previous props and skips re-rendering the component (reusing its previous render output) if they're all equal:
const UserCard = React.memo(function UserCard({ name, age }) { console.log("rendering UserCard"); return <div>{name}, {age}</div>; }); // Only re-renders if "name" or "age" actually changed (by reference/value) // compared to the last render — skips otherwise, similar to returning // false from shouldComponentUpdate
For a custom comparison function (instead of the default shallow-equal check), `React.memo` accepts an optional second argument, mirroring `shouldComponentUpdate`'s ability to define custom "should I skip this?" logic.
