Why Custom Hooks?

💡 A custom hook is just a JavaScript function whose name starts with use and that calls other hooks internally. It lets you EXTRACT reusable, STATEFUL logic out of components — sharing behavior (not just UI) across multiple components without duplicating code or resorting to higher-order components/render props.
Custom hooks share LOGIC; each component still gets its own independent state
✓ Key mental model: a custom hook is essentially a recipe for combining `useState`/`useEffect`/`useRef`/etc. that gets RE-RUN independently for every component that calls it — there's no shared/global state between callers unless you deliberately introduce one (e.g. via Context or a module-level cache, as `useFetch` will below).

useDebounce

const debouncedValue = useDebounce(value, delay)
Returns a copy of "value" that only updates after "delay" milliseconds have passed WITHOUT value changing again. Perfect for search inputs, live validation, or any rapidly-changing value feeding an expensive operation.
Typing "react" — debouncedValue only updates once, after typing stops
// hooks/useDebounce.js import { useState, useEffect } from "react"; function useDebounce(value, delay) { const [debouncedValue, setDebouncedValue] = useState(value); useEffect(() => { // schedule an update to debouncedValue after "delay" ms const timerId = setTimeout(() => { setDebouncedValue(value); }, delay); // if "value" changes again before the timer fires, cancel the OLD // timer — this is what makes it "debounce" rather than just delay return () => clearTimeout(timerId); }, [value, delay]); // re-run the effect every time "value" changes return debouncedValue; } export default useDebounce; // ── Usage ── function SearchBox() { const [query, setQuery] = useState(""); const debouncedQuery = useDebounce(query, 500); useEffect(() => { if (debouncedQuery) { searchAPI(debouncedQuery); // only fires 500ms after typing STOPS } }, [debouncedQuery]); return <input value={query} onChange={(e) => setQuery(e.target.value)} />; }
⚠ Why this differs from the imperative debounce() from a "debounce/throttle from scratch" exercise: this is a DECLARATIVE, hook-based version — instead of wrapping a callback function, it returns a delayed VALUE. Both achieve the same underlying goal (avoid reacting to every intermediate change), but this shape fits React's data-flow model more naturally for use inside JSX/effects.

useFetch (with Caching)

const { data, loading, error } = useFetch(url)
Fetches data from a URL, tracks loading/error state, CACHES results so repeated calls with the same URL don't re-fetch, and cancels stale in-flight requests to avoid race conditions.
Module-level cache — shared across every component instance, survives unmounts
// hooks/useFetch.js import { useState, useEffect } from "react"; // Module-level cache — lives OUTSIDE the hook function, so it persists // across every component instance and every mount/unmount cycle const cache = new Map(); function useFetch(url) { const [data, setData] = useState(() => cache.get(url) ?? null); const [loading, setLoading] = useState(!cache.has(url)); const [error, setError] = useState(null); useEffect(() => { if (!url) return; // cache HIT — skip the network entirely if (cache.has(url)) { setData(cache.get(url)); setLoading(false); return; } const controller = new AbortController(); // guards against race conditions setLoading(true); setError(null); fetch(url, { signal: controller.signal }) .then((res) => { if (!res.ok) throw new Error(`HTTP ${res.status}`); return res.json(); }) .then((json) => { cache.set(url, json); // store result for future callers/mounts setData(json); setLoading(false); }) .catch((err) => { if (err.name !== "AbortError") { // ignore errors from cancelled requests setError(err); setLoading(false); } }); // cleanup: cancel this specific request if "url" changes or on unmount, // preventing a slow OLD request from overwriting a newer one's result return () => controller.abort(); }, [url]); return { data, loading, error }; } export default useFetch; // ── Usage ── function UserProfile({ userId }) { const { data: user, loading, error } = useFetch(`/api/users/${userId}`); if (loading) return <Spinner />; if (error) return <ErrorMessage error={error} />; return <div>{user.name}</div>; }
🚨 Why the AbortController matters — a classic race condition it prevents: if url changes quickly (e.g. rapid navigation between user profiles), an OLDER, slower request could resolve AFTER a newer one, overwriting the correct, more recent data with stale results. Aborting the previous request when a new one starts (or on unmount) eliminates this class of bug entirely.

useLocalStorage

const [value, setValue] = useLocalStorage(key, initialValue)
Works exactly like useState, but automatically persists the value to localStorage — so it survives page refreshes — and (optionally) stays in sync if the SAME key changes in another browser tab.
// hooks/useLocalStorage.js import { useState, useEffect, useCallback } from "react"; function useLocalStorage(key, initialValue) { // Lazy initializer — reads from localStorage only ONCE, on mount const [value, setValue] = useState(() => { try { const stored = window.localStorage.getItem(key); return stored !== null ? JSON.parse(stored) : initialValue; } catch (err) { console.warn(`Error reading localStorage key "${key}":`, err); return initialValue; } }); // Wrapped setter — updates BOTH React state and localStorage together const setStoredValue = useCallback( (newValue) => { setValue((prev) => { // support the same functional-updater pattern as useState const valueToStore = newValue instanceof Function ? newValue(prev) : newValue; try { window.localStorage.setItem(key, JSON.stringify(valueToStore)); } catch (err) { console.warn(`Error writing localStorage key "${key}":`, err); } return valueToStore; }); }, [key] ); // Sync across OTHER browser tabs — the "storage" event only fires in // tabs that did NOT make the change themselves useEffect(() => { function handleStorageChange(e) { if (e.key === key && e.newValue !== null) { setValue(JSON.parse(e.newValue)); } } window.addEventListener("storage", handleStorageChange); return () => window.removeEventListener("storage", handleStorageChange); }, [key]); return [value, setStoredValue]; } export default useLocalStorage; // ── Usage ── function ThemeToggle() { const [theme, setTheme] = useLocalStorage("theme", "light"); return ( <button onClick={() => setTheme((prev) => (prev === "light" ? "dark" : "light"))}> Current theme: {theme} </button> ); } // Refresh the page — "theme" is restored automatically from localStorage. // Change it in ANOTHER open tab — this tab updates too, via the storage event.
⚠ The try/catch blocks aren't just defensive boilerplate — localStorage access can genuinely throw (e.g. in Safari's private browsing mode, when storage quota is exceeded, or when running in a server-side rendering context where window doesn't exist at all). Always guard localStorage access defensively in a reusable hook meant for general use.

Common Gotchas & Interview Traps

  • ⚠️useDebounce's cleanup function is what makes it a debounce, not just a delay — without `return () => clearTimeout(timerId)`, EVERY keystroke would schedule its own independent update, all eventually firing (a "delay," not a "debounce," which should only reflect the FINAL value).
  • ⚠️A module-level cache in useFetch means the cache is shared across your ENTIRE app, and never automatically expires — without a cache invalidation/TTL strategy, stale data could be served indefinitely; production-grade libraries (React Query, SWR) build in configurable staleness/revalidation logic that a simple hand-rolled cache like this omits.
  • ⚠️Forgetting AbortController in useFetch reintroduces race conditions — rapidly changing the fetched URL (e.g. fast pagination) without cancelling stale in-flight requests can result in an OLDER response overwriting a NEWER one's data if it happens to resolve later.
  • ⚠️useLocalStorage's lazy initializer function must not be called eagerly — passing `useState(readFromLocalStorage())` instead of `useState(() => readFromLocalStorage())` would read from localStorage on EVERY render, not just the first one, which is both wasteful and can cause subtle bugs if the stored value changes elsewhere mid-render-cycle.
  • ⚠️The "storage" event does NOT fire in the SAME tab that made the change — it's designed specifically for cross-tab sync, so testing "does my state update when I change it" within one tab will never trigger that listener; you need a second tab/window to observe it.
  • ⚠️JSON.stringify/JSON.parse in useLocalStorage means functions, undefined, and Symbols silently disappear or error — the hook is best suited for plain serializable data (strings, numbers, plain objects/arrays), not arbitrary JavaScript values.
  • ⚠️localStorage access will throw during server-side rendering (no `window` object exists) — a hook meant to work in an SSR framework needs an additional guard (e.g. checking `typeof window !== "undefined"`) before ever touching localStorage.
  • ⚠️useFetch's cache uses the URL string as its key — two logically-different requests that happen to hit the exact same URL with different HEADERS or a different HTTP METHOD would incorrectly share a cache entry in this simplified implementation; a production version would need a more robust cache key.
  • ⚠️Custom hooks don't share STATE between components by default — two separate components calling `useDebounce` each get their OWN independent timer and debounced value; only `useFetch`'s deliberately module-level cache is actually shared, which is a design choice, not automatic hook behavior.
  • ⚠️Debounce delay values need to match the use case — too short (e.g. 50ms) barely reduces excess calls; too long (e.g. 2000ms) makes the UI feel unresponsive. 300–500ms is a common starting point for search-as-you-type scenarios, but should be tuned based on the actual operation's cost and desired feel.

Interview Q&A — Why / What / When / How

🎯 Building custom hooks from scratch is a favorite "show me you actually understand hooks" interview exercise — practice explaining your DESIGN DECISIONS (why a module-level cache, why AbortController, why a lazy initializer), not just reciting working code.
WhatWhat makes a function a valid "custom hook" rather than just a regular utility function?
+
By convention (and enforced by ESLint's hooks plugin), a custom hook's name must start with `use`, and internally it calls one or more OTHER React hooks (`useState`, `useEffect`, `useRef`, etc.) or other custom hooks. This naming convention is what allows both React and tooling (like the Rules of Hooks ESLint plugin) to correctly identify it as a hook and apply the relevant rules — like not calling it conditionally or inside loops — since a plain utility function has no such constraints.
WhyWhy does useDebounce return a delayed VALUE, rather than a debounced FUNCTION like a classic debounce() utility?
+
React's data flow is fundamentally value-driven — components re-render in response to values (state/props) changing, and effects react to values in their dependency arrays. Returning a debounced VALUE fits naturally into this model: you can pass `debouncedValue` directly into a dependency array, render it, or pass it to another hook, exactly like any other piece of state. A debounced FUNCTION (the classic imperative utility) would require manually wiring it up to specific event handlers, which is a less idiomatic fit for React's declarative style, especially when the goal is simply "wait until this value settles before reacting to it."
WhenWhen would you reach for a hand-rolled useFetch versus a library like React Query or SWR?
+
A simple hand-rolled `useFetch` is reasonable for small apps, prototypes, or when you specifically want to avoid an external dependency and your data-fetching needs are modest (basic caching, loading/error states, avoiding duplicate requests). Reach for a dedicated library once you need more sophisticated behaviors this simple version doesn't handle well: automatic background revalidation, cache invalidation/expiration (TTL), request deduplication across rapidly-mounting/unmounting components, retry logic, pagination/infinite-scroll helpers, or optimistic updates — building and correctly maintaining all of that yourself quickly becomes its own significant undertaking.
HowHow does the AbortController in useFetch actually prevent a race condition, step by step?
+
1. When the effect runs (because `url` changed), a new `AbortController` is created and its `signal` is passed to `fetch`.
2. If `url` changes AGAIN before this fetch resolves, the effect's cleanup function runs FIRST (as part of React's effect lifecycle), calling `controller.abort()` on the PREVIOUS controller.
3. The aborted fetch's promise rejects with an `AbortError`, which the `.catch()` block explicitly checks for and ignores (rather than treating it as a real error).
4. Only the NEWEST request's `.then()` chain ever successfully calls `setData(...)`, since any earlier, now-aborted request's success handlers never fire. This guarantees the state always reflects the LATEST requested URL's result, never an outdated one that happened to resolve later.
WhatWhat's the purpose of the lazy initializer function passed to useState in useLocalStorage?
+
`useState(() => expensiveOrSideEffectfulComputation())` ensures the function is only INVOKED once, during the component's very first render — React calls it to obtain the initial value and then ignores it on every subsequent render. If you instead wrote `useState(expensiveOrSideEffectfulComputation())`, the function call itself would happen on EVERY render (since it's evaluated as a plain argument before `useState` is even called), even though the RESULT is only used once — wasteful for an expensive computation, and potentially incorrect for something with side effects like reading from localStorage, which shouldn't be re-triggered unnecessarily on every render.
WhyWhy does useLocalStorage need a "storage" event listener at all — doesn't useState already keep the UI in sync?
+
`useState` only keeps a SINGLE tab/window's React state in sync with re-renders WITHIN that same JavaScript environment — it has no way to know that a completely different browser tab (a separate, independent JS environment) just modified the SAME localStorage key. The browser's native `"storage"` event is specifically designed to notify OTHER tabs/windows (not the one that made the change) when localStorage changes, which is the only way for this hook to detect and react to that external change and update its own React state accordingly, keeping multiple open tabs visually consistent.
WhenWhen would using a module-level cache (like in useFetch) be the wrong choice, and what would you use instead?
+
A module-level cache is problematic when: data needs a defined expiration/staleness policy (this simple cache never invalidates on its own), you need the cache to be cleared or scoped differently per user/session (e.g. in server-side rendering, where a module-level variable could leak data between different users' requests if the server process is reused), or you need more advanced invalidation triggers (like "refetch when the window regains focus"). In those cases, a dedicated data-fetching library with configurable cache policies (React Query, SWR, Apollo Client for GraphQL) is a better fit, since they're built specifically to handle these more complex caching lifecycles correctly.
HowHow would you extend useFetch to support manually triggering a refetch (e.g. a "refresh" button), bypassing the cache?
+
Add a piece of state that acts as a "trigger" in the dependency array, and expose a function that increments it (forcing the effect to re-run) while explicitly deleting the stale cache entry first:
function useFetch(url) { // ...existing state... const [refetchIndex, setRefetchIndex] = useState(0); const refetch = () => { cache.delete(url); // invalidate the stale cached value setRefetchIndex((i) => i + 1); // forces the effect below to re-run }; useEffect(() => { // ...existing fetch logic... }, [url, refetchIndex]); // "refetchIndex" added purely to trigger manual re-runs return { data, loading, error, refetch }; }
The component can then call `refetch()` from a button's `onClick`, which clears the cache entry for that URL and increments the trigger state, causing the effect to re-run and fetch fresh data even though the URL itself hasn't changed.
