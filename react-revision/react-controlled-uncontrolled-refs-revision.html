Controlled Components

💡 A controlled component has its value driven entirely by React STATE — the input's value comes from state, and every keystroke fires an onChange that updates that state, which then re-renders the input with the new value. React is the "single source of truth."
The controlled input loop — value flows THROUGH React on every keystroke
function ControlledInput() { const [value, setValue] = useState(""); // React state IS the source of truth return ( <input value={value} // input DISPLAYS whatever state says onChange={(e) => setValue(e.target.value)} // every keystroke updates state /> ); } // The DOM input never "owns" its own value — React re-renders it with // whatever "value" currently is, on every single keystroke // Benefits this unlocks — instant, synchronous access to the current value: function SearchBox() { const [query, setQuery] = useState(""); const handleChange = (e) => { const newValue = e.target.value; setQuery(newValue.toUpperCase()); // ✓ transform/validate on EVERY keystroke }; return <input value={query} onChange={handleChange} />; } // e.g. force-uppercase as the user types, live-validate, live-format, etc.
✓ Use controlled components when you need to validate/transform input as the user types, conditionally disable a submit button based on live input, sync the value with other UI elements, or enforce a specific input format in real time.

Uncontrolled Components

💡 An uncontrolled component manages its own value internally, in the DOM itself — just like a normal HTML form field. React does NOT track every keystroke; you read the current value only when you actually need it, using a ref.
Uncontrolled — the DOM owns the value; React just reaches in when needed
function UncontrolledInput() { const inputRef = useRef(null); const handleSubmit = (e) => { e.preventDefault(); console.log(inputRef.current.value); // read the value ONLY when needed }; return ( <form onSubmit={handleSubmit}> <input ref={inputRef} defaultValue="initial text" /> <button type="submit">Submit</button> </form> ); } // No onChange handler, no state, no re-render per keystroke — // React only reaches in to READ the value when the form is submitted // Note: use "defaultValue"/"defaultChecked" for INITIAL value on uncontrolled // inputs — NOT "value", which would make React think it's controlled and // throw a warning about switching between controlled/uncontrolled
✓ Use uncontrolled components when you only need the value at a specific moment (like form submission), you're integrating with a non-React library that manages its own DOM state, or you want to avoid the performance cost of a re-render on every keystroke in a very large/complex form.

Refs — What They Are & When to Use Them

💡 useRef() creates a mutable "box" ({ current: ... }) that PERSISTS across re-renders WITHOUT causing a re-render when it changes — unlike state. Attached to a JSX element via the ref attribute, it gives you direct access to the underlying DOM node.
// Focus management — can't be done declaratively via props alone function SearchBox() { const inputRef = useRef(null); useEffect(() => { inputRef.current.focus(); // imperatively focus on mount }, []); return <input ref={inputRef} />; } // Other common imperative DOM needs refs are good for: // - .scrollIntoView(), .play()/.pause() on video/audio elements // - measuring an element's size/position (getBoundingClientRect) // - integrating a non-React library that needs a real DOM node (e.g. a chart library)
// A ref for data that needs to PERSIST across renders but should NOT trigger a re-render function StopWatch() { const [running, setRunning] = useState(false); const intervalRef = useRef(null); // holds the interval ID const start = () => { intervalRef.current = setInterval(() => console.log("tick"), 1000); setRunning(true); }; const stop = () => { clearInterval(intervalRef.current); // read it back later — persisted correctly setRunning(false); }; // Storing the interval ID in STATE instead would cause an unnecessary // re-render every time it's set — a ref avoids that entirely }
// Tracking the PREVIOUS value of a prop/state across renders function usePrevious(value) { const ref = useRef(); useEffect(() => { ref.current = value; // updates AFTER the render commits, so it lags by one render }); return ref.current; // during THIS render, still holds the value from last time } function Counter({ count }) { const prevCount = usePrevious(count); return <p>Now: {count}, before: {prevCount}</p>; }

forwardRef

💡 By default, ref is NOT a regular prop — you can't pass a ref to a custom function component and have it "just work" the way it does on a plain DOM element like <input>. forwardRef is the API that lets a component RECEIVE a ref from its parent and attach it to something inside (usually a DOM node).
Without forwardRef, a ref on a custom component does nothing
✗ Without forwardRef — ref is ignored
function FancyInput(props) { return <input className="fancy" {...props} />; } const ref = useRef(); <FancyInput ref={ref} />; ref.current; // → null! "ref" was never // passed through — it's a special // prop React strips out automatically
✓ With forwardRef — ref reaches the DOM node
const FancyInput = forwardRef((props, ref) => { return <input className="fancy" ref={ref} {...props} />; }); const ref = useRef(); <FancyInput ref={ref} />; ref.current; // → the actual <input> DOM node! ✓ ref.current.focus(); // now works from the parent
⚠ Newer React versions (19+) allow passing ref as a regular prop on function components directly, removing the need for forwardRef in many cases — but understanding WHY forwardRef exists (and how it works) is still core interview knowledge, since most existing codebases and older React versions still rely on it.
// useImperativeHandle — customize exactly what the forwarded ref exposes const FancyInput = forwardRef((props, ref) => { const inputRef = useRef(); useImperativeHandle(ref, () => ({ // only THESE methods are exposed to the parent — not the whole DOM node focus: () => inputRef.current.focus(), clear: () => { inputRef.current.value = ""; } })); return <input ref={inputRef} {...props} />; }); // Parent can now ONLY call ref.current.focus() or ref.current.clear() — // not arbitrary DOM methods, giving the child full control over its own API

When NOT to Use Refs

🚨 Refs are an escape hatch for imperative code, deliberately positioned OUTSIDE React's normal declarative rendering flow. Reaching for them to solve problems React's own state/props system already solves is a common anti-pattern.
✗ Anti-pattern — ref for UI that should be state
function Toggle() { const isOnRef = useRef(false); const handleClick = () => { isOnRef.current = !isOnRef.current; // ✗ UI never updates! Changing a ref // does NOT trigger a re-render — the // displayed text stays stuck forever }; return ( <button onClick={handleClick}> {isOnRef.current ? "ON" : "OFF"} </button> ); }
✓ Correct — this belongs in state
function Toggle() { const [isOn, setIsOn] = useState(false); return ( <button onClick={() => setIsOn(!isOn)}> {isOn ? "ON" : "OFF"} </button> ); } // setIsOn correctly triggers a re-render, // so the button label actually updates
SituationUse stateUse a ref
Value is displayed in the rendered UI✓ Yes✗ No — ref changes are invisible to the UI
Value determines what JSX to render✓ Yes✗ No
Value should trigger effects/derived calculations✓ Yes✗ No — effects with refs in deps won't "see" changes
Directly manipulating a DOM node (focus, scroll, measuring)✗ Overkill✓ Yes
Storing a mutable value the render logic doesn't use (timer ID, previous value for comparison)✗ Wasteful re-renders✓ Yes
⚠ Directly mutating the DOM via a ref while ALSO letting React manage that same element can cause conflicts — e.g. manually setting inputRef.current.value = "x" on a CONTROLLED input fights against React's own re-renders, leading to inconsistent, hard-to-debug behavior. Pick one owner (React state, OR the ref/DOM) per piece of UI, not both.

Common Gotchas & Interview Traps

  • ⚠️Switching between controlled and uncontrolled at runtime triggers a React warning — e.g. an input that starts with `value={undefined}` (uncontrolled) and later gets a real string value (controlled) mid-lifecycle. Always initialize state to a defined value (like `""`) from the start to keep it consistently controlled.
  • ⚠️Using both `value` and `defaultValue` on the same input is a common mistake — `value` makes it controlled (React owns it); `defaultValue` is only for the INITIAL value of an uncontrolled input. Mixing them causes confusing warnings and unpredictable behavior.
  • ⚠️Changing a ref's `.current` value does NOT trigger a re-render — if you need the UI to visually reflect a changing value, that value MUST live in state, not a ref, no matter how tempting it is to "just mutate the ref" to avoid a re-render.
  • ⚠️`ref` is not a real prop — it doesn't show up in `props` inside a function component, and passing it directly to a custom component without `forwardRef` (in React <19) silently does nothing; there's no error, just `ref.current` staying `null`.
  • ⚠️Reading `ref.current` during the render phase (not inside an effect or event handler) can give you stale or null values — refs attached to DOM elements are only guaranteed to be set AFTER the render commits (i.e., inside `useEffect` or later), not during the render function's own execution.
  • ⚠️Overusing refs to avoid "unnecessary re-renders" often backfires — if the value needs to affect what's rendered, using a ref just means the UI silently goes stale instead of updating, which is a worse bug than an extra re-render would have been.
  • ⚠️useImperativeHandle should be used sparingly — exposing a large, ad-hoc imperative API from a component undermines React's declarative model; prefer normal props/state whenever the parent's need can be expressed declaratively instead.
  • ⚠️forwardRef adds an extra layer that can complicate TypeScript typing and testing — components wrapped in `forwardRef` sometimes need extra generic type parameters, and some testing utilities historically had friction with ref-forwarding wrapper components.
  • ⚠️A callback ref (a function passed to `ref` instead of a ref object) runs on EVERY render if defined inline — `ref={node => doSomething(node)}` creates a NEW function each render, causing React to call it with `null` then the new node on every re-render; wrap it in `useCallback` if this matters for your use case.
  • ⚠️File inputs (`<input type="file">`) can ONLY be uncontrolled — for security reasons, browsers do not allow JavaScript to programmatically SET a file input's value, so `value` on a file input is not supported; you must read the selected file(s) via a ref instead.

Interview Q&A — Why / What / When / How

🎯 Answering from multiple angles (why does it exist, what is it exactly, when do you reach for it, how do you implement it) demonstrates depth beyond a memorized definition.
WhatWhat's the fundamental difference between a controlled and an uncontrolled component?
+
In a CONTROLLED component, the form element's value is driven by React state — you pass `value` and update it via `onChange`, making React the single source of truth. In an UNCONTROLLED component, the DOM element manages its own value internally (like a plain HTML form), and React only reaches in to read the current value via a `ref` when it's actually needed, rather than tracking it on every keystroke.
WhyWhy does React generally recommend controlled components as the default choice?
+
Controlled components keep form data consistent with React's single-source-of-truth philosophy — the current value is always available in state, ready to be validated, transformed, conditionally used to enable/disable other UI, or submitted, all without needing to imperatively reach into the DOM. This fits naturally with React's declarative rendering model: the UI is always a direct reflection of state, with no separate, hidden "DOM state" that could drift out of sync with what your component logic believes to be true.
WhenWhen would you deliberately choose an uncontrolled component over a controlled one?
+
When you only need the value at a specific moment rather than on every keystroke (e.g. a simple form only read on submit), when integrating a third-party/non-React widget that manages its own internal DOM state and doesn't expect to be controlled externally, when working with a file input (which technically CANNOT be controlled for security reasons), or in performance-sensitive scenarios with a very large number of fields where avoiding a re-render per keystroke provides a measurable benefit.
HowHow would you read a form's values on submit using an uncontrolled approach, without individual refs for every field?
+
Attach a single ref to the `<form>` element itself, then use the native `FormData` API on submit to collect every field's value at once, keyed by each input's `name` attribute:
function MyForm() { const formRef = useRef(); const handleSubmit = (e) => { e.preventDefault(); const data = new FormData(formRef.current); console.log(data.get("email")); // reads by input "name" }; return ( <form ref={formRef} onSubmit={handleSubmit}> <input name="email" /> </form> ); }
WhatWhat is a ref, and how is it different from state?
+
A ref (`useRef()`) is a mutable object (`{ current: value }`) that PERSISTS across re-renders, just like state — but unlike state, updating a ref's `.current` value does NOT trigger a re-render, and the update takes effect immediately/synchronously rather than being scheduled. Refs are used both for holding a reference to a real DOM node (via the `ref` JSX attribute) and for storing any mutable value that the component's rendering logic doesn't directly depend on.
WhyWhy doesn't updating a ref cause a re-render, and why is that actually useful?
+
Refs are specifically designed as an ESCAPE HATCH for values that exist outside React's normal rendering/reactivity model — things like a timer ID, a DOM node reference, or a "previous value" you're tracking purely for comparison, none of which need to visually affect the UI when they change. Skipping the re-render is useful because it avoids the performance cost of running the whole render cycle for data changes that have no bearing on what should actually be displayed on screen.
WhenWhen should you NOT use a ref, even though it might seem like the "simpler" choice?
+
Whenever the value needs to be REFLECTED in the rendered UI, or needs to trigger downstream effects/derived calculations — a ref update is invisible to React's rendering system, so the screen will silently go stale rather than update. If you find yourself reading `someRef.current` inside JSX to decide what to display, that's a strong signal the value should be state instead. Reaching for a ref purely to "avoid a re-render" when the value genuinely affects the UI trades a correctness bug for a performance micro-optimization that usually isn't even necessary.
WhatWhat problem does forwardRef solve?
+
By default, `ref` is a special attribute that React intercepts and does NOT pass through to a component's `props` — this works fine for built-in DOM elements like `<input>` (React attaches the ref to the actual DOM node automatically), but for a CUSTOM function component, there's no automatic DOM node for the ref to attach to, so the ref is simply dropped/ignored. `forwardRef` solves this by explicitly giving a component access to the ref its parent passed, as a second function argument, so the component can manually attach it to whatever internal DOM node makes sense.
WhyWhy would you use useImperativeHandle together with forwardRef, instead of just forwarding the raw DOM node?
+
Forwarding the raw DOM node gives the parent UNRESTRICTED access to everything the DOM element can do — every native method and property, which can make the component's internal implementation details part of its public "API" by accident, and makes future refactors of the internal markup riskier (anything a parent might have relied on could break). `useImperativeHandle` lets the component define a deliberate, minimal, custom set of methods/values to expose via the ref instead — the parent only sees exactly what the component author intended (e.g. `focus()` and `clear()`), keeping the internal DOM structure free to change without breaking consumers.
WhenWhen is it appropriate to reach for forwardRef, versus solving the problem with props/callbacks instead?
+
Reach for `forwardRef` when the parent genuinely needs IMPERATIVE access to something inside the child — like triggering a focus, scroll, or animation on demand, or measuring a DOM node's size — actions that don't fit naturally into a "pass data down, receive events up" declarative flow. If the interaction can instead be expressed as "the parent passes a prop that controls the child's behavior/appearance," prefer that declarative approach; reaching for a ref-based imperative API when a simple prop would do adds unnecessary complexity and moves away from React's strengths.
HowHow would you implement a custom input component that exposes only a focus() method to its parent, hiding everything else about its internals?
+
const CustomInput = forwardRef((props, ref) => { const internalRef = useRef(null); useImperativeHandle(ref, () => ({ focus: () => internalRef.current.focus() // intentionally nothing else exposed — parent can't reach // internalRef.current.value, .style, or any other DOM detail })); return <input ref={internalRef} {...props} />; }); // Parent usage const inputRef = useRef(); <CustomInput ref={inputRef} />; inputRef.current.focus(); // ✓ works inputRef.current.value; // → undefined — NOT exposed, by design
This pattern gives the child component full control over its public "imperative API," decoupled from its actual internal DOM structure.
WhyWhy is directly mutating a controlled input's DOM value via a ref (alongside its normal React state) a bad idea?
+
A controlled input's displayed value is meant to be entirely determined by React's `value` prop, re-rendered from state on every change. If you ALSO directly set `inputRef.current.value = "something"` imperatively, you're bypassing React's rendering pipeline — the actual DOM will temporarily show your imperatively-set value, but the next time React re-renders (for any reason), it will forcibly reset the DOM back to whatever its `value` prop/state says, potentially overwriting your manual change unexpectedly. This creates a genuine "who owns this value" conflict between React's declarative model and your imperative code, leading to inconsistent, hard-to-debug behavior. Pick ONE owner — either fully controlled via state, or fully uncontrolled via the DOM/ref — not both simultaneously for the same element.
