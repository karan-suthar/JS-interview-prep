Props vs State — The Core Distinction

💡 Props are data passed INTO a component from its parent — read-only from the receiving component's perspective. State is data a component OWNS and manages internally — it can change over time and triggers a re-render when updated.
Props flow in from outside · State lives inside
// PROPS — passed in, read-only from the child's perspective function Greeting({ name }) { // "name" is a PROP return <h1>Hello, {name}!</h1>; } <Greeting name="Alice" /> // parent controls the value // STATE — owned and managed internally, can change over time function Counter() { const [count, setCount] = useState(0); // "count" is STATE return ( <button onClick={() => setCount(count + 1)}> Clicked {count} times </button> ); } // Counter fully owns "count" — no parent needs to know or supply it

✓ Mental model: think of a component as a function. Props are its parameters — supplied by the caller. State is like a useRef/local variable that persists across calls and that the function itself is allowed to update.
2

Unidirectional Data Flow

💡 React data flows in ONE direction only: from parent to child, via props. A child can never directly modify a prop or reach "up" to change its parent's state — it can only ask the parent to change it, by calling a function the parent passed down.
The one-way cycle: state down as props → events up as callbacks
function App() { const [items, setItems] = useState(["Apple", "Banana"]); const handleAdd = (newItem) => { setItems([...items, newItem]); // ONLY App can update its own state }; return ( <> <ItemList items={items} /> // data flows DOWN <AddItemForm onAdd={handleAdd} /> // a CALLBACK flows down too </> ); } function AddItemForm({ onAdd }) { const [text, setText] = useState(""); return ( <button onClick={() => onAdd(text)}> Add Item </button> ); } // AddItemForm never touches "items" directly — it just CALLS the function // App gave it. This keeps the data flow predictable and traceable.
✓ Why this design matters: because data only flows one way, you can always answer "where did this value come from?" by tracing UP the component tree — there's no hidden two-way binding magic to reverse-engineer. This makes React apps significantly easier to debug than frameworks with implicit two-way data binding.

Lifting State Up

💡 When two or more sibling components need to share/stay in sync with the SAME piece of state, you move ("lift") that state to their closest common ancestor — the ancestor then owns the state and passes it down to both siblings as props.
✗ Before — state trapped in one sibling
function TemperatureInput() { const [celsius, setCelsius] = useState(0); return <input value={celsius} .../>; } function TemperatureDisplay() { // ✗ has NO WAY to know celsius's value — // it's trapped inside TemperatureInput! return <p>??? °F</p>; }
✓ After — lifted to the common parent
function Converter() { const [celsius, setCelsius] = useState(0); // lifted here return ( <> <TemperatureInput value={celsius} onChange={setCelsius} /> <TemperatureDisplay celsius={celsius} /> </> ); } // Both siblings now stay perfectly in sync — single source of truth
Where state lives before vs after lifting
⚠ Rule of thumb for WHERE to put state: place it in the lowest common ancestor of all components that need it — not higher (unnecessarily forces unrelated parts of the tree to re-render) and not lower (some components that need it won't have access).

Prop Drilling — The Problem

🚨 Prop drilling happens when you pass a prop through MULTIPLE layers of components that don't actually use it themselves — they only forward it along to some deeply nested descendant that finally needs it.
theme has to pass through 3 components that never use it, just to reach Avatar
// Prop drilling in code — "theme" passes through 3 components that never use it function App() { const [theme, setTheme] = useState("dark"); return <Page theme={theme} />; } function Page({ theme }) { return <Sidebar theme={theme} />; // Page doesn't use theme itself } function Sidebar({ theme }) { return <UserPanel theme={theme} />; // neither does Sidebar } function UserPanel({ theme }) { return <Avatar theme={theme} />; // nor UserPanel } function Avatar({ theme }) { return <img className={theme} />; // ✓ FINALLY used, 4 levels down! }
⚠ Why it becomes a real problem at scale: every intermediate component becomes tightly coupled to a prop it doesn't care about. Renaming, adding, or removing that prop means editing EVERY component along the chain. It also hurts readability (you can't tell what a component actually needs just by reading its own code) and can cause unnecessary re-renders of middle components.
5

Solutions to Prop Drilling

💡 React's built-in Context API lets a value be read directly by ANY descendant component, no matter how deeply nested — skipping all the intermediate "middlemen" components entirely.
const ThemeContext = createContext("light"); function App() { const [theme, setTheme] = useState("dark"); return ( <ThemeContext.Provider value={theme}> <Page /> // no "theme" prop needed anywhere below! </ThemeContext.Provider> ); } function Page() { return <Sidebar />; } // clean — no theme prop function Sidebar() { return <UserPanel />; } // clean — no theme prop function UserPanel() { return <Avatar />; } // clean — no theme prop function Avatar() { const theme = useContext(ThemeContext); // reads DIRECTLY, skipping all middlemen return <img className={theme} />; }
🧩 Instead of passing DATA down through props, pass already-built JSX (via children or other element-valued props) — the parent that has the data renders the deep component directly, no forwarding required.
// Instead of drilling "theme" through Page and Sidebar to reach UserPanel... function App() { const [theme, setTheme] = useState("dark"); // ...build the deep component HERE, where the data already lives... return <Page sidebar={<Sidebar userPanel={<UserPanel theme={theme} />} />} />; } // ...and pass it through as "children" or a slot prop — Page/Sidebar // never need to know "theme" exists at all, they just render what they're given function Page({ sidebar }) { return <div>{sidebar}</div>; } function Sidebar({ userPanel }) { return <aside>{userPanel}</aside>; } // Simpler common case — just "children" function Layout({ children }) { return <div className="layout">{children}</div>; } <Layout><Avatar theme={theme} /></Layout> // Layout never touches "theme"
⚠ For LARGE, complex apps with lots of shared/global state accessed from many unrelated parts of the tree, a dedicated state management library can be a better fit than Context (which can cause broad re-renders and gets unwieldy with many separate values).
// Example shape — using a library like Zustand or Redux (conceptual, not exact API) const useThemeStore = create((set) => ({ theme: "dark", setTheme: (theme) => set({ theme }), })); // ANY component, at ANY depth, can subscribe directly — no drilling, no Context wrapper function Avatar() { const theme = useThemeStore(state => state.theme); return <img className={theme} />; } // Trade-off: adds an external dependency and some architectural overhead — // usually only worth it once Context alone becomes hard to manage

Common Gotchas & Interview Traps

  • ⚠️Mutating props directly is a bug, not just bad style — `props.value = "x"` inside a child does NOT propagate back to the parent's state and can cause confusing, inconsistent rendering. Props must be treated as read-only.
  • ⚠️"Controlled" vs "uncontrolled" components hinges on this exact distinction — a controlled input's value comes from STATE (owned by a parent, passed as a prop) with changes reported via a callback; an uncontrolled input manages its own value internally via the DOM, only read via a ref when needed.
  • ⚠️Lifting state up too far hurts performance — putting state in a very high-level ancestor when only two nearby siblings need it forces a much larger part of the tree to re-render on every update than necessary.
  • ⚠️Context is not a full replacement for well-structured props — overusing Context for values only needed by ONE or TWO levels of nesting can make component dependencies less explicit and harder to trace than simply passing a prop directly.
  • ⚠️Every consumer of a Context re-renders when its value changes — even if the consuming component only cares about ONE field of a larger context object. Splitting a large context into several smaller, more focused ones can prevent unnecessary re-renders.
  • ⚠️Prop drilling isn't ALWAYS bad — for shallow trees (2-3 levels) it's often simpler and more explicit than introducing Context or a state library. Reach for a fix only once drilling actually becomes painful (many levels, or the same props threading through many different branches).
  • ⚠️Passing a new inline function/object as a prop on every render can cause unnecessary re-renders of memoized children (`React.memo`), since a new reference is created each time even if the logical content is the same — relevant when discussing performance alongside prop passing.
  • ⚠️"Single source of truth" doesn't mean only ONE state variable in the whole app — it means for any GIVEN piece of data, there should be exactly one component that owns/controls it, with everyone else reading a derived/passed-down copy, rather than multiple components independently tracking their own out-of-sync copies of the same logical value.
  • ⚠️Derived state duplicated into a separate useState is a common anti-pattern — if a value can be COMPUTED from existing props/state, just compute it during render rather than syncing it into its own state variable with a useEffect, which risks it becoming stale/out of sync.
  • ⚠️Callback props passed down for "lifting state up" must be stable in identity when performance matters — wrap them in `useCallback` if they're passed to memoized children, to avoid defeating the memoization.

Interview Q&A — Why / What / When / How

🎯 Interviewers often frame questions around these 4 angles. Practice answering each type for this topic — it shows depth beyond just reciting definitions.
WhatWhat exactly is the difference between props and state?
+
Props are data passed INTO a component by its parent — immutable from the receiving component's own perspective, like function arguments. State is data a component manages INTERNALLY and can change over time via its own setter function, triggering a re-render. Both cause re-renders when they change, but only the component itself can change its own state, while props can only be changed by whichever parent is supplying them.
WhyWhy does React enforce unidirectional data flow instead of allowing two-way binding?
+
Two-way data binding (where a child can directly mutate a parent's state) makes it hard to trace WHERE a change originated from, especially as an app grows — any component anywhere could be silently modifying shared data. Unidirectional flow means data always moves down via props, and changes always move up via explicit callback functions — so at any point you can trace a value's origin by walking UP the component tree, making apps significantly easier to reason about, debug, and predict.
WhenWhen should you lift state up vs keep it local to a single component?
+
Keep state LOCAL when only one component (and its own descendants) needs it — e.g. whether a single dropdown is open. LIFT state up as soon as TWO OR MORE sibling components need to read or stay synchronized with the same value — e.g. a shopping cart total that both a cart icon in the header and a checkout summary need to reflect. The state should live in the closest common ancestor of everyone who needs it — no higher, no lower.
HowHow would you refactor two sibling components that each keep their own separate copy of the same logical value?
+
Step 1: identify the closest common ancestor of both siblings.
Step 2: move the `useState` call from wherever it currently lives up into that ancestor.
Step 3: pass the state value down to both siblings as a prop.
Step 4: pass a callback function (e.g. the setter, or a wrapper around it) down to whichever sibling needs to trigger updates.
Step 5: remove the now-redundant local state from both siblings, having them read/update via the passed-down prop and callback instead.
WhatWhat is prop drilling, precisely?
+
Prop drilling is the pattern where a piece of data is passed as a prop through one or more INTERMEDIATE components that don't actually use that data themselves — they only accept it and immediately forward it further down to some descendant that does need it. The intermediate components become unwilling "pass-through" middlemen for data they have no real interest in.
WhyWhy is prop drilling considered a problem worth solving, rather than just "how React works"?
+
It creates tight, unnecessary COUPLING — every intermediate component's prop signature depends on something it doesn't actually care about, purely because of where it sits in the tree. This makes refactoring painful (renaming or restructuring the drilled prop means touching every component along the chain), makes components harder to understand in isolation (you can't tell what a component truly needs just by reading it — some props are "pass-through noise"), and makes components less reusable elsewhere, since they now carry an irrelevant dependency.
WhenWhen is prop drilling actually FINE, and you shouldn't reach for Context or a state library?
+
When the tree is SHALLOW — passing a prop through just one or two intermediate levels is often more explicit and easier to trace than introducing Context, which adds its own indirection (you have to go find the Provider to understand where a value comes from). Prop drilling becomes worth fixing once you're threading the SAME prop through many (4+) levels, or through MANY different branches of a large, deeply-nested tree — that's when the coupling and maintenance cost actually starts to outweigh the simplicity of plain props.
HowHow does the Context API solve prop drilling, mechanically?
+
You create a Context object with `createContext()`, wrap the part of the tree that needs access in a `<Context.Provider value={...}>`, and then any descendant component — no matter how deeply nested — can call `useContext(Context)` to read that value DIRECTLY, without it being explicitly passed as a prop through every component in between. This effectively creates a "wormhole" that skips the intermediate layers, so components that don't care about the value never need to mention it in their props at all.
WhatWhat's the difference between "component composition" and Context as solutions to prop drilling?
+
Context lets a deeply nested component pull a value directly from a Provider higher up, bypassing intermediate components entirely — the DATA travels invisibly through the tree. Component composition instead restructures HOW components are nested: instead of passing raw data down through props, you pass already-constructed JSX elements (often via `children` or a similarly-named prop) — the component that has the data builds the deeply nested element directly, and the components "in between" just render whatever element they're handed, without ever needing to know or care what data it contains.
WhyWhy can't a child component simply modify a prop value to communicate a change back to its parent?
+
Props are treated as immutable/read-only by convention AND by React's rendering model — a prop is really just a reference to a value the PARENT owns and controls via ITS OWN state. If a child directly mutated a prop, the parent's actual state (the true source of truth) would remain unchanged, and React wouldn't know to trigger a re-render, leading to an inconsistent UI. The correct pattern is for the parent to pass a CALLBACK function as a prop; the child calls that function to REQUEST a change, and the parent decides how (and whether) to update its own state in response — keeping the parent in full control of its own data.
WhenWhen would you reach for a state management library (like Redux or Zustand) instead of just using Context?
+
When the app has LARGE amounts of shared state accessed and updated FREQUENTLY from many unrelated parts of the component tree, and Context's "every consumer re-renders on any value change" behavior starts causing real performance problems, or when you need advanced features Context doesn't provide out of the box — like time-travel debugging, middleware for side effects, or fine-grained subscriptions to just one slice of a larger state object without over-rendering. For small-to-medium apps, or state that's mostly read-only/rarely-changing (like theme or logged-in user), plain Context is usually sufficient and simpler.
HowHow would you decide, step by step, whether a given piece of data should be props, local state, lifted state, or Context?
+
1. Does this component receive the value from somewhere else, and never change it itself? → It's a PROP.
2. Does only this ONE component (and its descendants) need this value, and does it change over time based on user interaction? → It's LOCAL STATE.
3. Do two or more SIBLING components need to read or affect the same value? → LIFT the state to their closest common ancestor, pass down as props/callbacks.
4. Is the value needed by MANY components scattered at DIFFERENT, deeply nested points across the tree, such that lifting would mean drilling through many uninterested layers? → Consider CONTEXT (or a state library, if updates are frequent and performance-sensitive).
