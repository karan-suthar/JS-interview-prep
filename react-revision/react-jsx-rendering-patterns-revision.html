JSX Compiles to React.createElement()

💡 JSX is not HTML and not part of JavaScript — it's syntactic sugar. A build tool (Babel, or the TypeScript compiler) transforms every JSX expression into a plain JavaScript function call BEFORE it ever reaches the browser. React itself never sees JSX — only the function calls it compiles down to.
What you write vs what actually runs
You write (JSX)
<h1 className="title"> Hello, {name}! </h1>
→
Babel compiles to
React.createElement( "h1", { className: "title" }, "Hello, ", name, "!" )
// React.createElement's signature React.createElement( type, // string ("div", "h1"...) OR a component function/class props, // object of attributes/props, or null if none ...children // any number of child elements/text/expressions ); // A component (capitalized) compiles the same way — just a different "type" function Welcome({ name }) { return <h1>Hello, {name}</h1>; } <Welcome name="Alice" /> // compiles to: React.createElement(Welcome, { name: "Alice" }) // Note: "Welcome" is passed as the ACTUAL FUNCTION REFERENCE, not a string — // this is EXACTLY why components must start with a capital letter: lowercase // tags compile to STRINGS ("div"), capitalized tags compile to VARIABLE lookups
// Nested JSX — each level becomes a nested createElement call <div className="card"> <h2>Title</h2> <p>Some text</p> </div> // compiles to: React.createElement( "div", { className: "card" }, React.createElement("h2", null, "Title"), React.createElement("p", null, "Some text") )
⚠ Since React 17, a NEW JSX transform exists that compiles differently (importing special jsx/jsxs functions from react/jsx-runtime instead of calling React.createElement directly) — this is why modern React files no longer need import React from 'react' just to use JSX. The underlying CONCEPT (JSX → function calls → element objects) is unchanged; only the specific function names differ.
// Old transform (React ≤16, or explicitly configured) import React from "react"; // REQUIRED — JSX secretly needs "React" in scope <div /> // → React.createElement("div", null) // New transform (React 17+, default in modern tooling) // No import needed — the compiler auto-injects its own import <div /> // → _jsx("div", {}) (from "react/jsx-runtime", auto-imported by the compiler)
✓ Key interview takeaway: since JSX is just function calls under the hood, you can write plain JavaScript ANYWHERE you'd write JSX — including conditionals, loops, and variables holding elements — because it's not special template syntax, it's regular expressions that happen to return objects.

What createElement() Actually Returns

💡 React.createElement() does NOT create a real DOM node — it returns a lightweight, plain JavaScript object describing what should be rendered (a "React element"). This is the foundation of the Virtual DOM.
The object React.createElement("h1", {className:"title"}, "Hi") returns (simplified)
{
$$typeof: Symbol(react.element),
type: "h1",
props: { className: "title", children: "Hi" },
key: null,
ref: null
}
// This is why you can store JSX in a variable, pass it around, return it conditionally — // it's just a plain object, like any other JS value const element = <h1>Hello</h1>; typeof element; // → "object" element.type; // → "h1" element.props.children; // → "Hello" // React then takes this object TREE and turns it into REAL DOM nodes // (or diffs it against the previous tree, in the case of updates) ReactDOM.createRoot(rootEl).render(element);
🌳 Virtual DOM in one sentence: React builds a tree of these lightweight element objects on every render, compares ("diffs") it to the tree from the previous render, and only applies the MINIMAL set of real DOM mutations needed to catch the actual DOM up to the new tree.

Why the "key" Prop Matters

💡 key is a special prop that helps React's reconciliation algorithm identify which items in a list have changed, been added, or been removed — across re-renders. Without stable keys, React falls back to comparing items by POSITION (index), which can cause it to mismatch elements and their internal state.
The classic bug — inserting an item at the FRONT of a list, without stable keys
Before
index 0: 🍎 Apple
index 1: 🍌 Banana
index 2: 🍊 Orange
After (added 🍇 Grape at front)
index 0: 🍇 Grape
index 1: 🍎 Apple
index 2: 🍌 Banana
index 3: 🍊 Orange
Using array INDEX as key: React thinks "index 0 changed from Apple→Grape, index 1 changed from Banana→Apple..." — it mutates EVERY row's content instead of recognizing that 3 items just shifted down and 1 was inserted. Any internal state per-row (like an input's typed text) ends up attached to the WRONG item.
✗ Using array index as key
{items.map((item, index) => ( <Item key={index} data={item} /> ))} // Works fine for STATIC lists that // never reorder/insert/delete — but // breaks for dynamic lists
✓ Using a stable, unique ID as key
{items.map((item) => ( <Item key={item.id} data={item} /> ))} // React correctly tracks each item // by its STABLE identity, regardless // of position changes
// Concrete bug demonstration: state gets attached to the WRONG row function TodoList({ todos }) { return ( <ul> {todos.map((todo, index) => ( // ✗ using index — if todos are reordered/filtered, each <TodoItem> // keeps its OWN internal useState (e.g. "isEditing") tied to its // POSITION, not the actual todo — editing state can jump to the // WRONG todo after the list changes! <TodoItem key={index} todo={todo} /> ))} </ul> ); } // Fix: use todo.id (a stable identifier from your data), not the array index
SituationIndex as key OK?Why
Static list, never reorders/filters/inserts✓ AcceptableIndex always maps to the same logical item
List can be reordered, filtered, or items inserted/removed✗ AvoidIndex no longer maps to a stable identity — causes state/DOM mismatches

⚠ key is NOT accessible as a regular prop inside the component (props.key is always undefined) — it's consumed internally by React for reconciliation only. If you need the same value inside the component, pass it again under a different prop name.

Fragments <>...</>

💡 A component must return a single root element — JSX can't return two sibling elements directly. Fragments let you group multiple children WITHOUT adding an extra wrapper <div> to the actual DOM output.
✗ Invalid — two root elements
function List() { return ( <li>First</li> <li>Second</li> ); } // ✗ SyntaxError: Adjacent JSX // elements must be wrapped
✓ Fragment shorthand — no extra DOM node
function List() { return ( <> <li>First</li> <li>Second</li> </> ); } // renders exactly: <li>First</li><li>Second</li>
// Two equivalent syntaxes <> // shorthand — most common <Header /> <Body /> </> <React.Fragment> // explicit form — REQUIRED when you need a "key" <Header /> <Body /> </React.Fragment> // Fragments CAN take a "key" — but ONLY the explicit <React.Fragment> form // supports props; the <></> shorthand does NOT accept any attributes at all {items.map(item => ( <React.Fragment key={item.id}> <dt>{item.term}</dt> <dd>{item.definition}</dd> </React.Fragment> ))} // Useful when you need multiple sibling elements per list item // (e.g. a <dt>/<dd> pair) WITHOUT an unwanted wrapping <div>
✓ Why avoid unnecessary wrapper divs: extra nesting can break CSS layouts relying on direct parent-child relationships (like CSS Grid/Flexbox children, or <table>/<tr>/<td> structure, which is strict about valid HTML nesting). Fragments solve this by grouping elements in React's virtual tree without adding anything to the real DOM.

Conditional Rendering Patterns

💡 Because JSX is just JavaScript expressions, you use REGULAR JS control flow to decide what to render — there's no special "if" template directive. Different patterns fit different situations.
&& short-circuit
Render something ONLY if a condition is true; render nothing otherwise.
{isLoggedIn && ( <WelcomeBanner /> )} // if isLoggedIn is false, renders // "false" — React knows to skip // rendering booleans, so nothing // visible appears
Ternary operator
Choose between TWO different things to render.
{isLoading ? <Spinner /> : <Content data={data} />} // Good for exactly 2 branches; // nesting ternaries gets unreadable fast
Early return
Return a completely different tree BEFORE the main render logic.
function Profile({ user }) { if (!user) { return <LoginPrompt />; } return <UserCard user={user} />; } // Cleanest for "guard clause" style checks
Variable assignment
Build up JSX in a variable before the return, for complex branching.
function Status({ state }) { let content; if (state === "loading") content = <Spinner />; else if (state === "error") content = <Error />; else content = <Data />; return <div>{content}</div>; }
Switch / object lookup map
Cleaner than long if/else chains for MANY possible states.
const statusViews = { loading: <Spinner />, error: <ErrorMsg />, success: <Data />, }; {statusViews[status] ?? <Idle />} // scales much better than 5+ chained ternaries
Returning null
Render "nothing at all" — a valid, explicit choice.
function Banner({ show }) { if (!show) return null; return <div className="banner">...</div>; } // React renders NOTHING for null, // undefined, true, or false
⚠ The classic && footgun: {count && <Badge count={count} />} — if count is 0, React renders the LITERAL number 0 on screen (since 0 is falsy but React DOES render numbers, unlike booleans). Fix: {count > 0 && ...} or {Boolean(count) && ...}.

Common Gotchas & Interview Traps

  • ⚠️The {count && ...} zero-rendering bug — when `count` is `0`, React actually renders the literal `0` on screen, because `0` is a valid renderable value (unlike `false`/`null`/`undefined`, which render as nothing). Convert to an explicit boolean first: `count > 0 && ...`.
  • ⚠️Array index as key breaks state association on reorder/insert/delete — components can end up rendering with the WRONG internal state attached, since React matches by position rather than actual item identity.
  • ⚠️Using Math.random() or Date.now() as key generates a NEW key on every render, which defeats the entire purpose of keys — React thinks every item is brand new every time, destroying and recreating all DOM nodes (and losing any component state) unnecessarily on every re-render.
  • ⚠️key must be set on the OUTERMOST element returned inside a `.map()`, not on some element nested deeper inside it — React only looks at the immediate children of the array for keys.
  • ⚠️The `<>...` fragment shorthand cannot accept a `key` prop (or any other prop) — if you need a fragment with a key (common inside `.map()`), you MUST use the explicit `` form instead.
  • ⚠️Components must start with a capital letter — `` is treated as an unknown HTML tag (compiles to the STRING `"welcome"`), while `` compiles to a variable reference to your component function. This is a compiler rule, not just a style convention.
  • ⚠️JSX attributes use camelCase, not the HTML attribute names — `class` becomes `className`, `for` becomes `htmlFor`, `onclick` becomes `onClick` — because these compile to JS object property names, and some (like `class`/`for`) are reserved words in JavaScript.
  • ⚠️Returning multiple top-level elements without a Fragment or array wrapper throws a compile error — `return
    ;` is invalid; you need `<>...`, an array `[
    ,
    ]`, or a single wrapping element.
  • ⚠️Deeply nested ternaries for conditional rendering become unreadable fast — beyond 2 branches, prefer early returns, a lookup object/map, or extracting a helper function/component instead of chaining `? :` operators.
  • ⚠️key is stripped before props reach your component — `props.key` is always `undefined` inside the component function; if you need that same value available INSIDE the component's logic, pass it again as a separate, differently-named prop.

Interview Q&A — click to reveal

Q1: What does JSX compile to, and why does that matter for how you write React code?
+
JSX compiles to React.createElement(type, props, ...children) calls (or the equivalent jsx()/jsxs() functions in the modern transform), which return plain JavaScript OBJECTS describing the UI — NOT real DOM nodes. This matters because it means JSX has no special runtime magic: you can use ordinary JavaScript expressions, variables, functions, and control flow (if/else, ternaries, .map(), etc.) anywhere you'd use JSX, since it's just function calls that happen to look like markup.
Q2: Why must component names start with a capital letter?
+
Because of how the JSX-to-createElement compilation works: the compiler checks whether a tag name starts with a lowercase letter (compiled to a STRING, e.g. `"div"`, treated as a built-in HTML element) or an uppercase letter (compiled to an IDENTIFIER/variable lookup, e.g. the actual `Welcome` function reference in scope, treated as a custom component). If you name a component lowercase, React would try to render it as an (unknown, invalid) HTML tag instead of calling your function.
Q3: Why is using array index as a key problematic, specifically?
+
React's reconciliation algorithm uses `key` to match elements between renders and determine whether to UPDATE an existing DOM node/component instance or CREATE/DESTROY one. When using array index, the key is tied purely to POSITION, not to the actual data item's identity. If the list is reordered, filtered, or has items inserted/removed anywhere except the very end, the index-to-item mapping shifts — React ends up matching the WRONG previous element to each new position, which can cause internal component state (like form input values or open/closed toggles) to appear attached to the wrong visual row after the update.
Q4: What problem do Fragments solve?
+
A component can only return ONE root element from JSX (since it compiles to a single function call/object). Fragments (`<>...` or ``) let you group multiple sibling elements to satisfy that requirement WITHOUT introducing an extra wrapper DOM node (like an unnecessary `
`) into the actual rendered output. This avoids breaking CSS layouts that depend on direct parent-child relationships (Flexbox/Grid children, or strict HTML nesting rules like ``/``/`
`).
Q5: What's the bug in `{count && }` and how do you fix it?
+
When `count` is `0`, the `&&` expression short-circuits and evaluates to `0` itself (since `0` is falsy) — but unlike `false`, `null`, or `undefined`, React DOES render the number `0` as visible text on the page. So instead of rendering "nothing" when the count is zero, you get a stray "0" showing up in the UI. Fix: make sure the left side of `&&` is an actual boolean, e.g. `{count > 0 && }` or `{Boolean(count) && }`.
Q6: Can you access the "key" prop inside your component's own logic?
+
No — `key` is a special prop that React strips out and uses purely for its own internal reconciliation bookkeeping; it is never passed through to `props` inside your component. `props.key` is always `undefined`. If you need the same value available inside your component's logic, you must pass it again explicitly under a different prop name, e.g. ``.
Q7: What's the difference between conditionally rendering with && vs a ternary, and when would you choose each?
+
`condition && ` renders the component if the condition is truthy, or renders NOTHING (well-behaved for `false`/`null`/`undefined`, but watch out for `0`) if falsy — it's for an "all or nothing" single-branch decision. A ternary `condition ? : ` is for choosing between TWO different things to render, always rendering ONE or the OTHER (never "nothing" unless one branch is explicitly `null`). Use `&&` for optional/conditional pieces of UI; use a ternary when there are genuinely two meaningful states to display.
Q8: Why can't you use the `<>...` fragment shorthand when rendering a list with keys?
+
The shorthand `<>...` syntax does not support ANY attributes/props at all — it's a purely minimal syntax with no way to pass `key` (or anything else) to it. When you need multiple sibling elements per list item (avoiding an unwanted wrapper `
`) AND need to supply a `key` for each group (required since it's the outermost element inside `.map()`), you must use the explicit, longer `...` form instead, since only that form accepts props.
