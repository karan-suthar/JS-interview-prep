The Landscape — Two Philosophies

💡 These four libraries split into TWO fundamentally different mental models: Redux and Zustand use a "top-down" STORE model (one or a few centralized objects holding state) — while Jotai and Recoil use a "bottom-up" ATOMIC model (many small, independent pieces of state that compose together).
Store model vs Atomic model
2

Redux

Redux (with Redux Toolkit)
"A single, predictable source of truth, updated through pure reducer functions."
One global (or feature-sliced) store. State changes happen by DISPATCHING actions, which are handled by pure REDUCER functions that compute the next state. Strict unidirectional flow, excellent devtools (time-travel debugging), and a massive ecosystem of middleware.
// Modern Redux, using Redux Toolkit (the current recommended approach) import { createSlice, configureStore } from "@reduxjs/toolkit"; const cartSlice = createSlice({ name: "cart", initialState: { items: [] }, reducers: { addItem: (state, action) => { state.items.push(action.payload); // looks mutable, but Immer handles it safely under the hood }, }, }); export const { addItem } = cartSlice.actions; const store = configureStore({ reducer: { cart: cartSlice.reducer }, }); // ── Usage in a component ── import { useSelector, useDispatch } from "react-redux"; function CartIcon() { const items = useSelector((state) => state.cart.items); // selector — subscribes narrowly const dispatch = useDispatch(); return <span>{items.length}</span>; }
✓ Why teams still choose Redux: unmatched debugging tools (time-travel, action replay, state diffing), a strict, enforceable pattern that scales well across LARGE teams (everyone updates state the same, predictable way), and a mature middleware ecosystem for side effects (redux-saga, redux-thunk, RTK Query for data fetching).
3

Zustand

Zustand
"State management that gets out of your way."
A minimal store built directly on hooks — no boilerplate actions/reducers/dispatch ceremony required. You define a store as a hook, read from it with a SELECTOR function (for fine-grained subscriptions), and update it by calling a "set" function directly.
// The entire store definition — no Provider wrapping needed at all import { create } from "zustand"; const useCartStore = create((set) => ({ items: [], addItem: (item) => set((state) => ({ items: [...state.items, item] })), clearCart: () => set({ items: [] }), })); // ── Usage — just call the hook, no Provider, no context ── function CartIcon() { // selector — this component ONLY re-renders when "items" changes const items = useCartStore((state) => state.items); return <span>{items.length}</span>; } function AddToCartButton({ product }) { const addItem = useCartStore((state) => state.addItem); return <button onClick={() => addItem(product)}>Add</button>; } // No reducers, no action types, no dispatch — direct, minimal API surface
✓ Why teams choose Zustand: dramatically less boilerplate than Redux for equivalent functionality, built-in selector-based subscriptions (avoiding the Context re-render problem entirely, without extra setup), no required Provider wrapping, and a gentle learning curve — often described as "just useState, but shareable across components."
4

Jotai

Jotai
"Primitive and flexible state management, built from small atoms."
Instead of one big store, state is defined as many small, independent "atoms" — each atom is its own unit of state. Components subscribe to EXACTLY the atoms they use, giving fine-grained reactivity by design, without needing to write selectors.
import { atom, useAtom } from "jotai"; // Each atom is an independent, standalone piece of state const cartItemsAtom = atom([]); const discountCodeAtom = atom(""); // Derived/computed atoms — automatically recompute when their dependencies change const cartTotalAtom = atom((get) => { const items = get(cartItemsAtom); // declares a dependency on cartItemsAtom return items.reduce((sum, item) => sum + item.price, 0); }); // ── Usage ── function CartIcon() { // subscribes ONLY to cartItemsAtom — nothing else can cause this to re-render const [items] = useAtom(cartItemsAtom); return <span>{items.length}</span>; } function CartTotal() { // subscribes to the DERIVED atom — recomputes automatically when cartItemsAtom changes const [total] = useAtom(cartTotalAtom); return <span>${total}</span>; } // Updating discountCodeAtom re-renders NEITHER of the above components — // true fine-grained reactivity, by design, with no manual selector needed
✓ Why teams choose Jotai: fine-grained reactivity is the DEFAULT (not something you have to remember to set up with selectors), a small React-like API (`atom`/`useAtom` mirrors `useState`'s mental model), and clean support for derived/computed state that automatically tracks its own dependencies.
5

Recoil

Recoil
"A state management library for React, built by Meta's React team."
Similar atomic philosophy to Jotai — state lives in "atoms" — but with an explicit "selector" concept for derived state, forming a data-flow GRAPH. Notably built by engineers on Meta's React team, giving it credibility for React-idiomatic design, though its long-term maintenance status has been less certain in recent years.
import { atom, selector, useRecoilState, useRecoilValue } from "recoil"; const cartItemsState = atom({ key: "cartItemsState", // unique string key REQUIRED for every atom/selector default: [], }); const cartTotalState = selector({ key: "cartTotalState", get: ({ get }) => { const items = get(cartItemsState); return items.reduce((sum, item) => sum + item.price, 0); }, }); // ── Usage — REQUIRES wrapping the app in <RecoilRoot> ── function App() { return ( <RecoilRoot> <CartIcon /> </RecoilRoot> ); } function CartIcon() { const [items] = useRecoilState(cartItemsState); return <span>{items.length}</span>; }
⚠ Important, current-state caveat: Recoil's maintenance pace and long-term community momentum have visibly SLOWED compared to Jotai in recent years — worth acknowledging directly if this comes up in an interview, since recommending Recoil for a brand-new project today without addressing this would be an incomplete answer.

Scenario & Justified Pick — A Model Answer

The Scenario
You're the tech lead for a mid-sized team (6 engineers) building a B2B SaaS dashboard product. The app has a complex, deeply nested filter/sort UI with dozens of independently-adjustable filter controls (each affecting different, independent widgets on the page), plus some genuinely global state (the logged-in user, feature flags). The team has moderate React experience but no prior experience with any state management library. You need to pick ONE primary tool for the next 2+ years of this codebase.
✓ My pick: Zustand for the global concerns, Jotai for the filter UI (or Zustand alone, kept simple)
Reasoning, step by step:

1. Rule out Redux first: Redux's strict reducer/action ceremony and steeper learning curve isn't justified here — the team has NO prior state-library experience, and Redux's biggest strengths (time-travel debugging, strict conventions for very large teams, mature middleware for complex async flows) aren't strongly needed for a 6-person team without an existing investment in Redux patterns. The learning curve cost outweighs the benefit for this team's starting point.

2. Rule out Recoil: its slowed maintenance momentum is a real risk for a codebase meant to last 2+ years — picking a library with uncertain long-term support for a multi-year commitment is a avoidable risk when a very similar (and more actively maintained) alternative, Jotai, exists.

3. Why the FILTER UI specifically favors an atomic model (Jotai): dozens of INDEPENDENT filter controls, each affecting different, independent widgets, is EXACTLY the scenario atomic state was designed for — each filter becomes its own atom, each widget subscribes only to the atoms it actually needs, and changing one filter never triggers unrelated widgets to re-render. Achieving the same fine-grained behavior in a single Zustand store would require carefully hand-writing a selector for every widget — doable, but more manual discipline to get right and keep right as the app grows.

4. Why GLOBAL concerns (user, feature flags) still favor Zustand's simplicity: this data changes rarely and is needed broadly — Zustand's minimal API (a single hook, no Provider) is the simplest possible tool for this job, and mixing in Jotai here would add unnecessary conceptual overhead for something that doesn't need atomic granularity.

Alternative, equally defensible answer: using Zustand ALONE for everything, with selectors applied carefully to the filter state, is also justifiable — it trades a small amount of manual selector discipline for having only ONE library/mental model for the whole team to learn, which can be the right call for a team explicitly prioritizing simplicity over the "automatic" fine-grained reactivity Jotai provides by default.
🎯 What this model answer demonstrates for an interviewer: ruling OUT options with explicit reasoning (not just picking a favorite), tying the decision to CONCRETE facts from the scenario (team size, experience level, UI shape, time horizon), and acknowledging a reasonable alternative — this is what separates a strong system-design-style answer from a shallow "I like X because it's popular."

Common Gotchas & Interview Traps

  • ⚠️"Which is BEST" has no single correct answer — interviewers are testing your REASONING, not fishing for one "right" library. Answering with a single favorite and no trade-off discussion is a weaker answer than reasoning through the scenario's specific constraints.
  • ⚠️Modern Redux (via Redux Toolkit) is dramatically less boilerplate-heavy than "classic" Redux — criticizing Redux purely for verbosity without acknowledging RTK's improvements (createSlice, built-in Immer, less manual action-type constants) is an outdated take.
  • ⚠️Zustand's selector pattern must be used correctly to get fine-grained subscriptions — calling `useCartStore()` with NO selector subscribes a component to the ENTIRE store, defeating the fine-grained benefit; you must call `useCartStore(state => state.items)` to subscribe narrowly.
  • ⚠️Jotai/Recoil's atomic model isn't automatically "better" for every case — a small app with mostly GLOBAL, infrequently-changing state (a logged-in user, a theme) gets little practical benefit from atomizing everything, and a simpler store-based tool may be easier to reason about for that specific shape of state.
  • ⚠️Recoil's requirement for globally-unique string "key" values for every atom/selector is an easy source of subtle bugs — accidentally reusing a key string across two different atoms causes silent, hard-to-diagnose conflicts.
  • ⚠️None of these libraries REPLACE React's own built-in state entirely — local component state (`useState`) and Context remain perfectly appropriate for state that's genuinely local to one component or a small, shallow part of the tree; reaching for a global state library for everything is itself an anti-pattern.
  • ⚠️Bundle size differences, while real, are rarely the DECIDING factor in a genuine architectural decision — team familiarity, the shape of the app's state, and long-term maintenance considerations usually matter more than a few extra kilobytes, though it's still a legitimate secondary factor to mention.
  • ⚠️Server state (data fetched from an API) is often better handled by a DEDICATED data-fetching library (React Query, SWR) rather than shoehorning it into Redux/Zustand/Jotai/Recoil — these libraries are primarily designed for CLIENT state, and mixing server-state caching/revalidation concerns into them (though possible) often duplicates functionality those dedicated tools already solve well.
  • ⚠️Migrating between these libraries mid-project is a real, nontrivial cost — a strong answer acknowledges that picking wisely upfront (based on the team and the app's actual state shape) matters more than picking whatever is currently trending, since switching later touches a large surface of the codebase.
  • ⚠️"Fine-grained reactivity by default" (Jotai/Recoil) vs "fine-grained reactivity via selectors" (Redux/Zustand) is a design trade-off, not a strict hierarchy — the SELECTOR approach gives you explicit control and visibility into subscriptions in the component's own code, while the ATOMIC approach is more automatic but can make it less obvious, just by reading one atom's definition, everywhere it's used across the app.

Interview Q&A — Why / What / When / How

🎯 This is fundamentally a SYSTEM DESIGN-style question dressed up as a library comparison — the strongest answers reason from the SHAPE of the problem (team, app, state characteristics) to the tool, not the other way around.
WhatWhat's the fundamental architectural difference between Redux/Zustand and Jotai/Recoil?
+
Redux and Zustand use a "top-down" STORE model — one (or a few) centralized objects hold ALL the relevant state, and components read from it via SELECTORS to achieve fine-grained subscriptions. Jotai and Recoil use a "bottom-up" ATOMIC model — state is decomposed into many small, independent units ("atoms") from the start, and components subscribe directly to only the specific atoms they use, making fine-grained reactivity the DEFAULT behavior rather than something you opt into via a selector function.
WhyWhy might a team choose Redux today despite its reputation for more boilerplate than the alternatives?
+
Modern Redux via Redux Toolkit has significantly reduced the historical boilerplate complaint (createSlice, built-in Immer for "mutable-looking" but safe updates, less manual action-type ceremony) — so the gap is smaller than its reputation suggests. Beyond that, Redux still offers unmatched DEBUGGING tooling (time-travel debugging, detailed action/state diffing in DevTools), which matters a great deal for large, complex applications where tracing exactly what caused a bug is a frequent, high-value need. It also enforces a strict, consistent pattern for how state changes happen — valuable for LARGE teams where consistency and predictability across many contributors outweighs the appeal of a more minimal API.
WhenWhen does Jotai's atomic model provide a genuinely better fit than a Zustand store?
+
When the application's state naturally decomposes into MANY independent pieces that different, separate parts of the UI care about individually — a complex form with dozens of independently-validated fields, a dashboard with many independently-configurable widgets, or a filter UI with numerous unrelated filter controls each feeding different, separate result views. In these cases, Jotai's per-atom subscriptions give you fine-grained re-render behavior automatically, without needing to hand-write and maintain a careful selector for every single piece of consumed state, as you would with a single Zustand store trying to achieve the same granularity.
HowHow would you migrate a small feature currently using Context (with its known re-render issues) to Zustand?
+
// Before — Context, all consumers re-render on any change const CartContext = createContext(); function CartProvider({ children }) { const [items, setItems] = useState([]); const value = useMemo(() => ({ items, setItems }), [items]); return <CartContext.Provider value={value}>{children}</CartContext.Provider>; } // After — Zustand, no Provider needed, selector-based fine-grained subscriptions import { create } from "zustand"; const useCartStore = create((set) => ({ items: [], setItems: (items) => set({ items }), })); // Consuming components — replace useContext(CartContext) with: const items = useCartStore((state) => state.items); // only re-renders when "items" changes
The migration removes the `<CartProvider>` wrapper entirely (Zustand doesn't require a Provider), and replaces every `useContext(CartContext)` call with a selector-based `useCartStore(state => state.someField)` call, which gives the SAME shared-state capability but with proper fine-grained subscriptions built in.
WhatWhat's the significance of Recoil's origin at Meta, and does that make it the "safest" choice?
+
Recoil was built by engineers on Meta's React team, which historically gave it credibility as a React-idiomatic design (its atomic model closely mirrors ideas that influenced React's own concurrent features). However, ORIGIN alone doesn't guarantee long-term safety — Recoil's public maintenance pace and community momentum have visibly slowed in recent years compared to Jotai, which has a very similar atomic philosophy but currently more active development. For a NEW project today, this makes Recoil a less safe long-term bet despite its pedigree — a nuance worth stating explicitly rather than assuming "built by the React team" automatically implies it's the current best choice.
WhyWhy is it often a mistake to use one of these libraries to manage server/API data, rather than a dedicated data-fetching library?
+
Server state has fundamentally different characteristics from client state: it can become STALE (the server's data may have changed since you fetched it), often needs caching/deduplication across multiple components requesting the same data, benefits from automatic background revalidation, and needs retry/error-handling logic for network failures. Redux/Zustand/Jotai/Recoil are general-purpose CLIENT state containers — they don't inherently provide any of these server-state-specific behaviors, meaning you'd end up manually re-implementing caching, staleness tracking, and revalidation logic that dedicated libraries like React Query or SWR already provide out of the box, well-tested and optimized for exactly that purpose.
WhenWhen would you recommend NOT adopting any of these libraries at all, and just using React's built-in state?
+
When the app's shared-state needs are genuinely small — a handful of values needed by a shallow, limited part of the component tree (like a single page's local UI state, or a theme value used by only a few components) — plain `useState` lifted to a common ancestor, or a single well-scoped Context (with the memoization/splitting techniques applied as needed), is often entirely sufficient. Introducing an external state management library adds a new dependency, a learning curve for the team, and additional architectural decisions to maintain — costs that should be justified by an ACTUAL complexity/performance need, not adopted preemptively just because "that's what serious apps use."
HowHow would you structure an answer if asked to justify a state management choice for a scenario you're given live in an interview?
+
1. Identify the KEY characteristics of the scenario that actually matter for this decision: team size/experience, the SHAPE of the state (few global values vs. many independent pieces), performance sensitivity, and the project's expected lifespan/maintenance horizon.
2. RULE OUT options explicitly, with a specific reason tied to the scenario — don't just pick a favorite; show you considered and dismissed alternatives for real reasons (e.g. "Redux's learning curve isn't justified here because...").
3. State your pick and connect it DIRECTLY back to the scenario's specific details, not generic library marketing points (e.g. "because this UI has dozens of independent filters, an atomic model avoids needing to hand-write selectors for each one").
4. Acknowledge a reasonable alternative or trade-off you're consciously accepting — this shows you understand the decision isn't objectively "solved," just well-reasoned for THIS specific context.
