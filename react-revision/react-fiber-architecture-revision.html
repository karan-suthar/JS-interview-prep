The Old "Stack Reconciler" (Pre-React 16)

💡 Before React 16, reconciliation (comparing the new Virtual DOM tree to the old one, and figuring out what changed) used the JavaScript engine's own call stack — recursively walking the element tree, function call within function call, all the way down and back up. This is why it was called the "stack reconciler."
Recursive tree-walk — once started, it can't pause partway through
🚨 The core limitation: a native JS function call stack is synchronous and uninterruptible by design — once renderApp() calls renderSidebar() which calls renderNavItem(), JavaScript must fully unwind that entire call chain before it can do ANYTHING else, including responding to a click, a keystroke, or letting the browser repaint the screen.
2

The Real-World Problem This Caused

💡 Browsers are also single-threaded — JavaScript execution, layout, painting, and responding to user input all compete for the SAME thread. If reconciliation for a large component tree takes, say, 300ms, the browser is BLOCKED from doing anything else — including redrawing the screen or responding to a click — for that entire 300ms.
A large synchronous render blocks the main thread — dropped frames, unresponsive UI
SymptomWhy it happened
Janky animations during a big re-renderThe browser can't paint new animation frames while JS is busy recursing through the tree
Input lag while typing in a large form/listEvery keystroke triggers a full synchronous re-render pass that must finish before the next keystroke is handled
UI feels "frozen" during heavy updatesClick/scroll/hover events sit in the queue, unprocessed, until the JS call stack fully unwinds
⚠ The 16ms budget: to maintain a smooth 60fps, the browser needs to complete a full cycle of JS + layout + paint within about 16.6ms per frame. A synchronous render that takes 100ms+ blows through many frames' worth of budget in one uninterruptible chunk — this was the exact problem Fiber was built to solve.
3

What Exactly Is a "Fiber"?

💡 A Fiber is a plain JavaScript object — one per component/element — that represents a UNIT OF WORK. Instead of relying on the native call stack, React builds its OWN in-memory linked-list-like tree of fiber nodes, which it can traverse manually, ONE NODE AT A TIME, pausing and resuming at will.
A fiber tree — each node knows its child, sibling, and return (parent) pointers
// A (heavily simplified) sketch of what a Fiber node conceptually holds { type: "div", // or a component function/class key: null, // ── Tree structure — a LINKED LIST, not recursive stack frames ── child: FiberNode, // first child sibling: FiberNode, // next sibling return: FiberNode, // parent (called "return" internally) // ── Work tracking ── pendingProps: {...}, memoizedState: {...}, // hooks state lives here! alternate: FiberNode, // pointer to the fiber from the PREVIOUS render (double buffering) effectTag: "UPDATE", // what DOM operation this fiber needs (add/update/delete) } // Because this is a plain JS object (not a call stack frame), React can: // - stop working on it at any point // - store a reference to "where it left off" // - come back and resume later // - or even throw the whole in-progress tree away and start over
✓ The key insight: by moving the "call stack" out of the JS engine and into React's OWN data structure (a fiber tree it manages by hand), React gains full manual control over WHEN and HOW work happens — instead of being at the mercy of whatever the native call stack allows.

Two Phases: Render (interruptible) & Commit (not)

Fiber splits work into two phases with very different rules
AspectRender PhaseCommit Phase
Can be paused/resumed✓ Yes✗ No — always runs to completion
Can be thrown away and restarted✓ Yes (e.g. if a higher-priority update comes in)✗ No
Touches the real DOM✗ No — only builds the fiber tree in memory✓ Yes — applies all DOM mutations

🎭 Double buffering: React keeps TWO fiber trees in memory — the "current" tree (what's actually on screen) and a "work-in-progress" tree (being built during the render phase). Once the work-in-progress tree is fully ready, the commit phase swaps it in as the new "current" tree in one atomic step — similar to how graphics engines avoid screen tearing.
5

Time-Slicing — Breaking Work into Chunks

💡 Time-slicing means React works through the fiber tree in small chunks, periodically YIELDING control back to the browser between chunks to check "does anything more urgent need to happen right now (like a click or a paint)?" — instead of doing all the work in one giant, blocking burst.
Old (stack): one giant block · New (fiber): small chunks with yield points
// Conceptual sketch of how the fiber "work loop" operates (simplified) function workLoop(deadline) { while (nextUnitOfWork && deadline.timeRemaining() > 0) { // process ONE fiber node, then check the clock again nextUnitOfWork = performUnitOfWork(nextUnitOfWork); } if (nextUnitOfWork) { // ran out of time this frame — yield back to the browser, // schedule continuation for the NEXT available idle time requestIdleCallback(workLoop); } else { commitRoot(); // all done — apply everything to the real DOM at once } } // (React's actual scheduler is far more sophisticated than this — it uses // its own custom scheduling package, not literally requestIdleCallback — // but this captures the core "chunk + yield + resume" idea)
✓ Because a fiber tree is a data structure React controls (not the native call stack), "pausing" simply means remembering a pointer to the next fiber node to process, and "resuming" means picking up from that pointer later — something completely impossible with recursive function calls on the native stack.
6

Prioritization — Not All Updates Are Equal

💡 Because Fiber can pause and resume work, React can also REORDER it — giving urgent updates (like text you just typed, or a button press) priority over less urgent ones (like a large list re-rendering after a filter), even INTERRUPTING in-progress low-priority work to handle the urgent one first.

Immediate / SynchronousDiscrete user input like a click that must feel instant

// startTransition — explicitly tell React "this update is LOW priority" function SearchPage() { const [query, setQuery] = useState(""); const [results, setResults] = useState([]); const [isPending, startTransition] = useTransition(); const handleChange = (e) => { setQuery(e.target.value); // HIGH priority — the input must feel instant startTransition(() => { // LOW priority — can be interrupted by more typing before it finishes setResults(expensiveFilter(allItems, e.target.value)); }); }; return ( <> <input value={query} onChange={handleChange} /> {/* stays snappy */} {isPending ? <Spinner /> : <ResultsList results={results} />} </> ); } // Without transitions: typing feels laggy because EVERY keystroke forces // a full re-filter of a potentially huge list before the input can update. // With transitions: the input updates immediately; the expensive re-filter // happens in the background and can be abandoned mid-way if you keep typing.
⚠ None of this (transitions, priority levels, concurrent features) would be POSSIBLE without Fiber underneath — Fiber is the low-level architectural foundation; APIs like useTransition, useDeferredValue, and Concurrent Mode/React 18's concurrent rendering are all built ON TOP of Fiber's ability to pause, resume, reorder, and abandon units of work.

Common Gotchas & Interview Traps

  • ⚠️"Interruptible" only applies to the render phase, never the commit phase — a common mix-up. The commit phase (actually touching the DOM) always runs synchronously to completion once started, to avoid ever showing a half-applied UI.
  • ⚠️Because the render phase can be paused, thrown away, and restarted, component function bodies (and anything called during rendering) must be PURE — no side effects during render — since React may call your component function multiple times for a single logical update, or abandon a render entirely without completing it.
  • ⚠️Fiber ships in React 16+, but Concurrent Features (transitions, Suspense for data fetching, automatic batching everywhere) are separate, LATER additions built on top of it — Fiber existing since 16 doesn't mean all "concurrent" behavior was available immediately; much of it arrived with React 18's `createRoot`.
  • ⚠️Time-slicing does not make individual renders "faster" — the SAME amount of total work still needs to happen; time-slicing makes the work feel smoother/more responsive by not blocking everything else for its entire duration, not by reducing the raw work itself.
  • ⚠️startTransition does not delay STATE updates from happening in the sense of being skipped — it marks them as interruptible/lower priority; the update still eventually happens, just potentially after more urgent updates, and can be restarted if a newer transition supersedes it.
  • ⚠️Fiber's "linked list" tree structure (child/sibling/return pointers) is an implementation detail, not something application code interacts with directly — you don't manipulate fibers yourself; you interact with the declarative component/hooks API, and Fiber operates invisibly underneath.
  • ⚠️Not every re-render benefits from or uses time-slicing — small, fast updates may well complete within a single time slice with no visible difference from the old synchronous model; the benefits become apparent specifically for LARGE trees or expensive render work.
  • ⚠️Double buffering means memory usage is technically higher (two fiber trees exist during a render pass) — a reasonable trade-off, but worth knowing if asked about the "cost" side of Fiber's design.
  • ⚠️React does not use the browser's native `requestIdleCallback` API directly in modern versions — it ships its OWN scheduler package (`scheduler`) with more precise control over timing and priority than the native browser API alone would allow.
  • ⚠️Fiber doesn't eliminate the need to optimize your own code — `React.memo`, `useMemo`, `useCallback`, virtualization for long lists, etc. are all still relevant and important; Fiber makes React's OWN internal work more interruptible, but doesn't make an inherently expensive render computation itself any cheaper.

Interview Q&A — Why / What / When / How

🎯 Fiber is an internals/architecture topic — interviewers use it to gauge depth beyond "how to use React." Framing answers around why it was built, what it fundamentally changed, when its benefits actually kick in, and how it works mechanically shows that depth.
WhatWhat is React Fiber, in one sentence?
+
Fiber is React's internal reconciliation engine (introduced in React 16) that represents the component tree as its OWN data structure of linked plain JavaScript objects (fiber nodes) rather than relying on the native JavaScript call stack — giving React manual control to pause, resume, reorder, or abandon rendering work at any point.
WhyWhy did React need to move away from the old stack-based reconciler?
+
The old reconciler walked the component tree using ordinary recursive JavaScript function calls, relying on the native call stack. A native call stack is synchronous and uninterruptible by design — once it starts unwinding through a large tree, it CANNOT pause partway through to let the browser handle a click, run an animation frame, or repaint the screen. For large component trees, this caused the main thread to be blocked long enough to visibly drop frames, delay input response, and make the UI feel janky or frozen. React needed an architecture that could break rendering work into interruptible chunks — which required replacing the call stack with its OWN manually-managed data structure (the fiber tree).
WhenWhen does Fiber's interruptibility actually make a noticeable difference to an app?
+
Primarily for LARGE component trees or expensive render computations — a small, fast update (a handful of components) completes well within a single frame's time budget regardless of architecture, so the difference is invisible there. The benefit becomes apparent when rendering work is substantial enough that it WOULD have blocked the main thread for a noticeable stretch under the old model — e.g. filtering/re-rendering a list with thousands of items, or a complex dashboard with many simultaneously-updating widgets — where Fiber can keep the UI responsive (handling clicks, keeping animations smooth, keeping text input snappy) by yielding control between chunks of that work.
HowHow does React manage to "pause" rendering, mechanically speaking?
+
Since the fiber tree is a plain JavaScript object graph (linked via child/sibling/return pointers) that React itself owns and traverses manually — not the native call stack — "pausing" simply means React's work loop stops after processing the current fiber node and keeps a reference to WHICH fiber node should be processed next. It then yields control back to the browser (allowing paint, input handling, etc.), and later — when the scheduler decides it's time to continue — resumes by picking up work starting from that saved pointer, exactly where it left off. This is only possible because the "call stack" here is data React controls, not the JS engine's own native stack frames.
WhatWhat is the difference between the render phase and the commit phase in Fiber's architecture?
+
The RENDER phase is where React builds the new "work-in-progress" fiber tree — calling component functions, computing new state/props, and figuring out what changed — and this phase is interruptible; React can pause it, throw it away, or restart it if a higher-priority update comes in. The COMMIT phase is where React actually applies the calculated changes to the real DOM (and runs things like `componentDidMount`/`useLayoutEffect`) — this phase is always synchronous and runs to completion once started, specifically so the user never sees a partially-updated, flickering UI.
WhyWhy must the commit phase be synchronous and non-interruptible, even though the render phase isn't?
+
If the commit phase COULD be paused midway, the user might see a half-updated DOM — some elements reflecting the new state, others still showing the old one — a jarring, visually broken intermediate state. By keeping the commit phase atomic (runs fully, uninterrupted, once it begins), React guarantees the DOM always transitions cleanly from one fully-consistent state to the next fully-consistent state, with nothing "torn" or half-applied ever visible on screen.
WhenWhen would you use startTransition, and what does it actually do under the hood?
+
Use `startTransition` when you have a state update that's expensive to render (like re-filtering a huge list) that you want to explicitly mark as LOWER priority than more urgent updates (like the text currently being typed into an input). Under the hood, it tells React's fiber scheduler to treat the wrapped state update as interruptible/deprioritized — React will process more urgent work (like the next keystroke) first, and can pause or even entirely discard and restart the transition's in-progress render if a newer, conflicting update comes in before it finishes — all made possible by Fiber's ability to interrupt and reorder units of work.
WhatWhat does it mean for component rendering to need to be "pure" specifically because of Fiber's architecture?
+
Because Fiber may call a component function multiple times for what is logically a SINGLE update (e.g. starting a render, pausing it, then having to restart it from scratch due to a higher-priority interruption, or React's StrictMode intentionally double-invoking for detection purposes), any side effects performed directly inside the render/component function body (like mutating an external variable, making a network call, or logging) could run MORE THAN ONCE, or run for a render that ultimately gets thrown away entirely and never committed. This is why component bodies must be pure functions of their props/state — side effects belong in `useEffect`, which only runs after a render has been fully committed, not during the interruptible render phase itself.
WhyWhy is "double buffering" (maintaining both a current and a work-in-progress fiber tree) a useful design choice?
+
Keeping the "current" tree (matching what's actually on screen) completely separate and untouched while building a new "work-in-progress" tree means the in-progress work can be freely modified, paused, or even discarded entirely WITHOUT ever risking corrupting or partially updating what the user currently sees. Once the work-in-progress tree is fully built and ready, React swaps it in as the new "current" tree in one atomic step — conceptually similar to how graphics rendering engines use double buffering to avoid showing a half-drawn frame (screen tearing).
WhenWhen did Fiber ship, and when did features like transitions/concurrent rendering become available — are they the same thing?
+
Fiber (the underlying architecture/data structure) shipped in React 16 — but for several years it mostly worked the same way as before FROM THE OUTSIDE, since most of the interruptibility/prioritization capabilities weren't yet exposed through public APIs. Concurrent features like `useTransition`, `useDeferredValue`, and full concurrent rendering (via `createRoot`) arrived later, primarily with React 18. Fiber is the necessary FOUNDATION; the concurrent APIs are built ON TOP of that foundation — Fiber existing doesn't automatically mean every concurrent capability was available from day one.
HowHow would you explain, step by step, what happens when setState is called in a Fiber-based React app?
+
1. The update is scheduled with a certain PRIORITY level (e.g. high for direct user input, lower if wrapped in `startTransition`).
2. React's scheduler begins (or resumes) the RENDER phase, building a new work-in-progress fiber tree by processing fiber nodes one at a time.
3. Periodically, React checks whether it should yield control back to the browser (e.g. running out of the current frame's time budget, or a higher-priority update arriving) — if so, it pauses and remembers where to resume.
4. Once the entire work-in-progress tree is complete (uninterrupted from that point), React enters the COMMIT phase — synchronously applying all DOM mutations at once, then running effects like `useLayoutEffect` synchronously and `useEffect` asynchronously afterward.
5. The work-in-progress tree becomes the new "current" tree, ready to serve as the baseline for the next update.
