What Is an Optimistic Update?

💡 An optimistic update immediately updates the UI to reflect what you EXPECT the result of a mutation to be — BEFORE the server actually confirms it succeeded. If the server request fails, the UI is rolled back to its previous state. This makes interactions feel instant, at the cost of occasionally needing to "undo" a UI change.
ApproachUser sees updateFeels like
Normal (pessimistic) mutationOnly AFTER the server responds successfullyA brief delay/spinner on every action
Optimistic updateIMMEDIATELY, before the server even respondsInstant, snappy — like a native app
⚠ The trade-off: optimistic updates are best suited for actions that are HIGHLY LIKELY to succeed (liking a post, checking off a todo, toggling a follow) — for actions with a meaningful failure rate or serious consequences (submitting a payment, deleting an account), showing a normal loading state until real confirmation is usually the safer, more honest choice.

The React Query Mutation Lifecycle

💡 React Query's useMutation exposes lifecycle callbacks that fire at specific points — onMutate (before the request fires), onError (if it fails), onSuccess (if it succeeds), and onSettled (always, regardless of outcome). Optimistic updates are built by hooking into ALL of these.
The full mutation lifecycle, in order
CallbackWhen it firesRole in an optimistic update
onMutateBEFORE the mutation function runsCancel conflicting queries, snapshot current data, apply the optimistic change
onErrorIf the mutation throws/rejectsRoll back to the snapshot taken in onMutate
onSuccessIf the mutation resolves successfullyOptional — often just leave the optimistic UI as-is
onSettledALWAYS, after either onSuccess or onErrorRefetch/invalidate to reconcile with the true server state

Full Implementation — Step by Step

Step 1Cancel outgoing refetches
onMutate: async (newTodo) => { // prevents an in-flight background refetch from overwriting our // optimistic update with STALE server data that hasn't caught up yet await queryClient.cancelQueries({ queryKey: ["todos"] });
If a background refetch happens to resolve right after we apply our optimistic change, it could overwrite our change with data that doesn't yet reflect it — cancelling first prevents this race.
Step 2Snapshot the current data
// save the CURRENT cached value so we can restore it if the mutation fails const previousTodos = queryClient.getQueryData(["todos"]);
This is the "undo point" — without it, there's nothing to roll BACK to if the request fails.
Step 3Apply the optimistic update
// manually update the cache to reflect what we EXPECT after success queryClient.setQueryData(["todos"], (old) => [...old, newTodo]); // return the snapshot as "context" — passed to onError/onSettled below return { previousTodos }; },
This is what makes the UI feel instant — the cache (and therefore anything reading it) updates immediately, before the server has even responded.
Step 4Roll back on failure
onError: (err, newTodo, context) => { // restore the EXACT snapshot taken before we optimistically changed anything queryClient.setQueryData(["todos"], context.previousTodos); },
The `context` object returned from `onMutate` is automatically passed here — this is React Query's built-in mechanism for threading the snapshot through to the failure handler.
Step 5Reconcile with the server, always
onSettled: () => { // refetch regardless of success/failure, to guarantee the cache EXACTLY // matches the server's true state (our optimistic guess might be slightly // off even on success — e.g. server-generated IDs, timestamps) queryClient.invalidateQueries({ queryKey: ["todos"] }); },
This is a critical safety net — it corrects any small discrepancies between our OPTIMISTIC guess and the server's ACTUAL result, even in the success case.
// ── The complete useMutation call, all steps combined ── import { useMutation, useQueryClient } from "@tanstack/react-query"; function useAddTodo() { const queryClient = useQueryClient(); return useMutation({ mutationFn: addTodoToServer, // the actual API call onMutate: async (newTodo) => { await queryClient.cancelQueries({ queryKey: ["todos"] }); const previousTodos = queryClient.getQueryData(["todos"]); queryClient.setQueryData(["todos"], (old) => [...old, newTodo]); return { previousTodos }; }, onError: (err, newTodo, context) => { queryClient.setQueryData(["todos"], context.previousTodos); }, onSettled: () => { queryClient.invalidateQueries({ queryKey: ["todos"] }); }, }); }

Handling Race Conditions

🚨 The exact race condition cancelQueries prevents: if a background refetch (triggered by React Query's automatic refetch-on-window-focus, or a previous invalidation) is ALREADY in flight when you apply an optimistic update, that refetch could resolve AFTER your optimistic change and silently overwrite it with old, pre-optimistic data.
// Without cancelQueries — a subtle, hard-to-reproduce bug onMutate: async (newTodo) => { // 🐛 if a background refetch is ALREADY in flight right now... const previousTodos = queryClient.getQueryData(["todos"]); queryClient.setQueryData(["todos"], (old) => [...old, newTodo]); // our optimistic update return { previousTodos }; // ...that in-flight refetch can resolve microseconds later and OVERWRITE // our optimistic change with the OLD data it fetched BEFORE our update } // ✓ With cancelQueries — the in-flight refetch is aborted FIRST onMutate: async (newTodo) => { await queryClient.cancelQueries({ queryKey: ["todos"] }); // stops the race before it can happen const previousTodos = queryClient.getQueryData(["todos"]); queryClient.setQueryData(["todos"], (old) => [...old, newTodo]); return { previousTodos }; }
⚠ This is precisely WHY onMutate is declared async and the cancellation is awaited — without awaiting it, the cancellation might not have actually taken effect before the optimistic `setQueryData` call runs, reopening the same race window this step exists to close.

Practical Example — Toggling a Todo's Completed State

// A complete, self-contained example: toggling a single todo item's "completed" flag function useToggleTodo() { const queryClient = useQueryClient(); return useMutation({ mutationFn: ({ id, completed }) => fetch(`/api/todos/${id}`, { method: "PATCH", body: JSON.stringify({ completed }), }), onMutate: async ({ id, completed }) => { await queryClient.cancelQueries({ queryKey: ["todos"] }); const previousTodos = queryClient.getQueryData(["todos"]); // find and flip ONLY the specific todo being toggled queryClient.setQueryData(["todos"], (old) => old.map((todo) => todo.id === id ? { ...todo, completed } : todo ) ); return { previousTodos }; }, onError: (err, variables, context) => { queryClient.setQueryData(["todos"], context.previousTodos); toast.error("Couldn't update the todo — reverted."); // inform the user! }, onSettled: () => { queryClient.invalidateQueries({ queryKey: ["todos"] }); }, }); } // ── Usage in a component ── function TodoItem({ todo }) { const toggleTodo = useToggleTodo(); return ( <input type="checkbox" checked={todo.completed} onChange={(e) => toggleTodo.mutate({ id: todo.id, completed: e.target.checked }) } /> ); } // The checkbox visually updates the INSTANT it's clicked — no waiting for // the PATCH request, with automatic rollback + error toast if it fails

Common Gotchas & Interview Traps

  • ⚠️Forgetting to cancel outgoing queries in onMutate reintroduces a real race condition — an in-flight background refetch can silently overwrite your optimistic update with stale data, a subtle bug that's easy to miss in casual testing but shows up under real network conditions.
  • ⚠️Forgetting to return the snapshot from onMutate means onError has nothing to roll back to — `context` will be `undefined`, and `context.previousTodos` will throw, rather than gracefully restoring the prior state.
  • ⚠️Mutating the cached data directly (instead of returning a new array/object) can cause subtle bugs — always use the functional updater form of `setQueryData` and return NEW objects/arrays, treating cached data as immutable, just like React state.
  • ⚠️Skipping onSettled's invalidation means small discrepancies between your optimistic guess and the server's actual result never get corrected — e.g. a server-generated ID, timestamp, or computed field that your optimistic version approximated differently.
  • ⚠️Applying optimistic updates for high-stakes or failure-prone actions (payments, irreversible deletions) is a poor product decision, even though it's technically implementable — a brief flash of "success" for something that then fails and gets reverted can feel worse than a normal loading state for actions with real consequences.
  • ⚠️Silently rolling back without informing the user is a common UX mistake — the user saw their action "succeed" for a moment, and if it just reverts with no explanation, it looks like a bug rather than a legitimate failure; always pair rollback with a visible error message.
  • ⚠️Optimistic updates for LIST operations (adding/removing items) need to construct a plausible temporary item — e.g. a temporary client-generated ID for a new todo before the server assigns its real one — and this temporary data needs to be reconciled once the real response arrives (handled by the onSettled invalidation).
  • ⚠️Multiple rapid mutations on the SAME query key can compound the snapshot/rollback logic in tricky ways — e.g. rapidly toggling the same checkbox multiple times before any request resolves; robust implementations sometimes need to think carefully about which snapshot is "correct" to roll back to if an earlier request fails after a later one has already succeeded.
  • ⚠️The mutationFn itself should not access the optimistic cache directly — it should just perform the real API call; all the cache manipulation belongs in the onMutate/onError/onSettled callbacks, keeping the "what actually happens on the server" logic cleanly separated from the "how we fake it locally" logic.
  • ⚠️Not every mutation needs to be optimistic — introducing this pattern adds real complexity (snapshotting, rollback, race handling); reserve it for interactions where the perceived responsiveness genuinely matters to the user experience, not as a default for every single mutation in an app.

Interview Q&A — Why / What / When / How

🎯 This is a favorite "show me you can implement something non-trivial end to end" question — interviewers want to see the FULL lifecycle (cancel, snapshot, update, rollback, reconcile), not just the happy path.
WhatWhat is an optimistic update, and what are the essential pieces needed to implement one correctly?
+
An optimistic update immediately reflects an EXPECTED result in the UI before the server confirms it, making the interaction feel instant. Implementing it correctly with React Query requires: (1) cancelling any conflicting in-flight queries to avoid a race condition, (2) snapshotting the current cache data so there's something to restore, (3) applying the optimistic change to the cache, (4) rolling back to the snapshot if the mutation fails, and (5) reconciling with the server's true state afterward (regardless of success or failure) via invalidation.
WhyWhy is it necessary to call cancelQueries inside onMutate, rather than just applying the optimistic update directly?
+
If a background refetch (triggered by something like React Query's automatic refetch-on-window-focus, or an earlier invalidation) happens to already be in flight when the optimistic update is applied, that refetch could resolve AFTER the optimistic change and silently overwrite it with the OLD, pre-optimistic data it fetched earlier — a race condition that would make the optimistic update appear to randomly "undo itself" for no visible reason. `cancelQueries` aborts any such in-flight request first, closing this race window before the optimistic update is applied.
WhenWhen is an optimistic update the right choice, versus a normal loading-state mutation?
+
Optimistic updates work best for actions that are HIGH FREQUENCY, LOW STAKES, and HIGHLY LIKELY to succeed — liking a post, checking off a todo, toggling a follow/favorite, reordering a list. These are exactly the interactions where perceived responsiveness matters most (they happen often, so any lag is noticeable) and where an occasional rollback is a minor, low-consequence inconvenience. A normal loading-state mutation is more appropriate for actions with real consequences on failure, meaningful failure rates, or where users need clear confirmation before proceeding — payments, account deletion, submitting a form with significant downstream effects — where a brief "flash of success" followed by a revert could be confusing or costly.
HowHow would you implement rollback for a mutation that adds a NEW item to a list (rather than toggling an existing one)?
+
onMutate: async (newTodoText) => { await queryClient.cancelQueries({ queryKey: ["todos"] }); const previousTodos = queryClient.getQueryData(["todos"]); // construct a PLAUSIBLE temporary item, including a temporary client-side ID const optimisticTodo = { id: `temp-${Date.now()}`, // placeholder — server will assign the REAL id text: newTodoText, completed: false, }; queryClient.setQueryData(["todos"], (old) => [...old, optimisticTodo]); return { previousTodos }; }, onError: (err, newTodoText, context) => { // simply restore the ENTIRE previous list — the temp item disappears with it queryClient.setQueryData(["todos"], context.previousTodos); }, onSettled: () => { // on success, this replaces the "temp-..." item with the server's REAL data // (including its real ID) once the invalidated query refetches queryClient.invalidateQueries({ queryKey: ["todos"] }); },
The key addition compared to toggling an existing item is constructing a REASONABLE placeholder for the new item (including a temporary, clearly-fake ID), and relying on the `onSettled` refetch to replace that temporary item with the server's authoritative version once the real request completes.
WhatWhat role does the "context" object play in the mutation lifecycle?
+
Whatever value is RETURNED from `onMutate` is automatically passed as the third argument to both `onError` and `onSuccess` (and available in `onSettled` too) — this is React Query's built-in mechanism for threading data captured at the START of the mutation (like the snapshot of previous data) through to the callbacks that run LATER, once the outcome is known. Without this, there'd be no clean way to access "what the data looked like before we optimistically changed it" from inside the `onError` handler, since that handler runs in a separate callback invocation.
WhyWhy is calling invalidateQueries in onSettled still necessary even when the mutation succeeds — isn't the optimistic data already correct?
+
The optimistic update is a GUESS based on what the client expects the result to be — it can be slightly wrong even on success, particularly for fields the SERVER determines (auto-generated IDs, computed timestamps, server-side validation/normalization of the submitted data, or fields affected by business logic the client doesn't fully replicate). Invalidating and refetching in `onSettled` guarantees the cache is eventually reconciled with the SERVER's authoritative version of the data, correcting any such small discrepancies — treating the optimistic update purely as a temporary, best-effort placeholder rather than a permanent substitute for the real server response.
WhenWhen would you skip the rollback step and just let onSettled's refetch fix things up?
+
Skipping the explicit rollback and relying solely on the `onSettled` refetch to "self-correct" is technically possible, but generally NOT advisable — it means the UI shows the INCORRECT optimistic state for however long the refetch takes to complete, which could be a noticeable delay on a slow connection, rather than immediately reverting the instant the failure is known. Explicit rollback in `onError` gives the fastest, most accurate correction the moment failure is confirmed, while the `onSettled` refetch serves as a secondary, more thorough reconciliation step afterward — the two are complementary, not substitutes for each other, and skipping rollback is rarely the right trade-off.
HowHow would you also show the user an error message on rollback, integrating with a toast notification system?
+
Add the toast call directly inside the `onError` handler, alongside the rollback logic:
import { toast } from "react-hot-toast"; // or any toast library useMutation({ mutationFn: updateTodo, onMutate: async (newTodo) => { /* ...snapshot + optimistic update... */ }, onError: (err, newTodo, context) => { queryClient.setQueryData(["todos"], context.previousTodos); // roll back toast.error(`Couldn't save your change: ${err.message}`); // inform the user }, onSettled: () => { queryClient.invalidateQueries({ queryKey: ["todos"] }); }, });
This ensures the user gets both the CORRECTED UI (via rollback) and a clear EXPLANATION of what happened — avoiding the confusing experience of an action silently reverting with no visible reason.
