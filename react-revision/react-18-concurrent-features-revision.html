Automatic Batching

💡 React 18's createRoot makes batching — grouping multiple state updates in the same tick into a single re-render — happen EVERYWHERE, not just inside React's own event handlers like it did before.
React 17 vs React 18 — batching inside a setTimeout
// React 18 with createRoot (the new default) import { createRoot } from "react-dom/client"; createRoot(document.getElementById("root")).render(<App />); setTimeout(() => { setCount(c => c + 1); // ✓ batched setFlag(f => !f); // ✓ same render as above — only 1 total }, 1000); // Also batched now: native event listeners, Promise .then(), async/await continuations fetch("/api").then(() => { setLoading(false); // ✓ batched together — 1 render setData(newData); // ✓ }); // Escape hatch, when truly needed — flushSync forces an IMMEDIATE, synchronous update import { flushSync } from "react-dom"; flushSync(() => setCount(c => c + 1)); // applied right away, not batched setFlag(f => !f); // this one is still batched normally
✓ Migration note: automatic batching only kicks in if you're using the NEW createRoot API. Apps still using the legacy ReactDOM.render keep the old, more limited batching behavior even on React 18 — upgrading the root API is what actually flips this feature on.

Suspense

💡 <Suspense> lets a component "pause" rendering while it's waiting on something asynchronous (lazily-loaded code, or — with supporting libraries/frameworks — data), showing a fallback UI in its place until it's ready, WITHOUT you manually wiring up loading-state booleans.
Suspense boundary — catches "not ready yet" from anything below it in the tree
// The most universally supported use case — code-splitting with React.lazy const Dashboard = React.lazy(() => import("./Dashboard")); function App() { return ( <Suspense fallback={<Spinner />}> <Dashboard /> {/* while the Dashboard.js chunk downloads, shows <Spinner /> */} </Suspense> ); } // No manual "isLoading" state needed — the Suspense boundary handles it
// Nested/multiple boundaries — different parts of the UI can load independently function ProfilePage() { return ( <div> <ProfileHeader /> {/* renders immediately, not wrapped */} <Suspense fallback={<PostsSkeleton />}> <ProfilePosts /> {/* this section can show its OWN loading state */} </Suspense> <Suspense fallback={<FriendsSkeleton />}> <ProfileFriends /> {/* independent — doesn't wait for Posts */} </Suspense> </div> ); } // Each section streams in independently as its own data becomes ready, // instead of the WHOLE page waiting on the SLOWEST piece of data
⚠ Suspense for DATA FETCHING (not just code-splitting) requires a compatible library/framework (like Next.js's data fetching, Relay, or React Query with Suspense mode) — you generally cannot make an arbitrary hand-written fetch call "suspend" on its own without that supporting infrastructure implementing the required promise-throwing contract.

useTransition

💡 useTransition lets you mark a STATE UPDATE (that you're triggering) as low-priority/"transition" — React keeps the UI responsive to more urgent updates (like typing) while this one happens in the background, and gives you an isPending flag to show a loading indicator.
function TabContainer() { const [tab, setTab] = useState("home"); const [isPending, startTransition] = useTransition(); const selectTab = (nextTab) => { startTransition(() => { setTab(nextTab); // marked low-priority — can be interrupted by more urgent work }); }; return ( <> <TabButton onClick={() => selectTab("home")}>Home</TabButton> <TabButton onClick={() => selectTab("posts")}>Posts (slow!)</TabButton> {isPending && <Spinner />} {/* shows while the transition is still in progress */} <TabContent tab={tab} /> </> ); } // Clicking "Posts" (which triggers an expensive re-render) doesn't freeze // the tab buttons themselves — they stay clickable and responsive throughout
✓ Classic use case: search-as-you-type with an expensive results render. Keep the input itself updating at HIGH priority (feels instant), while the potentially slow list re-render happens as a LOW priority transition — if the user keeps typing, React abandons the stale, in-progress transition and starts a fresh one for the latest input, rather than rendering results for text the user has already changed.

useDeferredValue

💡 useDeferredValue gives you a "lagging" copy of a VALUE — it returns the OLD value while a slow render for the NEW value happens in the background, then updates once ready. Use it when you receive a value (like a prop, or from a hook you don't control) rather than owning the setter yourself.
function SearchResults({ query }) { const deferredQuery = useDeferredValue(query); // deferredQuery LAGS BEHIND "query" during rapid changes — it's the LAST // value React had time to fully render with, not necessarily the latest one const results = useMemo( () => expensiveSearch(deferredQuery), [deferredQuery] // recompute only when the DEFERRED value settles ); const isStale = query !== deferredQuery; // true while results are "catching up" return ( <div style={{ opacity: isStale ? 0.5 : 1 }}> <ResultsList results={results} /> </div> ); } function App() { const [query, setQuery] = useState(""); return ( <> <input value={query} onChange={(e) => setQuery(e.target.value)} /> {/* stays snappy */} <SearchResults query={query} /> </> ); }
🎯 The classic distinction interviewers probe for: use useTransition when YOU are calling the state setter that triggers the slow update. Use useDeferredValue when you're just RECEIVING a value (e.g. as a prop from a parent you don't control, or from a third-party hook) and want to render an expensive consumer of it without blocking on every change.

useTransition vs useDeferredValue — Side by Side

AspectuseTransitionuseDeferredValue
What it wrapsA function that calls a state SETTERAn existing VALUE (state, prop, or context)
You need to own the state✓ Yes — you call setState inside it✗ No — works on any value you receive
Gives you a pending flag✓ Yes — isPending✗ No — you derive "isStale" yourself by comparing values
Typical triggerAn event handler you write (tab click, filter change)A prop/value that changes from ABOVE your component
Underlying mechanismMarks the UPDATE as low priorityMarks re-rendering FOR the new value as low priority
⚠ Both are built on the SAME underlying Fiber capability (interruptible, priority-based rendering) — they're just two different ergonomic APIs for the two different situations of "I'm triggering this update" vs "I received this value and want to consume it without blocking."

Common Gotchas & Interview Traps

  • ⚠️Automatic batching only applies with createRoot — apps still using the legacy `ReactDOM.render` API don't get it, even on React 18, since the new root API is what actually opts into the new behavior.
  • ⚠️startTransition's callback must be SYNCHRONOUS — you can't put an `await` directly inside it and expect the code after it to still be treated as part of the transition; only the state updates that happen synchronously within that callback are marked low-priority.
  • ⚠️useTransition's state update is still not "skipped" or delayed indefinitely — it WILL happen, just at lower priority; if nothing more urgent comes along, it may complete almost immediately.
  • ⚠️useDeferredValue does not debounce or throttle on a timer — it's not "wait 300ms" logic; it's priority-based, tied to React's actual rendering capacity, which behaves differently from a fixed-delay debounce/throttle utility.
  • ⚠️Suspense for data fetching is NOT automatically available for any random fetch() call — hand-rolled data fetching doesn't inherently support the "throw a promise" contract Suspense needs; you need a compatible framework/library (Next.js, Relay, React Query's Suspense mode, etc.) actually built to integrate with it.
  • ⚠️A Suspense fallback replaces the ENTIRE wrapped subtree, not just the missing piece — if you wrap too much in one boundary, unrelated already-loaded content gets hidden behind the fallback too; splitting into multiple, more granular Suspense boundaries avoids this.
  • ⚠️flushSync should be used sparingly — forcing a synchronous update defeats the performance benefits batching provides, and is really only needed for specific edge cases like reading DOM measurements immediately after a state change.
  • ⚠️Marking an update with startTransition does not make the RENDER itself faster — the same amount of computation still happens; the benefit is that OTHER, more urgent updates aren't blocked while it happens, not that the total work is reduced.
  • ⚠️useDeferredValue's "staleness" needs to be manually detected if you want to show a visual indicator (e.g. dimmed opacity) — React doesn't give you a built-in boolean like `isPending`; you compare the live value to the deferred value yourself (`value !== deferredValue`).
  • ⚠️None of these features change WHAT gets rendered — they only change the SCHEDULING/timing/priority of when rendering work happens; the final UI output for a given state is identical with or without transitions/deferred values, just potentially delayed under load.

Interview Q&A — Why / What / When / How

🎯 These React 18 features are frequently tested for practical judgment, not just API recall — expect questions probing WHY each exists, WHEN to reach for it over the alternatives, and HOW it behaves under specific scenarios.
WhatWhat is automatic batching, and what changed about it in React 18?
+
Batching is grouping multiple state updates that occur within the same tick into a single re-render, rather than re-rendering once per individual `setState` call. Before React 18, this only happened inside React's own synthetic event handlers (onClick, onChange). React 18, when using the new `createRoot` API, extends batching to happen EVERYWHERE — inside `setTimeout`, native DOM event listeners, Promise `.then()` callbacks, and async/await continuations — making the behavior consistent and more performant across the entire app by default.
WhyWhy was extending batching to "everywhere" considered valuable enough to be a headline React 18 feature?
+
The old inconsistency (batched in event handlers, NOT batched in timeouts/promises/native listeners) made performance unpredictable purely based on WHERE in your code a state update happened to originate — the exact same two `setState` calls could cause 1 render or 2 renders depending on their calling context, which is a confusing, easy-to-miss source of unnecessary re-renders. Making batching universal removes this inconsistency, reducing wasted render work across the entire app automatically, without requiring any code changes from developers.
WhenWhen would you need flushSync to opt OUT of automatic batching?
+
Rarely — but a legitimate case is needing to read an updated DOM measurement (like a scroll position or element height) immediately after a state change, before the browser paints, where the normal async/batched update timing would be too late for your synchronous DOM-reading logic. `flushSync(() => setState(...))` forces that specific update to apply synchronously and immediately. This should be used sparingly since it sacrifices the performance benefits of batching for that particular update.
HowHow would you migrate an app to get automatic batching if it's currently using ReactDOM.render?
+
Replace the legacy root API with the new one:
// Before import ReactDOM from "react-dom"; ReactDOM.render(<App />, document.getElementById("root")); // After import { createRoot } from "react-dom/client"; const root = createRoot(document.getElementById("root")); root.render(<App />);
This single change unlocks automatic batching (and other React 18 concurrent features) for the entire app, with no other code modifications strictly required.
WhatWhat problem does Suspense solve, and what exactly does it replace?
+
Suspense provides a declarative way to show a fallback UI while a component (or its data/code) isn't ready yet, replacing the common manual pattern of tracking an `isLoading` boolean in state, conditionally rendering a spinner, and juggling that logic across potentially many components. Instead, you wrap the part of the tree that might not be ready in a `<Suspense fallback={...}>` boundary, and React automatically shows the fallback until everything inside successfully renders, without you writing any loading-state plumbing yourself for that boundary.
WhyWhy can't you just wrap any regular fetch() call in Suspense and expect it to show the fallback automatically?
+
Suspense works by a component "throwing" a Promise during render when its data isn't ready yet — React catches that thrown Promise, shows the nearest fallback, and re-attempts rendering once the Promise resolves. A plain `fetch()` call inside a `useEffect` doesn't follow this contract; it resolves asynchronously and typically stores its result in state via a setter, which is a completely different mechanism that Suspense has no visibility into. To make data fetching work with Suspense, you need a library/framework specifically built to implement the throw-a-promise pattern under the hood (like Next.js's data layer, Relay, or React Query configured for Suspense) — you generally can't bolt it onto arbitrary hand-written fetch logic.
WhenWhen would you use multiple, smaller Suspense boundaries instead of one large one wrapping the whole page?
+
When different sections of a page have independent, separately-loading data and you don't want the WHOLE page to wait on the SLOWEST section before showing anything. Wrapping each independent section in its own Suspense boundary lets faster sections render and become visible as soon as THEIR data is ready, rather than the entire page staying on a single fallback until every single piece — including the slowest one — has finished loading. This creates a more progressive, streaming-like loading experience.
WhatWhat's the core difference between useTransition and useDeferredValue?
+
`useTransition` wraps a FUNCTION that calls a state setter YOU own — you use it when you're the one triggering the update and want to mark that specific state change as low priority, and it gives you an `isPending` flag. `useDeferredValue` instead wraps an existing VALUE (often a prop or value from a hook you don't control) and gives you back a version of it that "lags behind" during rapid changes, letting you render an expensive consumer of that value without blocking on every single change — but it does NOT give you a built-in pending flag; you compare the live and deferred values yourself to detect staleness.
WhyWhy would you choose useDeferredValue over useTransition for a search results list fed by a prop?
+
If the component rendering the expensive results list doesn't OWN the state setter for the search query — it just RECEIVES the query as a prop from a parent — there's no state-setting function available inside this component to wrap with `startTransition`. `useDeferredValue` solves exactly this scenario: it lets the component receiving the value decide, independently, to render an expensive consumer of that value at lower priority, without needing access to (or control over) whoever originally owns and updates the underlying state.
WhenWhen should you reach for useTransition/useDeferredValue at all, versus just leaving a component as a normal, synchronous update?
+
Only when you've identified an ACTUAL performance problem — specifically, an expensive render (large lists, complex computations, many simultaneously updating components) that's causing a noticeably janky or unresponsive experience, especially for OTHER, more urgent interactions happening at the same time (like typing feeling laggy because each keystroke triggers a slow re-render). For small or fast-rendering components, wrapping updates in these APIs adds complexity without any perceptible benefit — they're a targeted performance tool for a specific class of problem, not something to apply by default to every state update.
HowHow would you implement a search box where typing stays responsive even though filtering a huge list is slow, using useTransition?
+
function SearchBox({ allItems }) { const [query, setQuery] = useState(""); const [results, setResults] = useState(allItems); const [isPending, startTransition] = useTransition(); const handleChange = (e) => { const value = e.target.value; setQuery(value); // HIGH priority — input stays instant startTransition(() => { // LOW priority — can be interrupted by the NEXT keystroke setResults(allItems.filter(item => item.name.includes(value))); }); }; return ( <> <input value={query} onChange={handleChange} /> {isPending && <span>Updating...</span>} <ResultsList results={results} /> </> ); }
The input's own value updates immediately (high priority), while the expensive filtering happens as an interruptible background transition — if the user keeps typing quickly, React abandons stale in-progress filter renders and starts fresh with the latest query, rather than working through an ever-growing backlog of outdated renders.
