What Is a Stale Closure?

💡 A stale closure happens when a function "remembers" a variable's value from the render it was CREATED in, but that variable has since changed in a NEWER render — and the old function is still being used (e.g. inside a timer, event listener, or effect that hasn't re-run).
function Counter() { const [count, setCount] = useState(0); useEffect(() => { const id = setInterval(() => { console.log(count); // always logs 0, forever! }, 1000); return () => clearInterval(id); }, []); // empty array — effect runs ONCE, closing over count's value AT THAT TIME (0) return <button onClick={() => setCount(count + 1)}>{count}</button>; } // Even as "count" visibly increases on screen, the interval's callback is // STUCK using the "count" variable from the FIRST render — it's "stale."
⚠ This is not a React bug — it's how JavaScript closures fundamentally work. Every render of a function component creates a brand new set of local variables (including count). Any function DEFINED during that render (like the interval callback) permanently "closes over" — captures a reference to — that SPECIFIC render's variables, not some magical "live" binding that automatically stays current.

Why It Happens — Visualizing Renders as Snapshots

Each render is its OWN isolated snapshot — closures from render #1 never see render #2's variables
✓ The fix is always one of these three things: (1) add the missing dependency so the effect RE-RUNS with a fresh closure each time it changes, (2) use the FUNCTIONAL updater form (setCount(prev => prev + 1)) to avoid needing to read the stale variable at all, or (3) use a ref to hold a value that's always read "live," bypassing the closure problem entirely.

Practice — 5 Buggy Examples (Click to Reveal the Fix)

🎯 Read each snippet, try to identify the stale closure bug and how the dependency array is involved BEFORE revealing the answer.
Bug #1 — The Classic Interval Counter Easy
function Counter() { const [count, setCount] = useState(0); useEffect(() => { const id = setInterval(() => { setCount(count + 1); // 🐛 what happens here? }, 1000); return () => clearInterval(id); }, []); return <p>{count}</p>; }
🐛 Bug: count gets stuck at 1, forever.

The effect runs ONCE (empty deps), so the interval's callback closes over count = 0 permanently. Every tick calls setCount(0 + 1) — always computing "1" from the SAME stale count, never actually incrementing further, since the closure never sees a newer value.

✓ Fix: use the functional updater form.
useEffect(() => { const id = setInterval(() => { setCount(prev => prev + 1); // always reads the LATEST pending state }, 1000); return () => clearInterval(id); }, []); // correctly stays empty — no external value is being READ anymore

The functional updater form sidesteps the stale closure entirely — it doesn't need to read count from the outer scope at all, since React passes in the guaranteed-current value as an argument.

Bug #2 — Fetching Data for the Wrong User Easy
function UserProfile({ userId }) { const [user, setUser] = useState(null); useEffect(() => { fetchUser(userId).then(setUser); // 🐛 what happens if userId changes? }, []); return <div>{user?.name}</div>; }
🐛 Bug: switching users never re-fetches.

The effect closes over the FIRST userId it ever saw, and since the dependency array is empty, it never runs again. If the parent later passes a different userId prop, this component keeps showing the ORIGINAL user's data forever, silently out of sync with its own props.

✓ Fix: add "userId" to the dependency array.
useEffect(() => { fetchUser(userId).then(setUser); }, [userId]); // re-runs with a FRESH closure whenever userId actually changes

Now every time userId changes, React reruns the effect using the NEW value — each run gets its own fresh closure over the current userId, eliminating the staleness.

Bug #3 — The Stale Event Listener Medium
function KeyLogger() { const [keys, setKeys] = useState([]); const [isPaused, setIsPaused] = useState(false); useEffect(() => { function handleKeyDown(e) { if (isPaused) return; // 🐛 "isPaused" read inside — what's the issue? setKeys((prev) => [...prev, e.key]); } window.addEventListener("keydown", handleKeyDown); return () => window.removeEventListener("keydown", handleKeyDown); }, []); // 🐛 missing dependency return ( <button onClick={() => setIsPaused(!isPaused)}> {isPaused ? "Resume" : "Pause"} </button> ); }
🐛 Bug: clicking "Pause" never actually stops logging.

The listener is attached ONCE (empty deps), so handleKeyDown permanently closes over the FIRST render's isPaused = false. No matter how many times the button toggles isPaused in state, this specific closure's if (isPaused) check is always testing the ORIGINAL stale value.

✓ Fix: add "isPaused" to the dependency array.
useEffect(() => { function handleKeyDown(e) { if (isPaused) return; setKeys((prev) => [...prev, e.key]); } window.addEventListener("keydown", handleKeyDown); return () => window.removeEventListener("keydown", handleKeyDown); }, [isPaused]); // removes OLD listener, attaches a NEW one with fresh isPaused each time

Now, every time isPaused changes, the cleanup removes the OLD (stale) listener and a brand new one is attached — closing over the CURRENT value of isPaused each time it changes.

Bug #4 — The Object Dependency That Never Settles Medium
function Parent() { const [count, setCount] = useState(0); const config = { limit: 10 }; // 🐛 recreated every render return ( <> <button onClick={() => setCount(count + 1)}>{count}</button> <Child config={config} /> </> ); } function Child({ config }) { useEffect(() => { console.log("config effect ran"); // 🐛 runs WAY more than expected }, [config]); return <div>Limit: {config.limit}</div>; }
🐛 Bug: the effect fires on EVERY Parent re-render, even though "config" looks unchanged.

This isn't a MISSING dependency bug — it's the opposite problem. {'{ limit: 10 }'} is a brand NEW object reference created every time Parent re-renders. React's dependency comparison uses reference equality, not deep equality, so config is considered "different" on every single render of Parent — even clicking the unrelated counter button re-triggers this effect.

✓ Fix: memoize the object, or depend on its primitive fields.
// Option 1: useMemo to keep a stable reference const config = useMemo(() => ({ limit: 10 }), []); // Option 2 (often simpler): depend on the primitive value directly function Child({ config }) { useEffect(() => { console.log("config effect ran"); }, [config.limit]); // a number compares by VALUE, not reference }

This is technically the "opposite" of a stale closure (an OVER-eager effect instead of a stuck one), but it stems from the exact same root cause: misunderstanding how the dependency array's comparison actually works.

Bug #5 — The WebSocket That Only Sends the First Message Hard
function ChatRoom({ roomId }) { const [draft, setDraft] = useState(""); const [connection, setConnection] = useState(null); useEffect(() => { const ws = createConnection(roomId); ws.onmessage = (msg) => console.log("received:", msg); setConnection(ws); return () => ws.close(); }, [roomId]); function handleSend() { connection.send(draft); // 🐛 sometimes sends OLD draft text! setDraft(""); } return ( <> <input value={draft} onChange={(e) => setDraft(e.target.value)} /> <button onClick={handleSend}>Send</button> </> ); }
🎯 Trick question — this one is actually FINE!

handleSend is redefined FRESH on every render (it's not inside a useEffect or wrapped in useCallback with stale deps) — so every time it runs, it reads the CURRENT render's draft and connection directly from the component's own scope, not from some old closure captured long ago. Since it's attached fresh to the button's onClick on every render, there's no staleness here.

⚠ Where it WOULD break: wrapping handleSend in a badly-configured useCallback.
// 🐛 THIS version reintroduces the bug const handleSend = useCallback(() => { connection.send(draft); // closes over draft/connection from setDraft(""); // whenever this useCallback was LAST recreated }, []); // 🐛 missing "draft" and "connection" — stale closure returns! // ✓ Fix: include the real dependencies const handleSend = useCallback(() => { connection.send(draft); setDraft(""); }, [connection, draft]); // fresh closure whenever either changes

The lesson: stale closures aren't unique to useEffect — ANY memoized callback (useCallback, useMemo) or effect with an incomplete dependency array can capture and "freeze" outdated values from the render it was created in.

The ESLint Safety Net — exhaustive-deps

✓ The official eslint-plugin-react-hooks package's exhaustive-deps rule automatically analyzes your effect's body and WARNS you if you're using a value that isn't listed in the dependency array — catching most stale closure bugs before they ever ship.
// .eslintrc — enabling the rule { "plugins": ["react-hooks"], "rules": { "react-hooks/exhaustive-deps": "warn" } } // With the rule enabled, this triggers a warning automatically: useEffect(() => { fetchUser(userId).then(setUser); }, []); // ⚠️ ESLint: React Hook useEffect has a missing dependency: 'userId'
⚠ Do not silence this warning with an eslint-disable comment as a default habit. It's tempting when you "know" an empty array is intentional — but doing this routinely is exactly how real stale closure bugs slip into production. Reach for one of the fix patterns above INSTEAD of suppressing the warning, and reserve disabling it for the rare, deliberately-justified case.

Common Gotchas & Interview Traps

  • ⚠️Stale closures aren't unique to useEffect — any function defined during a render (a plain callback, a `useCallback`, a `useMemo` factory) can capture and "freeze" that render's values if it outlives the render and isn't recreated with fresh dependencies.
  • ⚠️An empty dependency array doesn't mean "correct" — it means "runs once, closes over that render's values forever." Whether that's a bug depends entirely on whether the effect body reads any value that could later change.
  • ⚠️Blindly adding every suggested dependency can cause a NEW bug: infinite effect loops — if an effect depends on a value it ALSO sets (directly or indirectly), adding it naively can cause the effect to re-run every single render.
  • ⚠️Functions defined inside the component and used inside an effect are also "dependencies" — if `handleThing` is defined in the component body and called inside a `useEffect`, and it's not wrapped in `useCallback`, it's technically a NEW function every render, so the exhaustive-deps rule will flag it too.
  • ⚠️The functional updater form only helps when you need the PREVIOUS state to compute the next one — it doesn't help if the effect needs to read some OTHER, unrelated prop/state value; that genuinely needs to be in the dependency array or accessed via a ref.
  • ⚠️Refs used to bypass staleness intentionally opt OUT of React's reactivity — reading `ref.current` inside a callback won't cause anything to re-render or re-trigger based on its changes; it's purely a way to read a "live" value, not a substitute for state when the UI needs to visually reflect that value.
  • ⚠️Cleanup functions can ALSO be stale — if a cleanup function references a value from the SAME closure as its effect, it has the identical staleness characteristics; this is usually fine since cleanup is paired with its own effect run, but worth remembering when reasoning about it.
  • ⚠️console.log inside an effect can lie to you during debugging — logging a value INSIDE a stale closure will keep printing the OLD captured value, which can look like "the app isn't updating" when actually the app IS updating fine; it's specifically that ONE captured closure that's frozen.
  • ⚠️Object/array/function dependencies create "false positive" staleness (effect re-runs unnecessarily) which is a DIFFERENT bug from true staleness (effect doesn't re-run when it should) — both stem from misunderstanding dependency comparison, but require opposite-feeling fixes (memoizing vs. adding to the array).
  • ⚠️Custom hooks can hide stale closures from view — if a custom hook internally uses a `useEffect` with an incomplete dependency array, the bug lives inside the hook's implementation, not visibly in the component using it, making it harder to spot just by reading the component's own code.

Interview Q&A — Why / What / When / How

🎯 Stale closures are one of the most common "gotcha" debugging questions in React interviews — practicing the reasoning behind WHY they happen (not just memorizing the fixes) is what separates a strong answer from a shallow one.
WhatWhat is a stale closure, in precise terms?
+
A stale closure is a function that continues to reference a variable's value from the specific render (or scope) it was originally CREATED in, even after that variable's "current" value has changed in a later render. Because each render of a function component creates entirely new local variable bindings, any function defined during that render permanently captures references to THAT render's specific variables — it has no way to automatically "see" updates from subsequent renders unless explicitly recreated with fresh values.
WhyWhy does useEffect's dependency array directly control whether a stale closure bug occurs?
+
The dependency array determines WHEN the effect function itself gets recreated and re-run — and a NEW run of the effect means a BRAND NEW closure, capturing whatever the CURRENT values are at that point. If a value the effect reads is missing from the dependency array, the effect never re-runs when that value changes, so it never gets a chance to capture a fresh, up-to-date closure — leaving it permanently stuck with whatever value existed the last time it actually ran (often just once, on mount, if the array is empty).
WhenWhen is an empty dependency array ([]) actually correct, versus when is it a bug waiting to happen?
+
An empty array is correct when the effect's body doesn't read ANY value from props, state, or context that could change over the component's lifetime — e.g. setting up a one-time subscription using only stable, unchanging references, or a truly "on mount only" side effect with no external values involved. It becomes a bug when the effect DOES read a prop or state value that can legitimately change later — in that case, an empty array silently freezes the effect's behavior to whatever that value was on the very first render, which is exactly the stale closure trap.
HowHow would you fix a stale closure bug where an interval needs to always use the CURRENT value of a frequently-changing prop, without restarting the interval on every change?
+
Use a ref to hold the "live" current value, updated on every render via a separate no-dependency-array effect, and read the ref's `.current` inside the interval callback instead of the prop directly:
function Ticker({ label }) { const labelRef = useRef(label); useEffect(() => { labelRef.current = label; // stays in sync every render }); useEffect(() => { const id = setInterval(() => { console.log(labelRef.current); // always current, via the ref }, 2000); return () => clearInterval(id); }, []); // interval itself is only created ONCE, never restarted }
This achieves both goals simultaneously: the interval is set up exactly once (no restart churn), and it always reads the truly current value of `label` at the moment it fires, because it reads through the ref rather than a captured closure variable.
WhatWhat's the difference between a "missing dependency" bug and an "over-firing effect" bug, and how are they related?
+
A missing dependency bug means the effect DOESN'T re-run when it should, because a value it depends on isn't listed — resulting in a stale closure using outdated data. An over-firing effect bug means the effect re-runs MORE OFTEN than logically necessary, typically because a dependency is an object/array/function literal that gets a new reference on every render (even though its actual content hasn't meaningfully changed), and dependency comparison is reference-based, not deep-equality-based. They're related because both stem from the SAME underlying mechanic — how React decides "has this dependency changed?" — just manifesting as opposite symptoms (effect runs too rarely vs. too often).
WhyWhy is disabling the exhaustive-deps ESLint rule considered risky as a default habit?
+
The rule exists specifically because manually tracking which values an effect closure depends on is easy to get wrong, especially as a component's code evolves over time — a dependency array that was correct when written can silently become incorrect after a later edit adds a new variable reference inside the effect that isn't reflected in the array. Disabling the rule removes this automated safety net, meaning such bugs can slip in silently and only surface later as a confusing runtime behavior (data not updating, listeners using outdated state) rather than being caught immediately during development.
WhenWhen would you choose the functional state updater form over adding the state variable to the dependency array?
+
When the ONLY thing the effect needs from that state is to compute its NEXT value based on the PREVIOUS one (e.g. incrementing a counter, toggling a boolean, appending to a list) — in that specific case, the functional updater form (`setCount(prev => prev + 1)`) eliminates the need to read the outer `count` variable at all, letting you correctly leave it OUT of the dependency array without introducing a stale closure. This is preferable to adding the dependency when doing so would otherwise force the effect to re-run (and potentially recreate expensive resources like intervals, subscriptions, or connections) every single time that state value changes, when the effect's actual SETUP logic doesn't need to change at all.
HowHow would you debug a suspected stale closure bug in an unfamiliar codebase?
+
1. Identify the symptom precisely — a value that "should" update but appears stuck, or behavior that only reflects the state from an earlier point in time.
2. Locate the `useEffect`/`useCallback`/`useMemo` (or plain closure inside a timer/listener) responsible for that behavior.
3. Check its dependency array against everything the function body actually READS from the surrounding scope (props, state, or other variables) — the ESLint `exhaustive-deps` rule will often flag this automatically if enabled.
4. For each value read but missing from the array, decide the right fix: add it as a dependency (if the effect should genuinely re-run), switch to a functional state update (if it's just computing next-from-previous), or introduce a ref for a "read current value without re-running" need.
5. Verify the fix doesn't introduce the OPPOSITE bug (an infinite loop, or an over-firing effect) — check whether any of the values now listed are objects/arrays/functions that get new references every render, and memoize them if so.
