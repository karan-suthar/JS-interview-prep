Closure Output Puzzles

10 "what does this log?" problems — setTimeout, async/await, loops, and closures

🎯 Try to predict the output before clicking "Reveal answer" on each problem. These are the exact style of questions asked in real JS interviews — they test whether you understand the event loop, closures, and scoping together, not just in isolation.
P1 P2 P3 P4 P5 P6 P7 P8 P9 P10 Patterns
1
Classic var loop + setTimeout
Easy
for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i), 0); } console.log("done");
Output
"done" 3 3 3
Two things happening at once:
  • Sync-first: the loop registers 3 timeouts but doesn't execute their callbacks yet — console.log("done") runs synchronously right after the loop, before any timeout fires (even with a 0ms delay, timeouts go through the task queue).
  • var trap: all three arrow functions close over the SAME i. By the time the callbacks run (after the current synchronous code finishes), the loop has already completed and i is 3.
2
The let fix
Easy
for (let i = 0; i < 3; i++) { setTimeout(() => console.log(i), 0); } console.log("done");
Output
"done" 0 1 2
let creates a brand new binding of i for each loop iteration — this is spec'd behavior, not a workaround. Each arrow function closes over its own separate copy of i with the value it had during that specific iteration. "done" still logs first because setTimeout callbacks are always deferred to the task queue, even with 0ms delay.
3
IIFE capture
Medium
for (var i = 0; i < 3; i++) { (function(i) { setTimeout(() => console.log(i), i * 100); })(i); }
Output
0 1 2
The IIFE (function(i) {...})(i) creates a new function scope on every iteration, and the outer i's current value is passed in as an argument — creating a new local i parameter that shadows the outer one. Each setTimeout callback closes over its own IIFE's local i, not the shared loop variable. This was the standard pre-ES6 fix for the closure-in-loop trap. The staggered delays (i * 100) also guarantee the order 0, 1, 2 — without them, order would still be 0,1,2 here since they're all queued in that order with equal delay.
4
async/await ordering
Medium
console.log("1"); async function foo() { console.log("2"); await null; console.log("3"); } foo(); console.log("4");
Output
"1" "2" "4" "3"
Async functions run synchronously until the first await.
  • "1" logs first (top-level sync code).
  • Calling foo() immediately runs its body synchronously up to await null — so "2" logs next, still synchronously.
  • At await, the rest of the function ("3") is scheduled as a microtask and execution returns to the caller.
  • "4" logs next (remaining synchronous top-level code).
  • Once the call stack is empty, the microtask queue runs — logging "3" last.
5
Promise vs setTimeout race
Hard
console.log("start"); setTimeout(() => console.log("timeout"), 0); Promise.resolve() .then(() => console.log("promise 1")) .then(() => console.log("promise 2")); console.log("end");
Output
"start" "end" "promise 1" "promise 2" "timeout"
Microtasks (Promises) always run before macrotasks (setTimeout), even with a 0ms delay.
  • "start" and "end" run first — pure synchronous code.
  • setTimeout schedules a macrotask — it goes to the back of the task queue, processed only after the current call stack AND all pending microtasks are done.
  • .then() callbacks are microtasks — they run immediately after the current synchronous code finishes, before the engine even checks the macrotask queue.
  • The chained .then() (promise 2) also runs before the timeout, because the engine fully drains the microtask queue (processing new microtasks added during draining) before moving to the next macrotask.
6
Closures inside an array of functions
Medium
function createFunctions() { const fns = []; for (var i = 0; i < 3; i++) { fns.push(() => i); } return fns; } const [f1, f2, f3] = createFunctions(); console.log(f1(), f2(), f3());
Output
3 3 3
Same root cause as Problem 1 — var creates one shared binding across the loop. All three stored functions (f1, f2, f3) close over the exact same i. By the time any of them are CALLED (after createFunctions() has already returned), the loop has finished and i is 3. Note this doesn't even need setTimeout — simply calling the functions later, after the loop, is enough to expose the shared-binding issue. Swap var for let to get 0 1 2.
7
async function inside a for loop
Hard
async function delay(ms) { return new Promise(resolve => setTimeout(resolve, ms)); } async function run() { for (let i = 0; i < 3; i++) { await delay(100); console.log(i); } console.log("all done"); } run(); console.log("sync end");
Output
"sync end" 0 (after ~100ms) 1 (after ~200ms) 2 (after ~300ms) "all done" (after ~300ms)
await pauses the entire async function, not just that iteration.
  • run() is called, immediately hits await delay(100) in the first iteration, and yields control back to the caller — so "sync end" logs before anything from inside the loop.
  • The loop runs sequentially, not in parallel — each iteration fully waits ~100ms for the previous await to resolve before starting the next one. Total time ≈ 300ms, not 100ms.
  • let ensures each iteration's i is correctly scoped (0, 1, 2 in order) — this would also work correctly with var here, unlike the setTimeout-in-loop trap, because each iteration's console.log runs synchronously relative to its own await resolving, not deferred all together.
8
forEach with async callback (the "forgot to await" trap)
Hard
async function delay(ms) { return new Promise(resolve => setTimeout(resolve, ms)); } async function run() { [1, 2, 3].forEach(async (num) => { await delay(100); console.log(num); }); console.log("done"); } run();
Output
"done" 1 2 3 (all ~100ms later, roughly together)
forEach does NOT wait for async callbacks — this is a famous real-world bug pattern.
  • forEach calls the async arrow function for each element but ignores the returned Promise entirely — it doesn't await anything and moves to the next iteration immediately.
  • All 3 async callbacks start virtually simultaneously (not sequentially!), each hits its own await delay(100), and run() continues past the forEach call right away — logging "done" before any of the numbers.
  • All three delays run in parallel, so 1, 2, 3 log at roughly the same time (~100ms later), in original order since they started together — NOT sequentially like Problem 7.
  • Fix: use a plain for...of loop with await inside, or Promise.all(arr.map(async fn)) if parallel execution is intended but you need to wait for completion.
9
Closures with shared mutable state
Medium
function makeCounters() { let count = 0; return { increment: () => ++count, decrement: () => --count }; } const counterA = makeCounters(); const counterB = makeCounters(); counterA.increment(); counterA.increment(); counterB.increment(); console.log(counterA.increment()); console.log(counterB.increment());
Output
3 2
Each call to makeCounters() creates a brand new, independent closure with its own private count variable — counterA and counterB do NOT share state, even though they were created by the same function.
  • counterA's count: 0 → 1 → 2 → 3 (three increments total)
  • counterB's count: 0 → 1 → 2 (two increments total)
This demonstrates that closures capture a scope per invocation of the outer function, not per function definition — a common point of confusion with the module/factory pattern.
10
The ultimate mashup — let, var, async, and setTimeout together
Hard
console.log("A"); for (let i = 0; i < 2; i++) { setTimeout(() => console.log("timeout", i), 0); Promise.resolve().then(() => console.log("promise", i)); } console.log("B");
Output
"A" "B" "promise" 0 "promise" 1 "timeout" 0 "timeout" 1
Combines event loop priority (microtasks before macrotasks) with the let-per-iteration binding.
  • "A" logs first (sync), then the loop runs twice — registering 2 timeouts and 2 promise .then() callbacks (as microtasks) — then "B" logs (still sync, since nothing async has resolved yet).
  • Once the synchronous code finishes, the engine drains the entire microtask queue before touching macrotasks — so BOTH promise callbacks ("promise 0", "promise 1") run before EITHER timeout callback.
  • let gives each loop iteration its own i, so both the promise and timeout callbacks correctly capture 0 and 1 respectively — no "3, 3" style bug here.
  • Order within each group (promise/timeout) follows insertion order — iteration 0's callbacks were queued before iteration 1's.
✓

Key Patterns to Remember

1. var = shared binding
var in a loop creates ONE variable shared by all closures. By the time async callbacks run, the loop has finished and the variable holds its final value.
2. let = fresh binding per iteration
Spec-guaranteed: each iteration of a let-based for-loop gets its own copy of the loop variable, correctly captured by any closure created that iteration.
3. Sync code always runs first
ALL synchronous code in the current call stack finishes executing before ANY callback (timeout, promise, or otherwise) runs — regardless of delay value, even 0ms.
4. Microtasks beat macrotasks
Promise .then()/catch/finally and await continuations are microtasks. setTimeout/setInterval are macrotasks. The ENTIRE microtask queue drains before the next macrotask runs.
5. async functions run sync until first await
Code before the first await inside an async function executes immediately/synchronously when the function is called — it does NOT defer right away.
6. forEach doesn't await async callbacks
array.forEach(async fn) fires all callbacks without waiting — they run "in parallel," and code after forEach continues immediately. Use for...of with await, or Promise.all, when order/completion matters.
7. Each function call = new closure scope
Calling a factory function multiple times creates independent closures each time — they do NOT share state unless you deliberately share a reference (e.g. a variable defined outside both).
8. Sequential await = one at a time
await inside a for loop pauses the ENTIRE function at each iteration — the loop total time is the SUM of each awaited delay, not the max (unlike parallel execution).
🧠 Mental model for the event loop: 1) Run all synchronous code to completion. 2) Drain the ENTIRE microtask queue (promises), including any new microtasks added while draining. 3) Run ONE macrotask (e.g. one setTimeout callback). 4) Drain microtasks again. 5) Repeat from step 3.
