debounce()

Delays invoking a function until after a period of inactivity — if called again before the delay expires, the timer resets. Only the LAST call in a rapid burst actually executes.

Visual — rapid calls (e.g. keystrokes), only the last one fires

4 rapid calls each RESET the timer. Only after the delay passes with no new calls does the function finally execute — once, with the LAST call's arguments.
Full implementation
function debounce(fn, delay) { let timerId; // held in closure — persists across calls return function (...args) { const context = this; // preserve caller's "this" (e.g. if used as an event handler) clearTimeout(timerId); // cancel any PREVIOUSLY scheduled call timerId = setTimeout(() => { fn.apply(context, args); // finally runs, using the MOST RECENT call's args }, delay); }; } // Usage — classic search-input example const handleSearch = (query) => console.log("Searching for:", query); const debouncedSearch = debounce(handleSearch, 300); searchInput.addEventListener("input", (e) => debouncedSearch(e.target.value)); // User types "hello" fast → 5 keystrokes fire the listener 5 times, // but handleSearch() only actually runs ONCE, 300ms after the LAST keystroke
Key design points: the timer ID must live in a closure OUTSIDE the returned function so it persists between calls. Using fn.apply(context, args) instead of a bare fn() preserves both the original this and all arguments from the triggering call.
💡 By default debounce fires on the trailing edge (after calls stop). Some use cases (like preventing double-submit) want it to fire immediately on the first call instead, then ignore subsequent calls until the cooldown passes.
function debounce(fn, delay, { leading = false } = {}) { let timerId; return function (...args) { const context = this; const callNow = leading && !timerId; // fire immediately only if leading AND no pending timer clearTimeout(timerId); timerId = setTimeout(() => { timerId = null; if (!leading) fn.apply(context, args); // trailing-edge call }, delay); if (callNow) fn.apply(context, args); // leading-edge call }; }
// Adding a .cancel() method — useful for cleanup (e.g. component unmount) function debounce(fn, delay) { let timerId; function debounced(...args) { const context = this; clearTimeout(timerId); timerId = setTimeout(() => fn.apply(context, args), delay); } debounced.cancel = () => clearTimeout(timerId); // attach cancel as a property of the returned function return debounced; } const debouncedFn = debounce(doSomething, 500); debouncedFn(); debouncedFn.cancel(); // prevents the pending call from ever firing

throttle()

Ensures a function runs at most once every N milliseconds, no matter how often it's called. Unlike debounce, it guarantees regular, predictable execution during continuous activity.

Calls keep coming in rapidly, but the function only actually EXECUTES at fixed intervals — the rest are dropped (basic version) or deferred (trailing-edge version).
Full implementation (timestamp-based)
function throttle(fn, interval) { let lastCallTime = 0; // timestamp of the last ALLOWED call return function (...args) { const now = Date.now(); if (now - lastCallTime >= interval) { lastCallTime = now; fn.apply(this, args); // enough time has passed — allow this call through } // else: silently ignore this call — still within the cooldown window }; } // Usage — classic scroll-position tracking example const handleScroll = () => console.log("Scroll Y:", window.scrollY); const throttledScroll = throttle(handleScroll, 200); window.addEventListener("scroll", throttledScroll); // Scroll events can fire dozens of times per second, but handleScroll() // only actually runs at most once every 200ms — much lighter on performance
Key design point: unlike debounce, throttle NEVER resets a timer on new calls — it just checks "has enough time passed since the last ALLOWED execution?" This guarantees regular execution even during continuous activity, rather than waiting for activity to fully stop.
⚠ The basic version above can DROP the very last call in a burst if it doesn't land exactly on an interval boundary. A more complete implementation schedules a trailing call to guarantee the final state is never missed.
function throttle(fn, interval) { let lastCallTime = 0; let timerId = null; return function (...args) { const context = this; const now = Date.now(); const remaining = interval - (now - lastCallTime); if (remaining <= 0) { clearTimeout(timerId); timerId = null; lastCallTime = now; fn.apply(context, args); // enough time passed — run immediately } else if (!timerId) { // schedule ONE trailing call for when the cooldown finally ends timerId = setTimeout(() => { lastCallTime = Date.now(); timerId = null; fn.apply(context, args); }, remaining); } }; } // Now guarantees: fires immediately on first call, AND fires one final // time with the LATEST args even if calls stop mid-cooldown
// Alternative: boolean-flag + setTimeout style (simpler, slightly different semantics) function throttle(fn, interval) { let isThrottled = false; return function (...args) { if (isThrottled) return; // still in cooldown — ignore this call entirely fn.apply(this, args); // run immediately on the FIRST call of a burst isThrottled = true; setTimeout(() => { isThrottled = false; }, interval); // re-open the gate after "interval" }; } // Simpler to reason about, but drops ALL calls made during the cooldown — // no trailing-call guarantee like the timestamp-based version above

memoize()

Wraps a pure function to cache its results — if called again with the same arguments, the cached result is returned instantly instead of re-computing.

Full implementation
function memoize(fn) { const cache = new Map(); // held in closure — persists across calls to the wrapped function return function (...args) { const key = JSON.stringify(args); // serialize args into a single, comparable cache key if (cache.has(key)) { return cache.get(key); // cache hit — skip computation entirely } const result = fn.apply(this, args); // cache miss — actually compute it cache.set(key, result); return result; }; } // Usage — expensive recursive Fibonacci, memoized const slowFib = (n) => n <= 1 ? n : slowFib(n - 1) + slowFib(n - 2); const fastFib = memoize(slowFib); fastFib(30); // computed the slow way once, then cached fastFib(30); // instant — read straight from cache, no recomputation
Key design points: only works correctly for pure functions — same input must always produce the same output, with no side effects. JSON.stringify is a simple, common way to build a cache key from multiple arguments, but has real limitations (see gotchas below).
💡 When the function takes exactly ONE argument, you can use that argument directly as the Map key — this avoids JSON.stringify entirely, and works correctly even for object arguments (compared by reference, which is often what you want).
function memoizeSingleArg(fn) { const cache = new Map(); return function (arg) { if (cache.has(arg)) return cache.get(arg); // works for primitives AND object references const result = fn.call(this, arg); cache.set(arg, result); return result; }; } const square = memoizeSingleArg(n => n * n); square(5); // → 25 (computed) square(5); // → 25 (cached)
⚠ An unbounded cache can grow forever and leak memory in a long-running app (e.g. server-side memoization of unique per-request inputs). A max-size cache with eviction addresses this.
function memoizeWithLimit(fn, maxSize = 100) { const cache = new Map(); return function (...args) { const key = JSON.stringify(args); if (cache.has(key)) { // Move to "most recently used" position (Map preserves insertion order) const val = cache.get(key); cache.delete(key); cache.set(key, val); return val; } const result = fn.apply(this, args); if (cache.size >= maxSize) { const oldestKey = cache.keys().next().value; // first key = least recently used cache.delete(oldestKey); } cache.set(key, result); return result; }; }

curry()

Transforms a function f(a, b, c) into a chain of single-argument (or partial-argument) calls: f(a)(b)(c). Enables partial application — "locking in" some arguments now, supplying the rest later.

Full implementation — generic curry (works for any arity)
function curry(fn) { return function curried(...args) { // If enough arguments have been collected, call the original function if (args.length >= fn.length) { return fn.apply(this, args); } // Not enough args yet — return a NEW function that collects more return function (...moreArgs) { return curried.apply(this, [...args, ...moreArgs]); }; }; } // fn.length = number of DECLARED (non-rest, non-default) parameters function sum3(a, b, c) { return a + b + c; } sum3.length; // → 3 const curriedSum = curry(sum3); // ALL of these are valid ways to call it — full flexibility! curriedSum(1, 2, 3); // → 6 (all at once) curriedSum(1)(2, 3); // → 6 (1, then 2 more) curriedSum(1)(2)(3); // → 6 (one at a time) curriedSum(1, 2)(3); // → 6 (2, then 1 more)
Key design points: fn.length gives you the number of parameters the original function EXPECTS, letting the wrapper know when "enough" arguments have accumulated. Each intermediate call returns a NEW closure holding all args collected SO FAR, spreading in any newly provided ones on the next call.
💡 If an interviewer specifically wants a curry function for a KNOWN fixed number of arguments (e.g. exactly 3), this simpler, explicit version is often easier to write correctly under pressure than the generic version above.
// Fixed-arity curry (exactly 3 arguments), one nested function per argument function curry3(fn) { return function (a) { return function (b) { return function (c) { return fn(a, b, c); }; }; }; } // Arrow function version — much more concise const curry3Arrow = fn => a => b => c => fn(a, b, c); const add3 = (a, b, c) => a + b + c; const curriedAdd = curry3Arrow(add3); curriedAdd(1)(2)(3); // → 6 // ⚠️ Note: this simple version does NOT support curriedAdd(1, 2)(3) — // each level accepts exactly ONE argument, unlike the generic version
// Practical: building reusable, specialized functions via partial application const curry = fn => (...args) => args.length >= fn.length ? fn(...args) : (...more) => curry(fn)(...args, ...more); const multiply = (a, b) => a * b; const curriedMultiply = curry(multiply); // "Lock in" one argument to create specialized, reusable functions const double = curriedMultiply(2); const triple = curriedMultiply(3); double(5); // → 10 triple(5); // → 15 // Practical: building configuration/validation function families const checkAge = (min, age) => age >= min; const curriedCheckAge = curry(checkAge); const isAdult = curriedCheckAge(18); // "min" locked to 18 isAdult(20); // → true isAdult(15); // → false

Common Gotchas & Interview Traps

  • ⚠️Forgetting to preserve `this` — calling fn(...args) instead of fn.apply(context, args) loses the original `this` binding, breaking usage as an object method or event handler. Always capture and pass through `this`.
  • ⚠️Debounce's timer variable must live in the OUTER closure, not be re-declared inside the returned function — otherwise every call gets its own fresh `timerId` and `clearTimeout` never actually cancels the previous pending call.
  • ⚠️Confusing debounce and throttle in conversation is an instant red flag — be precise: debounce delays until calls STOP; throttle limits the RATE while calls continue. Practice explaining the difference out loud.
  • ⚠️JSON.stringify as a cache key fails for functions, undefined values, Symbols, and circular references — it silently drops or mishandles these. It also doesn't reliably distinguish objects with the SAME keys in DIFFERENT order in older engines (modern engines preserve insertion order for string keys, making this less of an issue now, but worth mentioning).
  • ⚠️Memoizing an impure function produces WRONG results — if the function depends on external mutable state, has side effects, or returns different results for the same input over time (e.g. `Date.now()`, random values, network calls), memoization will incorrectly return stale cached data.
  • ⚠️curry() relies on fn.length, which breaks with default parameters or rest parameters — `function f(a, b = 1, ...rest) {}` has `f.length === 1` (only counts parameters BEFORE the first default/rest), which would break the generic curry implementation's "enough args" check for such functions.
  • ⚠️Arrow functions have no "arguments" object — if writing debounce/throttle/memoize as arrow functions, you must use rest parameters (`...args`) instead of the `arguments` keyword, since arrows don't have their own.
  • ⚠️Not clearing timers on component unmount (React) or page navigation — a debounced/throttled function's pending `setTimeout` can fire AFTER the relevant UI is gone, causing "can't update state on unmounted component" warnings or stale updates. Expose and call a `.cancel()` method in cleanup.
  • ⚠️Basic throttle implementations can silently DROP the final call in a burst — if the interviewer asks for "the last event to always be respected," you need the trailing-edge-guaranteed version, not the simplest boolean-flag version.
  • ⚠️An unbounded memoize cache is a memory leak waiting to happen — for functions called with many unique arguments over a long-running process (e.g. a server handling many different requests), always consider a cache size limit or a WeakMap for object keys (which allows garbage collection).

Interview Q&A — click to reveal

Q1: What's the fundamental difference between debounce and throttle? Give a real-world example of each.
+
Debounce delays execution until a burst of calls has fully STOPPED — it resets its timer on every new call, so if calls keep coming, the function never fires until there's a pause. Real-world example: a search-as-you-type box, where you want to wait until the user finishes typing before firing an API request.

Throttle guarantees execution happens at a regular, capped RATE even during continuous activity — it does NOT reset on every call, it just enforces a minimum gap between executions. Real-world example: tracking scroll position to trigger a "load more" action, where you want updates periodically during scrolling, not just once at the very end.
Q2: Why is it important to use fn.apply(this, args) instead of just calling fn(...args) inside these utilities?
+
Because these utility wrappers are often used as object methods or event handlers, where the ORIGINAL function relies on a specific `this` context (e.g. `this.value` inside an event handler referring to the DOM element, or `this` referring to a class instance). If you just call `fn(...args)` directly, `this` inside the wrapped function defaults to `undefined` (strict mode) or the global object — breaking any code inside that depends on `this`. Using `fn.apply(this, args)` (where the outer `this` is captured from the wrapper's own call site) correctly forwards the caller's context through to the original function.
Q3: Why must the timer/cache variable be declared OUTSIDE the returned function in debounce/throttle/memoize?
+
This is a direct application of closures — the returned function needs to remember state (a timer ID, a cache Map, a last-call timestamp) ACROSS multiple separate invocations. If that state were declared INSIDE the returned function, it would be reset to a fresh value on every single call, making it impossible to track "was there a previous pending call?" or "have we seen these arguments before?" By declaring it in the enclosing (outer) function's scope, the returned inner function closes over that single, shared variable, and every call to the wrapped function reads/writes the SAME persistent state.
Q4: How does the generic curry() implementation know when it has "enough" arguments to actually call the original function?
+
It uses fn.length — a built-in property on every function that reports the number of formal parameters DECLARED before the first default value or rest parameter. The curried wrapper accumulates arguments across calls (in an array via closure), and after each call checks if the accumulated count has reached fn.length. If yes, it calls the original function with all the collected arguments; if not, it returns another function to collect more.
Q5: What are the limitations of using JSON.stringify(args) as a memoization cache key?
+
It doesn't handle every value type correctly: undefined, functions, and Symbols are dropped/omitted from the resulting JSON string rather than represented distinctly, which can cause different-looking argument lists to accidentally produce the SAME cache key. Circular references throw an error entirely. It also can't reasonably distinguish some special values like NaN vs null in all cases, or handle complex object graphs efficiently for very large arguments. For single-argument functions where the argument is an object, using the object itself as a Map key (compared by reference) is often better and avoids these issues entirely.
Q6: Why would memoizing a function that calls Math.random() or Date.now() internally be a bug?
+
Memoization assumes the wrapped function is pure — that calling it again with the SAME arguments will always produce the SAME result. Functions relying on Math.random(), Date.now(), external mutable state, or network responses violate this assumption; they can return DIFFERENT results on each call even with identical arguments. Memoizing such a function would incorrectly return a STALE, cached result from the first call, silently hiding whatever new value the function would have actually computed on subsequent calls — a subtle and dangerous bug if not accounted for.
Q7: How would you add a "leading edge" option to debounce, so it fires immediately on the first call instead of waiting?
+
Track whether there's currently a pending timer. If there ISN'T one when a call comes in (meaning this is the start of a new burst) AND leading mode is enabled, call the function immediately. Then set the timer as usual for cooldown tracking, but on the trailing edge, only invoke the function again if NOT in leading mode (to avoid double-firing).
function debounce(fn, delay, leading = false) { let timerId; return function (...args) { const callNow = leading && !timerId; clearTimeout(timerId); timerId = setTimeout(() => { timerId = null; if (!leading) fn.apply(this, args); }, delay); if (callNow) fn.apply(this, args); }; }
Q8: What real problem does currying solve, beyond just being an interesting academic exercise?
+
Currying enables partial application — creating specialized, reusable functions by "locking in" some arguments ahead of time, while leaving others to be supplied later. This is powerful for building configuration-driven utilities (e.g. a generic request(method, url, data) function curried into get = request("GET"), then get(url)), composing pipelines of single-argument functions (which is common in functional programming, e.g. with `.map()`/`.filter()`/`.reduce()` chains), and reducing repetition when the same "fixed" arguments would otherwise need to be passed on every call.
