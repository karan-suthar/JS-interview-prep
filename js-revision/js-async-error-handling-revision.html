try/catch Basics with async/await

💡 When you await a promise that rejects, it throws the rejection reason as a regular JS exception at that line — meaning ordinary try/catch can catch it, just like synchronous errors.
✗ Promise chain style
function getUser(id) { return fetch(`/users/${id}`) .then(res => res.json()) .then(data => data.name) .catch(err => { console.error(err); throw err; }); }
✓ async/await style — flatter, reads like sync code
async function getUser(id) { try { const res = await fetch(`/users/${id}`); const data = await res.json(); return data.name; } catch (err) { console.error(err); throw err; } }
// A rejected await throws — catch it like any synchronous error async function fetchData() { try { const result = await Promise.reject(new Error("Network failed")); } catch (err) { console.log(err.message); // → "Network failed" } } // An async function that throws automatically returns a REJECTED promise async function risky() { throw new Error("boom"); } risky().catch(err => console.log(err.message)); // → "boom" // You never need to manually "return Promise.reject(...)" from an async fn // — a thrown error is automatically converted into a rejected promise.
⚠ try/catch only catches errors from await-ed expressions inside the try block — synchronous code that schedules a promise WITHOUT awaiting it (e.g. a fire-and-forget somePromise() call without await) will NOT be caught, since the try block has already exited by the time it rejects.

Practical try/catch Patterns

💡 A single try block can wrap multiple await calls — the FIRST one to reject jumps straight to catch, skipping the rest of the try block (just like sync exceptions).
async function checkout(cartId) { try { const cart = await fetchCart(cartId); // if this fails... const payment = await processPayment(cart); // ...this NEVER runs const receipt = await sendReceipt(payment); // ...neither does this return receipt; } catch (err) { // catches a failure from ANY of the three awaited calls above console.error("Checkout failed:", err.message); throw new Error("Unable to complete checkout"); // re-throw a cleaner error } }
💡 finally runs regardless of success or failure — perfect for cleanup like hiding loading spinners, closing connections, or releasing locks.
async function loadData() { setLoading(true); try { const data = await fetch("/api/data").then(r => r.json()); setData(data); } catch (err) { setError(err.message); } finally { setLoading(false); // ALWAYS runs — success, failure, or even a re-thrown error } } // finally runs even if you return early from try or catch async function example() { try { return "from try"; } finally { console.log("cleanup runs before the return actually completes"); } }
🎯 Popular alternative to try/catch — a helper that converts a promise into a [error, data] tuple (inspired by Go). Avoids nested try/catch blocks and makes error handling explicit at the call site.
// Helper: never rejects — always resolves with [error, data] function to(promise) { return promise .then((data) => [null, data]) .catch((err) => [err, undefined]); } // Usage — no try/catch needed, errors are just data now async function getUser(id) { const [err, user] = await to(fetch(`/users/${id}`).then(r => r.json())); if (err) { console.error("Failed to fetch user:", err.message); return null; } return user; } // Especially useful for sequential calls with DIFFERENT error handling needs const [err1, cart] = await to(fetchCart(id)); const [err2, payment] = await to(processPayment(cart)); // each step's error is handled independently, without deep nesting
// Reusable higher-order wrapper — centralizes error handling logic function withErrorHandling(asyncFn) { return async (...args) => { try { return await asyncFn(...args); } catch (err) { logToMonitoring(err); // e.g. Sentry, Datadog showToast("Something went wrong"); // user-facing UI feedback return null; // safe fallback value } }; } // Usage — wrap once, get consistent error handling everywhere const safeGetUser = withErrorHandling(async (id) => { const res = await fetch(`/users/${id}`); if (!res.ok) throw new Error(`HTTP ${res.status}`); return res.json(); }); const user = await safeGetUser(42); // errors handled automatically, consistently

Error Handling with Parallel Requests

⚠ Running await calls one after another (sequentially) when they don't depend on each other wastes time. But running them in parallel changes how you need to handle errors.
✗ Sequential — slow, unnecessary waiting
async function loadDashboard() { try { const user = await fetchUser(); const posts = await fetchPosts(); const stats = await fetchStats(); return { user, posts, stats }; } catch (err) { console.error(err); } } // Total time = sum of all three (e.g. 300ms)
✓ Parallel with Promise.all — faster
async function loadDashboard() { try { const [user, posts, stats] = await Promise.all([ fetchUser(), fetchPosts(), fetchStats() ]); return { user, posts, stats }; } catch (err) { console.error(err); // fires on the FIRST rejection, others ignored } } // Total time = the SLOWEST of the three (e.g. 150ms)
// Promise.all fails fast — ONE rejection loses you ALL the other results, // even the ones that succeeded. Use allSettled if partial success is OK. async function loadDashboardSafely() { const results = await Promise.allSettled([ fetchUser(), fetchPosts(), fetchStats() ]); const [userResult, postsResult, statsResult] = results; return { user: userResult.status === "fulfilled" ? userResult.value : null, posts: postsResult.status === "fulfilled" ? postsResult.value : [], stats: statsResult.status === "fulfilled" ? statsResult.value : null, }; } // Dashboard still renders with partial data even if one request fails

Unhandled Promise Rejections

🚨 An unhandled rejection happens when a promise rejects and NOTHING is attached to handle it (no .catch(), no surrounding try/catch on an await). In Node.js this can crash the process; in browsers it logs a console warning and fires a global event.
// Classic unhandled rejection — fire-and-forget async call async function riskyOperation() { throw new Error("failed"); } riskyOperation(); // ✗ NOT awaited, NOT .catch()'d — unhandled rejection! // The error is silently swallowed until the browser/Node reports it // as an "UnhandledPromiseRejectionWarning" — your app doesn't know it failed // Fix 1 — always await inside an async context async function main() { try { await riskyOperation(); } catch (err) { console.error("Caught:", err.message); } } // Fix 2 — attach .catch() if you can't/don't want to await riskyOperation().catch(err => console.error("Caught:", err.message));
💡 As a last line of defense (not a substitute for proper try/catch), you can globally catch any rejection that slipped through unhandled.
// Global safety net in the browser window.addEventListener("unhandledrejection", (event) => { console.error("Unhandled rejection:", event.reason); logToMonitoring(event.reason); // e.g. send to Sentry event.preventDefault(); // suppress the default console warning }); // Bonus: fires when a PREVIOUSLY unhandled rejection gets handled LATE window.addEventListener("rejectionhandled", (event) => { console.log("A rejection was handled after the fact"); });
⚠ In modern Node.js, an unhandled rejection terminates the process by default (since Node 15) — this global handler is important for logging before that happens, or to override the behavior.
// Global safety net in Node.js process.on("unhandledRejection", (reason, promise) => { console.error("Unhandled Rejection at:", promise, "reason:", reason); logToMonitoring(reason); // Best practice: log it, then gracefully shut down — // don't just ignore it and keep running in a possibly broken state process.exit(1); }); // Also catch synchronous uncaught exceptions (a related, separate concern) process.on("uncaughtException", (err) => { console.error("Uncaught Exception:", err); process.exit(1); });
✓ Best practice: global handlers are a safety net for logging/monitoring, NOT a substitute for handling errors at the source. Always prefer explicit try/catch or .catch() at the call site — global handlers should rarely (ideally never) actually fire in a well-written app.

AbortController — Cancelling Async Work

🛑 AbortController provides a standard way to cancel in-flight async operations — most commonly fetch() requests. Promises themselves can't be "cancelled" once created, so AbortController works by signaling the underlying operation to stop and reject early.
How it works

→
2. Pass signal
fetch(url, {signal})
→
3. Trigger cancel
controller.abort()
→
4. Fetch rejects
AbortError thrown
const controller = new AbortController(); async function fetchData() { try { const res = await fetch("/api/data", { signal: controller.signal }); const data = await res.json(); console.log(data); } catch (err) { if (err.name === "AbortError") { console.log("Request was cancelled"); } else { console.error("Fetch failed:", err); } } } fetchData(); // Somewhere else — e.g. user clicks "cancel" button cancelButton.addEventListener("click", () => { controller.abort(); // triggers the fetch's promise to reject with AbortError }); // Optional: pass a custom reason controller.abort("User navigated away"); // err.message or controller.signal.reason will reflect this
💡 The modern, native way to implement fetch timeouts — no need for the Promise.race trick anymore.
// Native shortcut — AbortSignal.timeout() (modern browsers/Node 17+) async function fetchWithTimeout(url, ms = 5000) { try { const res = await fetch(url, { signal: AbortSignal.timeout(ms) }); return await res.json(); } catch (err) { if (err.name === "TimeoutError") { throw new Error(`Request to ${url} timed out after ${ms}ms`); } throw err; } } // Manual version — for older environments / more control function fetchWithManualTimeout(url, ms) { const controller = new AbortController(); const timeoutId = setTimeout(() => controller.abort(), ms); return fetch(url, { signal: controller.signal }) .finally(() => clearTimeout(timeoutId)); // cleanup — avoid dangling timer }
⚠ Very common interview scenario: preventing a "setState on unmounted component" warning by cancelling in-flight requests when a component unmounts.
// React useEffect cleanup pattern useEffect(() => { const controller = new AbortController(); async function loadUser() { try { const res = await fetch(`/users/${userId}`, { signal: controller.signal }); const data = await res.json(); setUser(data); // only runs if the request wasn't aborted } catch (err) { if (err.name !== "AbortError") { setError(err.message); // ignore expected abort errors, handle real ones } } } loadUser(); // Cleanup function — runs on unmount OR before the effect re-runs return () => controller.abort(); }, [userId]); // Prevents calling setUser() after the component has already unmounted, // and cancels the STALE request if userId changes before the fetch finishes
// ONE controller can cancel MULTIPLE requests at once const controller = new AbortController(); const { signal } = controller; async function loadAll() { try { const [users, posts, comments] = await Promise.all([ fetch("/api/users", { signal }).then(r => r.json()), fetch("/api/posts", { signal }).then(r => r.json()), fetch("/api/comments", { signal }).then(r => r.json()) ]); return { users, posts, comments }; } catch (err) { if (err.name === "AbortError") { console.log("All requests cancelled together"); } } } controller.abort(); // cancels ALL THREE fetches sharing this signal at once // You can also listen for the abort event directly signal.addEventListener("abort", () => { console.log("Signal aborted, reason:", signal.reason); });

Common Gotchas & Traps

  • ⚠️try/catch does NOT catch errors from un-awaited promises — if you call an async function without await inside a try block, and it rejects LATER (after the try block has already finished), the catch block will NOT see it. Always await what you want to catch.
  • ⚠️forEach with async callbacks bypasses your try/catch — errors thrown inside arr.forEach(async fn) become unhandled rejections since forEach doesn't await the returned promises. Use a for...of loop with await instead if you need proper error propagation.
  • ⚠️Promise.all rejects fast and discards other results — even successful results from other promises in the array are lost when using try/catch around Promise.all; only the first error is caught. Use Promise.allSettled if you need partial results.
  • ⚠️fetch() does NOT reject on HTTP error status codes (404, 500, etc.) — it only rejects on network failures. You must manually check res.ok or res.status and throw yourself if you want 4xx/5xx to be treated as errors.
  • ⚠️AbortController.abort() causes the fetch promise to REJECT, not silently resolve with nothing — you must catch the resulting AbortError explicitly, or it becomes an unhandled/unexpected error in your catch block.
  • ⚠️A single AbortController can only be used once — after calling .abort(), that controller's signal is permanently aborted. You need a NEW AbortController instance for the next request (e.g. recreate it on each new fetch attempt, like in the React useEffect pattern).
  • ⚠️Not all APIs support AbortSignal — only APIs explicitly built to accept it (like fetch) can be cancelled this way. A plain setTimeout-based promise or a database call not written to check the signal will keep running even after .abort() is called, unless you manually check signal.aborted inside your own async logic.
  • ⚠️Errors thrown inside a .then() callback are caught by the NEXT .catch(), not synchronously — mixing async/await with raw .then() chains can create confusing error propagation paths; prefer to stick with one style consistently within a function.
  • ⚠️console.error inside a catch block does not stop propagation — if you log an error but don't explicitly handle/return/re-throw appropriately, calling code may still proceed as if nothing went wrong (e.g. using undefined data downstream), causing a second, confusing failure later.
  • ⚠️finally can swallow the original error if it also throws or returns a value — a return statement inside finally overrides any value/error from the try/catch block, which is rarely what you want.

Interview Q&A — click to reveal

Q1: How does try/catch work with await under the hood?
+
When an await-ed promise rejects, the JS engine converts that rejection into a thrown exception at that exact line — behaving exactly like a synchronous throw. This means ordinary try/catch syntax works for async code, catching both synchronous throws AND asynchronous rejections in the same block, which is the main ergonomic win over raw .then()/.catch() chains.
Q2: What is an unhandled promise rejection, and how do you prevent it?
+
It occurs when a promise rejects and no .catch() or surrounding try/catch (via awaiting it) ever handles that rejection. In Node.js this can crash the process by default; in browsers it logs a console warning.

Prevent it by always attaching error handling: either await the call inside a try/catch, or chain .catch() if you're not awaiting. As a last-resort safety net (not a fix), you can add a global window.addEventListener("unhandledrejection", ...) or Node's process.on("unhandledRejection", ...) handler for logging/monitoring.
Q3: Why doesn't fetch() reject on a 404 or 500 response?
+
By design, fetch() only rejects when the request itself fails at the network level (e.g. no connection, DNS failure, CORS block) — it treats any successful HTTP response, including 4xx/5xx status codes, as a "successful" fetch, since technically the server did respond. You must manually check response.ok (or response.status) and explicitly throw if you want error status codes to be treated as failures in your try/catch flow.
const res = await fetch(url); if (!res.ok) { throw new Error(`HTTP error: ${res.status}`); }
Q4: How does AbortController actually cancel a fetch request?
+
You create an AbortController, pass its .signal property into fetch(url, { signal }), and hold onto the controller. Calling controller.abort() sets the signal's aborted flag to true and dispatches an abort event — fetch is built to listen for this and immediately rejects its pending promise with a DOMException named "AbortError". This lets you cancel in-flight network requests, which is otherwise impossible with a plain Promise (once created, a promise's underlying work can't normally be stopped).
Q5: Why would you use Promise.allSettled instead of Promise.all with try/catch for parallel requests?
+
Promise.all fails fast — a SINGLE rejection causes the entire operation to reject, discarding any results from promises that DID succeed. This is fine when every result is required, but wasteful when partial success is acceptable (e.g. a dashboard with several independent widgets). Promise.allSettled always resolves with a status report for every promise, letting you render whatever succeeded while gracefully handling/displaying errors for whatever failed — without one failure blocking everything else.
Q6: Why is cancelling requests important in a React component, and how do you implement it correctly?
+
Without cancellation, if a component unmounts (or its dependencies change) before an in-flight fetch completes, the eventual .then()/await continuation may try to call setState on an unmounted component — causing a memory leak warning, or worse, applying stale data from an outdated request. The fix: create an AbortController inside useEffect, pass its signal to fetch, and return a cleanup function that calls controller.abort() — React automatically runs this cleanup on unmount or before the effect re-runs due to a dependency change.
Q7: What happens if you put a return statement inside a finally block?
+
It overrides any return value or thrown error from the corresponding try/catch block — this is a rarely-intentional but legal JS behavior, and a common source of subtle bugs.
async function example() { try { throw new Error("original error"); } finally { return "overridden!"; // swallows the thrown error entirely! } } example().then(console.log); // → "overridden!" — the error never surfaces
Best practice: avoid return (or throw) inside finally — reserve it purely for cleanup side effects like clearing timers or hiding loaders.
Q8: Can you reuse the same AbortController for multiple separate fetch attempts, one after another?
+
No — once .abort() is called on a controller, its signal is permanently marked as aborted; you cannot "reset" it for reuse. Any NEW fetch you attach to that same signal afterward would be immediately treated as already aborted. The correct pattern is to create a fresh new AbortController() for each new request attempt (this is exactly why the React cleanup pattern creates a new controller inside the effect on every run, rather than one shared across the component's lifetime).
