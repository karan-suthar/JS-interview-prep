The Event Loop — Visual Map

💡 JavaScript is single-threaded — only one thing runs at a time on the Call Stack. The Event Loop is the mechanism that lets JS handle async operations (timers, network requests, DOM events) without blocking, by coordinating between the stack and various queues.
Call Stack → Web APIs → Queues → back to Call Stack (via the Event Loop)
🔁 The Event Loop's single job: continuously check "is the Call Stack empty?" — if yes, first drain the ENTIRE Microtask Queue, then pull exactly ONE task from the Macrotask Queue onto the stack, run it to completion, and repeat.
2

Each Component, Explained

Call Stack
LIFO (Last In, First Out) structure that tracks function calls. JS can only execute what's on top of the stack — this is what makes JS single-threaded. When a function returns, it's popped off.
Web APIs (Browser/Node)
Provided by the runtime environment (browser or Node), NOT by the JS engine itself. Handle setTimeout, network requests, DOM events, file I/O — running outside the main JS thread, so they don't block it.
Microtask Queue
Holds Promise .then/.catch/.finally callbacks, await continuations, and queueMicrotask(). Higher priority — fully emptied before any macrotask runs.
Callback / Macrotask Queue
Holds setTimeout/setInterval callbacks, UI event handlers, I/O callbacks. Lower priority — only ONE macrotask is processed per event loop tick.
Event Loop
The coordinator. Repeatedly checks if the Call Stack is empty; if so, drains all microtasks, then moves one macrotask onto the stack. This is what makes async callbacks eventually run.
// Which queue does each thing go into? setTimeout(fn, 0); // → Macrotask queue (via Web APIs) setInterval(fn, 100); // → Macrotask queue (repeating) Promise.resolve().then(fn); // → Microtask queue await somePromise; // → continuation goes to Microtask queue queueMicrotask(fn); // → Microtask queue (explicit API) fetch(url).then(fn); // → network is a Web API; .then() callback → Microtask queue element.addEventListener("click", fn); // → Macrotask queue (when the event fires) requestAnimationFrame(fn); // → special queue, runs before repaint (~its own category)

The Priority Rules (memorize this order)

1. Run ALL synchronous code
→
2. Drain ENTIRE microtask queue
→
3. Run ONE macrotask
→
4. Drain microtasks again
→
repeat from step 3...
⚠ Critical detail: "drain the entire microtask queue" includes any NEW microtasks added WHILE draining. If a .then() callback schedules another .then(), that new one also runs before the engine moves to the next macrotask. Microtasks can theoretically starve macrotasks if they keep adding more microtasks.

Chained .then() calls
Medium
console.log("start"); setTimeout(() => console.log("timeout"), 0); Promise.resolve() .then(() => console.log("promise 1")) .then(() => console.log("promise 2")) .then(() => console.log("promise 3")); console.log("end");
Output
start end promise 1 promise 2 promise 3 timeout
Each .then() in the chain schedules its callback as a new microtask only once the previous one resolves. Since the engine keeps draining the microtask queue until it's truly empty (including newly-added microtasks), all 3 chained .then() calls resolve back-to-back before the engine even looks at the macrotask queue. The setTimeout callback — a macrotask — always runs last here, regardless of chain length.

Nested setTimeout vs Promise
Medium
console.log("A"); setTimeout(() => { console.log("B"); Promise.resolve().then(() => console.log("C")); }, 0); Promise.resolve().then(() => { console.log("D"); setTimeout(() => console.log("E"), 0); }); console.log("F");

StepActionOutput
1Sync: log "A"A

Key insight: after EVERY single macrotask, the engine drains microtasks again before running the next macrotask — even if that microtask was created inside the macrotask that just ran. This is why "C" (scheduled inside timeout1) runs before "E" (a separate, earlier-queued-relative-position macrotask... but actually queued AFTER timeout1 runs, so it lands after timeout1 in the macrotask queue anyway).

Common Gotchas & Traps

  • ⚠️setTimeout(fn, 0) does NOT run immediately — it still goes through the macrotask queue, always after ALL synchronous code and ALL pending microtasks, no matter how small the delay.
  • ⚠️async functions run synchronously until the first await — code before the first await executes immediately when the function is called, not deferred.
  • ⚠️The ENTIRE microtask queue drains before the next macrotask — including new microtasks added while draining. This can theoretically delay macrotasks indefinitely if microtasks keep scheduling more microtasks.
  • ⚠️forEach with an async callback does NOT wait — arr.forEach(async fn) fires all callbacks without awaiting any of them; code after the forEach call continues immediately regardless of what's inside.
  • ⚠️Multiple setTimeout(fn, 0) calls run in FIFO order — first registered, first executed, since they're all macrotasks with equal (zero) delay, processed in queue order.
  • ⚠️Node.js has additional queue types (process.nextTick, setImmediate) with their own priority rules slightly different from browsers — process.nextTick in Node actually runs BEFORE regular microtasks (Promises), a Node-specific quirk.
  • ⚠️requestAnimationFrame is neither a microtask nor macrotask — it runs in its own special phase, right before the browser repaints, separate from the standard queue priority described here.
  • ⚠️A long-running synchronous function blocks EVERYTHING — since JS is single-threaded, a slow loop or heavy computation freezes the UI and delays all queued callbacks (both micro and macro) until it finishes.
  • ⚠️Promise executor function runs synchronously — the code directly inside new Promise((resolve, reject) => { ... }) executes immediately, NOT asynchronously; only the .then() callback is deferred to the microtask queue.
  • ⚠️Rejected promises without a .catch() still go through the microtask queue the same way — an "unhandled rejection" is only detected AFTER the microtask queue is checked and no handler was ever attached.

Interview Q&A — click to reveal

Q1: Explain the event loop in your own words.
+
JavaScript runs on a single thread with a Call Stack that executes code. Asynchronous operations (timers, network calls, DOM events) are handed off to Web APIs provided by the browser/Node runtime, which run outside the main thread. When those operations complete, their callbacks are placed into either the Microtask Queue (Promises, await) or the Macrotask/Callback Queue (setTimeout, events). The Event Loop continuously checks: is the Call Stack empty? If so, it drains the entire Microtask Queue first, then pulls exactly one task from the Macrotask Queue, runs it, and repeats.
Q2: What's the difference between the microtask queue and the macrotask queue?
+
Microtask queue holds Promise callbacks (.then/.catch/.finally), await continuations, and queueMicrotask() — it has HIGHER priority and is fully emptied (including newly added microtasks) before the engine touches the macrotask queue.

Macrotask (callback) queue holds setTimeout/setInterval callbacks, DOM events, and I/O callbacks — LOWER priority, and only ONE macrotask runs per event loop tick before microtasks are checked again.
Q3: Why does setTimeout(fn, 0) not run immediately?
+
Even with a 0ms delay, setTimeout hands its callback to a Web API, which — once the (effectively instant) timer expires — places the callback into the macrotask queue. The callback can only run once the Call Stack is completely empty AND the entire microtask queue has been drained. So a 0ms timeout still guarantees "runs after all currently synchronous code and all currently pending promises," never truly "immediately."
Q4: If a microtask keeps scheduling more microtasks, what happens to the macrotask queue?
+
It gets starved — the spec requires the entire microtask queue to be fully drained (including any microtasks added during draining) before the event loop moves on to process a single macrotask. If code continuously adds new microtasks (e.g. a recursive .then() chain that never stops), macrotasks like setTimeout callbacks or UI rendering can be delayed indefinitely. This is a real performance hazard to be aware of, not just a theoretical trick question.
Q5: What runs first — code before the first await in an async function, or a separately-scheduled Promise.then() registered right after calling that function?
+
Code before the first await runs synchronously and immediately when the async function is called — before the separate .then() even gets registered (assuming the function call happens first in the source). What matters for ordering AFTER that point is simply: whichever microtask was queued first runs first. The await's continuation is typically queued before a .then() written on a later line, so it usually wins that race — but the real rule is just FIFO order of microtask registration, not some special async/await priority.
Q6: Where do DOM click events fit into the queue system?
+
DOM events (clicks, keypresses, etc.) are handled by the browser (a Web API) and their handlers go into the macrotask queue once the event fires — same priority tier as setTimeout. So a pending Promise microtask will always execute before a queued click handler, if both are ready to run at the same point in time.
Q7: Is the code inside `new Promise((resolve, reject) => {...})` synchronous or asynchronous?
+
Synchronous. The "executor" function passed to the Promise constructor runs immediately, right when the Promise is created — not deferred to any queue. Only the .then()/.catch() callbacks attached to that promise are deferred (to the microtask queue), and only once the promise actually settles (resolves or rejects).
new Promise((resolve) => { console.log("1 - runs immediately"); resolve(); }).then(() => console.log("3 - deferred microtask")); console.log("2 - still sync code"); // → "1", "2", "3"
