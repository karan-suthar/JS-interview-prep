Rule 1: Default Binding

4th
Plain function call — the fallback rule
Applies when NO other rule matches — just calling a function directly, with no object, no explicit binding, no `new`.
function showThis() { console.log(this); } showThis(); // called "bare" — no object before the dot // Non-strict mode: this → the global object (window in browsers, global in Node) // Strict mode: this → undefined "use strict"; function strictShowThis() { console.log(this); // → undefined } strictShowThis();
⚠ In non-strict mode, accidentally leaking this to the global object is a classic source of bugs — e.g. assigning this.value = 5 inside a bare function call silently creates a GLOBAL variable. All ES6 modules and classes are automatically strict, which is one reason this defaults to undefined more often in modern code.
// A very common way default binding sneaks in — extracting a method const obj = { name: "Alice", greet() { return this.name; } }; const greetFn = obj.greet; // extracted — loses its connection to "obj" greetFn(); // ✗ called BARE now → default binding applies → this is undefined/global // → TypeError: Cannot read properties of undefined (reading 'name') (strict mode)
2

Rule 2: Implicit Binding

3rd
Called AS a method of an object
When a function is called with an object reference immediately before the dot — `this` is set to that object.
const user = { name: "Bob", greet() { console.log(this.name); } }; user.greet(); // → "Bob" ("this" is "user" — the object right before the dot) // The RULE is about the CALL SITE, not where the function was defined const anotherUser = { name: "Carol", greet: user.greet }; anotherUser.greet(); // → "Carol" (SAME function, but "this" follows the call site!)
// Only the IMMEDIATE object before the dot matters — nested paths const a = { name: "outer", b: { name: "inner", greet() { console.log(this.name); } } }; a.b.greet(); // → "inner" (this = a.b, the object directly before ".greet()")
🚨 Implicit binding is easily "lost" — the #1 practical this bug. Any time a method is passed as a value (callback, assignment, destructuring) rather than called directly as obj.method(), it falls back to Default Binding.
// Implicit binding LOST — extremely common real-world bug const timer = { seconds: 0, tick() { this.seconds++; } }; setTimeout(timer.tick, 1000); // ✗ passed as a VALUE — implicit binding is lost! // Inside setTimeout, "tick" is called BARE — this is undefined/global, not "timer" // Fixes: wrap in an arrow function, or use .bind() setTimeout(() => timer.tick(), 1000); // ✓ arrow preserves outer "this" context via closure over timer.tick call setTimeout(timer.tick.bind(timer), 1000); // ✓ explicitly locks "this" to timer
3

Rule 3: Explicit Binding call / apply / bind

2nd
You explicitly SPECIFY what `this` should be
Overrides implicit and default binding by forcing `this` to a value of your choosing.
function greet(greeting) { console.log(`${greeting}, ${this.name}`); } const alice = { name: "Alice" }; const bob = { name: "Bob" }; // call(thisArg, arg1, arg2, ...) — arguments passed INDIVIDUALLY, runs IMMEDIATELY greet.call(alice, "Hello"); // → "Hello, Alice" greet.call(bob, "Hi"); // → "Hi, Bob" // Classic use: borrowing an array method for an array-like object function sum() { return Array.prototype.slice.call(arguments).reduce((a,b) => a+b, 0); } sum(1, 2, 3); // → 6 ("arguments" borrowed .slice from Array.prototype)
// apply(thisArg, [argsArray]) — SAME as call, but args passed as an ARRAY function greet(greeting, punctuation) { console.log(`${greeting}, ${this.name}${punctuation}`); } const alice = { name: "Alice" }; greet.apply(alice, ["Hey", "!"]); // → "Hey, Alice!" // Classic historical use: Math.max/min don't accept arrays directly const nums = [5, 2, 9, 1]; Math.max.apply(null, nums); // → 9 (spreads the array as individual args) // Modern equivalent (ES6 spread) — usually preferred now: Math.max(...nums); // → 9 (no need for apply anymore in most cases)
// bind(thisArg, arg1, ...) — does NOT call immediately! // Returns a NEW function with "this" (and optionally some args) permanently locked in function greet(greeting) { console.log(`${greeting}, ${this.name}`); } const alice = { name: "Alice" }; const greetAlice = greet.bind(alice); // new function, "this" locked to alice FOREVER greetAlice("Hello"); // → "Hello, Alice" — even called bare! // Partial application — bind can also pre-fill arguments const sayHiToAlice = greet.bind(alice, "Hi"); sayHiToAlice(); // → "Hi, Alice" (greeting is already baked in) // Practical: fixing the setTimeout / callback "this" loss problem const timer = { seconds: 0, tick() { this.seconds++; console.log(this.seconds); } }; setTimeout(timer.tick.bind(timer), 1000); // ✓ "this" locked to timer regardless of call site
🔒 Hard binding — once you .bind() a function, its this CANNOT be overridden again, even by another call(), apply(), or being used as a method. This is the highest-priority binding rule.
function showName() { console.log(this.name); } const alice = { name: "Alice" }; const bob = { name: "Bob" }; const boundToAlice = showName.bind(alice); boundToAlice(); // → "Alice" boundToAlice.call(bob); // → STILL "Alice"! call() cannot override a hard-bound function // Even attaching it as a method of another object doesn't help bob.show = boundToAlice; bob.show(); // → STILL "Alice"! implicit binding also loses to hard binding

Rule 4: new Binding

1st
Highest priority — always wins
When a function is called with `new`, a brand new object is created and `this` is bound to IT.
function Person(name) { this.name = name; // "this" refers to the NEW object being constructed } const alice = new Person("Alice"); alice.name; // → "Alice" // Recap of what "new" does to "this" (see the prototype-chain deep dive for full steps): // 1. A new empty object is created // 2. Its [[Prototype]] is linked to Person.prototype // 3. The function runs with "this" bound to that NEW object // 4. The new object is returned automatically (unless an object is explicitly returned)
// new binding beats explicit binding — even bind() can't override "new"! function Person(name) { this.name = name; } const obj = { name: "placeholder" }; const BoundPerson = Person.bind(obj); // hard-bound to "obj"... const alice = new BoundPerson("Alice"); // ...but "new" OVERRIDES the hard binding! alice.name; // → "Alice" (bound to the NEW object, not "obj") obj.name; // → "placeholder" (obj was never touched) // This is precisely how "new" is defined to behave with a bound function — // it's the ONE case where hard-binding's "this" can still be overridden.
⚠ ES6 classes always throw a TypeError if called without new — class Foo {}; Foo() → error. Old-style constructor functions do NOT have this protection, which is exactly what causes the "forgot new" bug covered in the gotchas section.

Precedence Rules — The Decision Tree

🧠 When multiple rules COULD apply to a single function call, JS resolves the conflict using a fixed precedence order. Walk through these questions in order — the first "yes" wins.
Ask these questions, in this exact order, for any function call
1. Was the function called with "new"?
YES →
this = the newly constructed object
2. Was the function called via call/apply/bind?
YES →
this = the explicitly specified object
3. Was the function called as obj.method()?
YES →
this = obj (the object before the dot)
4. None of the above (bare function call)
→
this = global object (or undefined in strict mode)
// Putting the WHOLE precedence chain to the test function identify() { return this.name; } const obj1 = { name: "obj1", identify }; const obj2 = { name: "obj2" }; identify(); // → undefined/global (default binding — bare call) obj1.identify(); // → "obj1" (implicit binding — obj before dot) obj1.identify.call(obj2); // → "obj2" (explicit beats implicit!) const bound = obj1.identify.bind(obj2); bound(); // → "obj2" (hard binding — call() below can't override it) bound.call(obj1); // → STILL "obj2" (hard bind wins over a later call()) const instance = new bound(""); // "new" is the ONE thing that overrides hard binding! // this now refers to the newly created object, not obj2

Arrow Functions — The Exception to All 4 Rules

🏹 Arrow functions don't follow ANY of the 4 rules above. They have no this binding of their own — they capture this lexically from the ENCLOSING scope at the time they're defined, and that binding can NEVER be changed afterward, not even with call/apply/bind/new.
// None of the 4 rules affect an arrow function's "this" const arrow = () => console.log(this); const obj = { name: "test", arrow }; obj.arrow(); // implicit binding does NOT apply — "this" is still whatever it was at definition time arrow.call(obj); // explicit binding does NOT apply either — call() is silently ignored for "this" // new arrow() throws immediately — arrows have no [[Construct]] internal method new arrow(); // ✗ TypeError: arrow is not a constructor // The ONLY way to control an arrow function's "this" is via where you DEFINE it const timer = { seconds: 0, start() { // arrow defined HERE — captures "this" from start()'s implicit binding (= timer) setInterval(() => { this.seconds++; }, 1000); } }; timer.start(); // arrow's "this" = timer, because start() was called as timer.start()

Common Gotchas & Traps

  • ⚠️Extracting/passing a method loses implicit binding — const fn = obj.method; fn(); or callback(obj.method) both strip away the "obj." context, falling back to default binding. This is the single most common `this` bug in real code.
  • ⚠️Array/object callbacks (map, filter, forEach, setTimeout, event listeners) call your function BARE — passing a regular function as a callback loses its original `this` unless you use `.bind()`, an arrow function wrapper, or the callback API's optional `thisArg` parameter (e.g. `arr.map(fn, thisArg)`).
  • ⚠️Hard-bound functions cannot be re-bound — calling `.bind()` again on an already-bound function, or using `.call()`/`.apply()` on it, has NO effect on `this`; the original bind() wins.
  • ⚠️`new` is the ONE exception that overrides hard binding — `new boundFn()` uses the newly constructed object as `this`, ignoring whatever `.bind()` originally set. This is a genuinely surprising edge case worth memorizing.
  • ⚠️Arrow functions used as object methods break implicit binding — `const obj = { name: "x", greet: () => this.name }` — the arrow's `this` is captured from the OUTER scope (often the module or global scope), NOT from `obj`, even though it's assigned as `obj`'s property.
  • ⚠️call()/apply() with null or undefined as thisArg defaults `this` to the global object in non-strict mode, but stays `null`/`undefined` in strict mode — don't assume passing `null` is always "safe."
  • ⚠️Nested regular functions inside a method lose the outer `this` — a plain `function(){}` defined inside a method does NOT inherit the method's `this`; it gets its own default binding when called bare. This is exactly why arrow functions (or `.bind(this)`) are needed for nested callbacks.
  • ⚠️Getters/setters follow implicit binding too — `this` inside a getter/setter refers to the object the property was accessed ON, following the same "object before the dot" logic as regular implicit binding.
  • ⚠️bind() called multiple times only honors the FIRST bind — `fn.bind(a).bind(b)` still has `this` locked to `a`; the second `.bind(b)` has no effect on `this` (though it CAN still pre-fill additional arguments).
  • ⚠️Class methods are NOT auto-bound — extracting a class instance method the same way as any other method loses `this`, exactly like implicit binding loss with plain objects. Class fields with arrow functions (`method = () => {...}`) are a common workaround, auto-binding `this` per-instance.

Interview Q&A — click to reveal

Q1: List the 4 rules for determining "this", in order of precedence from highest to lowest.
+
1. new binding (highest) — new Fn() always wins if present.
2. Explicit binding — call(), apply(), or bind() specify `this` directly.
3. Implicit binding — the function is called as a method: obj.method().
4. Default binding (lowest, the fallback) — a bare function call with no object context; `this` is the global object (non-strict) or `undefined` (strict mode).

Arrow functions are a separate exception — they ignore all 4 rules and use `this` from their enclosing lexical scope instead.
Q2: Why does `this` become undefined/global when you extract a method and call it separately?
+
Implicit binding is determined entirely by the CALL SITE, not by where or how the function was originally defined. When you do const fn = obj.method, you're copying a reference to the function itself — the connection to obj is NOT carried along. So when you later call fn(), there's no object immediately before the dot (there's no dot at all!) — it's a bare call, which triggers Default Binding instead of Implicit Binding.
Q3: What's the difference between call(), apply(), and bind()?
+
All three let you explicitly set what `this` should be inside a function. call(thisArg, arg1, arg2, ...) invokes the function IMMEDIATELY, passing arguments individually. apply(thisArg, [argsArray]) also invokes immediately, but takes arguments as a single array. bind(thisArg, arg1, ...) does NOT invoke immediately — it returns a NEW function with `this` (and optionally some leading arguments) permanently locked in, to be called later.
Q4: Can you override the `this` of a function that was created with .bind()?
+
No, with one exception. A "hard-bound" function's `this` cannot be changed by a SUBSEQUENT call(), apply(), another bind(), or by attaching it as a method on a different object (implicit binding). The ONLY thing that can override a hard-bound function's `this` is calling it with new — using new on a bound function still creates a fresh object and binds `this` to that new object, ignoring the original bind target. This is specified, intentional JS behavior, and a common trick interview question.
Q5: How do arrow functions determine `this`, and how is that different from the 4 rules?
+
Arrow functions have NO `this` binding of their own at all — they don't follow default, implicit, explicit, OR new binding. Instead, they capture `this` lexically from the immediately enclosing (non-arrow) function or scope, at the moment the arrow function is DEFINED — not when it's called. This binding is permanent and cannot be changed afterward by `call()`, `apply()`, `bind()` (these are silently ignored for `this` on arrow functions), or `new` (which throws a TypeError since arrows can't be constructors at all).
Q6: Why is passing a method directly as a callback (e.g. to setTimeout or an event listener) often a bug?
+
Because the callback API (setTimeout, addEventListener, array methods without a thisArg, etc.) invokes your function as a BARE call internally — there's no "obj." before it at the actual call site inside that API's implementation. Even though you wrote setTimeout(obj.method, 1000), by the time `method` actually runs, it's just being called as method(), triggering Default Binding and losing the connection to `obj`. Fix with an arrow function wrapper (() => obj.method()) or obj.method.bind(obj).
Q7: What does `this` refer to in a nested regular function inside an object method?
+
It does NOT inherit the outer method's `this` — a nested plain function(){} has its own independent `this` binding determined by how IT is called, not by where it's defined. If that nested function is called bare (which is the common case for a callback inside a method), it falls back to Default Binding, losing the outer object context entirely. This is precisely the problem arrow functions solve when used for nested callbacks — since arrows have no `this` of their own, they transparently use the surrounding method's `this` instead.
const obj = { name: "test", method() { function nested() { console.log(this.name); } // own "this" nested(); // bare call → this is undefined/global, NOT obj } };
Q8: In strict mode vs non-strict mode, what's the difference in default binding behavior, and why does it matter?
+
In non-strict mode, a bare function call sets `this` to the global object (`window` in browsers). In strict mode, `this` remains `undefined` for a bare call. This matters because in non-strict mode, accidentally writing `this.value = 5` inside a bare-called function SILENTLY creates a global variable — a hard-to-trace bug. In strict mode, that same code throws an immediate, clear TypeError (`Cannot set properties of undefined`), surfacing the bug right away instead of silently corrupting global state. ES6 modules and classes are automatically strict, which is a big part of why modern JS code is generally safer in this regard.
