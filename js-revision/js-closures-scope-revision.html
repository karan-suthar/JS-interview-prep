Lexical Scoping

💡 Lexical scoping means a variable's scope is determined by where it is written in the source code (its physical position), not by where or how the function is called. Every function can access variables from its own scope, plus all enclosing (outer) scopes — this is the scope chain.
Scope chain — inner scopes see outer variables, never the reverse
Global Scope
appName = "MyApp"
Function outer() — can see appName
city = "Delhi"
Function inner() — can see appName AND city
street = "MG Road"
✓ Can read: appName, city, street
✗ Global CANNOT read city or street — outer scopes never see inner variables
const appName = "MyApp"; // global scope function outer() { const city = "Delhi"; // outer() scope function inner() { const street = "MG Road"; // inner() scope console.log(appName, city, street); // ✓ all 3 visible } inner(); // console.log(street); ← ✗ ReferenceError, street not visible here } outer(); // "Lexical" = based on WHERE code is written, not how it's called function a() { const x = 10; b(); // b() is called from inside a(), but that does NOT give b() access to x } function b() { console.log(typeof x); // → "undefined" — b's lexical position is the global scope, not inside a() }
Conceptfunction scope (var)block scope (let/const)
Scope boundaryNearest enclosing functionNearest enclosing {} block
Visible inside if/for blocks?✓ Leaks out of the block✗ Contained to the block

// var is function-scoped — leaks out of blocks! if (true) { var x = 1; } console.log(x); // → 1 (leaked out of the if-block!) // let/const are block-scoped — contained to {} if (true) { let y = 1; } console.log(y); // → ReferenceError: y is not defined

Closures

🔒 A closure is formed when a function "remembers" and continues to access variables from its lexical scope, even after the outer function has finished executing. Every function in JS forms a closure over its surrounding scope — this happens automatically, always.
// Classic closure example — counter factory function createCounter() { let count = 0; // private variable return function() { count++; // inner function "closes over" count return count; }; } const counter1 = createCounter(); counter1(); // → 1 counter1(); // → 2 counter1(); // → 3 (count persists between calls — closure keeps it alive!) const counter2 = createCounter(); // a totally separate closure counter2(); // → 1 (independent count — its own closure) // createCounter() has already RETURNED — its execution context is gone — // but `count` lives on because the inner function still references it. // This is the essence of a closure: the variable is not garbage collected // because a live reference to it still exists.
✓ Private state (module pattern)
function createBankAccount(balance) { return { deposit(amt) { balance += amt; }, withdraw(amt) { balance -= amt; }, getBalance() { return balance; } }; } const acc = createBankAccount(100); acc.deposit(50); acc.getBalance(); // → 150 // balance is NOT accessible directly — true privacy! acc.balance; // → undefined
✓ Function factory / configuration
function multiplyBy(factor) { return (num) => num * factor; } const double = multiplyBy(2); const triple = multiplyBy(3); double(5); // → 10 triple(5); // → 15 // each closure remembers its own "factor"

The Closure-in-Loop Trap var vs let

🎯 This is the single most common closures interview question. Know it cold — including WHY it happens, not just the fix.
✗ var — the classic bug
for (var i = 0; i < 3; i++) { setTimeout(() => { console.log(i); }, 100); } // → 3 // → 3 // → 3 // All three log 3, not 0, 1, 2!
✓ let — works as expected
for (let i = 0; i < 3; i++) { setTimeout(() => { console.log(i); }, 100); } // → 0 // → 1 // → 2 // Each callback sees its own i!
Why: var creates ONE shared binding — let creates a NEW binding per iteration
With var — one box, shared by all 3 closures:
iteration 1→ iteration 2→ iteration 3→ shared box: i = 3 (final value)
All 3 callbacks point to the SAME "i" — by the time they run, the loop has finished and i is 3
With let — a fresh box created each iteration:
iteration 1→own box: i = 0
iteration 2→own box: i = 1
iteration 3→own box: i = 2
Each callback closes over its OWN copy of "i" from that specific iteration
💡 Pre-ES6 fix: wrap the loop body in an IIFE to create a new function scope per iteration, capturing the current value of i as an argument.
for (var i = 0; i < 3; i++) { (function(j) { // j is a new variable per IIFE call setTimeout(() => { console.log(j); // closes over the IIFE's own "j" }, 100); })(i); // pass current i's VALUE immediately } // → 0, 1, 2 ✓ fixed
💡 Pass the loop variable directly into setTimeout's extra arguments — this also copies the current value at call time.
for (var i = 0; i < 3; i++) { setTimeout((j) => { console.log(j); }, 100, i); // 3rd+ args to setTimeout are passed to the callback } // → 0, 1, 2 ✓ fixed
✓ Best modern fix: simply use let instead of var. The JS engine creates a fresh binding of the loop variable for each iteration automatically — no workaround needed.
for (let i = 0; i < 3; i++) { setTimeout(() => console.log(i), 100); } // → 0, 1, 2 ✓ fixed, and cleanest // This is specified behavior — the for-loop with `let` creates a NEW // lexical binding of the loop variable for EACH iteration, initialized // by copying the value from the end of the previous iteration.

Hoisting Rules

💡 Hoisting is JS's behavior of processing variable and function declarations during the compile phase, before any code executes — making the names known to the scope in advance. It does NOT physically "move" code; it's a mental model for how the JS engine sets up memory.
JS engine's two-phase process
Phase 1
Creation / Compile Phase — scan the code, register all var declarations (initialized to undefined) and function declarations (fully initialized with their body). let/const are also registered but left uninitialized (in the "Temporal Dead Zone").
Phase 2
Execution Phase — code runs top to bottom. var variables get their real value assigned when that line executes. let/const become usable once their declaration line runs.

let x✓ Yes (name only)uninitialized (TDZ)ReferenceError
const x✓ Yes (name only)uninitialized (TDZ)ReferenceError
function foo(){}✓ Yes (full body)the function itself✓ Works fine

// var hoisting — declaration moves up, assignment stays in place console.log(a); // → undefined (NOT an error — "a" is known, just not assigned yet) var a = 5; // The engine effectively treats this as: // var a; ← hoisted to top // console.log(a); → undefined // a = 5; ← stays here // let/const hoisting — name is known, but unusable (Temporal Dead Zone) console.log(b); // → ReferenceError: Cannot access 'b' before initialization let b = 5; // Function declarations — fully hoisted, callable before definition greet(); // → "hi" ✓ works! function greet() { return "hi"; } // Function EXPRESSIONS are not — only the var/let/const container is hoisted sayHi(); // → TypeError: sayHi is not a function (var) or ReferenceError (let/const) var sayHi = function() { return "hi"; };
⚠ var inside loops/if-blocks does NOT create a new scope — it's hoisted to the nearest enclosing function (or global scope). This is the root cause of the closure-in-loop bug covered in Section 3.

Temporal Dead Zone (TDZ)

⏳ The TDZ is the period between entering a scope (where let/const is hoisted as "known but uninitialized") and the actual declaration line executing. Accessing the variable during this window throws a ReferenceError.
Timeline of a let/const variable within its scope
TEMPORAL DEAD ZONE
USABLE
← scope starts (variable hoisted but uninitialized)   |   let x = 5 line executes → x becomes usable →
// TDZ in action { // TDZ starts here for "value" — scope entered, let hoisted but uninitialized console.log(value); // ✗ ReferenceError: Cannot access 'value' before initialization let value = 10; // TDZ ends — value now usable console.log(value); // → 10 ✓ } // typeof does NOT protect you from TDZ (unlike with undeclared vars) console.log(typeof undeclaredVar); // → "undefined" (safe, no error) console.log(typeof tdzVar); // ✗ ReferenceError! (TDZ applies even to typeof) let tdzVar = 1; // TDZ + default parameters — order matters function example(a = b, b = 2) { return [a, b]; } example(); // ✗ ReferenceError — "b" is in its TDZ when "a" tries to use it as default // const specific — must be initialized immediately, and cannot be reassigned const pi; // ✗ SyntaxError: Missing initializer in const declaration
✓ Why TDZ exists: it helps catch bugs early by preventing you from using a variable before it's properly declared and initialized, rather than silently giving you undefined like var does. It's a safety feature, not a limitation.

Practical Uses of Closures

// Memoization — cache results using a closure over a Map function memoize(fn) { const cache = new Map(); // private, persists across calls via closure return (...args) => { const key = JSON.stringify(args); if (cache.has(key)) return cache.get(key); const result = fn(...args); cache.set(key, result); return result; }; } const slowSquare = n => { /* expensive computation */ return n * n; }; const fastSquare = memoize(slowSquare); fastSquare(5); // computed, cached fastSquare(5); // instant — read from cache
// Debounce — closure remembers the timer ID between calls function debounce(fn, delay) { let timerId; // persists via closure across every returned-function call return (...args) => { clearTimeout(timerId); timerId = setTimeout(() => fn(...args), delay); }; } const handleSearch = debounce((query) => { console.log("Searching:", query); }, 300); searchInput.addEventListener("input", (e) => handleSearch(e.target.value)); // only fires 300ms after the user STOPS typing
// Currying — each returned function closes over previously supplied args function curry(a) { return function(b) { return function(c) { return a + b + c; // closes over a, b, AND c }; }; } curry(1)(2)(3); // → 6 // Arrow function version — more concise const curryAdd = a => b => c => a + b + c; curryAdd(1)(2)(3); // → 6 // Practical: partial application const addTax = rate => amount => amount + amount * rate; const addGST = addTax(0.18); // rate "locked in" via closure addGST(100); // → 118
// "Run once" pattern — closure tracks whether it already ran function once(fn) { let called = false; let result; return (...args) => { if (!called) { result = fn(...args); called = true; } return result; }; } const initialize = once(() => { console.log("init!"); return "done"; }); initialize(); // logs "init!", → "done" initialize(); // doesn't log again, → "done" (cached) // Event handler factories — each button gets its own closure over its id buttons.forEach((btn, index) => { btn.addEventListener("click", () => { console.log(`Button ${index} clicked`); // closes over correct index }); });

Common Gotchas & Traps

  • ⚠️var in a for-loop shares ONE binding across all iterations — this is the #1 closure trap. Switching to let is the cleanest fix since ES6.
  • ⚠️Closures capture variables by reference, not by value — if the closed-over variable changes after the closure is created (but before it's called), the closure sees the LATEST value, not a snapshot from creation time.
  • ⚠️Closures can cause memory leaks if they hold references to large objects or DOM nodes that are no longer needed — the closure keeps them alive as long as the closure itself is reachable.
  • ⚠️typeof does not protect against TDZ — normally typeof undeclaredVar safely returns "undefined", but typeof on a let/const variable still in its TDZ throws a ReferenceError.
  • ⚠️Function declarations inside blocks hoist differently in strict vs non-strict mode — behavior can vary across engines for edge cases; safest to avoid declaring functions directly inside if/for blocks.
  • ⚠️const does not make objects immutable — it only prevents reassignment of the variable binding. const obj = {}; obj.x = 1; works fine; only obj = {} (a full reassignment) would throw.
  • ⚠️Nested closures each get their own copy when created inside a loop with let, but if you deliberately want them to SHARE state, you need to hoist the shared variable outside the loop (use var, or declare it before the loop).
  • ⚠️Hoisting affects `this` differently than variables — hoisting only applies to declarations (var/let/const/function/class); it does not "hoist" the value of `this`, which is determined by the call-site as usual.
  • ⚠️Redeclaring a let/const in the same scope throws immediately at parse time (SyntaxError: Identifier 'x' has already been declared) — even if the redeclaration line is never reached at runtime.
  • ⚠️Closures in forEach/map callbacks close over the loop's iteration variables correctly because these use function scope per call, unlike a raw for-loop with var — array iteration methods don't have the classic loop trap.

Interview Q&A — click to reveal

Q1: What is a closure? Give a simple definition.
+
A closure is a function combined with references to its surrounding lexical scope — it "remembers" the variables from the scope where it was created, and can continue to access and modify them even after the outer function has returned. Every function in JavaScript forms a closure automatically; it's not something you opt into.
Q2: What will this log, and why? for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i), 100); }
+
It logs 3, 3, 3. Because var is function-scoped (not block-scoped), all three arrow functions close over the same single i variable. By the time the setTimeout callbacks actually run (after the synchronous loop has already finished), i has already reached 3 — so all three callbacks see the final value.

Fix: use let i instead — ES6 spec creates a fresh binding of i for each loop iteration automatically, so each closure captures its own value (0, 1, 2).
Q3: What is the Temporal Dead Zone?
+
The TDZ is the span of code between entering a scope (where a let/const variable is hoisted but left uninitialized) and the line where it's actually declared. Accessing the variable anywhere in that window — even with typeof — throws a ReferenceError. It exists to catch bugs early, unlike var which silently gives undefined.
Q4: What's the difference between function scope and block scope?
+
Function scope (used by var) means a variable is visible anywhere within the nearest enclosing function, regardless of nested blocks like if or for — it "leaks" out of those blocks.

Block scope (used by let/const) means the variable is only visible within the nearest enclosing { } pair — it does NOT leak out of an if-block, for-loop, or any other block.
Q5: Explain hoisting in your own words. Does let get hoisted?
+
Hoisting is the JS engine's behavior of scanning a scope during the compile phase and registering all declarations (var, let, const, function, class) before any code runs. var is hoisted and initialized to undefined. Function declarations are hoisted with their entire body, making them callable before their definition line.

Yes, let is hoisted — but only the name is registered, not a usable value. It remains in the Temporal Dead Zone until its declaration line executes, so accessing it early throws a ReferenceError rather than returning undefined.
Q6: How would you implement a private counter using closures (without classes)?
+
function createCounter(start = 0) { let count = start; // private — not accessible from outside return { increment: () => ++count, decrement: () => --count, reset: () => { count = start; }, value: () => count }; } const c = createCounter(); c.increment(); c.increment(); c.value(); // → 2 c.count; // → undefined (truly private, no direct access)
Each returned method closes over the same count variable — this is the classic "module pattern" for data privacy before ES2022 introduced native private class fields (#field).
Q7: Can closures cause memory leaks? How?
+
Yes. Since a closure keeps a live reference to its outer scope's variables, if that scope contains a large object, array, or DOM node, the JS garbage collector cannot free that memory as long as the closure itself is reachable (e.g. still attached as an event listener, or stored in a global variable). This is more of an edge-case concern than a common issue, but it's worth knowing — e.g. removing event listeners you no longer need helps closures (and what they capture) get garbage collected.
Q8: Why does typeof not protect you from a ReferenceError with let, when it normally does with undeclared variables?
+
typeof someUndeclaredVar is safe because the variable was never registered in any scope at all — typeof has special handling to return "undefined" instead of throwing for genuinely unknown identifiers.

But a let/const variable IS registered in the scope (hoisted), just left uninitialized in the TDZ. Since the engine knows the identifier exists but hasn't reached its initialization yet, accessing it via typeof still triggers the TDZ check and throws a ReferenceError.
Q9: Does closures capture variable values or references?
+
References — not a snapshot of the value at the time the closure was created. If the variable is reassigned after the closure is defined but before it's invoked, the closure will see the updated value.
let message = "hello"; function logMessage() { console.log(message); } message = "goodbye"; // changed AFTER closure created logMessage(); // → "goodbye" (sees the latest value, not "hello")
This is exactly why the classic var-loop bug happens — all closures reference the SAME variable, and by execution time it holds the final value.
