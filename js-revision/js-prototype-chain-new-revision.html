Prototype Basics

💡 Every JS object has an internal, hidden link to another object called its prototype — accessible via Object.getPrototypeOf(obj) or the (non-standard but widely supported) obj.__proto__. When you access a property that doesn't exist directly on an object, JS automatically looks it up on the prototype, then the prototype's prototype, and so on.
// Every object has a hidden [[Prototype]] link const animal = { eats: true, walk() { console.log("Animal walks"); } }; const rabbit = { jumps: true }; Object.setPrototypeOf(rabbit, animal); // rabbit's prototype is now "animal" console.log(rabbit.jumps); // → true (own property) console.log(rabbit.eats); // → true (found on prototype "animal"!) rabbit.walk(); // → "Animal walks" (method found via prototype) // Confirm the link Object.getPrototypeOf(rabbit) === animal; // → true rabbit.__proto__ === animal; // → true (same thing, older syntax) // hasOwnProperty distinguishes OWN vs INHERITED properties rabbit.hasOwnProperty("jumps"); // → true (own property) rabbit.hasOwnProperty("eats"); // → false (inherited, not own) "eats" in rabbit; // → true (in checks the WHOLE chain)
TermMeaning
[[Prototype]]Internal slot — the hidden link every object has to another object (or null)
__proto__Legacy getter/setter exposing [[Prototype]] — works everywhere but discouraged in new code
Object.getPrototypeOf(obj)Modern, standard way to READ an object's prototype
Object.setPrototypeOf(obj, proto)Modern way to CHANGE an object's prototype (slow — avoid in hot code paths)
Function.prototypeA property EVERY function has — becomes the prototype of objects created via new Fn()
prototype chainThe full lookup path: object → its prototype → that prototype's prototype → ... → null
⚠ Don't confuse obj.__proto__ (the LINK to the prototype object) with Fn.prototype (a regular property ON a function, used as the template for objects created via new Fn()). This naming is one of the most confusing parts of JS — the diagram in the next section clarifies it.

// Tracing the lookup for rabbit.toString() // 1. Is "toString" an OWN property of rabbit? No. // 2. Check rabbit's prototype (animal) — own property? No. // 3. Check animal's prototype (Object.prototype) — own property? YES! Found it. rabbit.toString(); // → "[object Object]" (from Object.prototype) // Object.prototype's own prototype is null — the chain terminates here Object.getPrototypeOf(Object.prototype); // → null // Writing NEVER walks the chain — it always creates an OWN property rabbit.eats = false; // creates a NEW own property on rabbit, doesn't touch "animal" rabbit.hasOwnProperty("eats"); // → true now (shadows animal's "eats") animal.eats; // → true (animal's own "eats" property is untouched) // Shadowing: rabbit.eats now "hides" animal.eats for THIS object only const otherRabbit = Object.create(animal); otherRabbit.eats; // → true (still finds animal's original, unaffected by the first rabbit)
✓ Performance note: longer prototype chains mean slower property lookups in the worst case (property not found anywhere), since the engine must check every link. In practice, JS engines heavily optimize this with inline caches, but it's worth knowing that chain depth isn't "free."

Object.create()

💡 Object.create(proto) creates a brand-new, empty object whose [[Prototype]] is set DIRECTLY to proto — the most explicit, direct way to set up prototypal inheritance, without involving constructor functions or classes at all.
// Basic usage — inherit directly from an object const animal = { eats: true, walk() { console.log("walking..."); } }; const rabbit = Object.create(animal); // rabbit's prototype IS animal, directly rabbit.jumps = true; // add its own property rabbit.eats; // → true (inherited) rabbit.jumps; // → true (own) Object.getPrototypeOf(rabbit) === animal; // → true // Object.create(null) — a TRULY empty object, no prototype chain at all! const dict = Object.create(null); dict.toString; // → undefined (no Object.prototype in the chain — useful as a pure map!) dict.hasOwnProperty; // → undefined too // Safer than {} as a dictionary — no risk of key collisions with // built-in Object.prototype members like "toString" or "constructor"
// Object.create's optional 2nd argument defines OWN properties // using the same descriptor format as Object.defineProperty const rabbit = Object.create(animal, { jumps: { value: true, writable: true, enumerable: true, configurable: true } }); rabbit.jumps; // → true // This is more verbose than plain assignment but gives full control // over enumerability, writability, and configurability of each property
// Object.create is the cleanest way to link one object's prototype // to another's .prototype — the "textbook" pre-ES6 inheritance setup function Animal(name) { this.name = name; } Animal.prototype.walk = function() { console.log(`${this.name} walks`); }; function Rabbit(name) { Animal.call(this, name); } // call parent constructor // THIS is the classic pattern — link prototypes with Object.create Rabbit.prototype = Object.create(Animal.prototype); Rabbit.prototype.constructor = Rabbit; // fix constructor reference (see gotchas) Rabbit.prototype.jump = function() { console.log(`${this.name} jumps`); }; const bugs = new Rabbit("Bugs"); bugs.walk(); // → "Bugs walks" (inherited from Animal.prototype) bugs.jump(); // → "Bugs jumps" (own to Rabbit.prototype) // Why Object.create(Animal.prototype), NOT "new Animal()"? // "new Animal()" would actually RUN the Animal constructor unnecessarily // (with no arguments!) just to get an object to use as a prototype. // Object.create only sets up the LINK, without executing any constructor.

What "new" Does — Step by Step

🎯 One of the most classic interview questions: "What happens when you call new Fn()?" There are exactly 4 steps. Memorize them — and better, know how to write a function that reimplements new manually.
function Person(name) { this.name = name; } Person.prototype.greet = function() { return `Hi, I'm ${this.name}`; }; const alice = new Person("Alice");
1
Create a brand-new, empty object
A new plain object {} is created in memory. At this point it has no properties of its own.
const newObj = {};
2
Link the new object's prototype to the constructor's .prototype
The new object's internal [[Prototype]] is set to the constructor function's .prototype property — this is how the new object gains access to methods defined on Person.prototype.
Object.setPrototypeOf(newObj, Person.prototype); // equivalently: newObj.__proto__ = Person.prototype;
3
Call the constructor function with "this" bound to the new object
The constructor function body runs, with this pointing to the newly created object — so any this.property = value assignments inside the constructor attach properties to newObj.
const result = Person.call(newObj, "Alice"); // inside Person: this.name = "Alice" → sets newObj.name
4
Return the new object (unless the constructor explicitly returns its own object)
If the constructor function returns an OBJECT explicitly, THAT object is used instead of the newly created one. If it returns a primitive (or nothing), the new object from step 1 is returned instead — the primitive return value is ignored entirely.
if (typeof result === "object" && result !== null) { return result; // rare — explicit object override } return newObj; // the normal case
// Full manual reimplementation of the "new" keyword function myNew(Constructor, ...args) { const newObj = {}; // step 1 Object.setPrototypeOf(newObj, Constructor.prototype); // step 2 const result = Constructor.apply(newObj, args); // step 3 return (typeof result === "object" && result !== null) ? result : newObj; // step 4 } const alice = myNew(Person, "Alice"); alice.greet(); // → "Hi, I'm Alice" — works identically to "new Person('Alice')"! alice instanceof Person; // → true
✓ Being able to write this myNew function from memory is one of the strongest signals of deep JS understanding you can show in an interview — it proves you understand prototypes, this binding, and object creation all at once.

ES6 Classes = Syntactic Sugar Over Prototypes

💡 The class keyword doesn't introduce a new object model — under the hood, it's still constructor functions and prototype chains. Knowing this equivalence is a strong interview signal.
Pre-ES6 — constructor function + prototype
function Animal(name) { this.name = name; } Animal.prototype.speak = function() { return `${this.name} makes a sound`; }; function Dog(name) { Animal.call(this, name); } Dog.prototype = Object.create(Animal.prototype); Dog.prototype.constructor = Dog; Dog.prototype.bark = function() { return "Woof!"; };
ES6 — class syntax (same result)
class Animal { constructor(name) { this.name = name; } speak() { return `${this.name} makes a sound`; } } class Dog extends Animal { bark() { return "Woof!"; } }
// Proof they compile to the same underlying structure typeof Animal; // → "function" (a class IS a function under the hood) const rex = new Dog("Rex"); Object.getPrototypeOf(rex) === Dog.prototype; // → true Object.getPrototypeOf(Dog.prototype) === Animal.prototype; // → true rex.speak(); // → "Rex makes a sound" (found via the SAME chain traversal) // Key differences class syntax DOES add (not just sugar): // 1. Class bodies are ALWAYS in strict mode // 2. Class declarations are NOT hoisted the same way (TDZ applies) // 3. Calling a class WITHOUT "new" throws a TypeError (constructor functions don't) // 4. Methods defined in a class body are non-enumerable by default Animal(); // ✗ TypeError: Class constructor Animal cannot be invoked without 'new'
!

Common Gotchas & Traps

  • ⚠️Forgetting `new` calls the function normally — for old-style constructor functions, calling Person("Alice") without new runs the function with this bound to the global object (or undefined in strict mode) instead of a new object, silently creating global properties or throwing a confusing error. ES6 classes fix this by throwing a TypeError when called without new.
  • ⚠️Object.create(proto) doesn't call any constructor — if you need to also run initialization logic (like a constructor's this.x = ... assignments), you must call that logic manually afterward, e.g. ParentFn.call(newObj, args).
  • ⚠️Resetting Rrototype.prototype breaks the .constructor reference — after Dog.prototype = Object.create(Animal.prototype), `Dog.prototype.constructor` now incorrectly points to Animal unless you manually fix it: Dog.prototype.constructor = Dog;
  • ⚠️Returning a primitive from a constructor is silently ignored — function Foo() { return 5; } — calling new Foo() still returns the newly created object, NOT the number 5. Only returning an actual object overrides the default.
  • ⚠️Modifying Object.prototype affects EVERY object — since all plain objects ultimately inherit from Object.prototype, adding a property there (e.g. Object.prototype.foo = 1) makes foo appear to exist on literally every object in your program. This is almost always a bad idea in real code.
  • ⚠️for...in loops over INHERITED enumerable properties too — not just own properties, unlike Object.keys(). Always pair for...in with a hasOwnProperty check if you only want own properties, or just use Object.keys()/Object.entries() instead.
  • ⚠️Setting obj.__proto__ directly, or via Object.setPrototypeOf, is a slow operation that de-optimizes property access in most JS engines — prefer setting the prototype at creation time (via Object.create or a class's extends) rather than mutating it afterward.
  • ⚠️Arrow functions cannot be used as constructors — they have no internal [[Construct]] method and no own prototype property, so new ArrowFn() throws a TypeError immediately.
  • ⚠️Class methods are non-enumerable, but constructor-function-assigned prototype methods are enumerable by default — this affects whether they show up in a for...in loop or Object.keys() on the prototype, a subtle but real difference between the two patterns.
  • ⚠️instanceof checks the prototype CHAIN, not the constructor name — it works by checking if Fn.prototype appears anywhere in the object's prototype chain, which means it can give unexpected results if you manually reassign Fn.prototype AFTER objects were already created from it.

Interview Q&A — click to reveal

Q1: What happens, step by step, when you call `new Fn()`?
+
Four steps: (1) a brand-new empty object is created; (2) that object's internal [[Prototype]] is set to Fn.prototype; (3) the constructor function Fn is called with this bound to the new object, running any initialization logic inside it; (4) if the constructor explicitly returns an object, THAT object is used instead — otherwise the newly created object from step 1 is returned automatically.
Q2: What's the difference between Object.getPrototypeOf(obj) and Fn.prototype?
+
Object.getPrototypeOf(obj) reads an OBJECT'S internal [[Prototype]] link — the object it inherits from. Fn.prototype is a regular, visible PROPERTY that exists on every FUNCTION — it's the object that becomes the new [[Prototype]] for any object created via new Fn(). They're related but distinct: Fn.prototype is a template; Object.getPrototypeOf(instance) tells you what that instance actually inherited from (which, after `new Fn()`, will equal `Fn.prototype`).
Q3: How would you implement inheritance using Object.create, without ES6 classes?
+
function Animal(name) { this.name = name; } Animal.prototype.speak = function() { return `${this.name} makes a sound`; }; function Dog(name) { Animal.call(this, name); // call parent's constructor logic } Dog.prototype = Object.create(Animal.prototype); // link prototypes Dog.prototype.constructor = Dog; // fix constructor reference Dog.prototype.bark = function() { return "Woof!"; };
Using Object.create(Animal.prototype) instead of new Animal() avoids unnecessarily running the parent constructor just to set up the prototype link.
Q4: Why would you use Object.create(null) instead of {} for a dictionary/map-like object?
+
{} still inherits from Object.prototype, which means it has built-in members like toString, hasOwnProperty, and constructor already present. If your dictionary needs a key that happens to collide with one of these (e.g. a user-supplied key literally named "toString" or "__proto__"), you can get confusing bugs. Object.create(null) creates an object with NO prototype at all — a truly "bare" object safe to use as a pure key-value store, with zero risk of prototype pollution or accidental built-in method collisions.
Q5: Are ES6 classes just syntactic sugar? What (if anything) do they add beyond prototypes?
+
Mostly yes — under the hood, a class is still a function, and methods are still placed on its .prototype, using the exact same prototype chain mechanism. However, classes DO add some real behavioral differences beyond pure syntax: class bodies always run in strict mode; class declarations are NOT hoisted the same way (they're subject to the Temporal Dead Zone); calling a class without new throws a TypeError (a plain constructor function doesn't); and methods defined in a class body are non-enumerable by default (unlike prototype methods manually assigned via Fn.prototype.method = ..., which ARE enumerable).
Q6: What happens if a constructor function explicitly returns an object?
+
That returned object REPLACES the newly created object that new would have normally returned. This is step 4 of the new algorithm — if the constructor's return value is an object (not a primitive), new Fn() evaluates to that returned object instead of the freshly created this-bound one. If the constructor returns a primitive (or nothing), that return value is ignored, and the normally-created object is returned as usual.
function Weird() { this.a = 1; return { b: 2 }; // explicit object return } new Weird(); // → { b: 2 } (NOT { a: 1 }!)
Q7: What's the difference between hasOwnProperty and the `in` operator?
+
obj.hasOwnProperty(key) only checks the object's OWN properties, ignoring anything inherited via the prototype chain. The in operator (key in obj) checks the ENTIRE prototype chain — it returns true even if the property is only found on some ancestor prototype, not directly on obj itself.
Q8: Why does calling a regular (non-class) constructor function WITHOUT `new` often cause subtle bugs instead of an obvious error?
+
Without new, the function just runs as a normal function call — this inside it is NOT bound to a newly created object. In non-strict mode, this defaults to the global object (window in browsers), so any this.property = value assignments silently create/overwrite GLOBAL variables instead of properties on a new instance — a hard-to-trace bug. In strict mode, this is undefined instead, so the assignment throws a clear TypeError. This exact footgun is why ES6 classes were designed to throw immediately if called without new.
